# 第10章\_软件交接\_部署与分层排障

## 10.1\_硬件模型闭合后\_软件该接管哪一段

前九章从事件建立了 **通用中断控制器（Generic Interrupt Controller，GIC）** 的物理中断模型。现在要在 RK3588 上用起来，不能只把寄存器写入动作依次塞进设备驱动：初始化权限、来源管理、设备数据和处理器入口分属不同软件。

本章把 [S0～S6](P04_一次中断的状态转换与完成协议.md#4.4_用同一组阶段闭合正常周期)映射到软件职责和可观察现象，不展开某个内核版本的函数体。它回答怎样选择部署位置、怎样查证、怎样避免用错误层次的工具修改系统；不是“已经验证可在某块板上运行”的承诺。

## 10.2\_固件\_控制器驱动与设备驱动怎样交接

启动固件可以准备高权限访问、安全分组及处理器启动条件；内核的架构入口负责建立异常现场；GIC 控制器驱动负责控制器初始化、确认与结束等架构交接；具体设备驱动负责设备数据、请求条件和应用语义。

Linux 的 **中断请求（Interrupt Request，IRQ）** 管理把硬件来源表示为软件对象，通过映射把控制器编号与软件编号关联，再分派到已注册的处理函数。**中断标识符（Interrupt Identifier，INTID）** 是 GIC 硬件编号；Linux 对外使用的 IRQ 编号可以由软件分配，不能用二者数值偶然相等证明它们是同一种身份。

**设备树（Device Tree，DT）** 是描述硬件拓扑和资源的结构化数据。中断描述会指出上级控制器及相应参数；这些参数的解释由该控制器的绑定规则决定，不是任意设备都使用“中断号、类型”两个同义整数。

例如 GIC 常见绑定用“类型与类型内编号”表达来源，而芯片连接表可能直接列绝对硬件编号。追踪时应明确当前读到的是哪一种表达，再核对绑定与解析逻辑；不能仅凭两个数字差 32 就自动修正设备树。

把这些职责放进一次普通接收：串口先保存数据并提出请求；公共入口与控制器驱动确认硬件来源，IRQ 框架依据已建立的映射找到处理动作，设备驱动才读取串口数据、处理设备条件，控制器协议由负责它的公共路径收尾。启动固件事先建立的权限让这条路径能够运行，却不负责每次替设备驱动读取字节。下表据此划定每层能改变的状态。

| 所属软件 | 应负责的状态 | 不应越界做什么 |
| --- | --- | --- |
| 启动及高权限固件 | 自己拥有的安全域、权限开放与启动交接 | 在内核接管后无协议地改写内核拥有的来源 |
| 架构入口与 GIC 控制器驱动 | 异常入口、控制器配置、确认和完成协议 | 代替设备驱动解释数据内容 |
| Linux IRQ 框架 | 软件编号、映射、处理函数与使用契约 | 把一个已注册软件对象当作硬件递送已经成功 |
| 具体设备驱动 | 数据缓冲、设备条件、消息生产和拆除 | 重新初始化全局 GIC，或额外读取中断确认寄存器，抢走公共框架应确认的中断 |

> 官方对照：Linux 上游 v6.12 的 [Documentation/devicetree/bindings/interrupt-controller/arm,gic-v3.yaml](https://github.com/torvalds/linux/blob/v6.12/Documentation/devicetree/bindings/interrupt-controller/arm%2Cgic-v3.yaml)，properties → #interrupt-cells，给出类型、类型内编号与标志的含义。这里只用已发布绑定验证描述格式，不把上游版本或示例节点当成 RK3588 板上配置；软件职责的进一步阅读仍回到本仓库 Linux IRQ 专题。

## 10.3\_部署之前先固定板与软件基线

**板级支持包（Board Support Package，BSP）** 是面向特定芯片或板的启动、内核、驱动和配置材料组合，不是架构规范。不同 BSP 可以对同一块硬件采用不同版本或配置，不能混合手册中的硬件事实与某份旧启动日志后称为同一实验。

准备实际实现时至少固定：板卡与芯片型号、启动固件版本、内核远端和提交、构建配置、实际使用的设备树及运行日志。GIC 硬件身份按[平台记录](../../rockchip/rk3588/P01_RK3588的GIC-600集成与手册核对.md#1.2_怎样确认控制器身份)核对，软件证据另行建立。

当前仓库的恩智浦厂商 Linux 源码基线（NXP 是该厂商的专名）不是 RK3588 板上运行证据。公共实现可以在明确版本边界下研究，但不能把 NXP 工作树的配置复制成 RK3588 的事实。阅读某个 Linux GIC 函数时，也要先确定所研究的源码版本，再判断其配置分支是否对应目标板；仅找到同名驱动文件，不能补齐这条证据链。

裸机教学程序与 Linux 设备驱动是两种不同的部署方式。前者若独占机器，需要自行承担向量、栈、内存属性、权限和完整控制器初始化；后者运行在已建立框架中，应使用其接口，不能同时重新接管 GIC。把一个裸机寄存器例子“改成内核模块”不会自动解决所有权冲突。

## 10.4\_从一个问题定位到有效证据

假设问题是“某个消息中断首次工作，修改目标后不再工作”。先将它拆成已建立的状态变化：新消息是否还在产生？新映射是否发布？命令是否完成？旧目标的挂起状态是否迁移？新目标是否接收？软件映射是否仍有效？

随后查资料，而不是搜索一句“中断失效解决方案”：

1. 在架构规范中查目标改变与同步命令的保证、前置条件和受影响对象。
2. 在 Arm CoreLink GIC-600（控制器硬件产品专名）的实现手册中核对目标编码、能力及访问限制。
3. 在 RK3588 手册中核对接口、地址访问范围、共享属性与电源域。
4. 在目标软件版本中追踪对应初始化、修改、完成等待和错误回滚路径。
5. 用日志、计数和可安全读取的状态判断实际停在哪个阶段。

每项资料都应记录文档编号或源码提交，以及具体章节、寄存器条目或相对路径。标题含“GICv3/v4”只描述资料范围，不能代替对当前功能版本条件的筛选。

规范中的 **IMPLEMENTATION DEFINED（实现定义）** 要继续查产品；**RES0（Reserved, must be zero，保留且必须为 0）/RES1（Reserved, must be one，保留且必须为 1）** 是保留位取值约束；**UNPREDICTABLE（不可预测行为）** 不是建议软件“试试看”，而是当前操作已超出可依赖的保证。读手册时，这些词往往比一段宣传性功能摘要更能约束代码。

> 官方对照：[规范 IHI0069 H.b](https://developer.arm.com/documentation/ihi0069/hb)，Preface → Conventions 与卷末 Glossary 用于辨认规范措辞；本例目标更改查 5.3.13 MOVALL、5.3.14 MOVI、5.3.15 SYNC。芯片条件再查 RK3588 TRM V1.0 Part1，11.1 Overview 与 11.2 Block Diagram。上面的五步是本专题提炼的查证方法，不是规范另行规定的调试算法。

## 10.5\_四个观察点怎样组成故障链

假设串口接收缓冲区已经出现数据，应用却没有收到字节。这个现象只证明设备端有工作：请求可能尚未形成，也可能留在控制器、被接收侧条件阻止，或者已经进入软件但没有正确消费。排查时，先确认一个交接点是否完成，再沿请求方向检查下一个，不能用最终的“没收到”反推某一层必然失效。由这条过程得到四个观察点：

| 观察点 | 应问的问题 | 能形成的有限证据 |
| --- | --- | --- |
| 外设 | 数据或完成队列是否变化，请求条件是否存在，消息是否发出 | 生产者是否有工作；不能证明已到 GIC |
| 控制器 | 来源是否存在，配置与目标是否正确，普通来源是否挂起或活动，消息映射是否完成 | 请求管理停在哪一步；单个状态不证明软件已处理数据 |
| 处理器接收侧 | 是否允许对应异常与优先级，接收侧是否完成启动或电源握手 | 当前目标能否接收；不能替代设备数据核对 |
| 内核及驱动 | 软件映射是否建立，处理函数是否被调用，设备条件是否正确处理 | 软件执行是否推进；计数增长不自动证明设备业务完成 |

普通中断不进入时，从 S1 的来源条件逐步走到 S3，而不是先随机改触发类型；不断重入时，重点回到 S4 的清源和 S5 的配对；仅某个处理器失败时，区分全局来源与每核初始化；仅休眠后失败时，继续检查平台电源交接。

消息路径还多出内存和命令观察点：队列被消费、**同步命令（SYNC，规范的命令名称）** 完成、配置缓存失效、硬件可访问地址和内存属性。不能直接写挂起表“试着补一个位”，也不应该为了观察而额外读取有确认副作用的寄存器。

## 10.6\_先做只读观察\_再设计有边界的实验

这里安排一次目标 Linux 板上的只读观察。前提是系统已正常启动，串口由既有驱动管理，有一条已知可用的接收/测试通路，并能产生可控的一小段输入。不要为实验改写 GIC 寄存器，也不要在不熟悉的控制台连接上随意注入字符。当前编辑环境不是目标板，以下步骤尚未在板上执行。

先在目标板终端运行 `uname -r`，记录运行内核版本，再把它与自己的固件、构建提交、配置和设备树关联。`uname` 只提供运行身份中的一部分，不会替你确认源码提交。

```bash
# 执行位置：目标 Linux 板终端；当前目录不限。
uname -r
cat /proc/interrupts
```

`/proc/interrupts` 是内核导出的中断计数视图。开头的 CPU 列表示逻辑处理器，设备所在行的第一个编号是软件 IRQ；后面通常还能看到控制器与处理动作名称。先根据实际设备名称和已有驱动信息定位目标行，不要预设行名称，也不要把本书的 INTID 64 当作行首编号。

为了避免凭记忆比较，在同一个目标板 shell 中保存前后快照：

```bash
# 执行位置：同一目标板 shell；当前目录不限。
# 建立本次观察专用目录；模板中的 X 由系统替换成唯一后缀。
gic_observation_dir=$(mktemp -d /tmp/gic_observation.XXXXXX) &&
cat /proc/interrupts > "$gic_observation_dir/before.txt"
```

只有前一步成功并生成快照才继续；`&&` 表示前一个命令成功后才执行后一个命令。若目录创建或读取失败，先排除错误，不执行后续块。现在通过已有接收通路发送一小段已知数据，例如 16 字节，并检查正常应用是否收到相同内容。随后在原终端执行：

```bash
# 执行位置：保存 before.txt 的同一目标板 shell。
cat /proc/interrupts > "$gic_observation_dir/after.txt"
diff -u "$gic_observation_dir/before.txt" "$gic_observation_dir/after.txt"
```

`diff` 是文本比较命令；有差异时退出码 1 是它的正常结果，不表示中断实验失败。寻找目标行各 CPU 列的增量，同时保留实际收到的字节数。一次输入可能合并成少数通知，也可能伴随设备超时或其他原因，所以“收到 16 字节”不要求“计数恰好加 16”。计数在哪个逻辑 CPU 上增长是软件执行证据，仍不能直接推导第七章介绍的硬件亲和性字段。

若计数没有变化，先确认目标行与输入通路选对，并检查应用是否收到数据；设备也可能通过轮询或其他通路处理。若计数明显增长却没有收到数据，优先检查设备原因、驱动消费和软件接收路径，不要立即断言 GIC 丢数据。若停止输入后仍持续快速增长，应结合设备状态检查未清源、触发类型或其他持续原因；计数快照本身还不能区分这些情况。

观察结束后可用 `cat` 查看并另行保存这两个小文本文件。确认不再需要本次快照时，只删除本实验生成的文件和目录：

```bash
# 执行位置：同一目标板 shell；仅清理本次已保存的观察文件。
rm -- "$gic_observation_dir/before.txt" "$gic_observation_dir/after.txt"
rmdir -- "$gic_observation_dir"
unset gic_observation_dir
```

没有改变硬件配置，所以无需“恢复一个 GIC 寄存器值”。如果 `mktemp` 失败、文件未生成或设备信息不完整，先解决观察环境，不能用空快照宣称“没有中断”。后续若要实验性修改亲和性，应另行固定来源可迁移性、停止生产与恢复协议；这不属于本次只读观察。

> 官方对照：[Linux v6.12《The /proc Filesystem》](https://www.kernel.org/doc/html/v6.12/filesystems/proc.html)，1.2 Kernel data → interrupts。对照中断计数的列与来源；其中的 x86 示例不代表 Arm 的控制器名字和额外统计行。这里给出可执行观察步骤与判断边界，未宣称完成板上实验。

## 10.7\_第一轮结束以后\_哪些结论已经建立

现在应能从一个串口事件重建普通中断的 S0～S6，解释各层状态和四个不同完成动作；也应能把消息来源沿设备身份、事件翻译、**局部性专属外设中断（Locality-specific Peripheral Interrupt，LPI）** 的挂起和处理器确认继续追下去。换一个错误条件时，能够说明它破坏了哪项前提，而不是只记住寄存器名字。

这完成的是 **GICv3.0 物理中断的第一轮机制讲解**。它不表示已经穷尽所有配置分支、逐行解释 Linux 实现，或完成 RK3588 板上实验。这些工作需要固定目标软件和实验环境后分别落地。

下一条扩展线首先是 GICv3 本身已有的虚拟化机制：先建立虚拟机、虚拟处理器和管理程序的概念，再解释状态如何交接。GICv4 在这些问题成立后再引入，不作为当前 RK3588 物理主线的前置，也不因为本卷结束就默认读者已经懂虚拟化。
