# 第5章\_优先级\_屏蔽与嵌套处理

## 5.1\_已经挂起的请求\_为什么仍然不能进入

**通用中断控制器（Generic Interrupt Controller，GIC）** 保存了一个挂起请求，只表示该请求在等待确认，不代表它现在就能打断处理器。上一章的 [S2～S3](P04_一次中断的状态转换与完成协议.md#4.4_用同一组阶段闭合正常周期)之间，还存在接收条件的筛选。

本章先固定 **非安全第 1 组（Non-secure Group 1）**：这是把来源交给非安全软件使用的中断安全归属，不决定优先级。后文会明确区分它与“组优先级”。再固定同一个接收 **处理单元（Processing Element，PE）**，先看两个来源竞争。这样可以分开“在等待者中选谁”和“能否打断已经运行的处理代码”，不把安全切换、目标路由和嵌套同时倒进一个例子。

## 5.2\_优先级数值为什么越小越紧急

先回到同一个 PE 面前的两个请求：串口有数据待取，另一个本地定时来源也已挂起。假设系统设计要求先服务后者，仅靠 INTID 只能认出“是谁”，还不能表达“当前应该先给谁机会”。软件需要为每个来源配置紧急程度，GIC 再把这份配置用于候选选择；这份紧急程度就是本节的优先级。

GIC 用无符号数表示优先级，数值较小的来源具有较高优先级。这是编码约定，不是“中断号小所以优先”。**中断标识符（Interrupt Identifier，INTID）** 负责识别来源，优先级是另一个配置维度。

架构提供 8 位优先级字段，但实现可以只实现其中的高若干位。未实现的低位不能提供额外区分能力。因此不能因为字段有 8 位，就宣称有 256 个有效优先级。本章算例取 0x40、0x60、0x68、0x80 这些值，并假设所需高位有效；对具体机器还应核对实现与当前安全访问视图。

两条请求都挂起时，控制器先依据有效优先级选择适合递送的来源。对无法从当前信息区分的请求，不应依赖“刚好这一次先来了谁”建立软件正确性；设备队列和任务依赖不能寄托在未确认的仲裁细节上。

这里的数值比较描述同一时刻已经进入仲裁观察范围的候选。请求与配置的传播需要时间，不能把这个静态比较升级为“真实机器总按优先级从高到低进入处理函数”的绝对承诺。规范保证满足条件的最高优先级请求会在有限时间内送达，同时明确不保证较高优先级中断总在较低优先级中断之前被接收。后面的排队算例都固定候选集合与配置已经稳定，用来练习比较规则。

这些数值不是保存在设备数据寄存器中，而是写入 GIC 的 **中断优先级寄存器（Interrupt Priority Registers）**。亲和性路由开启时，接口按来源归属分成两组。下表的 `GICD_base` 是 Distributor 的 MMIO 基址，`SGI_base` 是所选 PE 的 SGI/PPI 页基址；`n = INTID DIV 4`，`b = INTID MOD 4`，即每个 32 位寄存器容纳四个来源的优先级。

| 寄存器组与作用范围 | MMIO 地址、宽度与访问属性 | 字段及写入效果 |
| --- | --- | --- |
| `GICD_IPRIORITYR<n>`：共享的 SPI 优先级 | `GICD_base + 0x0400 + 4n`；32 位、可读写，也支持按字节访问 | bit `[8b+7:8b]` 保存 INTID `4n+b` 的优先级；按字节访问时地址为 `GICD_base + 0x0400 + INTID` |
| `GICR_IPRIORITYR<n>`：所选 PE 的 SGI/PPI 优先级，n 为 0～7 | `SGI_base + 0x0400 + 4n`；32 位、可读写，也支持按字节访问 | 相同的字节编号规则，但只影响这一 PE 的私有来源；0～3 号寄存器覆盖 SGI，4～7 号覆盖 PPI |

写这些字段修改仲裁配置，不会确认或结束中断。访问还受来源安全归属限制；未实现的优先级低位读作 0、写入无效。多字节访问包含多个来源，软件必须避免无意覆盖相邻配置。依据为 IHI0069 H.b 的 12.9.20（12-580～12-581）、12.11.21（12-680～12-681）及 12.1.3 的访问宽度规则。

> 官方对照：[规范 IHI0069 H.b](https://developer.arm.com/documentation/ihi0069/hb)，4.8 Interrupt prioritization（4-71～4-72），特别是实现优先级位数、同优先级仲裁的实现定义，以及有限时间递送与实际接收顺序的保证边界。数值算例仅在所用位有效、处于相同安全访问视图时成立，不是 RK3588 运行配置。

## 5.3\_先过固定门槛\_再过当前处理的门槛

选出了等待者中的高优先级来源，还不等于现在适合打断这个 PE。假设内核正在准备一段暂时不能被普通设备处理打断的本地状态，但仍希望允许更紧急的来源进入。逐个改写所有来源的优先级，既会改动原有先后关系，也不是只改变本 PE 当前接收政策的办法。接收侧需要一个独立门槛：来源保留自己的优先级和 Pending，当前 PE 只接收门槛以上的请求。

**优先级屏蔽寄存器（Priority Mask Register，PMR）** 的具体系统寄存器名为 `ICC_PMR_EL1`。它保存当前 PE 的优先级门槛，只有数值严格小于门槛的请求，才满足这一项递送条件。这里比较的是同一访问视图中的值；跨安全状态的数值转换不在本算例中混用。

如果门槛是 0x80，优先级 0x40 和 0x60 可以通过，0x80 本身不能通过。通过 PMR 仍不代表可以确认：来源可能未使能、目标不匹配，或者当前已经占用了更高的运行优先级。

但固定门槛还有一个缺口：门槛允许 0x40 和 0x60，不代表 0x60 已在处理时仍能无条件接受另一个 0x60。接收侧还要知道“此前确认、尚未完成优先级下降的处理，占用了什么优先级”，再判断后来者能否打断它。

**运行优先级（Running priority）** 表达接收侧尚未完成优先级下降的确认带来的约束。它不是 C 函数当前运行到哪行，也不是外设缓冲区的紧急程度。软件确认中断时，控制器更新它；软件按协议写结束寄存器后，再恢复之前的约束。可通过 `ICC_RPR_EL1`，即 **Running Priority Register（运行优先级寄存器）**，观察该接收侧状态。

```text
初始没有占用的中断优先级：运行优先级为 idle 值 0xFF
确认优先级 0x60 的来源：运行优先级收紧
优先级 0x40 的新来源到来：可能满足抢占条件
优先级 0x80 的新来源到来：不能因此抢占 0x60
完成当前优先级下降：恢复此前的接收侧约束
```

**抢占（Preemption）** 指更高优先级的请求引起嵌套处理，打断当前较低优先级的处理过程。硬件允许抢占，还不等于软件现场已经能安全嵌套；处理器异常屏蔽、栈、保存现场和处理程序可重入性仍须满足条件。

再把这条时间线延长一步：0x60 的来源尚未下降优先级时，0x40 的来源又被合法确认。现在接收侧首先受较高的那一档约束，但当 0x40 对应的 EOIR 到来，0x60 的约束还应恢复，不能直接变成 idle。**因此，接收侧必须保留尚未结束的活动优先级信息，运行优先级只是由这些信息形成的当前结果。** 仅抄下一个 RPR 读数，不能代替保存全部相关状态。

普通处理中，这些信息由确认和优先级下降协议推进，设备驱动无需手工维护它们。需要受控保存、恢复 CPU Interface 状态的软件，则通过 **活动优先级寄存器（Active Priority Registers，APR）** 访问这部分状态；它们不能与第四章按 INTID 保存的 Active 位混为一谈。下表都属于当前 PE 的 CPU Interface，AArch64 使用系统寄存器访问，不使用 MMIO 地址。

| 接口 | 宽度、访问方式与相关位 | 作用与副作用 |
| --- | --- | --- |
| `ICC_PMR_EL1` | 64 位、`MRS/MSR` 可读写；Priority `[7:0]` | 修改本 PE 的递送门槛，只有同一视图下数值严格更小的来源才通过；写入不清 Pending。写指令在架构上执行后，新的屏蔽约束就须生效，无需另加指令同步来阻挡被它屏蔽的优先级；这不证明其他 GIC 写入已完成 |
| `ICC_RPR_EL1` | 64 位、`MRS` 只读；本章使用 Priority `[7:0]` | 观察当前运行优先级；无活动优先级时为 idle 值 `0xFF`。读取不确认来源，也不下降优先级 |
| `ICC_AP0R<n>_EL1` | 每项 64 位、`MRS/MSR`；本章 GICv3.0 的低 32 位内容由实现定义 | 表达本 PE 的 Group 0 活动优先级信息；全零与没有活动优先级一致，不能按位号自行猜 INTID |
| `ICC_AP1R<n>_EL1` | 每项 64 位、`MRS/MSR`；低 32 位内容由实现定义，Group 1 按安全状态分副本 | 表达相应 Group 1 活动优先级信息；普通处理用 IAR/EOIR 推进状态，不直接改 APR 来代替确认或结束 |

APR 的 n 取值是否实现取决于支持的优先级位数；不能假定 0～3 四项都存在。直接写入任意 APR 数值可能破坏抢占关系，状态恢复须遵守原值和规定顺序；这里提供的是状态位置说明，不是一份切换上下文的代码。上述系统寄存器均以前述物理接口访问许可已建立为前提，PMR/RPR 的安全视图还需与来源优先级一致。

> 官方对照：[规范 IHI0069 H.b](https://developer.arm.com/documentation/ihi0069/hb)，4.8.5 Preemption、4.8.6 Priority masking；上表按 12.2.19 ICC_PMR_EL1（12-267～12-269）、12.2.20 ICC_RPR_EL1（12-270～12-272）、12.2.1 ICC_AP0R（12-216～12-218）及 12.2.2 ICC_AP1R（12-219～12-222）整理。门槛、运行优先级与活动优先级保存接口各自承担不同问题。

## 5.4\_为什么还要区分组优先级与子优先级

有时希望两个来源在排队时分先后，但不希望它们互相打断。例如 B、C 都处理同一类低紧急度设备，先处理更紧急的 B 有价值，但在 C 已经执行时再为 B 保存一层现场，未必值得。如果始终比较完整优先级，B 比 C 紧急就会同时影响排队和抢占；若把两者设成完全相等，又失去等待者中的细分。因此需要让两种判断使用不同精度：把优先级拆成两个部分，高位的 **组优先级（Group priority）** 决定能否抢占，低位的 **子优先级（Subpriority）** 在等待者之间继续区分先后。这里的“同组优先级”准确地说是 **高位部分相等**，不是又创建了一个名叫 Group 0 或 Group 1 的来源集合。

### 5.4.1\_把一个优先级数值按位拆开

先对控制器使用的 **完整 8 位优先级** 做教学计算，暂不把它当作非安全软件直接读写的数值。假设低 4 位属于子优先级，高 4 位属于组优先级：

```text
完整优先级：  b7 b6 b5 b4 | b3 b2 b1 b0
用于抢占：  保留高 4 位 | 低 4 位视为 0
等待者选择：比较完整有效优先级，仍保留低位的先后差异

B = 0xB0 = 1011 | 0000，抢占比较值 0xB0
C = 0xB4 = 1011 | 0100，抢占比较值 0xB0
A = 0xA0 = 1010 | 0000，抢占比较值 0xA0
```

| 来源 | 完整优先级 | 抢占比较值 | B 已确认且尚未下降优先级时 |
| --- | --- | --- | --- |
| A | 0xA0 | 0xA0 | 小于 B 的比较值，可以成为抢占候选 |
| B | 0xB0 | 0xB0 | 当前占用者 |
| C | 0xB4 | 0xB0 | 高位与 B 相等，不能抢占 B |

反过来，若 C 已在处理，B 也不能抢占 C；若 B、C 都未确认，且已经进入同一稳定候选集合，完整优先级 0xB0 小于 0xB4，B 是其中优先级更高的候选。两者没有矛盾：前一个问题比较 **能否打断当前处理**，后一个问题比较 **等待者中的选择优先级**；实际接收时间仍受前节所述的递送边界约束。

### 5.4.2\_分割点编码与软件看到的数值不能混用

上面的算例已经确定了希望得到的行为：高 4 位相同的来源不互相抢占，但完整数值仍能区分等待先后。现在才需要把这个边界配置进 CPU Interface。硬件允许选择不同的分割位置，而安全组之间也可以使用各自的分割设置；软件不能只写一个“4”，便假定所有视图都把低 4 位当作子优先级。

切分由 **二进制分割点寄存器（Binary Point Register，BPR）** 控制。当前非安全 Group 1 路径通常使用 `ICC_BPR1_EL1`；其中的 1 是安全分组名称，寄存器内容才决定优先级位的分割。**共同二进制分割点（Common Binary Point Register，CBPR）** 是控制字段名称，置位后可以让 Group 1 使用 `ICC_BPR0_EL1` 的分割规则；下面固定 CBPR 为 0，避免两个配置分支混用。

| 当前 PE 的系统寄存器 | 宽度与访问方式 | 本节相关字段 | 配置效果与边界 |
| --- | --- | --- | --- |
| `ICC_BPR0_EL1` | 64 位、`MRS/MSR` 可读写 | BinaryPoint `[2:0]` | 决定 Group 0 的分割点；在相应 CBPR 为 1 的配置下，还作为 Group 1 的共同分割点来源 |
| `ICC_BPR1_EL1` | 64 位、`MRS/MSR`；按安全状态分副本 | BinaryPoint `[2:0]` | CBPR 为 0 时决定相应 Group 1 的分割点；最小有效编码受实现优先级位数限制，不能任意选择 |
| `ICC_CTLR_EL1` | 64 位、`MRS/MSR`，字段权限各异 | CBPR bit 0 | 选择独立或共同分割点，不修改中断的安全组；EL3 存在且两安全状态有效时，这个位在 EL1 视图只读，不能假定普通内核可自行切换 |

它们都是 CPU Interface 配置，访问前提与上一节一致，读写本身不确认或结束来源。CBPR 为 1 时，BPR1 的读写可能变成相应的别名视图或被忽略，不能仍按独立寄存器处理。本节只在 CBPR 为 0 的前提下推导数值。位域依据为 IHI0069 H.b 的 12.2.4（12-226～12-228）、12.2.5（12-229～12-232）和 12.2.6（12-235）。

在规范的两安全状态模型、CBPR 为 0 时，下列编码都能把 **完整优先级** 切成高 4 位与低 4 位，但属于不同接口视图：

| 使用的分割点寄存器视图 | 分割点值 | 完整优先级中的组优先级位 | 子优先级位 |
| --- | --- | --- | --- |
| Secure `ICC_BPR1_EL1` | 3 | `[7:4]` | `[3:0]` |
| Non-secure `ICC_BPR1_EL1` | 4 | `[7:4]` | `[3:0]` |

这是对 IHI0069 H.b 表 4-10、表 4-11 中本例所需两行的整理，两行都可在印刷页 4-75 找到。它们表达的是同一个位划分为什么需要两个不同编码，不是要求软件连续写两次同一个寄存器。CBPR 为 1 时改用共同分割点的规则属于表 4-12，不混入本次 CBPR 为 0 的算例。

这些编码还受实现支持的优先级位数和最小分割点约束，不能跳过读回能力核对。上面的 A、B、C 算例要求区分 0xB0 与 0xB4 的位实际存在；未实现的位写进去不会创造新的优先级。

具体到 GIC-600 r1p6，手册规定它支持 32 个物理优先级，即完整优先级只有高 5 位有效。因此，0xB4 与 0xB0 在这个产品上不能形成两档优先级；本例用于说明规范允许的更精细实现，不能原样当作 RK3588 的寄存器配置。要在该产品上保留“组优先级相同、子优先级不同”的比较，可以把 C 的完整值改成 0xB8，并核对当前安全视图与 BPR 设置。

为什么本节改用 0xA0、0xB0、0xB4？前节 0x40、0x60、0x68 是同一非安全访问视图中的教学值；在启用两安全状态时，非安全优先级的视图存在变换。对本例涉及的有效位，完整优先级为 `0x80 | (非安全视图值 >> 1)`，所以它们分别对应 0xA0、0xB0、0xB4。规范要求优先级分割作用在完整优先级上，不能把非安全读到的数值直接套进完整位图，再猜一个 BPR 编码。

本章只在这个固定边界下做算例。若关闭两安全状态，或改用共同分割点，要重新按对应表格计算；不能把本表当作所有模式都相同的初始化常量。

此外，PMR/RPR 是否使用变换后的非安全数值视图，还与高权限安全路由配置有关。前面的门槛算例以来源与门槛视图已经对齐、PMR 当前允许非安全软件配置为前提；不能只因代码在非安全环境执行，就把两个寄存器读数直接相减。具体访问条件见规范 4.8.2，配置责任由下一章展开。

> 官方对照：[IHI0069 H.b](https://developer.arm.com/documentation/ihi0069/hb)，4.8.3 Priority grouping，Table 4-10、4-11、4-12（印刷页 4-74～4-76）与 4.8.7 Software accesses of interrupt priority；12.2.5 ICC_BPR1_EL1。[GIC-600 r1p6 手册](https://developer.arm.com/documentation/100336/0106)，附录 B 表 B-1（Appx-B-203）明确 32 个物理优先级。重点查完整值、非安全视图、CBPR 和分割点编码分别改变哪一步。

## 5.5\_控制器屏蔽与处理器屏蔽不能互相替代

现在把“能不能送达”放回硬件路径。**来源使能** 是一个 INTID 的开关；**中断安全组使能** 是 Group 0、Secure Group 1 或 Non-secure Group 1 对应的递送开关；PMR 是当前 PE 的优先级门槛。中断安全组使能与上节的组优先级不是同一件事：关闭 Non-secure Group 1，会挡住这个安全分组中不同优先级的来源，不是只挡住高位相等的一档优先级。

对共享来源，来源使能保存在 **分发器（Distributor）** 的 `GICD_ISENABLER<n>` 等寄存器接口中；私有来源由对应 **再分发器（Redistributor）** 的 `GICR_ISENABLER0` 等接口管理。全局安全组递送由 `GICD_CTLR` 控制，而每 PE 的 `ICC_IGRPEN1_EL1`，即 **Interrupt Controller Interrupt Group 1 Enable register（中断控制器第 1 组使能寄存器）**，控制该 PE 对相应安全状态 Group 1 的接收。本例需要 Non-secure Group 1 的全局与本 PE 接收条件都成立。

处理器另外维护 **处理器状态（Processor State，PSTATE）**。在本专题的 AArch64（64 位执行状态的架构专名）模型中，**中断请求（Interrupt Request，IRQ）** 是一种异步异常类别。先固定 IRQ 路由到当前执行的 EL1、没有更高异常级接管：此时 **PE0 的 PSTATE.I 为 1，只屏蔽 PE0 对这类 IRQ 的接收**；PE1 的 PSTATE.I 不会随它改变。设备仍可接收数据，GIC 仍可保留请求，已在其他 PE 上运行的处理代码也不会因此停止。

图中的 **中断确认寄存器（Interrupt Acknowledge Register，IAR）** 用于领取具体来源；**中断结束寄存器（End Of Interrupt Register，EOIR）** 与 **中断停用寄存器（Deactivate Interrupt Register，DIR）** 执行第四章的完成协议。下文合写 EOIR/DIR 时只是并列这两类接口，不表示必须无条件写两次。设备处理代码也称 **中断服务程序（Interrupt Service Routine，ISR）**，由公共入口识别来源后调用。

下图先画 GIC 硬件中的 **逻辑条件与阶段关系**，再跨入 PE 异常硬件和在它上面执行的软件。前半段不是芯片内部按框串行排列的物理筛选流水线。

```mermaid
flowchart TD
    device["S1 外设硬件保存数据，产生请求"] -->|"请求输入建立状态"| pending["S2 GIC 硬件保留 Pending"]
    pending -->|"来源与目标条件满足"| enabled["GIC 硬件的递送条件<br/>来源使能、安全组全局与每 PE 使能"]
    enabled -->|"完整优先级通过 PMR"| priority["CPU Interface 硬件<br/>按 BPR 比较组优先级与运行优先级"]
    priority -->|"向选定 PE 呈现 IRQ"| pe["PE 异常硬件<br/>已路由到当前 EL1，PSTATE.I 允许接收"]
```

沿这条链看一次串口请求：来源尚未开放时，它不能仅凭高优先级进入；来源和组已开放后，当前 PE 的组接收与优先级条件仍要允许它；GIC 已经呈现 IRQ，PE 的异常屏蔽又可能暂缓进入。关闭其中一道许可并没有把外设数据或此前的 Pending 一并删掉。下面把这几处已经分清的 GIC 开关对应到编程接口。

| 当前使用的开关 | 地址或系统寄存器、宽度 | 本节使用的读写语义 |
| --- | --- | --- |
| SPI 来源使能 `GICD_ISENABLER<n>` | MMIO `GICD_base + 0x0100 + 4n`，32 位；n 为 `INTID DIV 32` | 读出当前使能；向 `INTID MOD 32` 对应位写 1 使能，写 0 无效；它不会清除 Pending，也不会确认来源 |
| 本 PE 的 SGI/PPI 使能 `GICR_ISENABLER0` | MMIO `SGI_base + 0x0100`，32 位 | 位号等于本地 INTID，读及写 1 置使能规则同上；SGI 是否允许禁止由实现选择 |
| 实例级组使能 `GICD_CTLR` | MMIO `GICD_base + 0x0000`，32 位，按字段读写 | 在两安全状态有效、亲和性路由开启的安全视图，`EnableGrp1NS` 为 bit 1；对应非安全视图用 bit 1 的 `EnableGrp1A` 别名。0 禁止、1 允许该组，不改变其安全归属 |
| 本 PE 的 Group 1 接收 `ICC_IGRPEN1_EL1` | 64 位系统寄存器，`MRS/MSR` | 当前安全状态副本的 Enable bit 0；0 禁止、1 允许该组接收，不改变另一 PE 的开关 |

以上访问都需要相应权限，普通非安全软件不能借表格修改安全来源。来源使能的清除接口、三种组使能及实现定义边界，在下一章的[硬件结构与配置归属](P06_权限_安全分组与初始化闭环.md#6.3.2_硬件结构与配置归属先对齐)集中列出；本表只保留本节递送链使用的操作。依据为 IHI0069 H.b 的 12.9.26（12-593～12-594）、12.11.25（12-688～12-689）、12.9.4（12-544～12-549）和 12.2.16（12-260～12-262）。

若任一递送条件不成立，Pending 不会因为“尚未送达”就自动变为 Active；在本章普通递送协议中，真实确认才建立对应的活动交接。处理器接收异常与入口读 IAR 也必须分开观察。图中的软件动作都由同一个 PE 执行，读取 IAR 或写入结束寄存器后，再由相应 GIC 硬件推进状态。

### 5.5.1\_哪些异常受哪个屏蔽位约束

“普通异常”不是本章采用的正式分类。AArch64 的异常向量区分以下四类；本章主线只处理其中的 IRQ：

| 异常类别 | 从哪里来 | 与本章屏蔽位的关系 |
| --- | --- | --- |
| 同步异常（Synchronous exception） | 执行指令时触发，例如系统调用、地址访问异常 | 不因 PSTATE.I 为 1 就禁止发生 |
| IRQ | 外设或核间通知经中断路径递送 | 在本章当前 EL1 接收模型下，由 I 位屏蔽 |
| FIQ（Fast Interrupt Request，快速中断请求） | 另一类中断异常输入，其呈现与安全分组有关 | 在对应的当前异常级接收模型下，由 F 位屏蔽；Fast 不保证设备更快 |
| SError（System Error，系统错误） | 异步系统错误，例如某些内存系统错误报告 | 由相应错误路由规则及 A 位等控制，不由 I 位统一控制 |

PSTATE 的 D 位还屏蔽适用的调试异常，它不是第五个与上表同级的向量类别。这些位不是“关闭整个 PE”的总开关。尤其是路由到更高异常级的中断，要按目标异常级与架构路由规则判断，不能用低异常级当前的 I/F 位一概推断能否屏蔽。具体路由在下一章建立。

若软件需要观察或调整这些屏蔽位，AArch64 用下面的接口访问当前 PE 的相应状态。

| 处理器接口 | 访问方式与宽度 | 本节相关位域与效果 |
| --- | --- | --- |
| `DAIF`：访问当前 PE 的 PSTATE 屏蔽位 | AArch64 64 位系统寄存器接口，EL1 在当前前提下用 `MRS Xt, DAIF` / `MSR DAIF, Xt` 读写；不是 GIC MMIO 寄存器 | D/A/I/F 分别位于 `[9]`、`[8]`、`[7]`、`[6]`，置 1 表示相应屏蔽；改变 I/F 不清除 GIC 的 Pending/Active，也不替换异常目标 EL |

这里只列本章使用的屏蔽位，PSTATE 并非一个可以整体映射成设备寄存器的对象。`DAIF` 的定义及访问依据为 [DDI0487 M.c](https://developer.arm.com/documentation/ddi0487/mc)，C5.2.3（C5-942～C5-945）；上述异常分类限定了各位的作用边界。

本卷固定 GICv3.0，不把后续 GICv3.3 引入的 **不可屏蔽中断（Non-maskable Interrupt，NMI）** 支持混入当前模型，也不把 FIQ 简称为 NMI。

| 观察 | 能说明什么 | 不能据此断言什么 |
| --- | --- | --- |
| 来源 Pending，但尚未进入 | 控制器有待确认状态 | 路由、优先级和 PE 接收条件都正确 |
| 来源使能为 0 | 该来源不能按此使能条件递送 | 数据停止产生、Pending 已清空、旧处理已结束 |
| 当前 EL1 的 IRQ 被本 PE 的 I 位屏蔽 | 本 PE 暂不接收这一模型中的 IRQ | 其他 PE 被屏蔽，或共享数据已经免于并发访问 |
| 设备 ISR 已返回 | 设备处理函数本次调用结束 | 已按当前模式完成 EOIR/DIR，或已经执行异常返回 |

> 官方对照：[概览 198123，3.2-01](https://developer.arm.com/documentation/198123/0302)，第 5～6 章的使能和递送条件；[Exception model，Version 1.0](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Exception%20model.pdf?revision=a62f2bf2-b08a-4a4f-8cbe-38c67ddf4434)，第 4 章 Exception types、第 5 章 Handling exceptions、第 6 章 The vector tables。GIC 的 NMI 版本边界见概览第 5 章来源配置中的 Non-maskable 项。

## 5.6\_嵌套需要成对恢复\_不能乱序结束

这里的 A、B 是两个中断来源及其处理过程，不是两个线程。假设外层 B 正在 PE0 的 EL1 执行，高优先级 A 随后满足 GIC 抢占条件，而且入口软件已经允许同 EL 的 IRQ 嵌套。A 不需要知道 B 正在执行哪行代码；B 也不会预知 A 何时到来。**中断接收由硬件触发，现场的保存与恢复由 PE 硬件和公共异常入口软件分担，设备 ISR 只承担该框架交给它的设备工作。**

### 5.6.1\_硬件先保存什么\_公共入口还必须保存什么

**异常链接寄存器（Exception Link Register，ELR）** 保存异常返回地址，**保存的程序状态寄存器（Saved Program Status Register，SPSR）** 保存进入前的处理器状态。A 被接收时，PE 硬件把返回 B 所需的地址写入 `ELR_EL1`，把进入前的 PSTATE 写入 `SPSR_EL1`，更新屏蔽等执行状态，再转向异常向量。

硬件没有因此把所有通用寄存器自动压栈。公共入口代码必须把需要保留的寄存器、返回地址和状态保存到软件栈帧，再调用 A 的 **中断服务程序（Interrupt Service Routine，ISR）**。这里要保留的不只是普通函数调用约定中的部分寄存器，因为异步打断可能发生在 B 使用任意寄存器保存临时值的时候。

而且同一个 EL 的 ELR/SPSR 不是硬件无限深栈。B 首次进入时，这两个寄存器保存的是返回 B 之前执行路径的信息；如果 B 的公共入口没有先把这份信息保存到软件栈，A 再进入就会覆盖它。因此 **B 的入口在允许嵌套之前要先建立完整栈帧**；这是公共入口保护异常返回链的责任，不是要求 B 的设备函数替未来 A 的代码做备份。

表中的 `ADDR` 是地址（Address）字段名；`NZCV` 指运算结果的负数、零、进位、溢出四个条件标志，M 是返回执行模式字段。它们与前面已经解释的 DAIF 一起，说明要保护的是哪些返回状态。**异常返回指令（Exception Return，ERET）** 根据恢复后的返回地址与状态继续旧路径。

| 当前 PE 的处理器寄存器 | 宽度与访问方式 | 本次异常所用内容 | 谁在什么时候使用 |
| --- | --- | --- | --- |
| `ELR_EL1` | 64 位系统寄存器；EL1 在当前前提下可 `MRS/MSR` | ADDR `[63:0]`，异常返回地址 | 进入 EL1 的异常由硬件写入；公共入口保存到栈，退出前恢复，`ERET` 据此返回 |
| `SPSR_EL1` | 64 位系统寄存器；EL1 在当前前提下可 `MRS/MSR` | 返回状态，包括 NZCV `[31:28]`、DAIF `[9:6]`、模式 M `[4:0]` 等当前有效字段 | 硬件保存异常前的返回状态；软件保护嵌套层的副本，退出前恢复，`ERET` 用它恢复相应 PSTATE |

读这些寄存器不会确认 GIC 来源，写它们也不会完成 EOI。表中的 EL1 访问仍以前述无虚拟化重定向或上层截获为前提；不能从“可读写”推导出任意返回地址或状态编码都合法。依据为 [DDI0487 M.c](https://developer.arm.com/documentation/ddi0487/mc)，C5.2.5（C5-953～C5-954）、C5.2.21，特别是 AArch64 返回状态字段（C5-1013～C5-1017）。

### 5.6.2\_从打断到恢复B的完整时间线

下面固定 EOImode 为 0，且 B 尚未优先级下降，最后通过已经解释的 ERET 恢复旧路径。图中的“硬件”“公共入口”和“设备 ISR”是同一 PE 上不同职责的阶段，不是三颗处理器。

```mermaid
sequenceDiagram
    autonumber
    participant gic as GIC 接收侧硬件
    participant pe as PE0 异常硬件
    participant entry as PE0 公共入口与退出软件
    participant isr as PE0 设备 ISR 软件
    Note over entry,isr: B 的入口已保存返回旧路径的栈帧<br/>已确认 B，并允许 IRQ 嵌套
    isr->>isr: S4 正在执行 B 的设备处理
    gic-->>pe: S2 A 通过组优先级等条件，呈现 IRQ
    pe->>pe: S3 保存返回 B 的 ELR/SPSR，设置异常入口状态
    pe->>entry: 按异常向量执行公共入口
    entry->>entry: 保存 B 的通用寄存器与返回状态到内层栈帧
    entry->>gic: 读 IAR，确认 A 并记录确认结果
    entry->>isr: S4 分派并调用 A 的设备 ISR
    isr-->>entry: 处理 A 的设备条件后返回
    entry->>gic: S5 写 A 的 EOIR，下降优先级并停用 A
    entry->>entry: 恢复 B 的寄存器与异常返回状态
    entry->>pe: S6 执行 ERET 异常返回指令
    pe->>isr: 恢复进入 A 之前的状态，继续 B
    isr-->>entry: B 的设备处理结束
    entry->>gic: S5 写 B 的 EOIR，下降优先级并停用 B
    entry->>pe: S6 恢复 B 的外层栈帧并异常返回
```

步骤 3 是硬件建立最小异常返回状态，步骤 5 是公共入口保存软件现场；步骤 8 的 ISR 函数返回也还不是步骤 11 的 **异常返回指令（Exception Return，ERET）**。ERET 根据恢复后的 SPSR/ELR 原子恢复执行状态和返回位置，才使 B 继续。

步骤 9 先结束 A 的优先级占用，步骤 14 再结束 B，顺序与确认相反。若在内层 A 尚未完成优先级下降时先写 B 的结束信息，就破坏接收侧维护的嵌套优先级关系。分离模式还要另外追踪各来源的停用责任，不能只按 C 函数返回顺序猜测全部动作都完成。

即使现场保存正确，设备处理代码也可能因重入、锁或共享数据不允许嵌套。例如 B 持有一个只能由它释放的锁，A 打断 B 后在同一 PE 忙等该锁，B 就没有机会继续释放。因此允许嵌套是整个入口框架与处理代码共同满足的策略条件；本图解释架构可支持的协议，不代表某套 Linux 的硬中断入口采用这种策略。

> 官方对照：[Exception model，Version 1.0](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Exception%20model.pdf?revision=a62f2bf2-b08a-4a4f-8cbe-38c67ddf4434)，5.2 Taking an exception、5.5 Returning from an exception；[IHI0069 H.b](https://developer.arm.com/documentation/ihi0069/hb)，4.1.1 的确认与优先级下降配对规则、4.8.5 Preemption。


## 5.7\_改变一个条件\_预测谁能继续

沿用 5.4 的完整优先级值，A=0xA0、B=0xB0、C=0xB4，高四位为组优先级；所需位已实现，所有来源、组和目标条件满足。这里暂不填写 PMR 的非安全寄存器读数，而是明确假定门槛足以放行三者，避免把两种数值视图混用。

先按以下三种现场分别作答，不要把上一行发生的确认带入下一行。排队问题固定候选与配置已经稳定，判断的是选择优先级，不预测真实板上异步到达的先后次序：

| 独立现场 | 要预测的问题 |
| --- | --- |
| B、C 均 Pending 且已进入同一稳定候选集合，当前无优先级占用 | 谁是最高优先级候选？ |
| C 已确认且尚未下降优先级，B 后来 Pending | B 能否因数值更小立即抢占？ |
| B 已确认且尚未下降优先级，A 后来 Pending | 即使满足 GIC 抢占条件，为何仍可能不进入？ |

第一行的最高优先级候选是 B，因为完整优先级较高；第二行 B 的组优先级与 C 相同，子优先级差异不能触发抢占。第三行 A 的高位更高，可以成为抢占候选，但同级 IRQ 的 PSTATE.I、入口现场是否允许嵌套、软件策略仍须满足。硬件的仲裁资格不能代替软件的可重入性。

接着只改 PMR。使用 5.3 已对齐的同一非安全数值视图，来源优先级 0x60、PMR 也为 0x60，其他条件不变。它会被挡住，因为门槛要求严格小于；把门槛改到 0x80 才满足这一项。若结果仍不进入，应继续检查其他条件，不应反过来宣布“数值越大优先级越高”。

最后把嵌套例子中的 B 改为“确认后已在分离模式下完成优先级下降，但尚未停用”。此时不能继续用 B 的原优先级代表接收侧当前约束，必须检查恢复后的运行优先级；B 自己的 Active 却还存在。这个变体检验的是第四章建立的两个状态维度，而不是又多背一个寄存器。

本章解释了 S2 为什么可能等待，以及 S5 为什么不只是清一个来源位。下一章回到 S0：谁有权配置这些状态，怎样保证来源放开以前接收路径已经准备好？
