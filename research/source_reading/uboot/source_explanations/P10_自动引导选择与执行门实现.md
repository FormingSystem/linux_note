# 第10章\_自动引导选择与执行门实现

本页固定 U-Boot v2022.10、提交 `4debc57a3da6c3f4d3f89a637e99206f4cea0a96`。先从 [模块导读](../navigation/P10_自动引导选择与交互退路导读.md) 确定 A0～A4，再读本页唯一实现；整体版本入口在 [源码索引](../navigation/README.md)。源码沿用上游 GPL-2.0+，中文 Doxygen 与行内说明为仓库补充；裁剪处明确省略，不作为可单独编译的替代实现。

## 10.1\_A0与A1\_环境和控制树怎样形成候选

**讲解层次：实现层，`common/main.c` 与 `common/autoboot.c`。** `main_loop` 的局部 `s` 持有待执行文本指针；延时则不随指针返回，而保存在 `autoboot.c` 的静态 `stored_bootdelay`。两份状态稍后由 `autoboot_command` 共同消费。

```c
/**
 * @brief 仓库阅读说明：主循环先选择，再执行，最后进入 CLI。
 * @note 裁剪版本打点、版本环境值和可选 TFTP/EFI 更新支路。
 */
void main_loop(void)
{
    const char *s;

    /* 本函数原先在这里还有上述可选支路；以下保留相对顺序。 */
    cli_init();
    if (IS_ENABLED(CONFIG_USE_PREBOOT))
        run_preboot_environment_command();
    /* 上游 TFTP/EFI 支路位于预处理之后、选择命令之前。 */

    s = bootdelay_process();
    if (cli_process_fdt(&s))
        cli_secure_boot_cmd(s);

    autoboot_command(s);
    cli_loop();
    panic("No CLI available");
}
```

`cli_init` 的实际实现只按配置启动 Hush 和初始化其变量，不遍历命令表注册回调。`run_preboot_environment_command` 从环境取 `preboot`，存在时调用 `run_command_list`；keyed 配置下先保存并关闭 Ctrl-C 检查，返回后恢复。它不在此处检查脚本返回值。TFTP 与 EFI 分支是否出现由相应配置决定，不能据此推断实际板已经执行过更新。

`bootdelay_process` 的完整先后关系为：增加启动计数；从环境读取 `bootdelay`，无值时用 `CONFIG_BOOTDELAY`；可选控制树覆盖延时；可选菜单显示调整延时；初始化命令重试超时；按自检/启动计数选择候选字符串；处理控制树的其他环境选项；保存延时并返回字符串。这里的菜单显示与倒计时中的菜单键是两个不同入口。

```c
/**
 * @brief 仓库阅读说明：A1 中先确定延时，再按状态选择命令。
 * @note 以下为 bootdelay_process 的两处裁剪，省略处的顺序见正文。
 */
s = env_get("bootdelay");
bootdelay = s ? (int)simple_strtol(s, NULL, 10) : CONFIG_BOOTDELAY;
if (IS_ENABLED(CONFIG_OF_CONTROL))
    bootdelay = ofnode_conf_read_int("bootdelay", bootdelay);

/* 上游在此还有可选菜单、重试超时以及 CONFIG_POST 失败分支。 */
if (bootcount_error())
    s = env_get("altbootcmd");
else
    s = env_get("bootcmd");

/* 上游在保存前还按配置调用 process_fdt_options。 */
stored_bootdelay = bootdelay;
return s;
```

开启 `CONFIG_POST` 且 `GD_FLG_POSTFAIL` 成立时，先选择 `failbootcmd`，不再进入这段 `bootcount_error` 分支。任一环境名不存在都可能返回空指针；没有在此自动改用其他命令。`process_fdt_options` 在定义 `CONFIG_SYS_TEXT_BASE` 时，按控制树偏移设置 `kernaddr`/`rootaddr`，并不等于已经读取内核或根盘数据。

启用本阶段 `OF_CONTROL` 时，随后 `cli_process_fdt` 的源码是：

```c
/**
 * @brief 仓库阅读说明：有控制树命令才覆盖指针，返回值另取 bootsecure。
 */
bool cli_process_fdt(const char **cmdp)
{
    const char *env = ofnode_conf_read_str("bootcmd");
    if (env)
        *cmdp = env;
    return ofnode_conf_read_int("bootsecure", 0);
}
```

源码没有强制“`bootsecure` 非零时命令一定来自控制树”。树中没有 `bootcmd` 时，`*cmdp` 保留前值；这点与紧邻上游注释表达的预期不能混淆。控制树本身的认证也不在此函数完成。

## 10.2\_A2与A3\_特殊延时如何决定是否读取输入

**讲解层次：实现层，`common/autoboot.c::autoboot_command`。** 下面保留完整控制结构，去掉调试打印；静态延时由 A1 写入，静态菜单键由单键输入分支写入。

```c
/**
 * @brief 仓库阅读说明：条件短路决定是否调用输入等待，返回后另查菜单。
 * @param s 借用的候选命令文本；可能为空。
 */
void autoboot_command(const char *s)
{
    if (s && (stored_bootdelay == -2 ||
         (stored_bootdelay != -1 && !abortboot(stored_bootdelay)))) {
        bool lock;
        int prev;

        lock = autoboot_keyed() &&
            !IS_ENABLED(CONFIG_AUTOBOOT_KEYED_CTRLC);
        if (lock)
            prev = disable_ctrlc(1); /* 记住并暂时关闭命令中的 Ctrl-C 检查 */

        run_command_list(s, -1, 0);  /* 返回值未用于选择后续路径 */

        if (lock)
            disable_ctrlc(prev);    /* 只有返回才执行恢复 */
    }

    if (IS_ENABLED(CONFIG_AUTOBOOT_USE_MENUKEY) &&
        menukey == AUTOBOOT_MENUKEY) {
        s = env_get("menucmd");
        if (s)
            run_command_list(s, -1, 0);
    }
}
```

按 C 的短路规则，空 `s` 与 `-1` 都绕开 `abortboot`；`-2` 也绕开它，但进入执行块。非负延时进入 `abortboot`，后者按 `autoboot_keyed()` 选择键串/口令路径或普通单键路径。其他负值不属于正文推荐的配置值；此实现的 `abortboot` 不进入非负分支，会返回未打断，不能把任意负数都说成禁用。

单键路径先以 `tstc()` 检查已经到达的字符：有输入便 `getchar()` 消费并置 `abort=1`。随后仅在 `bootdelay>0 && !abort` 时逐秒检查输入；这个循环里收到字符，才在菜单键配置下写 `menukey=key`。因此零延时仍可被已有输入打断，但该提前输入分支不会更新菜单键。静态 `menukey` 也未在每次调用前清零，不应把它想成当前按键的必然镜像。

`autoboot_keyed()` 在普通目标按配置返回，在 sandbox 则允许运行时控制。沙箱是 U-Boot 作为宿主程序运行的目标，不改变这个函数的逻辑分工。若输入打断且启用静默控制台，`abortboot` 还会清除 `GD_FLG_SILENT`，让后续交互能够显示；它没有在此装载任何系统镜像。

字符串进入执行器以后，按 [列表包装与失败边界](P09_命令解析缓冲区与失败传播实现.md#9.1_列表包装层何时取得可写副本) 继续；回调分派由 [命令记录与检查](P08_命令记录与查找分派实现.md#8.3_两层回调怎样分别返回结果与重复能力) 解释，本页不重复这些函数体。

## 10.3\_A4\_受限执行与CLI返回怎样改变退路

`common/cli.c::cli_secure_boot_cmd` 的合同与普通执行器不同：空命令跳错误路径；否则先禁用 Ctrl-C。启用 `CONFIG_CMDLINE` 时直接 `find_cmd(cmd)`，找到后调用记录中的 `cmd`，传 `flag=0`、`argc=1`，`argv[0]` 就是传入字符串；不做 shell 拆词。未启用命令行时改走板级 `board_run_command`。命令只要返回，无论结果为 0 还是错误，都打印返回信息并 `hang()`。

```c
/**
 * @brief 仓库阅读说明：受限帮助器把返回也视作不能继续的情况。
 * @note 裁剪 CONFIG_CMDLINE 分支的查找和调用；错误出口仍为 hang。
 */
cmdtp = find_cmd(cmd);
if (!cmdtp) {
    printf("## Error: \"%s\" not defined\n", cmd);
    goto err;
}
rc = (cmdtp->cmd)(cmdtp, 0, 1, (char **)&cmd);
printf("## Error: \"%s\" returned (code %d)\n", cmd, rc);
err:
hang();
```

所以一串带参数的 shell 脚本不能在此自动获得普通解析语义；这里也没有镜像签名验证步骤。“命令找到了”和“输入可信”属于不同证明。

普通路径返回后则进入 `cli_loop`：Hush 调 `parse_file_outer`，其后还有无限循环；simple 配置调 `cli_simple_loop`；无 CLI 时打印禁用提示。simple 循环在配置重试超时且读行返回 `-2` 时，按 `CONFIG_RESET_TO_RETRY` 选择 `do_reset` 或 `return`。如果返回到 `cli_loop` 再返回 `main_loop`，后面是本页 10.1 的 `panic`，不是直接返回外层。

`common/board_r.c::run_main_loop` 虽有 `for (;;) main_loop();`，注释也提到重试，但当前代码中间的不可返回动作必须一并考虑。外层循环存在，只能证明“若 `main_loop` 正常返回就会再次调用”；不能证明某条 CLI 超时路径真的到达它。
