# 第2章\_构建上下文与入口选择实现

本页对应 [构建上下文模块导读](../navigation/P02_构建上下文与入口选择导读.md)，版本为上游 U-Boot v2022.10、提交 `4debc57a3da6c3f4d3f89a637e99206f4cea0a96`。正文的两个主机程序解释选择原理，这里只裁剪真实源码，避免把教学 Makefile 当成项目实现。中文阅读说明均为仓库补充，完整原件保存在同目录树下的 `upstream/v2022.10/`。

## 2.1\_对象列表由当前解析上下文重新建立

上游相对位置：顶层 `Makefile`、`scripts/Makefile.spl`、`scripts/Makefile.build`、`common/Makefile` 与 `common/spl/Makefile`。第一步是确定实际启动哪套规则：

```make
# 仓库补充阅读说明：顶层目标以 obj=spl 发起阶段构建。
# -f 选择脚本，目录前缀与配置继续参与脚本求值。
spl/u-boot-spl: tools prepare $(if $(CONFIG_SPL_OF_CONTROL),dts/dt.dtb)
	$(Q)$(MAKE) obj=spl -f $(srctree)/scripts/Makefile.spl all
```

`scripts/Makefile.spl` 读取 `include/config/auto.conf` 和 `$(obj)/include/autoconf.mk`，并向 C 预处理参数加入 `-DCONFIG_SPL_BUILD`。该版 `scripts/Makefile.autoconf` 生成 `spl/u-boot.cfg` 时也带此定义，然后由 `define2mk` 转换流程产生阶段 `autoconf.mk`。所以 Make 判断使用的阶段值与 C 预处理看到的阶段宏都有具体来源，不能把 `CONFIG_SPL_BUILD` 简化为用户在菜单里随意切换的运行开关。

递归处理对象时，`scripts/Makefile.build` 从 `obj` 的 `spl/`、`tpl/`、`vpl/` 前缀还原源目录，并重新初始化局部列表：

```make
# 仓库补充阅读说明：以下两处来自 Makefile.build，省略其他局部变量。
# 普通文件赋值清除继承的环境列表；命令行强制赋值另受 Make 优先级规则约束。
obj-y :=
obj-m :=
lib-y :=
lib-m :=

# 配置及 Kbuild.include 已读取，再选择当前源目录规则。
kbuild-dir := $(if $(filter /%,$(src)),$(src),$(srctree)/$(src))
kbuild-file := $(if $(wildcard $(kbuild-dir)/Kbuild),$(kbuild-dir)/Kbuild,$(kbuild-dir)/Makefile)
include $(kbuild-file)
```

这解释了为什么不能把父进程中的一个 `obj-y` 当作整个构建共享的唯一列表。`common/Makefile` 的关键分支如下，省略中间无关对象但保留条件边界：

```make
# 仓库补充阅读说明：board_f.o / board_r.o 在非 SPL 块内加入。
ifndef CONFIG_SPL_BUILD
obj-y += init/
obj-y += main.o
obj-y += exports.o
# ……上游还有命令解析、自动启动等对象规则。
obj-y += board_f.o
obj-y += board_r.o
# ……其余非 SPL 对象规则。
endif # !CONFIG_SPL_BUILD
```

SPL framework 则在 `common/spl/Makefile` 中使用另一条规则：

```make
# 仓库补充阅读说明：SPL_TPL_ 取当前阶段前缀，例如 SPL_。
ifdef CONFIG_SPL_BUILD
obj-$(CONFIG_$(SPL_TPL_)FRAMEWORK) += spl.o
# ……其他加载器按配置加入。
endif
```

因此本版是由文件选择排除主 `board_r.o`，不是先把它强行编译进 SPL 再依靠虚构的 C 宏隐藏整个函数。`common/board_r.c` 和 `common/spl/spl.c` 的两份实现分别被对应链接任务收集。若板配置替换弱实现或使用特殊路径，仍须跟踪该配置的实际对象与绑定属性。

## 2.2\_架构对象选择与入口符号位置分别核对

上游相对位置：`config.mk`、`arch/arm/Makefile`、`arch/arm/lib/Makefile`。先由配置字符串形成目录：

```make
# 仓库补充阅读说明：config.mk 中的关键表达式；去掉配置字符串的引号。
ARCH := $(CONFIG_SYS_ARCH:"%"=%)
CPU := $(CONFIG_SYS_CPU:"%"=%)
CPUDIR=arch/$(ARCH)/cpu$(if $(CPU),/$(CPU),)
```

`arch/arm/Makefile` 通常给出 `head-y := arch/arm/cpu/$(CPU)/start.o`，并有特定平台条件分支。库对象由下列真实规则选择：

```make
# 仓库补充阅读说明：arch/arm/lib/Makefile，不能简化为只有 v7/v8 两类。
ifdef CONFIG_CPU_V7M
obj-y += vectors_m.o crt0.o
else ifdef CONFIG_ARM64
obj-y += crt0_64.o
else
obj-y += vectors.o crt0.o
endif
```

路径选择仍没有证明 `_start` 定义在哪里，必须查看对象对应源码。普通 ARM32 的 `arch/arm/lib/vectors.S` 将 `_start` 放进 `.vectors` 并展开 `ARM_VECTORS`；不启用特殊 boot0 hook 时，通常首个动作是分支到 `reset`。其余异常入口是否生成还受 `SYS_NO_VECTOR_TABLE` 等配置影响。AArch64 的 `arch/arm/cpu/armv8/start.S` 则直接声明 `_start`，根据内核镜像头/boot0 hook 分支选择头部，否则分支到 `reset`。

这是实现组织证据，不是架构对源文件名的要求。`ENTRY(_start)` 只告诉链接器采用该符号值作为 ELF 入口，实际复位与前级跳转仍是另一层协议。两个架构分支的 CPU 初始化不能从文件名对称性推出，相关运行关系回到 [布局与启动正文](../../../../knowledge/system_software/uboot/P01_从链接布局到启动阶段的交接.md)。

## 2.3\_配置字符串由特征选择导出\_阶段宏由当前编译选择

上游相对位置：`arch/arm/mach-qemu/Kconfig` 与 `arch/arm/Kconfig`。前者选择 `TARGET_QEMU_ARM_32BIT` 时 `select CPU_V7A`，选择 64 位目标时 `select ARM64`；后者为 `SYS_CPU` 提供如下默认值片段：

```kconfig
# 仓库补充阅读说明：仅列出当前比较涉及的默认分支。
config SYS_CPU
	default "armv7" if CPU_V7A
	default "armv7" if CPU_V7R
	default "armv7m" if CPU_V7M
	default "armv8" if ARM64
```

defconfig 可以只提供板/架构选择，派生字符串由求值产生。直接把任意字符串写成 `armv8` 并不保证所有 AArch64 配置和 ABI 条件同步成立。

另一个独立维度位于 `include/linux/kconfig.h`。其 `_CONFIG_PREFIX` 选择依次考虑宿主工具、TPL、VPL、SPL 或普通构建；`CONFIG_VAL(FOO)` 拼成相应的配置名，`CONFIG_IS_ENABLED(FOO)` 再用配置是否为 1 的展开规则求值。普通 `IS_ENABLED(CONFIG_FOO)` 只检查传入的名称。以上均发生在编译期，不是运行中的 if 语句去读取 `.config`。

这三节分别落到文件集合、入口位置和宏取值。实际调试时应逐层保留证据：一个正确的路径字符串不能证明编译宏正确，一个正确的宏也不能证明链接器最终收到了预期对象。
