# 第1章\_ARM32链接布局与启动实现

本篇是 [源码阅读索引](../navigation/P01_ARM32链接布局与启动交接阅读索引.md) 的实现层，固定上游 U-Boot v2022.10、提交 `4debc57a3da6c3f4d3f89a637e99206f4cea0a96`。对应的 [机制正文](../../../../knowledge/system_software/uboot/P01_从链接布局到启动阶段的交接.md) 已建立 S0～S5：有限环境、规划目标、切换复制、修正引用、建立完整环境、后期初始化。以下裁剪沿用这组阶段，不把 ARM32 分支当成所有架构的实现。

代码块中的中文 Doxygen 阅读说明及中文行内注释均为 **仓库补充**；上游原文、许可证与条件分支保存在 `upstream/v2022.10/`，不会把补充注释混入原始文件。裁剪用于阅读，不是可独立编译的启动代码。

## 1.1\_先确定实际使用哪份脚本

上游相对位置：`Makefile` 的 `LDSCRIPT` 选择、`cmd_cpp_lds`；`scripts/Makefile.spl` 的阶段脚本选择与同名预处理规则。主构建可受显式 `LDSCRIPT`、`CONFIG_SYS_LDSCRIPT` 和板/CPU/架构默认路径影响；SPL/TPL 则先检查阶段配置，再沿其回退路径选择。不能因为仓库里有 `arch/arm/cpu/u-boot.lds` 就断言当前板使用它。

```make
# 仓库阅读说明：以下为主 Makefile 的预处理命令裁剪。
# LDSCRIPT 是已选中的源脚本；输出 $@ 才交给 ld。
cmd_cpp_lds = $(CPP) -Wp,-MD,$(depfile) $(cpp_flags) $(LDPPFLAGS) \
             -D__ASSEMBLY__ -x assembler-with-cpp -std=c99 -P -o $@ $<
```

`-x assembler-with-cpp` 指定预处理语言方式，`-D__ASSEMBLY__` 使共享头文件避开不适用于汇编/脚本的 C 声明，`-P` 去掉行号标记。这里是生成链接脚本，不是生成处理器机器码。主 Makefile 的 `LDPPFLAGS` 还引入 U-Boot 的脚本辅助头；这些输入与配置共同决定展开结果。

此处需要核对三份证据：被选中的源脚本、构建目录里生成的脚本、实际 ld 参数。它们分别回答“从哪里来”“条件分支留下什么”“链接时还施加什么约束”。本次只验证固定版本源码，没有构建某块板，所以没有伪造一份板级生成脚本或最终 map。

## 1.2\_把输出布局分成复制内容与阶段数据

上游相对位置：`arch/arm/cpu/u-boot.lds`。下列裁剪保留 S2 复制终点、S3 记录和 S4 BSS 之间的真实先后，省略它们前面的代码、数据、列表及中间旧平台 MMU 区域。

```ld
/* 仓库补充阅读说明：
 * @brief 连接 S2 复制范围、S3 重定位记录与 S4 BSS。
 * @note 省略的普通内容位于 image_copy_end 之前。
 *       链接边界本身不执行复制、修正或清零。
 */
.image_copy_end : { *(.__image_copy_end) }
.rel_dyn_start : { *(.__rel_dyn_start) }
.rel.dyn : { *(.rel*) }
.rel_dyn_end : { *(.__rel_dyn_end) }
.end : { *(.__end) }
_image_binary_end = .;

/* 原脚本这里还有 .mmutable；以下继续引用原有覆盖布局。 */
.bss_start __rel_dyn_start (OVERLAY) : {
    KEEP(*(.__bss_start));
    __bss_base = .;
}
.bss __bss_base (OVERLAY) : {
    *(.bss*)
    . = ALIGN(4);
    __bss_limit = .;
}
.bss_end __bss_limit (OVERLAY) : {
    KEEP(*(.__bss_end));
}
```

`__image_copy_end` 是 S2 的主体复制终点，`__rel_dyn_start/end` 给 S3 指定记录范围。主脚本收集的是 `.__...` 输入节；`arch/arm/lib/sections.c` 定义对应的零长度边界对象，把 C/汇编引用连接到这些位置。这里的 `__bss_base/limit` 用于链接布局，不能擅自与所有 `__bss_start/end` 的定义方式等同。

S4 的 BSS 从 `__rel_dyn_start` 对应的链接位置开始，是生命周期优化。它不是“把重定位记录作为 BSS 一起复制”；S2 复制终点在记录之前。链接布局、源镜像当前位置与目标运行位置是三套需要关联的坐标，必须由下面的运行代码说明谁读哪一份。

主脚本的完整顺序还把 EFI 运行时内容放在宽泛 `.text*` 之前，并用配置条件组织安全状态相关区域；[原文件](../upstream/v2022.10/arch/arm/cpu/u-boot.lds) 保留所有分支。正文已经给出它们的职责对照，查看裁剪时不能假定这些配置始终关闭或全部启用。

## 1.3\_复制区间与重定位记录不是同一段数据

上游相对位置：`arch/arm/lib/relocate.S`，`relocate_code`。先从普通 ARM32 加载地址符合链接预期的路径理解：输入 `r0` 是目标起点；代码用相对偏移求当前源侧的 `__image_copy_start`，得到目标与源之间的差值 `r4`。如果差值为零，直接走完成分支；否则以两字为一组复制到 image-copy 终点。

```asm
/* 仓库补充阅读说明：
 * @brief S2 计算源位置与目标偏移，并复制主体。
 * @param r0 目标起点。
 * @note 只裁剪关键路径；链接布局须满足上游复制粒度等前提。
 */
    adr r3, relocate_base
    ldr r1, _image_copy_start_ofs
    add r1, r3
    subs r4, r0, r1       /* 目标减当前源起点。 */
    beq relocate_done
    ldr r1, _image_copy_start_ofs
    add r1, r3
    ldr r2, _image_copy_end_ofs
    add r2, r3
copy_loop:
    ldmia r1!, {r10-r11}  /* 源侧读取两个字。 */
    stmia r0!, {r10-r11}  /* 目标侧写入两个字。 */
    cmp r1, r2
    blo copy_loop
```

相对偏移文字值位于同一文件尾部，例如 `_image_copy_start_ofs` 保存 `__image_copy_start - relocate_code`，这是为了避免该早期代码自身依赖尚未修好的绝对引用。若涉及位置无关启动、特殊 CPU 或不同初始加载位置，必须继续核对相应前置分支，不能只把这一段公式移植过去。

复制之后，原函数计算源侧 `[__rel_dyn_start, __rel_dyn_end)`，每项读取两个字。以下是 S3 的核心裁剪：

```asm
/* 仓库补充阅读说明：
 * @brief S3 读取 ELF32 REL 项，处理本循环支持的 R_ARM_RELATIVE。
 * @note r2/r3 是源侧记录游标/终点，r4 沿用目标偏移。
 *       REL 的加数来自被修补位置内容，不是额外 r_addend 字段。
 */
fixloop:
    ldmia r2!, {r0-r1}    /* 取 r_offset、r_info。 */
    and r1, r1, #0xff
    cmp r1, #R_ARM_RELATIVE
    bne fixnext
    add r0, r0, r4       /* 定位目标副本中的待修补字。 */
    ldr r1, [r0]
    add r1, r1, r4       /* 更新该字内保存的地址。 */
    str r1, [r0]
fixnext:
    cmp r2, r3
    blo fixloop
```

本循环只对检查通过的类型执行修正，其余走 `fixnext`；不能描述成“所有 ELF REL/RELA 类型都按同一公式处理”。ARM64 的 `.rela.dyn` 和 RELA 加数规则必须另查相应实现。成功退出后，`crt0.S` 预先安排的返回地址让执行继续到重定位后的 `here`，然后完成 S4。

## 1.4\_谁清\_BSS\_要沿\_crt0\_的条件分支判断

上游相对位置：`arch/arm/lib/crt0.S`，`_main` 与 `CLEAR_BSS`。S0 先建立栈，调用保留和初始化 GD 的辅助函数，再把 GD 指针放入 ARM32 的 `r9`。`board_init_f()` 在此有限环境里运行；非 SPL 分支随后读取 GD 里的新地址并转入重定位。

下面直接保留 BSS 宏的两种实现，不把它改写成由 `board_init_f()` 调用的伪函数：

```asm
/* 仓库补充阅读说明：
 * @brief CLEAR_BSS 对链接区间写零，推进 S4 的数据初始化条件。
 * @note 宏调用点还受 SPL_EARLY_BSS 和 FRAMEWORK 等条件控制。
 */
.macro CLEAR_BSS
    ldr r0, =__bss_start
#ifdef CONFIG_USE_ARCH_MEMSET
    ldr r3, =__bss_end
    mov r1, #0
    subs r2, r3, r0
    bl memset
#else
    ldr r1, =__bss_end
    mov r2, #0
clbss_l:
    cmp r0, r1
    strlo r2, [r0]
    addlo r0, r0, #4
    blo clbss_l
#endif
.endm
```

有架构 memset 时传入地址、零和长度；否则按字写零直到边界。宏不会建立边界，它消费链接给出的边界。正常主路径在 `board_init_f()` 返回、重定位及后续环境处理后调用；SPL 的 `CONFIG_SPL_EARLY_BSS` 可以把调用提前到 `board_init_f()` 之前，并避免后面重复清零。清零时机变化必须有相应可用内存条件，而不是为了让早期代码随意使用任意全局变量。

SPL 还受 framework 条件影响，且可调用 `spl_relocate_stack_gd` 改变栈/GD 位置。`arch/arm/cpu/u-boot-spl.lds` 本身包含链接列表、binman 符号表与大小断言；“SPL 不走主代码重定位”与“没有任何需要布局的阶段状态”完全是两个判断。

## 1.5\_链接列表怎样从声明变成有边界的数组

上游相对位置：`include/linker_lists.h`。本协议让同一类型的条目按节名排序聚合，起点与终点也由编译器生成的特殊输入节提供；它不是运行时逐项执行 `list_add` 的链表。

```c
/**
 * ll_entry_declare() - 仓库补充阅读说明：声明一个链接生成数组条目。
 * @_type: 表项类型，同一列表须遵守一致的布局协议。
 * @_name: 条目名字。
 * @_list: 列表名字。
 *
 * 以下宏体按上游裁剪；unused 抑制未使用警告，
 * __section 决定输入节名，是否进入最终链接还依赖构建规则。
 */
#define ll_entry_declare(_type, _name, _list) \
    _type _u_boot_list_2_##_list##_2_##_name __aligned(4) \
        __attribute__((unused)) \
        __section("__u_boot_list_2_"#_list"_2_"#_name)
```

`ll_entry_start` 在 `__u_boot_list_2_<list>_1` 声明零长度起点数组，使用 `CONFIG_LINKER_LIST_ALIGN` 对齐；`ll_entry_end` 在相应 `_3` 节声明零长度终点数组。条目位于 `_2_<name>`，脚本排序后便夹在边界之间。`ll_entry_count` 用这两个边界转换得到的同类型指针之差求数量，依赖项目的类型和链接布局协议；零长度数组等也是 GNU C 扩展，不能照搬成严格 ISO C 的普通容器实现。

主脚本与通用 SPL 脚本都有如下接收规则：

```ld
/* 仓库补充阅读说明：排序形成数组布局，KEEP 防止匹配节被 GC 清理。 */
__u_boot_list : {
    KEEP(*(SORT(__u_boot_list*)));
}
```

消费发生在具体子系统路径中。例如命令系统查找描述符并调用回调，设备模型按绑定和探测过程使用驱动描述符；宏声明和 ld 排序不会启动硬件。若需要研究某个消费者的函数体，应从 [总阅读索引](../navigation/P01_ARM32链接布局与启动交接阅读索引.md#1.2_沿状态交接定位源码) 进入相应源码，不把本页的列表布局解释扩张成所有消费者的调用链。
