# 第3章\_配置求值与构建产物实现

**讲解层次：实现层，U-Boot v2022.10。** 固定上游提交为 `4debc57a3da6c3f4d3f89a637e99206f4cea0a96`，原件摘要、阅读顺序与本页回链在 [模块导读](../navigation/P03_配置工具与镜像产物导读.md)。中文注释是仓库补充的阅读说明，下面只裁剪承担本次结论的规则，不改变上游原件。

## 3.1\_配置目标先构建宿主工具\_再求值板模板

上游相对位置：`Makefile`、`scripts/Kbuild.include`、`scripts/Makefile.build`、`scripts/kconfig/Makefile`、`scripts/Makefile.host`。正文的 B1 从目标名字进入规则，不从 `.config` 文件反猜它如何产生。

```make
# 仓库补充阅读说明：顶层 Makefile；$@ 保留本次请求的配置目标。
%config: scripts_basic outputmakefile FORCE
	$(Q)$(MAKE) $(build)=scripts/kconfig $@
```

`build` 在 `scripts/Kbuild.include` 中展开为 `-f $(srctree)/scripts/Makefile.build obj`，因此 `$(build)=scripts/kconfig` 形成脚本选择与 `obj=scripts/kconfig` 赋值。`scripts/Makefile.build` 包含该目录 Kbuild/Makefile 的过程已经在 [对象上下文实现](P02_构建上下文与入口选择实现.md#2.1_对象列表由当前解析上下文重新建立) 展开，这里沿同一入口继续读取配置目标。

```make
# 仓库补充阅读说明：scripts/kconfig/Makefile 中分散的相关规则。
# 本版借用 Linux 规则形式，以 .. 将 arch/../configs 解析为 configs。
SRCARCH := ..

%_defconfig: $(obj)/conf
	$(Q)$< $(silent) --defconfig=arch/$(SRCARCH)/configs/$@ $(Kconfig)

conf-objs := conf.o zconf.tab.o
hostprogs-y := conf
```

例如目标为 `qemu_arm64_defconfig` 时，模板路径对应 `configs/qemu_arm64_defconfig`。`Kconfig` 变量默认指向顶层 `Kconfig`，显式 `KBUILD_KCONFIG` 可替换入口。这里的 `%` 是 Make 模式规则的 stem 匹配，不是 Shell 在目录里展开的 `*`。

`$(obj)/conf` 是前置目标，不是仅凭名字就已经可执行。`hostprogs-y` 和 `conf-objs` 交给宿主构建规则处理，`zconf.tab.o` 还依赖生成的词法/语法分析材料。最终链接规则位于 `scripts/Makefile.host`：

```make
# 仓库补充阅读说明：多对象宿主程序的链接命令，不带 -c。
quiet_cmd_host-cmulti = HOSTLD  $@
      cmd_host-cmulti = $(HOSTCC) $(KBUILD_HOSTLDFLAGS) -o $@ \
			  $(addprefix $(obj)/,$($(@F)-objs)) \
			  $(KBUILD_HOSTLDLIBS) $(HOSTLDLIBS_$(@F))
```

`$(@F)` 取得目标的文件名部分 `conf`，于是 `$($(@F)-objs)` 找到 `conf-objs`；`addprefix` 将对象名补成当前输出目录路径。这里 HOSTCC 把多个对象链接为宿主程序。相邻的单对象编译规则才带 `-c`，不能把两种操作混写成 `gcc -c conf.c -o conf`。

配置工具读取模板和规则后生成 `.config`；进一步同步配置和预处理板头，才形成 Make/C 使用的配置输入。本版板头与 Kconfig 共存的背景见本地 `doc/README.kconfig`；其中有历史名称与拼写残留，具体生成命令以 `scripts/Makefile.autoconf` 为准。阶段 `CONFIG_SPL_BUILD` 的生成来源继续见上面的对象上下文实现，不在这里重复展开。

## 3.2\_从库目录与启动对象走到主\_ELF

上游相对位置：顶层 `Makefile` 的 U-Boot objects 区域与 `u-boot` 目标。正文 B2 的输入集合是由目录规则逐层得到的：

```make
# 仓库补充阅读说明：省略其他库和配置分支，保留类型转换。
libs-y += boot/
libs-y += cmd/
libs-y += common/
libs-y += $(if $(BOARDDIR),board/$(BOARDDIR)/)

libs-y := $(sort $(libs-y))
# ……上游还有相关配置处理。
libs-y := $(patsubst %/, %/built-in.o, $(libs-y))

u-boot-init := $(head-y)
u-boot-main := $(libs-y)

u-boot: $(u-boot-init) $(u-boot-main) $(u-boot-keep-syms-lto) u-boot.lds FORCE
	+$(call if_changed,u-boot__)
```

前半段收集的是目录；转换后收集对应 `built-in.o`。把它们当作 `.c` 文件列表会丢掉每个目录内部的配置选择。`u-boot-keep-syms-lto` 对应链接时优化相关的保留符号条件，不能在复制规则时把这个依赖无条件删掉并声称完整还原。

`u-boot.lds` 先经过预处理，实际链接命令由 `cmd_u-boot__` 组织；脚本和链接布局的具体解释已在 [ARM32 布局实现](P01_ARM32链接布局与启动实现.md)。`if_changed` 利用依赖与保存的命令判断是否执行，即使规则有 `FORCE`，也不意味着每次都无条件重链接。`.cmd` 是构建记录，不是用户配置输入。

该目标在 `CONFIG_KALLSYMS` 等条件下还有后续处理。本节只解释主 ELF 的入口依赖关系；不能把裁剪后的一条 recipe 当作所有配置下完整的链接流水。

## 3.3\_INPUTS\_与\_binman\_把单文件构建连接到镜像组合

上游相对位置：顶层 `Makefile` 的 INPUTS、`inputs`、`all` 和 `.binman_stamp`。正文 B3 中要生成哪些文件，由当前配置继续选择：

```make
# 仓库补充阅读说明：关键汇总片段，其他平台输入省略。
INPUTS-y += u-boot.srec u-boot.bin u-boot.sym System.map binary_size_check
INPUTS-$(CONFIG_SPL) += spl/u-boot-spl.bin
INPUTS-$(CONFIG_TPL) += tpl/u-boot-tpl.bin
INPUTS-$(CONFIG_VPL) += vpl/u-boot-vpl.bin

PHONY += inputs
inputs: $(INPUTS-y)

all: .binman_stamp inputs
ifeq ($(CONFIG_BINMAN),y)
	$(call if_changed,binman)
endif

.binman_stamp: FORCE
	@touch $@
```

`INPUTS-y` 不是所有 U-Boot 版本通用的变量名；旧分支的 `ALL-y` 需要在旧树中核对。各个 `INPUTS-$(CONFIG_...)` 是 Make 变量名展开，配置为 y 的项合并到 `INPUTS-y`。`PHONY` 汇总稍后进入 `.PHONY`，不要把项目的汇总变量与 Make 内建特殊目标混为一谈。

`.binman_stamp` 用于使打包检查重新进行。依赖图保证 `inputs` 的前置输入满足后才进入相应 recipe，但多个独立依赖可以并行完成，不能从 Makefile 文本的上下行推断严格执行时间线。

## 3.4\_设备树追加只属于具体的产物分支

上游相对位置：顶层 `Makefile` 的 `u-boot-nodtb.bin`、`u-boot-dtb.bin` 和 `u-boot.bin` 规则。先看 ELF 到基础二进制的规则：

```make
# 仓库补充阅读说明：其他 objcopy 参数由架构和配置提供。
u-boot-nodtb.bin: u-boot FORCE
	$(call if_changed,objcopy_uboot)

# 仓库补充阅读说明：以下来自 DTB 分支中间，保留上游 else ifeq 条件。
# 前面是 CONFIG_MULTI_DTB_FIT 分支，不能独立复制执行本片段。
else ifeq ($(CONFIG_OF_SEPARATE).$(CONFIG_OF_OMIT_DTB),y.)
u-boot-dtb.bin: u-boot-nodtb.bin dts/dt.dtb FORCE
	$(call if_changed,cat)

ifneq ($(CONFIG_MPC85XX_HAVE_RESET_VECTOR)$(CONFIG_OF_SEPARATE),yy)
u-boot.bin: u-boot-dtb.bin FORCE
	$(call if_changed,copy)
endif
```

条件中的 `y.` 表示 OF_SEPARATE 为 y、OF_OMIT_DTB 为空；它不是省略号。`cat` 的消费者是组合文件，`copy` 将选择结果放到常规名字。之前的多 DTB/FIT 分支和之后的无追加分支有各自规则，因此文件名不能单独证明是否包含设备树。

`objcopy_uboot` 在 `CONFIG_STATIC_RELA` 条件下还会调用宿主 `tools/relocate-rela`，不能说每个平台都只执行一条纯 objcopy。这个构建期处理与 CPU 执行中的运行时重定位是不同动作，不能因为都有 relocation 字样就合并；本节只定位它在产物依赖图中的位置。

读完四节后，应能从一个请求目标追到配置工具、实际链接输入和后续消费者。若要证明某块板的最终镜像，仍需该板配置和真实命令日志；本模块没有用局部规则阅读代替整项目构建验收。
