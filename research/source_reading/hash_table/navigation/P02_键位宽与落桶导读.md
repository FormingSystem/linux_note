# 第2章\_键位宽与落桶导读

[总索引](P01_Linux_6.12_哈希计算源码阅读索引.md)给出固定版本。这里从调用点追到桶位置，明确计算规则由哪里决定；函数体只在实现目录展开。

## 2.1\_从调用表达式追到计算路径

应用对象保存完整键和成员节点；桶数组保存各桶头。hash_add 从传入键的表达式类型和数组大小计算桶号，再调用 hlist_add_head。HASH_BITS 是取得数组桶数对应位数的宏，BITS_PER_LONG 则表示内核 unsigned long 的位数。hash_for_each_possible 重新做同样的计算，只遍历候选桶；是否真正匹配仍由调用者比较完整键。

```mermaid
flowchart LR
    caller["调用方：键表达式与桶数组"] -->|"sizeof 键、HASH_BITS 数组"| select["hash_min 选择入口"]
    select -->|"不超过四字节"| small["hash_32"]
    select -->|"超过四字节"| word["hash_long"]
    word -->|"BITS_PER_LONG 决定"| width["hash_32 或 hash_64"]
    small -->|"桶号"| bucket["对应 hlist_head"]
    width -->|"桶号"| bucket
    bucket -->|"候选遍历"| compare["调用方比较完整键"]
```

hash.h 的 GOLDEN_RATIO 常数、通用乘法和取高位语句见[32 位实现](../source_explanations/include/linux/hash.h.md#1.1_32位乘法与取高位)。CONFIG_HAVE_ARCH_HASH 允许体系结构提供内部覆盖；当前 ARM 配置未启用它，不意味着所有平台都执行同一段生成指令。

## 2.2\_稳定的类型是表协议的一部分

hash_min 选择的是 hash_32 或 hash_long，而不是直接在 hash_32 与 hash_64 之间按输入大小选择。32 位 unsigned long 的转换可能截去 u64 高半部。显式 hash_64 的通用路径则先混合高半部再折叠，与直接截断不同。

64 位路径和指针入口的具体语句见[64 位与指针实现](../source_explanations/include/linux/hash.h.md#1.2_64位输入与指针入口)。hash32_ptr 只折叠，不接受桶位数。hash_ptr 散列地址身份，不比较对象内容。把两者换用会改变表的选桶协议，不能只看返回类型都是 u32。

DEFINE_HASHTABLE 带静态初始化式；DECLARE_HASHTABLE 没有显式初始化式。HASH_SIZE 依赖数组表达式；传成指针再调用不是保留原容量的方法。改变 bits、键类型、哈希函数或种子时，应让所有操作一起采用新规则，必要时重新登记全部成员。

## 2.3\_索引之外的职责

| 状态 | 保存者与修改责任 | 哈希计算没有提供的保证 |
| --- | --- | --- |
| 完整键、值、成员节点 | 业务对象；发布前由创建者填写 | 键唯一、字段一致性、引用保活 |
| 桶数与桶头数组 | 容器拥有者；初始化或重建时维护 | 自动增长、内存限额、低碰撞 |
| 桶内 next/pprev | 按 hlist 协议修改 | 自动加锁、RCU 发布或延迟释放 |
| 查找所用键类型和转换 | 调用者封装与参数类型 | 不同表达式必然得到同一桶 |

该计算路径自身没有异步通知或状态汇聚。添加共享访问后，锁与对象寿命应独立论证；不能把单纯整数乘法当成一次发布操作。

## 2.4\_沿实际函数核对PID示例

固定 kernel/pid.c 的 find_pid_ns 通过 idr_find 访问 ns->idr；include/linux/pid_namespace.h 保存该索引，include/linux/pid.h 的 upid 只保存 nr 与 ns，没有旧稿的 pid_chain。部分源码历史注释仍可能使用 hash table 字样，实际语句和字段比注释里的旧称更能确定当前实现。

这纠正的是旧教材的证据身份，并不否定“编号必须结合命名空间理解”这一知识点。当前版本的 PID 查找不能继续用伪造的 pid_hashfn 展开，哈希课程也不在这里改写完整 PID 生命周期。返回[总索引](P01_Linux_6.12_哈希计算源码阅读索引.md#1.2_从问题选择入口)。
