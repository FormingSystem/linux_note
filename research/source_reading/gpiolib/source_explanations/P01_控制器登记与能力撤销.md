# 第1章\_控制器登记与能力撤销

一个 Consumer 持有的描述符为什么能比 Provider 能力活得更久？本页用固定 Linux 6.12.20 的实际字段和撤销顺序回答。先读 [生命周期导读](../navigation/P02_线路对象怎样完成请求与退出.md#2.1_先找到哪些状态会跨过函数返回)，版本与配置统一见 [阅读索引](../navigation/P01_Linux_6.12_GPIO源码阅读索引.md#1.1_版本身份与阅读路线)。以下中文 Doxygen 和标注是仓库补充，裁剪代码保留原有语句次序，不作为可独立编译的替代实现。

## 1.1\_框架对象怎样把描述符和硬件能力分开

S1 登记以后，Consumer 需要的线路对象由公共层保存，Provider 回调则仍属于具体驱动。`drivers/gpio/gpiolib.h` 用两个指向关系表达这种分工：`gdev->descs` 保存数组，数组中的每个 desc 用 `gdev` 回指登记对象；可撤销的 `chip` 再指向硬件能力。

```c
/**
 * @brief 裁剪的登记对象和每线对象；两者不包含通用硬件寄存器布局。
 * @note 仓库补充的中文阅读说明；下方为上游源码，裁剪处另有标注。
 */
struct gpio_device {
	struct device		dev;
	struct cdev		chrdev;
	int			id;
	/* 裁剪：遗留sysfs字段。 */
	struct module		*owner;
	struct gpio_chip __rcu	*chip;
	struct gpio_desc	*descs;
	struct srcu_struct	desc_srcu;
	unsigned int		base;
	u16			ngpio;
	bool			can_sleep;
	const char		*label;
	void			*data;
	struct list_head        list;
	struct blocking_notifier_head line_state_notifier;
	struct blocking_notifier_head device_notifier;
	struct srcu_struct	srcu;
	/* 裁剪：CONFIG_PINCTRL下的pin_ranges。 */
};

struct gpio_desc {
	struct gpio_device	*gdev;
	unsigned long		flags;
	/* 裁剪：此处的flag位号宏，见下表。 */
	struct gpio_desc_label __rcu *label;
	const char		*name;
	/* 裁剪：CONFIG_OF_DYNAMIC下的hog节点。 */
};
```

`chrdev` 是实际字段名，`dev` 的引用生命周期支撑登记对象存续；`id` 对应 gpiochip 身份，`base` 属于被弃用的全局 GPIO 整数空间。每线 `name` 是线路名，`label` 是当前请求者的诊断标签，不能把二者当作认证凭据。主要 flags 的精确位号如下，位号只对本版本有效。

| 宏 | 位号 | 状态用途 |
| --- | --- | --- |
| `FLAG_REQUESTED` / `FLAG_IS_OUT` | 0 / 1 | 占用 / 框架输出用途 |
| `FLAG_ACTIVE_LOW` | 6 | 逻辑值反相 |
| `FLAG_OPEN_DRAIN` / `FLAG_OPEN_SOURCE` | 7 / 8 | 电气驱动语义 |
| `FLAG_USED_AS_IRQ` / `FLAG_IRQ_IS_ENABLED` | 9 / 10 | IRQ使用 / IRQ使能 |
| `FLAG_IS_HOGGED` / `FLAG_TRANSITORY` | 11 / 12 | hog请求 / 睡眠或复位时可能丢值 |
| `FLAG_PULL_UP` / `FLAG_PULL_DOWN` / `FLAG_BIAS_DISABLE` | 13 / 14 / 15 | 偏置配置语义 |
| `FLAG_EDGE_RISING` / `FLAG_EDGE_FALLING` | 16 / 17 | 字符设备边沿配置 |
| `FLAG_EVENT_CLOCK_REALTIME` / `FLAG_EVENT_CLOCK_HTE` | 18 / 19 | 字符设备事件时间戳配置 |

访问 `chip` 还需要短期保护，否则读取指针以后到调用之前可能与撤销交错。`gpio_chip_guard` 把进入 SRCU、读取指针和离开作用域时解锁组合起来；这是作用域资源管理宏，不能按普通函数调用返回后立即解锁理解。

```c
/**
 * @brief 作用域guard持有gdev的SRCU读锁，退出作用域才释放。
 * @note 仓库补充的中文阅读说明；下方为上游源码，裁剪处另有标注。
 */
struct gpio_chip_guard {
	struct gpio_device *gdev;
	struct gpio_chip *gc;
	int idx;
};

DEFINE_CLASS(gpio_chip_guard,
	     struct gpio_chip_guard,
	     srcu_read_unlock(&_T.gdev->srcu, _T.idx),
	     ({
		struct gpio_chip_guard _guard;

		_guard.gdev = desc->gdev;
		_guard.idx = srcu_read_lock(&_guard.gdev->srcu);
		_guard.gc = srcu_dereference(_guard.gdev->chip,
					     &_guard.gdev->srcu);

		_guard;
	     }),
	     struct gpio_desc *desc)
```

`CLASS(gpio_chip_guard, guard)(desc)` 建立这个局部 guard，调用者必须检查 `guard.gc` 是否为 NULL。`desc_srcu` 则服务于向查询者暴露的一致描述符信息，例如标签读取；它不是此处能力指针保护的同义字段。全局 `gpio_devices_srcu` 又属于控制器列表查找，这三者不能因都带 SRCU 就合并解释。原定义见固定版本 [gpiolib.h](https://github.com/nxp-imx/linux-imx/blob/dfaf2136deb2af2e60b994421281ba42f1c087e0/drivers/gpio/gpiolib.h#L57)。

## 1.2\_登记怎样建立数组身份并处理阶段失败

上游相对位置：`drivers/gpio/gpiolib.c`，`gpiochip_add_data_with_key()`。以下按源顺序裁剪，聚焦对象建立、列表入口和错误退出；省略的固件、IRQ、有效位图等仍在文字中列出，不能据裁剪代码另造一个可运行注册函数。

```c
/**
 * @brief S1按阶段建立登记；裁剪片段保留入口和两种最终释放路径。
 * @note 仓库补充的中文阅读说明；下方为上游源码，裁剪处另有标注。
 */
int gpiochip_add_data_with_key(struct gpio_chip *gc, void *data,
			       struct lock_class_key *lock_key,
			       struct lock_class_key *request_key)
{
	struct gpio_device *gdev;
	unsigned int desc_index;
	int base = 0;
	int ret = 0;

	gdev = kzalloc(sizeof(*gdev), GFP_KERNEL);
	if (!gdev)
		return -ENOMEM;
	/* 裁剪：device的type/bus/parent初始化。 */
	rcu_assign_pointer(gdev->chip, gc);
	gc->gpiodev = gdev;
	gpiochip_set_data(gc, data);
	/* 裁剪：fwnode、id、名字、owner、ngpio及其失败出口。 */
	gdev->descs = kcalloc(gc->ngpio, sizeof(*gdev->descs), GFP_KERNEL);
	if (!gdev->descs) {
		ret = -ENOMEM;
		goto err_free_dev_name;
	}
	/* 裁剪：label分配及失败处理。 */
	gdev->ngpio = gc->ngpio;
	gdev->can_sleep = gc->can_sleep;
	scoped_guard(mutex, &gpio_devices_lock) {
		/* 裁剪：动态base分配、静态base警告及范围检查。 */
		gdev->base = base;
		ret = gpiodev_add_to_list_unlocked(gdev);
		if (ret) {
			chip_err(gc, "GPIO integer space overlap, cannot add chip\n");
			goto err_free_label;
		}
	}
	for (desc_index = 0; desc_index < gc->ngpio; desc_index++)
		gdev->descs[desc_index].gdev = gdev;
	/* 裁剪：notifier、两组SRCU、名字、有效位图、初始方向、固件/IRQ等初始化。 */
	if (gpiolib_initialized) {
		ret = gpiochip_setup_dev(gdev);
		if (ret)
			goto err_remove_irqchip;
	}
	return 0;
	/* 裁剪：已完成的IRQ、hogs、固件、位图、SRCU等逐阶段清理。 */
err_remove_from_list:
	scoped_guard(mutex, &gpio_devices_lock)
		list_del_rcu(&gdev->list);
	synchronize_srcu(&gpio_devices_srcu);
	if (gdev->dev.release) {
		gpio_device_put(gdev);
		goto err_print_message;
	}
err_free_label:
	kfree_const(gdev->label);
err_free_descs:
	kfree(gdev->descs);
err_free_dev_name:
	kfree(dev_name(&gdev->dev));
err_free_ida:
	ida_free(&gpio_ida, gdev->id);
err_free_gdev:
	kfree(gdev);
err_print_message:
	/* 裁剪：错误诊断。 */
	return ret;
}
```

这条路径中，动态 GPIO base 与 gpiochip id 分别分配；前者服务旧整数接口，后者命名登记设备。Provider 新驱动用负 base 请求动态分配，固定非负 base 会得到弃用警告，稳定连接不应靠它命名。

列表登记以后还要初始化 notifier、两组 SRCU、线路名字和有效位图，读取或推导初始方向，并接入 OF、pin ranges、ACPI、hogs 与可选 IRQ。字符设备建立受 `gpiolib_initialized` 控制，早期注册会延期到核心初始化后。因此注册没有一个能概括全部可见性的简单“最后一步发布”故事；读者必须按所用入口的检查条件判断子功能是否可用。

失败出口也有两类最终所有者：若 `gpiochip_setup_dev()` 已安装 `dev.release`，走 `gpio_device_put()` 交给设备释放协议；否则函数自行释放名字、描述符、ID 等已建立的资源。不能在前一种路径外面再手工 free 同一对象。完整函数与省略分支见 [固定源码注册入口](https://github.com/nxp-imx/linux-imx/blob/dfaf2136deb2af2e60b994421281ba42f1c087e0/drivers/gpio/gpiolib.c#L920)。

## 1.3\_撤销为何分两次等待和最后一次放引用

上游相对位置：`drivers/gpio/gpiolib.c`，`gpiochip_remove()`。正常使用契约要求没有仍被请求的 GPIO 才移除 Provider。即便如此，框架仍需要协调查找、在途访问和可残留的用户对象引用，而不能直接释放。

```c
/**
 * @brief 先撤销查找和能力、等待各自读者，再拆关联并放下登记方引用。
 * @note 仓库补充的中文阅读说明；下方为上游源码，裁剪处另有标注。
 */
void gpiochip_remove(struct gpio_chip *gc)
{
	struct gpio_device *gdev = gc->gpiodev;

	/* FIXME: should the legacy sysfs handling be moved to gpio_device? */
	gpiochip_sysfs_unregister(gdev);
	gpiochip_free_hogs(gc);
	gpiochip_free_remaining_irqs(gc);

	scoped_guard(mutex, &gpio_devices_lock)
		list_del_rcu(&gdev->list);
	synchronize_srcu(&gpio_devices_srcu);

	/* Numb the device, cancelling all outstanding operations */
	rcu_assign_pointer(gdev->chip, NULL);
	synchronize_srcu(&gdev->srcu);
	gpiochip_irqchip_remove(gc);
	acpi_gpiochip_remove(gc);
	of_gpiochip_remove(gc);
	gpiochip_remove_pin_ranges(gc);
	gpiochip_free_valid_mask(gc);
	/*
	 * We accept no more calls into the driver from this point, so
	 * NULL the driver data pointer.
	 */
	gpiochip_set_data(gc, NULL);

	/*
	 * The gpiochip side puts its use of the device to rest here:
	 * if there are no userspace clients, the chardev and device will
	 * be removed, else it will be dangling until the last user is
	 * gone.
	 */
	gcdev_unregister(gdev);
	gpio_device_put(gdev);
}
```

第一次 `synchronize_srcu()` 对应从全局列表删除，等待已经进入查找侧的读者。第二次对应 `gdev->chip = NULL`，等待已经进入这个控制器能力访问侧的读者。此后才清 driver data，意味着受该协议保护的新调用不会再进入旧 Provider 回调。

源码注释中的 cancelling 不能翻译为“强行中止一切硬件操作”：代码实际做的是清能力指针和等待受保护访问结束；Provider 自己的工作项、供电和外设事务仍须遵守各自退出协议。最后 `gpio_device_put()` 只放下登记方的引用，其他引用尚在时对象可以继续存在，但它的 `chip` 已不可用。

用这个顺序检查一次退出：先问是否还有合法 Consumer，再问新查找入口是否已撤销、旧回调是否已排空，最后才问对象引用何时归零。回到 [生命周期导读的退出阶段](../navigation/P02_线路对象怎样完成请求与退出.md#2.5_控制器退出时还有哪两类读者)，或继续 [描述符请求与释放](P02_描述符请求与托管释放.md#2.1_查找为何必须交接到请求后才能返回)。
