# 第1章\_linux系统基础知识

学 Linux 内核时，最容易把四种东西混在一起：正在运行的操作系统、保存实现的源码树、选择功能的构建配置，以及适配某块开发板的支持代码。于是会出现这样的疑问：“源码里明明有驱动，为什么系统没有设备？”要回答它，先建立这些对象之间的关系，比立即背目录或编译一份大镜像更有效。

本组是围绕原书主题组织的读书笔记。第一章建立系统和源码坐标，第二章按访问需求选择数据结构，第三章解释这些机制怎样在启动中逐步可用，第四章再细化内核接手前的 U-Boot 交接。每篇将问题连到仓库已有权威专题；书目信息与材料性质见 [本组入口](README.md)。

## 1.1\_从一次读取看见内核的职责

假设 C 程序打开文件、读取几十个字节，再关闭它。程序知道路径和接收缓冲区，却没有给存储控制器编程，也没有独占整台机器。库帮助程序组织接口，内核管理权限、文件对象、缓存和执行资源；真正需要访问设备时，再由相应驱动按设备协议完成。若内容已经在缓存里，这次读取不必重新访问物理介质。

这让我们先认识 **Linux 内核**：它是系统中负责受控访问资源和协调执行的重要部分。完整可用的系统还包括初始化程序、库、命令、服务和文件内容；仅有一个内核镜像并不等于已经有可以登录的系统。

```mermaid
flowchart LR
    A[用户程序与库] -->|请求打开 读取 关闭| K[内核管理文件 内存与执行]
    K -->|权限检查与操作结果| A
    K -->|需要设备I/O时提交请求| D[设备驱动与硬件协议]
    D -->|完成结果与数据| K
    C[构建配置与平台描述] -->|选择实现并描述连接| K
```

图的上半部分是运行时请求，配置和平台描述则是影响运行内容的输入；它们不是每次读取时才临时编译的代码。详细推导和可运行的完整 C 小程序在 [从读取文件认识内核](../../../knowledge/linux/architecture/kernel_composition/linux内核概貌.md#1.1_先让程序读到几个字)。先在那里观察返回字节数与错误，再回到本章定位每层职责，会比只记“内核管理硬件”具体得多。

## 1.2\_功能放在哪里决定了通信与故障边界

文件系统需要驱动提供数据，两者必须通信。若它们都在同一内核保护域，可以通过函数与共享内核对象协作，这体现了宏内核的组织方式。若将某些服务放到受到独立内存保护的进程，就需要受控通信来传递请求、权限和结果，这是理解微内核方向的起点。

区别在于职责与保护边界，不能按镜像文件大小判断。Linux 可以模块化地编译、装入驱动，但装入内核的模块通常仍在内核保护域执行；分成多个源文件或 `.ko` 文件，并不会自动获得服务进程之间的隔离。

一次系统调用也不必然换成另一条线程执行。当前线程可以进入内核态完成请求；确需等待设备时，才可能阻塞并让调度器选择其他线程。把权限切换和线程切换分开，后面才有条件比较通信成本、等待和故障传播。完整的同场景比较见 [宏内核和微内核](../../../knowledge/foundations/operating_systems/concepts/宏内核和微内核.md)。

## 1.3\_沿职责找到源码\_再确认它是否参与构建

知道内核要完成什么以后，再去看源码树。文件操作从 `fs/` 定位，内存管理关注 `mm/`，通用执行机制常在 `kernel/`，具体设备看 `drivers/`，架构差异在 `arch/`。这些是源码根目录下的职责入口，不是运行系统中同名的绝对路径，也不是一次请求必须依次经过的调用顺序。

例如“文件读到了错误内容”可能涉及文件位置、缓存、驱动或应用缓冲区，不能因为设备属于硬件就只查 `drivers/`。先沿请求的输入、状态与输出划分问题，再从声明、调用者和构建配置继续收窄。已有 [源码树阅读单元](../../../knowledge/linux/architecture/source_tree/Linux_kernel_目录结构说明.md) 提供目录表和只读 Git 命令，本章只固定辨别证据的次序。

| 手里拿到的东西 | 能回答的问题 | 还缺哪一步证据 |
| --- | --- | --- |
| 一个源码文件或函数 | 这个版本提供了怎样的候选实现 | 相关配置和 Makefile 是否把它编入目标 |
| 一份 `.config` | 这次构建选择了哪些功能 | 配置是否对应当前源码、输出目录和实际构建产物 |
| 内核或模块文件 | 已经产生了可交付的字节 | 启动或加载的是否正是这份文件，入口参数是否匹配 |
| 运行日志与设备状态 | 已执行路径留下了什么结果 | 未覆盖分支、未启用检查及其他设备状态仍须单独判断 |

因此，“驱动在源码里”到“设备可用”之间至少还要经过构建选择、加载、设备描述和实际匹配执行。后续学习驱动模型时再展开这些环节；现在先不要把其中任何一层当作全部成立的证明。

## 1.4\_把旧编译记录和固定源码基线分开

本组早期笔记使用过 NXP `imx_5.4.70_2.3.0` 和 Ubuntu 22.04 的环境记录，原 [i.MX8 ARM64内核编译说明](../../../platforms/arm/nxp/imx8/P01_imx_v8配置与ARM64内核构建.md) 保留板级操作线索。它说明一次历史环境，不能作为所有后续章节共用的版本身份，也不能仅凭文件名中的 5.4 或 6.1 判断实际检出的提交。

本轮涉及固定实现的说明采用 [Linux 源码基线](../../../research/source_reading/linux/SOURCE_BASELINE.md)：NXP 官方 `linux-imx`，发布标签 `lf-6.12.20-2.0.0`，提交 `dfaf2136deb2af2e60b994421281ba42f1c087e0`。通用机制与板级实践仍要分别声明配置和平台；一个 ARM32 的运行结果不能证明 ARM64 的入口协议已经验证。

学习时可以先在宿主环境完成概念和 C 模型，再对照固定源码，最后进入真实板级构建与部署。模拟器是否有用取决于验证目标：它可以帮助观察所支持机器的执行过程，却不能替代实板焊接、时钟和外设集成证据。不要把“某次问答建议不用模拟器”变成所有实验的规则。

做两个简短判断。**修改源文件后，当前运行系统会立即改变吗？** 不会，还需要重新构建并让相应产物进入运行系统。**查到某个内核字段，就能把它用于不同版本的模块吗？** 不能，须核对该版本声明、接口合同和构建上下文。带着这两项边界进入 [第二章](P02_Linux内核中常用的数据结构和算法.md)，才能把数据结构看成服务于具体查询和生命周期的工具。
