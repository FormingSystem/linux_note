# 内核源码证据参考

## 1. 建立基线

按照当前仓库说明取得源码树位置，并核对：

```text
顶层 Makefile 版本
目标架构
相关 .config 配置项
通用实现目录
体系结构特有实现目录
厂商/BSP 边界
```

记录源码属于上游、稳定版、厂商版本还是本地补丁版本。不得仅因为某个源码分支存在，就推断实际运行配置。

## 2. 按状态转换搜索

不得只搜索 API 定义。对于每个 S 阶段，追踪：

1. 字段声明；
2. 初始化；
3. 每个写入者；
4. 每个会改变控制流的读取者；
5. 调用者和被调用者链；
6. 锁、IRQ、抢占、任务、CPU 或进程上下文要求；
7. 唤醒、回调、IPI、轮询或分层传播；
8. 清理和错误路径。

优先使用 `rg`。先搜索精确字段名和赋值位置，再阅读足够的上下文以确定分支和所有权。

## 3. 建立证据矩阵

每项重要结论都记录：

| 结论 | 版本/配置 | 路径 | 函数/字段 | 写入者 | 读取者 | 顺序/锁 | 含义 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 出现局部债务 | 精确配置项 | 上游相对路径 | 精确字段 | 执行上下文 | 后续路径 | 必要约束 | 该状态位证明什么 |
| 上报局部债务 | 精确配置项 | 路径 | 函数链 | 上报者 | 汇聚者 | 锁/屏障 | 通信方向 |
| 达成全局完成 | 精确配置项 | 路径 | 序号/等待字段 | 协调者 | 等待者 | 唤醒条件 | 为什么可以安全继续 |

不得让表格取代因果解释或端到端时序。

对承担关键推导的结论建立四层证据链：

1. **抽象不变量：** 不依赖具体版本仍然成立的因果或协议保证；
2. **源码落点：** 当前版本中承载该保证的字段、写路径、读路径和完成条件；
3. **边界标签：** 明确 API 契约、通用实现、配置分支、体系结构或厂商边界；
4. **可观察证据：** 能够支持或反驳该结论的 trace、日志、实验、指标或故障现象。

正文可以用短标签或证据表表达这四层，但不能把“找到源码字段”直接当成抽象结论已经得到证明。

## 4. 建立模块概念导读与唯一实现讲解

同一源码专题同时具有阅读导航和源码讲解时，采用以下职责目录：

```text
research/source_reading/<topic>/
├── navigation/             # 总索引，以及子功能/模块的源码概念导读
└── source_explanations/    # 具体宏、函数和字段的唯一源码实现讲解
```

`navigation/` 不只放一张链接清单：它包含一个总阅读索引，以及按子功能或模块组织的源码概念导读。模块导读借源码回答“这一模块解决什么问题、有哪些参与者和状态、调用链怎样闭环、应按什么顺序阅读”，可以使用应用示例、伪代码、表格和 Mermaid，但不逐段展开上游宏体或函数体。`source_explanations/` 面向具体实现，保存精确版本的宏、函数、字段和配置分支，并用中文 Doxygen 注释、中文行内注释和实现原理解释逐段还原代码。前者是借源码理解模块，后者是逐函数理解实现。

同一版本、同一源码实现只在 `source_explanations/` 的一个权威标题下展开。总索引链接模块导读，模块导读遇到具体实现时精确链接该标题，知识正文同时把读者引向总索引、相关模块导读和本场景直接遇到的实现标题。

### 4.1\_全量信息同步矩阵

“全量信息同步”同步的是发现入口、事实边界和实现所有权，不是把不同职责文档全文同步。逐项检查：

| 层次 | 必须核对的闭环 |
| --- | --- |
| 稳定正文 | 专题大纲、父级大纲、上一篇/下一篇、相邻机制边界 |
| 源码导航 | 总阅读索引枚举全部模块导读；模块导读精确链接实现标题 |
| 实现讲解 | 关联入口回链总索引、所属模块导读、知识场景和交叉专题 |
| 证据身份 | `SOURCE_BASELINE.md` 登记版本、配置边界、保存文件和阅读入口 |
| 全仓发现 | Atlas 地图、路线、内容索引和仓库首页能够找到稳定正文与总阅读索引 |
| 编排调用方 | 只更新真实存在的出版清单、Obsidian、Canvas/Base 和其他入链；不存在时不造占位文件 |

每层先判断读者要完成的任务，再决定链接到文件入口还是具体标题。源码基线、Atlas 和仓库首页属于导航入口时也优先使用完整标题锚点，避免读者落到文件顶部后再次搜索。

知识章节包含演示代码时，先在代码附近建立接口清单：

| 接口或检查点 | 本场景作用 | 调用上下文 | 省略或误用后果 | 版本化源码讲解 |
| --- | --- | --- | --- | --- |
| 公共 API | 完成哪一步状态转换 | 进程/IRQ/锁/抢占约束 | 破坏哪项保证 | `source_explanations/PXX_源码讲解.md#N.N_接口标题` |
| 调试检查点 | 核对哪条调用声明 | 所需 Kconfig 与检查器状态 | 漏报、误用或覆盖边界 | `source_explanations/PXX_源码讲解.md#N.N_检查标题` |

知识正文在首次进入版本化源码证据时链接 `navigation/` 中的总阅读索引，再链接相关模块导读；遇到具体接口则直接链接唯一源码实现标题。源码实现讲解按以下顺序组织：

1. 使用关联入口表回链总阅读索引、所属模块导读、知识场景和需要该接口的调用链；
2. 给出具体宏、函数或字段的实现索引，把名称链接到当前实现文件的对应标题；该标题下再链接仓库保存的上游相对源码文件；
3. 在不改变源码语义的前提下裁剪足以支撑结论的原始实现，明确标注省略区间，并添加“仓库补充、非上游原文”的中文 Doxygen 注释和中文行内注释；
4. 单列“实现原理”，说明执行前后状态、调用者/被调用者、执行上下文、锁/抢占/中断约束、错误路径、配置分支和状态副作用；
5. 将功能机制与检查机制分列，说明检查开启/关闭后的展开、静态或动态属性以及未覆盖路径；
6. 回链稳定机制、诊断、实验和专题大纲，不在其他源码文档复制同一讲解。

功能路径包括真正改变状态或建立保证的锁、原子操作、内存序、状态机、通知、GP 和回调。检查路径包括 Sparse、Lockdep、debug objects、KASAN/KCSAN、断言和告警。检查宏即使嵌在公共 API 内，也不得被写成算法本身；关闭检查通常只移除诊断，不自动取消 API 契约。

先检查 `source_explanations/` 是否已经存在同一版本、同一宏、函数或字段的权威标题。已有标题时只增加入链和必要的关联入口；没有时按实现关联性补充现有讲解文件，只有版本边界、实现簇或调用上下文能够独立成立时才新建文档。模块层的新问题进入 `navigation/` 的模块概念导读，不得把模块归纳和逐函数实现混成同一种文件，也不得为每个接口制造一个无法维护的源码微专题。

面向 Typora 的章节链接必须包含文件路径和完整标题片段，不能只写 `PXX_源码讲解.md`。片段按标题渲染结果书写：标题源码中的 `\_` 在链接片段中写成 `_`。接口标题避免括号等会截断 Markdown 链接目标的符号；结构审计必须同时验证目标文件和目标标题。移动目录后全仓清除旧路径，不保留兼容副本。

## 5. 对每项结论分类

- **API 契约：** 调用者可以跨实现依赖的保证。
- **通用实现：** 当前内核在上游公共代码中的设计。
- **配置分支：** 只在所述 Kconfig 选择下成立。
- **体系结构实现：** 依赖具体架构路径，不能外推。
- **厂商/BSP 行为：** 只适用于本地源码树或开发板。
- **推论：** 由多个源码事实共同推出，但源码没有直接陈述；必须明确标为推论。

## 6. 在变化发生的位置比较版本

比较旧内核时，检查：

- 状态位置，而不只是字段拼写；
- 读者定义和 Kconfig 选择；
- 函数体和调用路径；
- 完成/唤醒的传递方式；
- 上下文跟踪或体系结构集成；
- 回调执行上下文。

只有同时核对两个版本后，才能写出“证明骨架保持稳定，但状态 X 从 A 移到了 B”这类结论。链接或保存精确的旧版源码证据。

## 7. 保存证据但不制造源码分叉

只有仓库把源码快照作为长期证据时，才将选定的上游相对文件保存到 `research/source_reading/linux/`，并记录版本和来源。保存的副本必须与声明的源码树进行哈希核对。

知识整理任务不得编辑、格式化或提交外部源码树，也不得修改其 Git 配置。

## 8. 检查常见错误

拒绝以下源码写作错误：

- 因为某个函数存在，就断言当前配置一定调用它；
- 把旧内核字段名当作当前实现；
- 把异步的局部到全局窗口压缩成一次调用；
- 把业务写入者描述为直接执行宽限期协调；
- 把超时、强制路径或停顿检测器描述成可以破坏安全性的许可；
- 用 CPU 级状态解释任务级债务，或反过来；
- 把实现优化描述为 API 的唯一语义；
- 复制行号却不记录版本和文件上下文。
- 在知识正文末尾堆放带版本的完整源码，却没有独立源码附录和双向导航；
- 只解释功能宏体而漏掉嵌入其中的检查分支，或把检查分支误写成功能保证；
- 因一次动态检查没有告警，就断言未执行路径和未来交错已经得到证明。

## 9. 动态验证器的额外证据

主题涉及 Lockdep、KCSAN、debug objects、sanitizer、断言或其他运行时检查器时，读取 [lockdep-case-study.md](lockdep-case-study.md)，并额外建立：

1. 被检查机制的真实功能状态及其写入者；
2. 检查器维护的当前影子状态；
3. 跨时间累积的类型、依赖、调用或告警历史；
4. 检查器启用、递归抑制、容量耗尽和停检状态；
5. 检查事件相对功能尝试、成功、失败、取消与释放的精确先后关系；
6. 无告警结论所依赖的配置、检查器有效性、事件接入和路径覆盖。

同一个检查器被多个子系统复用时，检查器核心状态与查询实现在检查器源码专题唯一展开；子系统只展开自己的虚拟身份、适配宏和调用条件，并双向使用 Typora 精确标题锚点链接。
