# Lockdep 案例：动态验证机制的状态分层

本案例来自仓库的独立 Lockdep 专题：稳定入口为 `knowledge/linux/synchronization/lockdep/大纲.md`，版本源码入口为 `research/source_reading/lockdep/navigation/P01_Linux_6.12_Lockdep源码导读.md`。它补充 RCU 案例中较少展开的 **动态检查器** 写作方法，不是要求所有专题复刻 Lockdep 的文件数量或字段。

## 1. 先分开功能状态与影子状态

动态验证器主题至少识别两条因果链：

```text
功能路径
  → 真正改变互斥、对象、内存、调度或设备状态

检查路径
  → 接收事件、维护影子状态、验证契约并报告
```

例如 mutex owner 和等待队列决定功能取得与释放，`lockdep_map`、`held_locks[]` 和锁类图只验证上报的锁协议。关闭检查不取消功能契约；检查通过也不代替功能正确性证明。

写其他调试机制时同样先问：检查状态是否只是功能状态的投影，事件漏报或错误分类会造成什么误报/漏报，检查器是否会主动修改功能结果。

## 2. 动态验证器通常不止一组状态

Lockdep 专题明确区分：

| 状态轴 | 时间尺度 | 典型问题 |
| --- | --- | --- |
| 被检查功能状态 | 当前真实执行 | 功能原语是否真正成功、对象是否仍存在 |
| 当前影子状态 | 当前任务或 CPU | 检查器认为当前有哪些未结束事件 |
| 跨时间历史知识 | 全局 | 过去观察到哪些类型、顺序、依赖或调用组合 |
| 检查器生命状态 | 全局/局部 | 检查是否启用、递归抑制、容量是否耗尽、是否已经由某条错误路径显式停检 |

其他动态验证器只有适用时才使用这些轴，但不得把“已编译检查器”“检查器当前有效”“目标路径已覆盖”和“没有报告错误”压成一个布尔结论。

## 3. 精确标出事件与功能动作的相对顺序

检查事件不一定发生在功能动作以后。Lockdep 为了建模等待依赖，阻塞锁的 acquire 注解可能在真正取得功能锁以前发生；可中断取得失败时再用 release 注解回退影子记录。

写动态检查专题时必须核对：

1. 事件是在功能尝试前、成功后还是释放前/后上报；
2. 功能失败、取消、超时或异常退出怎样撤销影子状态；
3. 临时候选状态何时变成正式当前状态；
4. 当前事件结束时，哪些局部状态撤销，哪些全局历史保留；
5. 检查器递归进入自身、IRQ/NMI 或并发写全局状态时怎样隔离。

只根据 `acquire`、`release`、`check` 等函数名猜时间边界不合格。

## 4. 身份分类本身是证明输入

动态验证器经常把大量实例归入某种逻辑类别。Lockdep 的实例、`lockdep_map`、key、锁类和 subclass 分工说明：

- 分类过宽可能把不同协议错误合并而误报；
- 分类过窄可能使同一协议无法跨实例闭包而漏报；
- 分类身份的生命期必须覆盖历史知识引用；
- 改分类、加 subclass 或关闭验证不能作为压制告警的默认修复。

创建其他验证机制专题时，若存在类型 ID、allocation site、对象类、域或注解 key，也要说明它怎样形成、何时回收，以及错误分类的双向后果。

## 5. 当前证据与历史闭包不能混写

Lockdep 的 `held_locks[]` 回答 current 当前持有什么；锁类依赖图回答历史上观察到什么顺序。release 只撤销当前记录，不删除已经验证的历史边。

可复用写法是：

```text
当前事件证据
  → 生成候选关系
  → 与跨时间历史组合检查
  → 验证通过后提交历史知识
  → 当前事件结束只回退局部状态
```

如果动态检查器还使用缓存，必须说明缓存命中省略了什么昂贵检查，以及仍必须维护哪些当前状态。不能把“跳过重复验证”写成“本次事件完全无检查成本”。

## 6. 无报告必须附带有效性与覆盖条件

动态检查专题的“没有告警”至少绑定：

- 对应 Kconfig/构建选项确实启用；
- 检查器当前没有因某条错误路径、内部不一致或容量耗尽而显式停检；
- 目标组件路径实际执行过；
- 功能原语或自定义机制完整上报；
- 身份分类、事件类型和上下文模型与真实协议一致。

诊断章节应提供检查器生命状态、容量计数、覆盖路径和预期报告，而不只给一个开关名称。

## 7. 源码材料分工

Lockdep 专题继续验证 `navigation/` 与 `source_explanations/` 的职责：

- 总索引组织源码地图、主调用链和建议阅读顺序；
- 模块导读讲身份/事件、图规则、查询/诊断三类功能环；
- 实现讲解按具体结构和函数簇唯一展开中文 Doxygen、中文行内源码和状态副作用；
- RCU 只引用 Lockdep 核心查询，Lockdep 只引用 RCU 虚拟 map 与告警适配，双方各自维护所属实现，避免跨专题复制。

这说明“同一实现单一展开”也适用于两个源码专题的交叉边界：先按实现所有权选择权威标题，再建立双向精确链接。

Lockdep 专题做全量信息同步时还要沿发现链复核：同步总纲与锁/RCU 相邻专题能够进入稳定正文，Atlas 地图、学习路线、内容索引和仓库首页能够分别发现正文与源码总索引，`SOURCE_BASELINE.md` 能定位已保存文件和带锚点的阅读入口。这里只同步发现关系和版本事实，不要求这些入口复制 Lockdep 的检查模型。

## 8. 动态验证器交付核对

- [ ] 功能状态、当前影子状态、历史知识和检查器生命状态已经区分。
- [ ] 事件上报相对功能尝试、成功、失败和释放的先后关系已经核对。
- [ ] 身份分类规则、生命期、误报和漏报后果已经解释。
- [ ] 当前状态怎样产生候选关系、候选怎样提交为历史已经闭环。
- [ ] 缓存、容量、递归抑制、停检和关闭配置的边界已经说明。
- [ ] 无告警结论同时记录启用状态、检查器有效性和覆盖范围。
- [ ] 检查机制没有被写成功能保证，功能契约没有因检查关闭而消失。
- [ ] 跨专题的具体源码实现只有一个权威讲解标题，并使用 Typora 精确锚点互链。
