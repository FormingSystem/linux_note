## 1. 确定读者结果

写出读者完成专题后必须能够重建或判断的结果。优先选择需要重建时间线、状态机、通信路径或所有权关系的问题：

- 事件发生前后，每项状态分别归哪个参与者所有；
- 什么条件封闭了旧使用者集合；
- 哪项证据证明操作已经完成；
- 一个局部事实如何变成共享或全局事实；
- 谁唤醒等待者，或者谁执行延迟动作；
- 哪项成本从快路径消失了，它被转移到了哪里；
- 什么约束下原方案更合适，什么约束下新机制才成立。

除非已经分解成可观察、可推理的任务，否则拒绝使用“了解主要 API”或“理解原理”作为专题目标。

## 2. 服从本次编辑权限

先按 `SKILL.md` 的“先确定编辑授权”选择仅排版、保留内容的结构调整或内容修改/重写模式。本参考只决定怎样设计专题，不扩大正文修改权限。

记录任务开始时的工作树和已审材料。仅排版时，只显化现有章节的职责与依赖；结构调整时完整移动已盘点内容；内容修改时才允许补充推演、修正模型或重写正文。

## 3. 执行两遍生成

创建、扩写或重写专题时，先设计后写作。

第一遍建立专题设计账本：

| 设计项 | 内容 |
| --- | --- |
| 读者结果 | 最终能重建的过程、证明或选择 |
| 贯穿场景 | 真实负载、规模、参与者和共享对象 |
| 旧方案 | 已有保证、实际价值和适用范围 |
| 故障链 | 从触发条件到错误或停顿的有序步骤 |
| 证明义务 | 安全性、活性、顺序、生命周期或隔离 |
| 执行模型 | 会改变参与者定义、状态位置或证明方式的配置与上下文 |
| 状态轴 | 单一状态机或多组正交状态 |
| 证据计划 | 稳定知识、版本源码、实验和平台证据的目的位置 |

随后选择章节角色，画出依赖关系，并为每章建立契约。第二遍才按依赖图写正文。不要先生成大量章节，再反向寻找它们为什么存在。

仅排版任务不重新建立技术模型；第一遍改为内容账本，把现有信息单元映射到阅读阶段和目的位置。

## 4. 准备贯穿场景

比较不同设计时尽可能复用同一个场景：

| 项目 | 必备内容 |
| --- | --- |
| 负载 | 读写频率、CPU 数量、时延、内存、睡眠和拆除约束 |
| 参与者 | 有名称的任务、CPU、中断、回调、设备和数据结构 |
| 被保护对象 | 正式入口、共享状态、对象或硬件事务 |
| 现有设计 | 它提供什么保证，以及当前为什么正确 |
| 故障链 | 从触发条件到错误观察、竞争、UAF、停顿或泄漏的有序步骤 |
| 所需保证 | 安全性、顺序、生命周期、进展性或隔离属性 |
| 证据 | 所需的源码版本、配置、跟踪、实验或基准测试 |

先给出具体场景和必要代码，再从约束推导抽象角色。这里的代码用于固定问题现场；完整 API 模板可以在抽象契约成立以后出现。

## 5. 按职责选择章节角色

本地 RCU 专题提供的是以下可复用职责，而不是固定的 28 篇文件：

| 章节角色 | 解决的问题 | 使用条件 |
| --- | --- | --- |
| 问题压力 | 旧方案解决了什么，缺口如何逐步形成 | 所有专题 |
| 抽象机制 | 不依赖目标系统字段，怎样从约束推出角色、边界和证明义务 | 机制不能只靠 API 定义时 |
| 最小使用闭环 | 抽象动作怎样对应接口、正常路径、失败路径和拆除 | 存在公共 API 或调用协议时 |
| 组合与生命周期 | 多种独立机制怎样由对象所属模块完成交接 | 涉及引用、回调、工作队列或复合分配时 |
| 执行模型证明 | 某一配置或上下文下，安全性为什么成立 | 不同模型具有不同参与者集合或证明方式时 |
| 源码实现映射 | 证明模型怎样落实为字段、写路径、读路径和完成条件 | 需要版本化实现证据时 |
| 现实条件加固 | 哪些抢占、迁移、中断、离线、乱序或迟延条件击穿朴素模型 | 真实运行条件会改变模型时 |
| 统一状态与通信全景 | 多组状态和多条通信路径怎样完成一个操作周期 | 分布式或分层机制 |
| 子状态机纵深 | 统一全景中的关键模块怎样独立推进 | 单篇总图不足以解释实现时 |
| 实现家族与配置 | 不同变体改变了哪些保证、参与者和成本 | 存在可选择实现时 |
| 应用、诊断与选择 | 怎样正确组合、观察故障并选择替代方案 | 所有完整专题的收尾 |

抽象契约建立以后，最小正确用法应早于大段实现纵深，使后续源码讨论具有具体落点。

## 6. 决定合并与拆分

章节角色可以合并或省略：

- 只有一个简单执行模型时，证明与源码映射可以同篇；
- 没有跨机制所有权时，不创建组合与生命周期章节；
- 状态不分层、通信路径简单时，不强制建立统一总图；
- 没有实现家族时，不为对齐 RCU 创建变体章节；
- 一个子状态机不足以独立学习时，保留在统一实现章节；
- 一篇同时承担两套独立证明、两个完整生命周期或多种配置模型并影响连续阅读时，才拆分。

文件数量由证明边界和阅读连续性决定，不由 RCU 篇数、历史七段式或八步法决定。

## 7. 为每章建立契约

写正文前为每章记录：

| 契约项 | 必须明确的内容 |
| --- | --- |
| 前置结论 | 本章允许假设读者已经知道什么 |
| 本章问题 | 本章只解决哪一个主要问题 |
| 贯穿场景 | 继续复用哪个对象、参与者和时间边界 |
| 新增模型 | 新增了哪些角色、状态、约束或通信路径 |
| 输出结论 | 本章结束后能够证明什么 |
| 证据 | 由代码、源码、配置、图、trace 或实验中的什么支撑 |
| 后续缺口 | 哪个问题有意留给下一章 |

章节契约不是必须提交的额外文件；优先把精简结果写入 `大纲.md` 的阅读地图。

章节之间通过未决问题连接，而不是只通过文件编号连接。每章开头回收上一章输出并暴露一个新缺口；正文一次只引入解决该缺口所需的模型增量；结尾明确本章新结论和下一章尚待兑现的证据。不得为了形式统一强迫 API 章、源码章和诊断章使用相同小节模板。

## 8. 区分抽象机制与具体实现

抽象章节使用调用者、参与者、局部证据、协调者、等待者和延迟执行者等角色，并推导这些角色为什么存在。

源码章节随后将角色映射到任务、per-CPU 状态、节点、全局结构、锁、回调以及调度器或中断路径。不得用某个 Linux 字段的存在反过来充当抽象机制存在的理由。

主要执行模型的证明方式确实不同时，先分别建立证明，再分别映射源码；只有字段不同而证明相同时，放入同一实现章比较，不机械成对拆篇。

## 9. 加固朴素模型

从 [mechanism-reasoning.md](mechanism-reasoning.md) 选择适用反例，检查未来参与者、抢占迁移、异步传播、多轮交叠、中断离线、对象逃逸、内存乱序和拆除竞态。

每发现一个缺口，都必须增加一种状态、一条通信路径、一项约束，或者一个明确的不支持场景。反例没有改变模型时，说明它由哪条既有不变量覆盖。

## 10. 保持权威专题独立

当一种机制依赖缓存一致性、内存顺序、原子操作、调度、kref 或其他可复用机制时：

- 将完整的通用教程保存在它自己的权威位置；
- 在当前场景保留该依赖及其失败后果；
- 在实际使用前置知识的位置添加链接；
- 避免创建无法独立成为研究专题的微型“扩展概念”；
- 确保被链接的权威专题拥有自己的场景、推导、证据，以及适用时的实验。

## 11. 让大纲成为学习地图

大纲先画章节依赖图，再为每章说明：

- 前置结论；
- 本章解决的问题；
- 新增的角色、状态或证明；
- 交给下一章的未决问题。

大纲只链接真实存在的文件，不复制各章解释，也不把尚未落地的设想章节列成已经完成的内容。读者沿默认顺序阅读时，应能看见模型怎样被问题和反例逐步完善。
