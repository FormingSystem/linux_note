# 构建 linux-note 技术书籍与专题

构建可长期维护、可验证并能支持继续推理的知识体系，而不是一次性长回答。默认读者尚未掌握本专题的缩写、源码黑话、实现家族名和项目私有命名；先让读者获得进入概念所需的语言，再按认知路径组织材料。始终区分稳定知识、带版本的源码证据、实验、平台差异和导航。

## 以讲清楚为完成条件

教学正文以读者能够解释、预测、操作和修改为完成条件。用户要求“不惜一切代价讲解清楚”时，在授权专题范围内，解释完整性优先于篇幅、生成速度、token 节约和单轮收尾；需要更长正文、拆章或多轮核对就继续完成。不得为了省篇幅省略前提、推导、命令含义、状态变化和失败后的恢复，也不得以“内容已经很多”、官方链接或自动测试通过代替读者理解。交付回复可以简洁，教材不能因此被压缩成摘要。

讲清楚不等于堆字数。**Markdown 文档非必要不得超过 10,000 字词；超过时必须审查拆分必要性，不能继续无边界堆叠。** 中文按汉字、英文按连续单词计数，正文、表格和代码/图示文本均计入，不计 Front Matter、链接目标和 HTML 标记；使用 `scripts/audit_document_length.py` 统一统计。长度明显过大且包含可独立学习的问题时，按问题或学习阶段拆分。完整实验说明、较长但必要的代码、需要连读的操作周期与推导可以超过阈值；仅稍微超出且拆分只会留下短尾巴时，也应保留连贯性，不为了数字强拆或先压缩内容。记录具体保留理由即可，不额外要求用户逐篇审批。“资料很多”不是理由，理由应说明拆开会损害哪段阅读或操作。保留因果解释、原始证据与完整操作周期，不能删去必要内容、图像化文字或移走关键解释来规避阈值。拆分后同步序号、大纲、前后篇、所有标题锚点与实际调用方，每篇都有自己的问题与闭环。

保留用户已有的编程与工程基础，但不把熟悉一种语言当成掌握实验所用另一种语言的模块、项目组织和运行规则。补足当前实验赖以成立的知识，不展开无关语法；每段解释应解决一个具体理解障碍。用户反馈“晦涩”“像提纲”“只有命令”时，必须检查并重写实际章节的讲解链，不能只增补实验 README、术语表、导航或参考链接后宣称问题解决。

编写或重写教学正文时，阅读 [讲解写法与读者理解验收](references/explanation-quality.md)，用其中的冷读检查验收理解过程。清单、脚本和覆盖率是辅助证据，不能取代这项验收。

## 默认写成可连续阅读的教材

面向本仓库C/C++开发者，教学示例、机制模型和配套测试默认使用C/C++；非必要不使用Python或其他语言。例外必须来自具体学习任务或被讲工具的真实接口，不能仅因作者实现更方便。采用例外前说明它在本实验中不可省略的职责，并按下文补齐读者需要的语言与运行前提。用户更新语言要求时，回查本轮已经引入的代码、测试、命令与材料，不能只约束后续新增内容。

知识专题的教学正文默认采用耐心、平等、循序渐进的教材叙述，以读者认识的变化组织知识，而非按工具选项、源码字段或审稿清单逐项填充。用户以《C Primer Plus》《C++ Primer Plus》等教材为参照时，落实其要求的可学性：贯穿实例、逐步增加难度、自然过渡、适量幽默、动手实验和引导思考；使用原创内容，不承诺复刻原书措辞或已获得原书全文。

先选定阅读契约：**连续教材章节**可以依赖明确列出的前置章节，并用简短回顾唤回已经建立的认识，不反复重讲完整定义；**独立入门文章**须在本地补齐承诺范围内的专题前提；**参考页**以查询为主，不强行套故事和实验。Markdown 文件能被单独打开，不等于它必须从零重新教完整专题。下文及参考文件中的“首次解释”“局部闭环”和术语审计均按这一契约执行。

在当前推理需要之前解释必要概念。允许标题提出尚待回答的问题，也允许先展示一个待解释的现象并立即展开；不要求在标题以前定义标题中的所有词。完整性由整套教材及明确的依赖关系保证，不把全部选项、例外和实现细节塞入第一次接触。作者账本与审稿要求留在工作记录，正文不向读者展示一套验收表。

**跨模块内容必须有当前用途，不能只因名字相似就顺带提及。** 本节解释一种身份、状态或输入输出关系时，先在该对象及所属层内闭合；不把硬件来源编号、固件描述编号、操作系统管理编号等不同模块的规则放进一组未经铺垫的判断。删去该旁支仍不影响当前推导时，正文不插入这条旁支，已有有效知识放回其负责模块。确需跨模块解释时，先点名模块、它管理的对象，以及它与当前对象的具体交接关系，在本地说明当前需要的最小结论，再给出真实存在的精确章节入口；链接承担深化和查证，不能代替这段关系说明。禁止仅写“也不一定相同”“后续再解释”而不交代谁负责、为什么现在需要以及到哪里继续。软件发起配置、处理设备或完成握手是硬件事务的真实参与动作，不因出现“软件”二字就移除；具体操作系统的管理机制则按当前推理需要决定是否进入。详见 [跨模块边界与当前问题](references/concept_implementation_mapping.md#跨模块边界与当前问题)。

标题可以概括结论或提出问题，但不计作正文已经完成的解释。每个小节都要接住读者从上文带来的对象、条件和未决问题；改变场景、执行者、时间阶段或观察层次时，在正文中交代当前推理需要的变化及其缘由。语序优先从已知对象走向新条件、动作和结果，不让“因此、此时、这种方式、它”等词依赖只写在标题或作者脑中的前提。按 [讲解写法第 8.1 节](references/explanation-quality.md#81-标题之间的正文必须接得起来) 检查跨标题边界；不机械复述标题，不为自然连贯的段落硬加过渡句。

实验嵌入认识发生变化的位置，形成可预测、可观察、可解释、可修改的经历；不能只是章末验收附件。自然幽默服务于现场理解，不嘲笑读者、不卖萌、不按数量硬塞笑话。详细写法、练习梯度和样章校准见 [讲解写法与读者理解验收](references/explanation-quality.md)。

连续教材默认把本单元实验写在本单元正文内，配套源码、配置与输入数据放在专门材料目录。正文展示当前实验所需的完整小程序或配置，解释后即可执行；材料链接只便于取用和对照，不承担核心教学步骤。每个单元只使用已经建立的知识与本单元正在讲解的新知识；不得让初阶章节跳到包含后续概念的综合实训，也不得为让每个链接页面“独立闭环”而把整门课程前提反灌进低阶实验。具体编排与检查见讲解写法第 5 节。

操作教学采用就地讲解：可复制命令块用注释标明执行位置和必要环境，命令或不可拆的操作单元之后紧接含义与观察结果，不让读者在长命令块和远处解释间配对。实验目录、源端与使用端、语言模块与 Git 仓库先建立关系；约定文件名与作者自定名称首次出现时说明区别和实际定位办法。区分尚未生成与已经存在的文件，先完成创建动作再要求打开产物。多步骤实验先给总路线，在各步骤入口复用同图、同编号并突出当前步骤；重复导航图承担定位职责，不受下文“表示增量”的去重要求限制。详见讲解写法第 4.1、4.2、8.2 节。

用户给出全局性批注时，保存带批注基线，记录“原意见 → 通用规则 → 所有受影响正文”的对应关系；局部案例用于提炼实际缺口，不把工具名、盘符或某一次实验特例写成全局规定。正文修复后可将批注移入审阅记录，保留原文与落实位置，不能只删除标记或只补规则。

新增长篇教材或整体纠正写法时，先完成一个有代表性的完整样章并验证实验，检查语言、节奏、内容深度和练习是否符合目标，再按该质量基准推进。样章不是额外审批关卡：已有清楚授权时继续工作，不把等待用户逐章确认设为默认流程；也不能用样章代替已授权的完整交付。

## 先确定编辑授权

编辑前选择并说明以下一种模式：

1. **仅排版（layout-only）：** 适用于用户明确只要求格式、导航、编号、阅读地图或参照某专题的排版，尤其是材料已经审稿的情况。保留技术语义、信息量、代码语义、图表含义、实验和检查项；允许调整标题编号、空白、列表、表格、导航、锚点以及其他排版所需的机械表达。用户要求改善教材叙述、教学风格或实验引导时，不得仅因提到“风格”就误选此模式。
2. **保留内容的结构调整（structure-preserving）：** 适用于用户明确要求拆分、合并、移动或重排的情况。盘点每个已审内容单元，完整移动，不得缩写。
3. **内容修改或重写（rewrite）：** 适用于用户明确要求补充、纠错、扩写、优化、重写、压缩、去重、替换或删除的情况。材料是否经过审稿不构成永久禁止修改；修改范围不得超出本次授权。

单独出现“重构”既不自动选择重写模式，也不自动选择仅排版模式。应结合“已审稿”“只排版”“补充内容”“重写”等限定语判断；如果不同选择会实质改变结果且上下文无法确定，先确认再改动技术语义。文件很长、规则重复、目标结构更整洁或通用审计出现警告，都不构成删除授权。

## 以仓库事实为起点

1. 阅读当前仓库的 `AGENTS.md`、根 `README.md`、信息架构文档、目标专题大纲和 Git 规范。
2. 编辑前检查 `git status`。将任务开始时的目标工作树作为内容基线，记录已提交和未提交的材料；是否修改其技术内容由本次用户授权决定。
3. 只有新增或修改证据结论时，才定位对应规范、芯片手册、源码树或实验环境并验证身份；涉及外部 Linux 源码时，按照当前仓库说明重新发现和核对版本。
4. 盘点目标目录、入链、出链、文档 ID、出版清单、Atlas 入口、Obsidian 产物和相关权威专题。
5. 在仅排版模式中，盘点并组织已有问题场景，不得用新编场景替换原场景，也不得改变其技术结论。在内容创作模式中，先明确读者需要重建的具体问题。

开始创建、扩写或重组专题前，按顺序读取 [references/topic-design.md](references/topic-design.md) 和 [references/repository-topic-requirements.md](references/repository-topic-requirements.md)：先建立技术书籍的认知路径，再选择仓库题型骨架和章节角色，不得机械叠加 P01～P05 的历史模板。分析并发、异步、生命周期或多角色状态机制时，读取 [references/mechanism-reasoning.md](references/mechanism-reasoning.md)。把结论映射到 Linux 源码前，读取 [references/source-evidence.md](references/source-evidence.md)。需要理解本地 RCU 专题怎样落实阅读地图时，使用 [references/rcu-case-study.md](references/rcu-case-study.md)；涉及 Lockdep、KCSAN、debug objects、sanitizer、断言或其他动态检查器时，再使用 [references/lockdep-case-study.md](references/lockdep-case-study.md)。案例用于校正方法，不提供固定篇数或字段模板。交付前使用 [references/review-checklist.md](references/review-checklist.md)。

## 先设计再生成

新建、扩写或重写专题时执行两遍生成，先完成全书设计再开始正文：

1. 第一遍建立工作型专题蓝图和术语依赖账本，明确读者起点与结果、术语进入顺序、系统全景、贯穿场景、问题链、错误模型、动态过程、观察视角、层次映射、工程约束和证据计划；
2. 按题型选择章节职责，建立完整章节依赖图和每章契约，确保每章都回答“为何现在讲、承接什么、只解决什么、留下什么”；
3. 第二遍才按依赖图生成正文，允许证据不足反向修正模型，不允许先写大量章节再寻找存在理由。

仓库正式 `大纲.md` 只登记真实存在的可点击章节。分批生成时，完整规划保留在工作型蓝图中，每落地一章再同步正式大纲；不得制造空占位文件或死链接。仅排版模式不重新推导技术模型；第一遍改为内容账本，把现有信息单元映射到阅读阶段和目的位置。

## 模块身份与分类坐标

设计、重组、创建、扩写或重写专题时，必须按 [模块身份与分类坐标](references/reader_first_writing.md#让模块平台与代际也从零建立) 先建立模块、平台、架构、产品、家族与代际的身份及关系，再按同篇的 [分类轴和模块变体矩阵](references/reader_first_writing.md#先确定分类轴和模块变体矩阵) 组织公共职责与差量。不能把作者已知的终局分类作为读者入口，也不能在分类对象尚未建立时提前比较。

## 正文入口、术语与连续阅读门禁

创建、扩写或重写正文前，必须完整阅读 [正文入口、术语与连续阅读门禁](references/reader_first_writing.md)，完成章节入口、术语依赖与模块闭环，并在交付前逐章执行其中的冷读硬门禁。已出现标题、表格、图、源码和链接不能代替读者理解；该参考保留全部进入卡与验收条件，不能以自动审计通过而跳过。

## 兼顾独立讲解与官方资料阅读指导

专题必须同时支持两种阅读：不打开官方资料也能从正文理解设计、概念及边界；需要纵深时，能从关键解释旁的引用追到官方文档的具体目录位置。采用 [独立讲解与官方资料溯源](references/official_source_reading.md#独立讲解与官方资料溯源) 的证据契约：标注文档身份与版本、章节号与原文标题、可核对的入口及阅读问题，区分规范要求、实现选择、平台集成、教学推演和实验观察。参考资料总表不能替代就近引用，引用也不能替代正文讲解。

图表补齐先通过因果讲解门禁：**背景与具体缺口 → 为什么需要此职责或设计选择 → 能做什么及一次完整过程 → 表格比较或细化**。不能用表前一句“为便于查询”或“手册如下”代替背景、作用和出现意义；隐藏表格后，读者仍应能说明对象为何需要、怎样工作，表格再提供精确字段、数值或比较增量。硬件职责的必要性与某产品物理划分的选择分别解释，不编造唯一历史起因；具体检查见下述图表自足规则。

正文的推理、计算、比较或练习答案依赖外部图表时，按 [外部图表落地与教材自足](references/official_source_reading.md#外部图表落地与教材自足) 在首次使用处呈现必要内容及读图说明；不能只给图表号、页码或链接让读者自行补齐。交付前逐项核对图表覆盖台账，并在隐藏外链的条件下验证读者能从本地材料推出结论。

正文实际讲解或使用的寄存器、寄存器组还须按 [寄存器与寄存器组的本地查用表](references/official_source_reading.md#寄存器与寄存器组的本地查用表) 就地列出当前所需的地址或访问方式、字段及读写效果；寄存器名称列表和手册链接不能代替该表。

读者直接浏览的专题章节文件使用 `PXX_中文主题.md`，允许保留必要的技术标识；不因中文命名改动稳定 ID、英文目录、源码路径或官方附件名。细则见 [仓库命名与交付要求](references/repository-topic-requirements.md#10-调试验证与交付)。

## 从全景、错误模型和动态过程建立理解

专题开端先说明“是什么、解决什么问题、位于系统何处、与谁交互”，再进入 API、寄存器、数据结构或源码。全景只建立坐标，不提前倾倒成熟实现的全部术语。

容易误解的关键机制按以下顺序展开：

```text
错误模型为什么看似成立
    → 在具体参与者、状态和时间线上出现什么矛盾
    → 只增加解决当前矛盾所需的模型增量
    → 用正确模型重新解释原场景
    → 说明仍未覆盖的条件与下一步
```

同一机制按需选择概念、数据结构、状态机、时间/时序、CPU/线程/中断、调用者、源码、硬件和工程部署视角。所有视角必须复用同一组关键对象、阶段和事件，不得写成互不连接的知识点清单。

关键结论必须展示动态过程：转换前状态、触发动作、中间传播、完成条件、转换后状态和失败分支。图是第二套表达系统，用于状态、时序、Before/After、层级、数据流、角色和生命周期；箭头标出动作或状态流，正文解释关键转折。不得用装饰图替代推导，Mermaid 换行使用 `<br/>`，不使用 `\n`。

每张 Mermaid `sequenceDiagram` 必须提供可定位的顺序编号，默认使用 `autonumber`；图后的关键转折说明必须引用这些步骤号，不只写“前面”、“之后”。两个方案、配置或失败/正常路径需要对比时，如果它们对“同一时刻是否发生了动作”、参与者集合或证明条件的结论不同，使用两张复用同一组对象名的独立时序图，并用颜色标出差量；只有两条路径真正共享同一条时间轴且 `alt` 不会造成事件已发生/未发生的歧义时，才在一张图内分支。

## 严格区分抽象层并建立映射

概念阶段使用选定规范或契约的术语，先建立职责、状态、输入输出和对象计数单位；进入产品、平台或源码实现时，先说明版本与层次，再交代这些概念由哪些实际载体兑现，之后才展开内部流程与收益。规范术语和产品术语即使同名，也不能默认同义、同边界或同数量；不得用实现名称反过来替换尚未建立的概念。

讲解开始、层次切换以及可独立进入的小节入口，先用读者可见的短行标注 **讲解层次：概念层** 或 **讲解层次：实现层**，同时点明规范/契约或产品/源码版本；桥接两层时标注 **讲解层次：概念到实现的映射**。标注须在正文展开以前出现，不能仅存在于作者蓝图、元数据或文末；同层连续段落不逐段重复，标题已经同样明确标出层次与对象时可不另加一行。

涉及跨层对应、物理分块、共享实现或用户追问“包含还是连接、到底配置谁”时，必须读取 [概念到实现的映射与输入输出](references/concept_implementation_mapping.md)。正文在首次跨层处完成三件事：**分别数清资料可确认的逻辑对象与实现载体；区分实现、包含、连接和地址视图；沿一次操作追到真正保存并修改状态的位置**。一个模块承载多个逻辑对象、一个逻辑职责分散于多个模块时，逐项说明已确认的职责与状态落点，未公开的部分明确标出；不能用“整合”“实现了一部分”代替对应关系，也不能凭每核一个逻辑对象画出每核一个独立物理器件。

图与正文使用同一组对象和边界。关系图说明盒子表示物理模块、功能分区还是逻辑归属；事务图分别标出请求、配置、响应和完成的实际端点与方向。软件可见地址、访问入口与状态所在位置分别说明，不把转发访问写成修改入口模块自己的状态，也不臆造独立对象及状态同步线路。多个对象共用接口时解释汇聚、选择与目标标识；讲布线、分组或电源收益以前先建立实现路径，并区分设计/集成时确定的结构与运行时可配置的策略。

同样分别核对 API 契约与内部机制、软件同步与硬件一致性、协议保证与平台能力、稳定模型与版本源码，不能跨层借用保证。用相应层次的规范、实现手册、源码或实验核对映射。尚未公开的内部结构明确标为未知，已证实的归属直接说明；不得用不确定的细节模糊已经成立的关系。交付前按映射参考中的冷读问题检验读者能否定位实际对象、追踪配置和预测结果，不能只检查是否写了“逻辑与物理不同”。

**变化与不变必须绑定具体操作。** 先直接回答当前问题，再点明比较对象、动作、操作前与生效后的时点及必要条件；“不受本次操作影响”不能写成“永远不变”。易混关系用前后对照表或时序图，只展示本问所需维度，不为填表引入额外操作。按 [变化与不变必须绑定动作和时点](references/concept_implementation_mapping.md#变化与不变必须绑定动作和时点) 核对必要边界。

## 按题型调整讲解顺序

- **数据结构与 API：** 在最小概念和契约成立后，尽早给出常用操作、最小正确用法、失败清理和典型模式，再进入内部结构、动态算法、实现证据和性能选择；涉及算法题时补充题型识别、朴素方案、优化动机、复杂度、隐藏边界、易错点和变形。
- **硬件、芯片与协议：** 从系统位置与概念职责进入，先把规范角色映射到选定实现的模块、状态和接口，再沿一次完整事务展开信号、时序、寄存器、驱动和板级约束；不得直接按数据手册目录复述。
- **内核机制与并发：** 从问题压力和抽象证明进入，闭合状态所有权、通信、完成通知和源码证据；并发机制至少提供角色/状态关系图与端到端时序图。
- **工程系统：** 同时纳入资源预算、构建产物、镜像或部署布局、启动流程、故障恢复、可观测性和验收；理论上正确但目标环境无法落地的方案不算完成。

## 区分产物职责

按产物立意保存结论；同版本的具体源码实现只展开一次：

| 层次 | 职责 |
| --- | --- |
| `knowledge/` | 跨版本稳定的机制、因果解释、API 契约和选择边界 |
| `research/source_reading/` | 精确版本、配置、源码路径、字段、函数和调用链 |
| `labs/` | 验证单一结论的最小可复现实验 |
| `platforms/` | 架构、SoC、BSP 或开发板特有行为 |
| `atlas/` 与专题 `大纲.md` | 阅读顺序与链接，不复制第二份教程 |
| `reference/` | 面向查询的 API、命令、术语或外部资料索引 |

动态验证器专题还要分别记录：被检查机制的真实功能状态、当前任务/CPU 的影子状态、跨时间累积的全局历史，以及检查器自身是否启用、递归抑制、容量耗尽或已经停检。检查事件可能发生在功能尝试以前或失败回退路径中，必须核对真实先后关系，不能仅从 `acquire`、`release` 等名称推断功能动作已经完成。

`knowledge/` 正文和 `research/source_reading/<topic>/navigation/` 模块概念导读可以围绕同一机制保留必要交叉，但不能互相替代：前者建立跨版本稳定的因果模型、接口契约和应用选择，后者面向特定版本组织源码入口、状态落点、函数协作和阅读顺序。不得把相同术语、状态阶段、调用链结论或必要背景直接判为重复，也不得因为编辑其中一层就自动删除、同步、合并或改写另一层。单一展开只约束同版本上游宏体、函数体和逐句实现说明；只有用户范围或链接、版本与事实边界明确同时影响两层时，才分别审查和独立修改两边。

在保留内容的结构调整或重写模式中，只有记录好目的位置后，才能移动通用硬件、编译器、内存顺序或对象生命周期解释。在仅排版模式中，可以按排版目标调整展示形式并增加权威链接，但不得改变技术语义或遗漏原有信息单元。

## 源码阅读组织与实现讲解

知识正文使用版本化源码证据，或任务创建、修改、整理、审查源码概念导读及实现讲解时，必须完整阅读 [源码阅读组织与实现讲解](references/source_documentation_workflow.md) 和 [源码证据规范](references/source-evidence.md)。据此建立总索引、模块概念导读、唯一实现标题及精确互链，逐项解释影响行为的源码符号，并验证读者能够预测局部修改的影响；不能把源码链接当成本地讲解，也不得修改外部源码树。

## 保持跨章节阶段和数据结构可追踪

当下游章节放大上游章节已建立的完整周期、状态机、阶段表或功能模块时，不能只写“承接 PXX”。必须建立 **阶段回链**：

1. 上游阶段表若需被其他章节精确引用，将表按真实交接边界放在可稳定跳转的完整标题下；不依赖无标题锚点的单个表格行。
2. 下游章节如果为局部模块创建 R0～Rn、T0～Tn 等新编号，在第一次展开前给出“本地阶段 → 上游公共阶段”交叉表，每行链接到上游的完整标题锚点。
3. 正文、表格、图、源码和实验后续都复用这个交叉关系；不得让两套阶段各自推进，再要求读者自行对齐。

当数据结构、对象字段簇、寄存器块或协议头首次承担推理职责时，必须同时提供 **本地最小解释 + 独立结构入口**：本地先说明它是什么类型、由谁拥有、当前字段在本次交接中保存什么、谁写谁读；然后用完整标题锚点链接到权威的数据结构、状态机或版本化实现讲解。如果已有权威入口，直接复用，不复制结构体全字段；如果不存在，只在该结构可跨场景复用或本章无法局部闭环时创建独立讲解，不为每个字段制造微型文档。

## 建立因果学习链

设计新材料或在大纲中组织已有章节时使用本节。仅排版模式只改变阅读组织和展示形式，不重新论证或替换已审技术内容。

除非具体领域证明其他顺序更清楚，否则采用以下顺序：

1. **问题压力：** 展示真实负载、参与者、旧方案、旧方案提供的保证，以及暴露缺口的精确交错或规模。
2. **抽象推演：** 不使用 Linux 字段名，从约束推出角色、状态、时间边界和证明义务。
3. **最小闭环：** 抽象契约成立后尽早给出最小正确接口、正常路径、失败路径、清理和拆除，使后续实现讨论具有具体落点。
4. **分类坐标与公共骨架：** 存在多个家族或配置时，先区分正交轴，并只讲一次跨变体共享的角色、模块和完整周期。
5. **模型分化与加固：** 只有参与者集合或证明方式确实不同时才拆分执行模型；使用适用反例检验未来参与者、异步窗口、迁移、交叠、乱序和对象逃逸。
6. **模块实现与变体差量：** 把抽象状态按功能模块映射到地址、所有者、写入者、读取者、通信和完成条件；先公共实现，再比较变体差量，只为真正独立的子状态机或实现家族拆篇。
7. **应用、实验与选择：** 给出组合方式、诊断方法、可观察实验、误用、成本转移和替代条件，说明何时原方案仍更合适。
8. **证据与导航：** 按职责保存稳定知识、带版本源码、实验和平台证据，更新大纲、上一篇/下一篇链接、稳定 ID 和仓库检查。

保持认知悬念链：先复述已经成立的结论，再提出它无法解释的一个具体问题；用反例暴露缺少的状态维度，只增加解决本轮反例所需的角色、状态、通信路径或约束；随后用源码或实验兑现新增模型，并把尚未解决的问题交给下一章。不得在问题尚未出现时一次性展示成熟机制的全部字段和术语。

章节开头优先交代“上一章已经证明什么 → 仍然无法解释什么 → 本章只解决什么”，结尾交代“现在可以证明什么 → 仍然不能解释什么 → 下一章继续追踪什么”。这是思维桥接，不要求机械使用相同小节标题。

正文重写或职责扩展后，按 [标题契约](references/reader_continuity_review.md#标题契约) 重新核对当前标题、父子范围与同级问题推进关系；标题应让读者看见具体对象及其设计问题、因果或角色关系，不能保留已经失约的旧概括。标题无需一律问句，也不靠加长或堆术语表示完整；改名后同步 Typora 完整标题锚点、实际入链和导航。

不要强迫所有阶段进入一个文件。如果一篇文档承担多个可独立学习的机制，或者源码细节打断因果解释，应拆分文档。只有确实承担连续性职责时，才保留短桥接文档。

## 让承担证明的章节从具体场景写起

创作或重写内容时使用本节。在仅排版模式中，保留已审场景的技术语义，只显化其顺序和关系。

讲理论前先建立：

- 有名称的负载及其规模；
- 具体任务、CPU、中断、线程、回调或设备；
- 共享状态的存储位置；
- 足以固定问题现场的真实或结构完整代码路径；
- 预期交错和可观察故障；
- 需要保护的正确性属性。

随后解释解决该场景的理论。完整应用代码必须覆盖分配、发布、错误清理、拆除流程和关键竞态语句；问题章中的最小现场代码不必提前承担最终 API 模板的全部职责。

## 把完整实例写成可以验收的小闭环

只有代码块不构成“完整实例”。用户要求完整、具体、可运行或足以讲清用途的实例时，至少闭合以下内容：

1. **需求背景：** 谁在什么任务中遇到什么限制，为什么需要当前语法、宏、接口或机制；
2. **环境与边界：** 语言/内核/工具版本、配置和运行上下文；说明是上游原样代码、结构完整的教学代码还是只固定问题的现场片段；
3. **输入与准备：** 必要类型、状态、初始化、调用入口和测试数据，不让关键对象凭空出现；
4. **正常与失败路径：** 展示成功动作、至少一个与主题相关的失败或错误用法，以及配套的回滚、清理、释放或退出；
5. **逐步过程：** 展开关键宏、调用链、状态变化、求值次数或产物流，让结论能从过程推出；
6. **观察与验收：** 给出可执行命令或明确观察位置、预期输出/诊断/状态，并解释结果证明什么；
7. **证明边界：** 说明该实例不能证明什么、哪些平台或配置需要另行验证，并链接权威实现或规范。

示例复杂度按主题裁剪，但不能省略恰好决定正确性的语句。孤立函数、只有声明没有调用者、只有成功路径没有清理、只有命令没有预期结果、只展示宏定义却不展开调用位置，均不得标为完整实例。若本章只需要一段最小现场，应明确称为“现场片段”或“裁剪示例”，并链接已经闭环的完整实例。

并发或多角色机制专题整体至少包含：

- 一张角色/状态关系图，箭头标明状态或所有权流；
- 一张端到端时序图，覆盖正常路径和改变状态归属的关键分支；
- 对完整状态机制复用同一组 S0、S1……周期，并用阶段表说明；
- 明确区分安全性和活性；
- 解释被移除成本的去向和选择边界。

图表按证明需要放入相应章节，不要求每篇各自凑齐一套。

Mermaid 换行使用 `<br/>`，不得使用 `\n`。

## 显式建模分布式状态

先说明机制是单一状态机，还是由多个正交状态轴组成。区分当前状态、已经锁存的历史事件、绑定操作周期的代际证据以及仍未清偿的等待债务。每个阶段都记录：

| 必备事实 | 必须回答的问题 |
| --- | --- |
| 触发条件 | 什么事件使机制进入本阶段？ |
| 转换前后 | 哪个精确状态发生了什么变化？ |
| 存储位置 | 状态位于哪个结构、任务、per-CPU 区域、节点、对象或全局地址？ |
| 写入者 | 哪个执行上下文完成写入？ |
| 读取者 | 后续哪条路径消费该状态？ |
| 通信方式 | 本地写、共享内存、锁、轮询、回调、唤醒、IPI 还是分层上报？ |
| 退出条件 | 满足什么条件才能进入下一阶段？ |

机制实际具有相应状态转移、汇聚或异步完成时，闭合以下回路；没有这一环节时说明真实完成方式，不为套用清单制造共享登记或后台线程：

1. 状态所有权变化时，本地状态如何变成共享状态；
2. 局部证据如何汇聚为全局结论；
3. 等待方或延迟动作如何得知结论已经完成。

明确说明机制采用直接登记/通知，还是通过“不变量 + 已观察事件”间接证明参与者已经越过边界。未来参与者为什么不属于当前集合，必须由入口、代际或协议边界证明。

快路径移除全局登记或通知时，要说明被转移的工作分别怎样出现在正常的每操作路径、特殊状态转移路径以及延迟或强制路径中。

## 单独处理对象生命周期

区分发布可达性、临时受保护访问、长期所有权、宽限期完成、回调执行和最终内存销毁。在组合 RCU、kref/refcount、锁、工作队列或模块拆除前，先画出分配与所有权关系图。

每次分配只能有一个最终销毁协议。不得暗示彼此独立的机制会自动通知或适配。明确由哪个模块回调把控制权从一种机制交给下一种机制。

## 重构、验证与交付

本技能的每项任务交付前都必须完整阅读并执行 [重构、验证与交付](references/delivery_validation.md)，按授权保存基线、完整迁移内容、同步真实调用方，运行长度、结构、连续阅读与术语审计及适用的内容守恒检查。脚本报告须人工裁决，不能代替冷读；准确报告已执行与未执行的验证。编辑使用 `apply_patch`，未经用户明确要求不得暂存或提交。
