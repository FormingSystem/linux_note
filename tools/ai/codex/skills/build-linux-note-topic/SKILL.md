# 构建 linux-note 技术书籍与专题

构建可长期维护、可验证并能支持继续推理的知识体系，而不是一次性长回答。默认读者尚未掌握本专题的缩写、源码黑话、实现家族名和项目私有命名；先让读者获得进入概念所需的语言，再按认知路径组织材料。始终区分稳定知识、带版本的源码证据、实验、平台差异和导航。

## 先确定编辑授权

编辑前选择并说明以下一种模式：

1. **仅排版（layout-only）：** 适用于用户明确要求格式、导航、编号、阅读地图或“参照某专题风格”，尤其是材料已经审稿的情况。保留技术语义、信息量、代码语义、图表含义、实验和检查项；允许调整标题编号、空白、列表、表格、导航、锚点以及其他排版所需的机械表达。用户没有要求时，不新增论证、源码研究或实验。
2. **保留内容的结构调整（structure-preserving）：** 适用于用户明确要求拆分、合并、移动或重排的情况。盘点每个已审内容单元，完整移动，不得缩写。
3. **内容修改或重写（rewrite）：** 适用于用户明确要求补充、纠错、扩写、优化、重写、压缩、去重、替换或删除的情况。材料是否经过审稿不构成永久禁止修改；修改范围不得超出本次授权。

单独出现“重构”既不自动选择重写模式，也不自动选择仅排版模式。应结合“已审稿”“只排版”“补充内容”“重写”等限定语判断；如果不同选择会实质改变结果且上下文无法确定，先确认再改动技术语义。文件很长、规则重复、目标结构更整洁或通用审计出现警告，都不构成删除授权。

## 以仓库事实为起点

1. 阅读当前仓库的 `AGENTS.md`、根 `README.md`、信息架构文档、目标专题大纲和 Git 规范。
2. 编辑前检查 `git status`。将任务开始时的目标工作树作为内容基线，记录已提交和未提交的材料；是否修改其技术内容由本次用户授权决定。
3. 只有新增或修改证据结论时，才定位对应规范、芯片手册、源码树或实验环境并验证身份；涉及外部 Linux 源码时，按照当前仓库说明重新发现和核对版本。
4. 盘点目标目录、入链、出链、文档 ID、出版清单、Atlas 入口、Obsidian 产物和相关权威专题。
5. 在仅排版模式中，盘点并组织已有问题场景，不得用新编场景替换原场景，也不得改变其技术结论。在内容创作模式中，先明确读者需要重建的具体问题。

开始创建、扩写或重组专题前，按顺序读取 [references/topic-design.md](references/topic-design.md) 和 [references/repository-topic-requirements.md](references/repository-topic-requirements.md)：先建立技术书籍的认知路径，再选择仓库题型骨架和章节角色，不得机械叠加 P01～P05 的历史模板。分析并发、异步、生命周期或多角色状态机制时，读取 [references/mechanism-reasoning.md](references/mechanism-reasoning.md)。把结论映射到 Linux 源码前，读取 [references/source-evidence.md](references/source-evidence.md)。需要理解本地 RCU 专题怎样落实阅读地图时，使用 [references/rcu-case-study.md](references/rcu-case-study.md)；涉及 Lockdep、KCSAN、debug objects、sanitizer、断言或其他动态检查器时，再使用 [references/lockdep-case-study.md](references/lockdep-case-study.md)。案例用于校正方法，不提供固定篇数或字段模板。交付前使用 [references/review-checklist.md](references/review-checklist.md)。

## 先设计再生成

新建、扩写或重写专题时执行两遍生成，先完成全书设计再开始正文：

1. 第一遍建立工作型专题蓝图和术语依赖账本，明确读者起点与结果、术语进入顺序、系统全景、贯穿场景、问题链、错误模型、动态过程、观察视角、层次映射、工程约束和证据计划；
2. 按题型选择章节职责，建立完整章节依赖图和每章契约，确保每章都回答“为何现在讲、承接什么、只解决什么、留下什么”；
3. 第二遍才按依赖图生成正文，允许证据不足反向修正模型，不允许先写大量章节再寻找存在理由。

仓库正式 `大纲.md` 只登记真实存在的可点击章节。分批生成时，完整规划保留在工作型蓝图中，每落地一章再同步正式大纲；不得制造空占位文件或死链接。仅排版模式不重新推导技术模型；第一遍改为内容账本，把现有信息单元映射到阅读阶段和目的位置。

## 先确定分类轴和模块变体矩阵

当一个专题同时具有 **公共概念/API** 与 **多个实现家族、配置分支或执行模型** 时，正文生成前必须先完成专题级分类，不能把不同轴上的名称混成一串“类型”，也不能直接选择一个变体纵向讲完整系统。

1. 先区分公共契约、保护域或语义 flavor、实现家族、执行模型、运行策略/优化、诊断设施等正交轴；同一个名称只能在它所属的轴上参与比较。
2. 分类坐标必须早于第一个变体内部实现。读者进入“抢占/非抢占”“轮询/中断”“同步/异步”等分支前，应已经知道哪些语义和模块共同存在、该分支只改变哪一轴。
3. 先建立公共概念、常用接口和一轮公共端到端骨架，再建立 **模块 × 变体矩阵**：行是能够独立学习的功能模块，列是公共职责、公共实现、各变体差量、源码/规范证据和对应实验。
4. 默认按模块推进：每个模块先讲概念、输入输出和公共职责，再比较变体怎样改变参与者、状态、通信、完成条件与成本。公共 GP、队列、拓扑、生命周期或错误处理不得在多个变体章节中各复制一遍。
5. 只有一个变体确实改变了大部分端到端参与者集合、证明方式、控制流和完成条件时，才允许为它建立完整纵向章节；若差异只落在一个或少数模块，就在对应模块内做并列比较。
6. 组合应用、对象生命周期、诊断与选型不能插入“公共接口 → 分类坐标 → 公共骨架”的必要前置链；它们在基础机制成立后进入各自阶段。
7. 实验既可以集中编排，也必须回链它所验证的具体概念或变体差异。不得在正文只写抽象结论、最后堆一个无法对应前文证明义务的实验目录。

全书蓝图必须能够回答：哪些内容跨变体保持不变，哪些只属于某个变体，为什么选择“按模块比较”或“按变体纵切”。如果两个变体章节都重复讲同一组公共执行者、状态载体和完整周期，说明专题主轴很可能选反，必须在写正文前重新设计。

## 为说明型章节固定建立读者入口

创建或补写概念、语法、接口、配置、源码导读等说明型章节时，不要在标题后直接罗列定义、字段、API 或分类表。先按以下顺序建立背景；这六步是内容契约，不要求机械写成六个同名标题：

1. **回收前置结论：** 说明读者已经从上一章、上层机制或常见实践中获得了什么有效认识，避免把既有知识写成错误。
2. **固定实际遭遇：** 选一段结构完整的代码、配置、日志、调用路径或操作现场，说明读者通常在哪里遇到本章主题以及当时正在完成什么任务。
3. **暴露剩余缺口：** 列出仅凭当前模型仍无法回答的具体问题，并解释按名称、表面语法或压缩结论猜测为什么会得出错误判断。
4. **定位本章层次：** 说明问题属于定义、语法、抽象机制、实现、运行时、诊断或工程流程中的哪一层，以及它与前后层怎样连接。
5. **限定讲解边界：** 明确本章只解决什么、不重复哪个权威专题、哪些问题有意留给下一章，防止背景演变成成熟术语总览。
6. **声明可检验结果：** 用读者完成后能执行的动作收束背景，例如能够手工展开、画出时间线、判断接口前置条件、定位状态地址或选择验证证据；随后正文继续复用同一场景和对象。

背景不是章节摘要，也不是“很重要、很复杂”式动机。完成入口后，读者应能回答“我为什么现在需要这一章、我要带着哪个现场往下读、读完后能多做哪一步”。若现有开头已经完整覆盖这三问，不重复添加第二份背景。

## 执行反形式主义与连续阅读硬门禁

创建、扩写或重写正文时，**要素齐全不等于章节合格**。不能因为文档已经包含场景、术语表、S0～Sn、Mermaid、源码链接、版本边界和核对表，就判定它完成了讲解。交付以前逐章执行以下硬门禁；任一项失败都必须继续修改，不能用“链接有效”“证据另有权威位置”或“专题其他章节已经讲过”抵消：

1. **标题契约：** 标题承诺“概念”“问题”“机制”“源码实现”“实验”或“导航”中的哪一种读者任务，正文就必须在本地兑现。标题包含“源码实现、源码讲解、源码机制”等承诺时，每个主要实现模块都要在当前章节解释实现原理、输入输出、关键状态和源码证据；如果正文只负责建立稳定模型或组织链接，应改用准确标题，不得让读者点入后才发现需要跳转。
2. **断链阅读：** 假设读者打印本文、隐藏 URL 且不点击任何链接，仍应能沿正文重建基础概念、背景问题、解决方案、关键状态转换和本章结论。链接只能验证、深化或进入唯一源码函数体，不能承担当个概念、模块职责或关键因果的首次解释。
3. **模块局部闭环：** 每个主要模块首次出现时，都要在本地完成“基础概念与类型定位 → 当前模块面对的问题 → 解决方案与状态/通信 → 留给读者的预测或反例 → 实现验证或源码证据”。这五项是内容闭环，不要求机械使用五个同名标题；不得先跨模块倾倒全部字段，再在后文反向解释。
4. **类型分层：** 在同一段、表格或全景图混用术语以前，先区分抽象概念、执行角色、状态载体、流程阶段、配置变体、优化分支和诊断机制。GP、GP 请求、GP kthread、`rcu_state`、SRS 和 stall 这类不同类型对象不能作为一组并列“概念”直接抛给读者。
5. **术语债清零：** 默认读者不认识专题私有术语。任何承担推理职责的缩写、专名、配置、源码符号或内部阶段名，在标题、正文、表格、图、代码、配置或日志中出现以前，都必须完成本章所需的中英文名称、类型、朴素含义、当前职责和边界对齐；解释不得继续依赖尚未对齐的词。术语未对齐以前，不得展开建立在这些词上的分类、比较或机制推理。
6. **主线优先：** 先选定一个默认配置和正常路径闭合主线；优化、版本差异、诊断、异常慢路径和其他执行模型只能在主线成立后作为分支出现。不得为了覆盖完整性打断本章正在解决的问题，也不得提前讲完下一章赖以产生认知悬念的反例。
7. **表示增量：** 第二张表、第二幅图或第二套阶段编号必须回答前一种表示无法回答的新问题。只把同一流程在时间线、位图表、关系图、阶段表、函数清单和证据表之间反复转写，属于形式堆叠，必须合并或删除。
8. **首屏与冷读验收：** 在源码文件清单、版本台账和密集链接以前，读者必须先知道“为什么现在读、正在追哪个现场、读完能完成什么”。审稿时由未参与写作的读者视角用五到八句话复述主线；如果必须点击链接、搜索后文或先理解测试编排器才能复述，章节不合格。
9. **标题层级不是装饰：** H2 不能只是去掉“第 N 章”后复述 H1，也不能在没有任何承上启下正文时直接进入下一个标题。空标题、标题回声和只为满足层级数量而建立的伞形小节必须改成真实阅读任务，或者删除并重新编号。

详细判据见 [references/topic-design.md](references/topic-design.md) 的“连续阅读与反形式主义验收”和 [references/review-checklist.md](references/review-checklist.md)。源码章节还必须执行 [references/source-evidence.md](references/source-evidence.md) 的“链接只能作证，不能代替讲解”。

## 零基础术语门禁：先对齐语言，再展开概念

把读者视为 **知道一般计算机常识、但尚未掌握当前专题私有词汇的小白**。不得因为术语出现在内核源码、官方文档、前一章、开发者日常交流或专题标题中，就假定读者已经理解。解释完整性和思考连续性优先于篇幅；术语太多时拆分章节或增加前置术语入口，不得用压缩解释换取短文。

写作前建立工作型 **术语依赖账本**，至少记录：原始写法、正式英文全称或名称性质、准确中文名、术语类型、朴素定义、当前场景职责、前置术语、易混项、版本/配置边界、首次出现位置和权威精确入口。按依赖顺序安排正文；一个定义只能使用已经对齐的词，若解释中又出现陌生术语，先递归解释它，不能用一串新黑话解释旧黑话。

“首次出现”包括 H1/H2 标题、Front Matter 标题以外的可见导航、正文、脚注、表格单元格、Mermaid 节点、图片说明、代码及注释、配置、命令、日志和错误消息。任何位置先抛出名称、后文才解释，都算 **先使用后定义**。每篇可以独立打开阅读的章节，都要重新完成本章第一次术语进入；不能只用“前文讲过”免除英文全称、中文名和一句本地提醒。

术语第一次承担推理职责时，按适用范围完成一张“进入卡”：

1. **名字：** 缩写使用“中文名（English Full Name，ABBR）”或同等明确形式，同时给出中文与英文全称；命令、项目、实现家族、历史昵称和源码标识符若不是缩写，明确说“这是专名/标识符，不存在可展开的英文全称”，不得杜撰词源。
2. **类型：** 说明它是抽象概念、公共契约、执行角色、状态载体、流程阶段、实现家族、执行模型、策略优化、诊断设施、配置项、源码宏/函数/字段、语言语法、文件格式、构建产物还是观察工具。不同类型不得未经说明放在同一层比较。
3. **朴素含义：** 先用不依赖本专题黑话的一两句话回答“它到底是什么”，再引入精确定义。类比只能辅助，不能代替定义和边界。
4. **当前职责：** 说明它为什么在本场景出现，读取或接收什么，写入、输出或改变什么，由谁拥有，在哪个事件或阶段生效。
5. **边界与易混项：** 说明它不能保证什么、最容易与谁混淆、二者按哪条分类轴区分；版本、架构或 Kconfig 会改变含义时立即标注。
6. **本地解释与深入入口：** 当前章节先写足以继续阅读的最小解释，再给正文内精确标题锚点、权威专题精确标题或官方资料。链接用于深入和取证，不得替代本地首次解释；本地一句话也不得冒充完整权威讲解。

同一小节需要连续引入多个陌生词时，在第一个词进入以前设置“本节术语入口”或按依赖分组的小段，逐个完成进入卡，再进入分类表、关系图或机制推演。表格和图中的每个私有名称要么已经在紧邻正文对齐，要么直接链接到 **完整标题锚点**；不得把术语表放在使用之后，也不得给出只到文件首页的模糊链接。

专题私有命名还必须解释命名主体和作用域：是谁定义的名称、它指向概念还是某个版本的对象/状态/实现、状态保存在哪里且归谁所有、与通用概念是什么关系。Tree、Tiny、Tasks、flavor、debt、epoch 之类看似普通的英文词，一旦在专题内取得特殊含义，就按专有名词处理，不能依赖读者猜词义。

只有在术语依赖已经清零以后，才能开始类型比较、因果推演、源码链或配置矩阵。交付时随机抽取标题、表格、图和代码中的名称做冷读测试：读者应能不搜索外部资料说出中英文名称或名称性质、所属类型、当前职责、边界和精确深入入口。自动审计只能找候选词和明显的首次出现风险，不能代替这项人工判断。

## 从全景、错误模型和动态过程建立理解

专题开端先说明“是什么、解决什么问题、位于系统何处、与谁交互”，再进入 API、寄存器、数据结构或源码。全景只建立坐标，不提前倾倒成熟实现的全部术语。

容易误解的关键机制按以下顺序展开：

```text
错误模型为什么看似成立
    → 在具体参与者、状态和时间线上出现什么矛盾
    → 只增加解决当前矛盾所需的模型增量
    → 用正确模型重新解释原场景
    → 说明仍未覆盖的条件与下一步
```

同一机制按需选择概念、数据结构、状态机、时间/时序、CPU/线程/中断、调用者、源码、硬件和工程部署视角。所有视角必须复用同一组关键对象、阶段和事件，不得写成互不连接的知识点清单。

关键结论必须展示动态过程：转换前状态、触发动作、中间传播、完成条件、转换后状态和失败分支。图是第二套表达系统，用于状态、时序、Before/After、层级、数据流、角色和生命周期；箭头标出动作或状态流，正文解释关键转折。不得用装饰图替代推导，Mermaid 换行使用 `<br/>`，不使用 `\n`。

每张 Mermaid `sequenceDiagram` 必须提供可定位的顺序编号，默认使用 `autonumber`；图后的关键转折说明必须引用这些步骤号，不只写“前面”、“之后”。两个方案、配置或失败/正常路径需要对比时，如果它们对“同一时刻是否发生了动作”、参与者集合或证明条件的结论不同，使用两张复用同一组对象名的独立时序图，并用颜色标出差量；只有两条路径真正共享同一条时间轴且 `alt` 不会造成事件已发生/未发生的歧义时，才在一张图内分支。

## 严格区分抽象层并建立映射

不得混淆定义与实现、API 契约与内部机制、逻辑状态与具体字段、软件同步与硬件一致性、协议保证与平台能力、稳定模型与版本源码。每次跨层都写清映射载体，例如抽象角色落到哪个任务或设备对象、逻辑状态落到哪个字段或寄存器、协议阶段由哪条调用链、消息、回调或中断推进。

先用机制解释为什么成立，再用规范、源码、实验、日志、trace、波形或基准证明当前实现怎样兑现。证据不足时标记推论和边界，不得用“大概如此”补齐。

## 按题型调整讲解顺序

- **数据结构与 API：** 在最小概念和契约成立后，尽早给出常用操作、最小正确用法、失败清理和典型模式，再进入内部结构、动态算法、实现证据和性能选择；涉及算法题时补充题型识别、朴素方案、优化动机、复杂度、隐藏边界、易错点和变形。
- **硬件、芯片与协议：** 从系统位置、参与设备和一次完整事务进入，再展开信号、时序、寄存器、控制器状态、驱动映射和板级约束；不得直接按数据手册目录复述。
- **内核机制与并发：** 从问题压力和抽象证明进入，闭合状态所有权、通信、完成通知和源码证据；并发机制至少提供角色/状态关系图与端到端时序图。
- **工程系统：** 同时纳入资源预算、构建产物、镜像或部署布局、启动流程、故障恢复、可观测性和验收；理论上正确但目标环境无法落地的方案不算完成。

## 区分产物职责

按产物立意保存结论；同版本的具体源码实现只展开一次：

| 层次 | 职责 |
| --- | --- |
| `knowledge/` | 跨版本稳定的机制、因果解释、API 契约和选择边界 |
| `research/source_reading/` | 精确版本、配置、源码路径、字段、函数和调用链 |
| `labs/` | 验证单一结论的最小可复现实验 |
| `platforms/` | 架构、SoC、BSP 或开发板特有行为 |
| `atlas/` 与专题 `大纲.md` | 阅读顺序与链接，不复制第二份教程 |
| `reference/` | 面向查询的 API、命令、术语或外部资料索引 |

动态验证器专题还要分别记录：被检查机制的真实功能状态、当前任务/CPU 的影子状态、跨时间累积的全局历史，以及检查器自身是否启用、递归抑制、容量耗尽或已经停检。检查事件可能发生在功能尝试以前或失败回退路径中，必须核对真实先后关系，不能仅从 `acquire`、`release` 等名称推断功能动作已经完成。

`knowledge/` 正文和 `research/source_reading/<topic>/navigation/` 模块概念导读可以围绕同一机制保留必要交叉，但不能互相替代：前者建立跨版本稳定的因果模型、接口契约和应用选择，后者面向特定版本组织源码入口、状态落点、函数协作和阅读顺序。不得把相同术语、状态阶段、调用链结论或必要背景直接判为重复，也不得因为编辑其中一层就自动删除、同步、合并或改写另一层。单一展开只约束同版本上游宏体、函数体和逐句实现说明；只有用户范围或链接、版本与事实边界明确同时影响两层时，才分别审查和独立修改两边。

在保留内容的结构调整或重写模式中，只有记录好目的位置后，才能移动通用硬件、编译器、内存顺序或对象生命周期解释。在仅排版模式中，可以按排版目标调整展示形式并增加权威链接，但不得改变技术语义或遗漏原有信息单元。

## 用模块概念导读和唯一实现讲解关联正文

知识章节依赖版本化内核源码时，建立“正文 → 总阅读索引 → 相关模块概念导读 → 具体实现讲解”和“正文中的具体接口 → 实现讲解具体标题”两条互补路径：

1. 同一源码专题同时具有概念阅读和实现讲解时，在 `research/source_reading/<topic>/` 下使用英文 `snake_case` 子目录：`navigation/` 保存一个总阅读索引以及按子功能或模块组织的源码概念导读，`source_explanations/` 只保存宏、字段和函数体的具体实现讲解。
2. 模块概念导读解释子功能目标、参与者、状态、调用链、阅读顺序和结论，可以使用应用场景代码、伪代码、表格和 Mermaid，但不展开上游宏体或函数体。实现讲解必须给出上游相对位置、明确标识为仓库补充的中文 Doxygen 阅读说明、带中文注释的裁剪源码、实现原理、调用上下文和状态副作用。
3. 正文与模块概念导读之间的概念交叉是有意的双视角，不参与源码实现去重，也不建立自动同步关系。审查时先判断两篇文档分别帮助读者完成什么任务，再判断是否真的重复了同版本实现；不得仅按术语、字段名、阶段名或调用链相似度跨层删改。
4. 一个宏、函数、字段或配置分支在同一版本边界内只选择一个权威源码讲解标题。多个知识正文或调用链遇到它时直接复用该标题，不得各自复制宏体和完整解释。相关接口可以按同一功能类聚合到一个可独立阅读的讲解文件，不为每个宏创建微型文件。
5. 知识正文开始使用版本化源码证据时链接 `navigation/` 中的总阅读索引和相关模块概念导读；演示代码附近再列出本章实际使用的接口或检查点，逐项说明作用、调用上下文和误用后果，并直接链接 `source_explanations/` 中的对应标题，不能只链接文件后让读者再次查找。
6. 模块概念导读只展开该子功能特有的状态位置、通信与时序。遇到具体宏、字段或函数体时保留精确链接，不重复源码块；权威实现讲解用关联入口表回链总索引、对应模块导读和知识场景。
7. “使用到的机制”必须区分功能路径与检查路径。例如把锁、状态转换、内存序、GP 和回调与 Sparse、Lockdep、debug objects、断言或告警分别标注；检查宏嵌入功能 API 时，说明检查开启/关闭后的展开以及动态检查的覆盖边界。
8. 稳定的接口语义、因果模型和选择边界只保存在 `knowledge/`；精确版本的宏体、字段、分支和行号只保存在 `research/source_reading/`。移动到职责子目录后同步更新所有调用方，不保留旧路径别名或兼容副本。
9. 更新专题大纲和源码基线入口，明确区分“总阅读索引”“模块概念导读”和“源码实现讲解”。总索引链接全部模块导读，模块导读精确链接用到的实现标题，实现文档回链对应模块导读和总索引；任何知识正文只要链接 `source_explanations/`，就必须同时提供 `navigation/` 阅读入口。
10. 用户要求“全量信息同步”时，按职责逐层审计专题大纲与相邻正文、父级大纲、总索引与模块导读、实现讲解关联入口、源码基线、Atlas 地图/路线/内容索引、仓库首页，以及真实存在的出版清单和 Obsidian 调用方。不能只搜索专题名，也不能把正文同步成互相镜像；应同步入口、版本/配置边界、实现所有权和受影响规则，并让面向阅读的入口尽量直达完整标题锚点。

锚点片段必须等于目标标题渲染后的完整文字，例如标题源码 `## 5.3\_rcu\_replace\_pointer接口实现` 对应 `source_explanations/P05_xxx.md#5.3_rcu_replace_pointer接口实现`。源码讲解标题避免 `()` 等会干扰 Markdown 链接解析的符号；标题变化时同步更新所有入链，并用结构审计验证目标标题真实存在。

需要建立或审查这种结构时，读取 [references/source-evidence.md](references/source-evidence.md) 的模块概念导读与唯一实现讲解规范。

## 保持跨章节阶段和数据结构可追踪

当下游章节放大上游章节已建立的完整周期、状态机、阶段表或功能模块时，不能只写“承接 PXX”。必须建立 **阶段回链**：

1. 上游阶段表若需被其他章节精确引用，将表按真实交接边界放在可稳定跳转的完整标题下；不依赖无标题锚点的单个表格行。
2. 下游章节如果为局部模块创建 R0～Rn、T0～Tn 等新编号，在第一次展开前给出“本地阶段 → 上游公共阶段”交叉表，每行链接到上游的完整标题锚点。
3. 正文、表格、图、源码和实验后续都复用这个交叉关系；不得让两套阶段各自推进，再要求读者自行对齐。

当数据结构、对象字段簇、寄存器块或协议头首次承担推理职责时，必须同时提供 **本地最小解释 + 独立结构入口**：本地先说明它是什么类型、由谁拥有、当前字段在本次交接中保存什么、谁写谁读；然后用完整标题锚点链接到权威的数据结构、状态机或版本化实现讲解。如果已有权威入口，直接复用，不复制结构体全字段；如果不存在，只在该结构可跨场景复用或本章无法局部闭环时创建独立讲解，不为每个字段制造微型文档。

## 建立因果学习链

设计新材料或在大纲中组织已有章节时使用本节。仅排版模式只改变阅读组织和展示形式，不重新论证或替换已审技术内容。

除非具体领域证明其他顺序更清楚，否则采用以下顺序：

1. **问题压力：** 展示真实负载、参与者、旧方案、旧方案提供的保证，以及暴露缺口的精确交错或规模。
2. **抽象推演：** 不使用 Linux 字段名，从约束推出角色、状态、时间边界和证明义务。
3. **最小闭环：** 抽象契约成立后尽早给出最小正确接口、正常路径、失败路径、清理和拆除，使后续实现讨论具有具体落点。
4. **分类坐标与公共骨架：** 存在多个家族或配置时，先区分正交轴，并只讲一次跨变体共享的角色、模块和完整周期。
5. **模型分化与加固：** 只有参与者集合或证明方式确实不同时才拆分执行模型；使用适用反例检验未来参与者、异步窗口、迁移、交叠、乱序和对象逃逸。
6. **模块实现与变体差量：** 把抽象状态按功能模块映射到地址、所有者、写入者、读取者、通信和完成条件；先公共实现，再比较变体差量，只为真正独立的子状态机或实现家族拆篇。
7. **应用、实验与选择：** 给出组合方式、诊断方法、可观察实验、误用、成本转移和替代条件，说明何时原方案仍更合适。
8. **证据与导航：** 按职责保存稳定知识、带版本源码、实验和平台证据，更新大纲、上一篇/下一篇链接、稳定 ID 和仓库检查。

保持认知悬念链：先复述已经成立的结论，再提出它无法解释的一个具体问题；用反例暴露缺少的状态维度，只增加解决本轮反例所需的角色、状态、通信路径或约束；随后用源码或实验兑现新增模型，并把尚未解决的问题交给下一章。不得在问题尚未出现时一次性展示成熟机制的全部字段和术语。

章节开头优先交代“上一章已经证明什么 → 仍然无法解释什么 → 本章只解决什么”，结尾交代“现在可以证明什么 → 仍然不能解释什么 → 下一章继续追踪什么”。这是思维桥接，不要求机械使用相同小节标题。

不要强迫所有阶段进入一个文件。如果一篇文档承担多个可独立学习的机制，或者源码细节打断因果解释，应拆分文档。只有确实承担连续性职责时，才保留短桥接文档。

## 让承担证明的章节从具体场景写起

创作或重写内容时使用本节。在仅排版模式中，保留已审场景的技术语义，只显化其顺序和关系。

讲理论前先建立：

- 有名称的负载及其规模；
- 具体任务、CPU、中断、线程、回调或设备；
- 共享状态的存储位置；
- 足以固定问题现场的真实或结构完整代码路径；
- 预期交错和可观察故障；
- 需要保护的正确性属性。

随后解释解决该场景的理论。完整应用代码必须覆盖分配、发布、错误清理、拆除流程和关键竞态语句；问题章中的最小现场代码不必提前承担最终 API 模板的全部职责。

## 把完整实例写成可以验收的小闭环

只有代码块不构成“完整实例”。用户要求完整、具体、可运行或足以讲清用途的实例时，至少闭合以下内容：

1. **需求背景：** 谁在什么任务中遇到什么限制，为什么需要当前语法、宏、接口或机制；
2. **环境与边界：** 语言/内核/工具版本、配置和运行上下文；说明是上游原样代码、结构完整的教学代码还是只固定问题的现场片段；
3. **输入与准备：** 必要类型、状态、初始化、调用入口和测试数据，不让关键对象凭空出现；
4. **正常与失败路径：** 展示成功动作、至少一个与主题相关的失败或错误用法，以及配套的回滚、清理、释放或退出；
5. **逐步过程：** 展开关键宏、调用链、状态变化、求值次数或产物流，让结论能从过程推出；
6. **观察与验收：** 给出可执行命令或明确观察位置、预期输出/诊断/状态，并解释结果证明什么；
7. **证明边界：** 说明该实例不能证明什么、哪些平台或配置需要另行验证，并链接权威实现或规范。

示例复杂度按主题裁剪，但不能省略恰好决定正确性的语句。孤立函数、只有声明没有调用者、只有成功路径没有清理、只有命令没有预期结果、只展示宏定义却不展开调用位置，均不得标为完整实例。若本章只需要一段最小现场，应明确称为“现场片段”或“裁剪示例”，并链接已经闭环的完整实例。

并发或多角色机制专题整体至少包含：

- 一张角色/状态关系图，箭头标明状态或所有权流；
- 一张端到端时序图，覆盖正常路径和改变状态归属的关键分支；
- 对完整状态机制复用同一组 S0、S1……周期，并用阶段表说明；
- 明确区分安全性和活性；
- 解释被移除成本的去向和选择边界。

图表按证明需要放入相应章节，不要求每篇各自凑齐一套。

Mermaid 换行使用 `<br/>`，不得使用 `\n`。

## 显式建模分布式状态

先说明机制是单一状态机，还是由多个正交状态轴组成。区分当前状态、已经锁存的历史事件、绑定操作周期的代际证据以及仍未清偿的等待债务。每个阶段都记录：

| 必备事实 | 必须回答的问题 |
| --- | --- |
| 触发条件 | 什么事件使机制进入本阶段？ |
| 转换前后 | 哪个精确状态发生了什么变化？ |
| 存储位置 | 状态位于哪个结构、任务、per-CPU 区域、节点、对象或全局地址？ |
| 写入者 | 哪个执行上下文完成写入？ |
| 读取者 | 后续哪条路径消费该状态？ |
| 通信方式 | 本地写、共享内存、锁、轮询、回调、唤醒、IPI 还是分层上报？ |
| 退出条件 | 满足什么条件才能进入下一阶段？ |

始终闭合以下三个回路：

1. 状态所有权变化时，本地状态如何变成共享状态；
2. 局部证据如何汇聚为全局结论；
3. 等待方或延迟动作如何得知结论已经完成。

明确说明机制采用直接登记/通知，还是通过“不变量 + 已观察事件”间接证明参与者已经越过边界。未来参与者为什么不属于当前集合，必须由入口、代际或协议边界证明。

快路径移除全局登记或通知时，要说明被转移的工作分别怎样出现在正常的每操作路径、特殊状态转移路径以及延迟或强制路径中。

## 将结论映射到源码，但不以源码替代解释

使用 `rg` 追踪定义、调用者、配置分支和状态写入。通用机制优先检查上游公共目录。只有结论依赖指令、屏障、异常入口、缓存维护、页表或其他体系结构契约时，才检查架构代码。

每项重要源码结论都记录：

- 内核版本和相关 `.config` 选项；
- 上游相对源码路径；
- 结构体和字段；
- 函数及调用者/被调用者关系；
- 函数执行前后的状态；
- 执行上下文以及锁、抢占和 IRQ 约束；
- 该结论属于稳定契约、实现细节还是平台特有事实。

## 建立源码符号覆盖账本并面向修改能力验收

进入 `research/source_reading/<topic>/source_explanations/` 后，目标不再只是用源码印证机制，而是让读者能够继续追踪并安全修改实现。采用 **无沉默符号** 规则：源码摘录、调用链、阶段表或流程图中出现且会影响控制流、状态、同步、配置或生命周期的结构体、字段、全局对象、宏、函数和关键参数，必须满足以下三者之一：

1. 在当前唯一实现标题下解释完整；
2. 使用 Typora 精确标题锚点链接到已有权威实现讲解；
3. 明确标为与本轮结论无关的机械语句或已裁剪区间，并说明为什么可以省略。

先按 **实现所有权** 决定修改位置。通用框架的数据结构、算法和查询在框架专题唯一展开；子系统专题只展开自己的实例、初始化参数、事件接入、调用时序、配置退化和消费场景，并精确链接框架实现。不得因为对象类型属于另一个专题就省略本实例在当前子系统中的角色，也不得把框架核心复制到每个调用方专题。

不得让 `extern` 声明、静态 key、全局实例、初始化器、配置退化分支、辅助包装、回调上下文标记或检查器对象只出现在代码块中而没有正文解释。名称看似直观、对象不直接改变功能状态、或其他专题已经讲过同一类型，都不能成为跳过本实例角色和调用位置的理由。

编辑前建立源码符号覆盖账本，至少记录：

| 符号或实现簇 | 必须回答的问题 |
| --- | --- |
| 实现所有权 | 通用框架还是当前子系统负责展开，交叉边界链接到哪个唯一标题？ |
| 声明与定义 | 在哪个头文件声明、哪个实现文件定义，谁需要跨翻译单元访问？ |
| 身份与初始化 | 初值来自静态初始化、启动路径还是首次使用；key、名称和生命期怎样确定？ |
| 写入与读取 | 哪条路径修改或登记状态，哪条路径查询、消费或清除？ |
| 调用与时序 | 位于功能动作之前还是之后；失败、嵌套、回退和异步窗口怎样配对？ |
| 配置展开 | 相关 Kconfig 开启与关闭时对象、宏、函数和返回值分别怎样变化？ |
| 状态副作用 | 修改的是功能状态、检查器影子状态、历史状态还是诊断生命状态？ |
| 修改边界 | 改字段、初始化器、调用顺序或配置分支时，哪些不变量、调用方和测试必须同步？ |
| 讲解位置 | 当前标题、其他权威标题或有理由的裁剪说明位于哪里？ |

源码实现讲解至少提供一张能定位对象关系与状态地址的图，以及一张覆盖进入、状态登记或修改、消费、退出/回滚的端到端时序图；简单叶函数只有在上级实现簇的图已经完整覆盖时才可复用，不得让图只停留在抽象机制层。图、源码摘录、状态表和文字必须使用同一组具体符号。

每个实现簇在“实现原理”之后增加可修改性说明，回答：当前代码依赖哪些不变量，最小安全修改点在哪里，改动后必须同步检查哪些配置分支、调用点、异常路径、配对动作和可观察验证。只有读者能够从声明追到定义、从初始化追到消费、从正常路径追到退化/回滚路径，并能预测一次局部修改的影响范围，源码讲解才算完成。

不得修改外部内核源码树。源码树不可用时，明确标记源码核对未完成，不得凭记忆重建细节。旧版本差异必须定位到精确字段或调用链边界，不得使用含糊的兼容性结论。

## 单独处理对象生命周期

区分发布可达性、临时受保护访问、长期所有权、宽限期完成、回调执行和最终内存销毁。在组合 RCU、kref/refcount、锁、工作队列或模块拆除前，先画出分配与所有权关系图。

每次分配只能有一个最终销毁协议。不得暗示彼此独立的机制会自动通知或适配。明确由哪个模块回调把控制权从一种机制交给下一种机制。

## 干净重构

章节顺序或路径发生变化时：

1. 先记录所选编辑模式和内容基线；
2. 移动前盘点每个 H2/H3 章节、代码块、图表、表格、实验、检查清单和链接；
3. 将每个属于保留范围的内容单元映射到一个目的位置，不得因为另一段内容看起来相似就删除；
4. 仅排版模式保留文件身份、技术语义和全部信息单元；允许记录在案的机械排版变化，不要求字节或正文行绝对不变；
5. 保留内容的结构调整模式完整移动单元，除非桥接内容必须变化，否则保留原措辞；
6. 内容修改或重写模式只修改明确授权的内容；
7. 更新专题大纲和上一篇/下一篇导航链；
8. 更新 Markdown、Obsidian、Atlas、出版清单、源码映射和其他真实调用方；全量信息同步时使用上面的分层审计矩阵，并记录不存在的调用方为无须修改；
9. 全仓搜索旧文件名和旧 ID；
10. 确认没有覆盖无关脏文件或已审内容。

编辑使用 `apply_patch`。除非用户明确要求，不得暂存、提交，也不得修改外部源码树。

```text
python <skill-dir>/scripts/audit_topic.py <topic-directory> --repo-root <repository-root>
```


随后运行术语首次出现审计，取得缩写、配置名和反引号源码标识符的候选账本：

```text
python <skill-dir>/scripts/audit_terminology_onboarding.py <chapter.md> --strict
```

该脚本只检查可机械识别的候选词、首次出现位置和附近是否具有中英文展开或名称类型信号；它看不懂术语是否解释正确，也无法发现所有专题私有昵称。严格模式报告的问题必须补齐，或者逐项给出“为何不是术语、为何当前窗口已经完成进入卡”的具体理由。脚本通过以后仍要人工检查定义是否夹带未解释词，以及表格、图、代码和日志中的私有名称是否全部进入。

对具有干净 Git 基线的仅排版任务，还要运行内置内容守恒审计：

```text

```

如果任务开始时已有未提交的审定材料，应另行保存修改前快照或内容账本，因为仅使用 `HEAD` 不能代表该基线。记录修改前后的行数、标题数、代码围栏数、表格数和 Mermaid 图数，并证明每个属于保留范围的内容单元都有目的位置。内容守恒脚本执行严格的行级对比：失败表示存在需要人工核对的差异，不自动等同于技术内容丢失。排版必需的机械变化可以逐项说明并接受；超出授权的语义变化、无法解释的信息减少或遗漏才视为错误。随后在运行环境可用时，执行仓库自身的格式化、元数据/链接检查、针对性构建或实验编译，以及 `git diff --check`。条件允许时使用仓库渲染器解析 Mermaid。只有源码证据属于本次范围时才检查源码副本哈希。

所需环境不可用时，完成全部安全的静态检查，并准确报告未执行验证及其原因。不得把未编译的实验或未渲染的图表描述为已执行。
