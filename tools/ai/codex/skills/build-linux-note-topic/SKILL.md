# 构建 linux-note 技术书籍与专题

构建可长期维护、可验证并能支持继续推理的知识体系，而不是一次性长回答。按读者认知路径组织材料，始终区分稳定知识、带版本的源码证据、实验、平台差异和导航。

## 先确定编辑授权

编辑前选择并说明以下一种模式：

1. **仅排版（layout-only）：** 适用于用户明确要求格式、导航、编号、阅读地图或“参照某专题风格”，尤其是材料已经审稿的情况。保留技术语义、信息量、代码语义、图表含义、实验和检查项；允许调整标题编号、空白、列表、表格、导航、锚点以及其他排版所需的机械表达。用户没有要求时，不新增论证、源码研究或实验。
2. **保留内容的结构调整（structure-preserving）：** 适用于用户明确要求拆分、合并、移动或重排的情况。盘点每个已审内容单元，完整移动，不得缩写。
3. **内容修改或重写（rewrite）：** 适用于用户明确要求补充、纠错、扩写、优化、重写、压缩、去重、替换或删除的情况。材料是否经过审稿不构成永久禁止修改；修改范围不得超出本次授权。

单独出现“重构”既不自动选择重写模式，也不自动选择仅排版模式。应结合“已审稿”“只排版”“补充内容”“重写”等限定语判断；如果不同选择会实质改变结果且上下文无法确定，先确认再改动技术语义。文件很长、规则重复、目标结构更整洁或通用审计出现警告，都不构成删除授权。

## 以仓库事实为起点

1. 阅读当前仓库的 `AGENTS.md`、根 `README.md`、信息架构文档、目标专题大纲和 Git 规范。
2. 编辑前检查 `git status`。将任务开始时的目标工作树作为内容基线，记录已提交和未提交的材料；是否修改其技术内容由本次用户授权决定。
3. 只有新增或修改证据结论时，才定位对应规范、芯片手册、源码树或实验环境并验证身份；涉及外部 Linux 源码时，按照当前仓库说明重新发现和核对版本。
4. 盘点目标目录、入链、出链、文档 ID、出版清单、Atlas 入口、Obsidian 产物和相关权威专题。
5. 在仅排版模式中，盘点并组织已有问题场景，不得用新编场景替换原场景，也不得改变其技术结论。在内容创作模式中，先明确读者需要重建的具体问题。

开始创建、扩写或重组专题前，按顺序读取 [references/topic-design.md](references/topic-design.md) 和 [references/repository-topic-requirements.md](references/repository-topic-requirements.md)：先建立技术书籍的认知路径，再选择仓库题型骨架和章节角色，不得机械叠加 P01～P05 的历史模板。分析并发、异步、生命周期或多角色状态机制时，读取 [references/mechanism-reasoning.md](references/mechanism-reasoning.md)。把结论映射到 Linux 源码前，读取 [references/source-evidence.md](references/source-evidence.md)。需要理解本地 RCU 专题怎样落实阅读地图时，使用 [references/rcu-case-study.md](references/rcu-case-study.md)；涉及 Lockdep、KCSAN、debug objects、sanitizer、断言或其他动态检查器时，再使用 [references/lockdep-case-study.md](references/lockdep-case-study.md)。案例用于校正方法，不提供固定篇数或字段模板。交付前使用 [references/review-checklist.md](references/review-checklist.md)。

## 先设计再生成

新建、扩写或重写专题时执行两遍生成，先完成全书设计再开始正文：

1. 第一遍建立工作型专题蓝图，明确读者起点与结果、系统全景、贯穿场景、问题链、错误模型、动态过程、观察视角、层次映射、工程约束和证据计划；
2. 按题型选择章节职责，建立完整章节依赖图和每章契约，确保每章都回答“为何现在讲、承接什么、只解决什么、留下什么”；
3. 第二遍才按依赖图生成正文，允许证据不足反向修正模型，不允许先写大量章节再寻找存在理由。

仓库正式 `大纲.md` 只登记真实存在的可点击章节。分批生成时，完整规划保留在工作型蓝图中，每落地一章再同步正式大纲；不得制造空占位文件或死链接。仅排版模式不重新推导技术模型；第一遍改为内容账本，把现有信息单元映射到阅读阶段和目的位置。

## 从全景、错误模型和动态过程建立理解

专题开端先说明“是什么、解决什么问题、位于系统何处、与谁交互”，再进入 API、寄存器、数据结构或源码。全景只建立坐标，不提前倾倒成熟实现的全部术语。

容易误解的关键机制按以下顺序展开：

```text
错误模型为什么看似成立
    → 在具体参与者、状态和时间线上出现什么矛盾
    → 只增加解决当前矛盾所需的模型增量
    → 用正确模型重新解释原场景
    → 说明仍未覆盖的条件与下一步
```

同一机制按需选择概念、数据结构、状态机、时间/时序、CPU/线程/中断、调用者、源码、硬件和工程部署视角。所有视角必须复用同一组关键对象、阶段和事件，不得写成互不连接的知识点清单。

关键结论必须展示动态过程：转换前状态、触发动作、中间传播、完成条件、转换后状态和失败分支。图是第二套表达系统，用于状态、时序、Before/After、层级、数据流、角色和生命周期；箭头标出动作或状态流，正文解释关键转折。不得用装饰图替代推导，Mermaid 换行使用 `<br/>`，不使用 `\n`。

## 严格区分抽象层并建立映射

不得混淆定义与实现、API 契约与内部机制、逻辑状态与具体字段、软件同步与硬件一致性、协议保证与平台能力、稳定模型与版本源码。每次跨层都写清映射载体，例如抽象角色落到哪个任务或设备对象、逻辑状态落到哪个字段或寄存器、协议阶段由哪条调用链、消息、回调或中断推进。

先用机制解释为什么成立，再用规范、源码、实验、日志、trace、波形或基准证明当前实现怎样兑现。证据不足时标记推论和边界，不得用“大概如此”补齐。

## 按题型调整讲解顺序

- **数据结构与 API：** 在最小概念和契约成立后，尽早给出常用操作、最小正确用法、失败清理和典型模式，再进入内部结构、动态算法、实现证据和性能选择；涉及算法题时补充题型识别、朴素方案、优化动机、复杂度、隐藏边界、易错点和变形。
- **硬件、芯片与协议：** 从系统位置、参与设备和一次完整事务进入，再展开信号、时序、寄存器、控制器状态、驱动映射和板级约束；不得直接按数据手册目录复述。
- **内核机制与并发：** 从问题压力和抽象证明进入，闭合状态所有权、通信、完成通知和源码证据；并发机制至少提供角色/状态关系图与端到端时序图。
- **工程系统：** 同时纳入资源预算、构建产物、镜像或部署布局、启动流程、故障恢复、可观测性和验收；理论上正确但目标环境无法落地的方案不算完成。

## 区分产物职责

按产物立意保存结论；同版本的具体源码实现只展开一次：

| 层次 | 职责 |
| --- | --- |
| `knowledge/` | 跨版本稳定的机制、因果解释、API 契约和选择边界 |
| `research/source_reading/` | 精确版本、配置、源码路径、字段、函数和调用链 |
| `labs/` | 验证单一结论的最小可复现实验 |
| `platforms/` | 架构、SoC、BSP 或开发板特有行为 |
| `atlas/` 与专题 `大纲.md` | 阅读顺序与链接，不复制第二份教程 |
| `reference/` | 面向查询的 API、命令、术语或外部资料索引 |

动态验证器专题还要分别记录：被检查机制的真实功能状态、当前任务/CPU 的影子状态、跨时间累积的全局历史，以及检查器自身是否启用、递归抑制、容量耗尽或已经停检。检查事件可能发生在功能尝试以前或失败回退路径中，必须核对真实先后关系，不能仅从 `acquire`、`release` 等名称推断功能动作已经完成。

`knowledge/` 正文和 `research/source_reading/<topic>/navigation/` 模块概念导读可以围绕同一机制保留必要交叉，但不能互相替代：前者建立跨版本稳定的因果模型、接口契约和应用选择，后者面向特定版本组织源码入口、状态落点、函数协作和阅读顺序。不得把相同术语、状态阶段、调用链结论或必要背景直接判为重复，也不得因为编辑其中一层就自动删除、同步、合并或改写另一层。单一展开只约束同版本上游宏体、函数体和逐句实现说明；只有用户范围或链接、版本与事实边界明确同时影响两层时，才分别审查和独立修改两边。

在保留内容的结构调整或重写模式中，只有记录好目的位置后，才能移动通用硬件、编译器、内存顺序或对象生命周期解释。在仅排版模式中，可以按排版目标调整展示形式并增加权威链接，但不得改变技术语义或遗漏原有信息单元。

## 用模块概念导读和唯一实现讲解关联正文

知识章节依赖版本化内核源码时，建立“正文 → 总阅读索引 → 相关模块概念导读 → 具体实现讲解”和“正文中的具体接口 → 实现讲解具体标题”两条互补路径：

1. 同一源码专题同时具有概念阅读和实现讲解时，在 `research/source_reading/<topic>/` 下使用英文 `snake_case` 子目录：`navigation/` 保存一个总阅读索引以及按子功能或模块组织的源码概念导读，`source_explanations/` 只保存宏、字段和函数体的具体实现讲解。
2. 模块概念导读解释子功能目标、参与者、状态、调用链、阅读顺序和结论，可以使用应用场景代码、伪代码、表格和 Mermaid，但不展开上游宏体或函数体。实现讲解必须给出上游相对位置、明确标识为仓库补充的中文 Doxygen 阅读说明、带中文注释的裁剪源码、实现原理、调用上下文和状态副作用。
3. 正文与模块概念导读之间的概念交叉是有意的双视角，不参与源码实现去重，也不建立自动同步关系。审查时先判断两篇文档分别帮助读者完成什么任务，再判断是否真的重复了同版本实现；不得仅按术语、字段名、阶段名或调用链相似度跨层删改。
4. 一个宏、函数、字段或配置分支在同一版本边界内只选择一个权威源码讲解标题。多个知识正文或调用链遇到它时直接复用该标题，不得各自复制宏体和完整解释。相关接口可以按同一功能类聚合到一个可独立阅读的讲解文件，不为每个宏创建微型文件。
5. 知识正文开始使用版本化源码证据时链接 `navigation/` 中的总阅读索引和相关模块概念导读；演示代码附近再列出本章实际使用的接口或检查点，逐项说明作用、调用上下文和误用后果，并直接链接 `source_explanations/` 中的对应标题，不能只链接文件后让读者再次查找。
6. 模块概念导读只展开该子功能特有的状态位置、通信与时序。遇到具体宏、字段或函数体时保留精确链接，不重复源码块；权威实现讲解用关联入口表回链总索引、对应模块导读和知识场景。
7. “使用到的机制”必须区分功能路径与检查路径。例如把锁、状态转换、内存序、GP 和回调与 Sparse、Lockdep、debug objects、断言或告警分别标注；检查宏嵌入功能 API 时，说明检查开启/关闭后的展开以及动态检查的覆盖边界。
8. 稳定的接口语义、因果模型和选择边界只保存在 `knowledge/`；精确版本的宏体、字段、分支和行号只保存在 `research/source_reading/`。移动到职责子目录后同步更新所有调用方，不保留旧路径别名或兼容副本。
9. 更新专题大纲和源码基线入口，明确区分“总阅读索引”“模块概念导读”和“源码实现讲解”。总索引链接全部模块导读，模块导读精确链接用到的实现标题，实现文档回链对应模块导读和总索引；任何知识正文只要链接 `source_explanations/`，就必须同时提供 `navigation/` 阅读入口。
10. 用户要求“全量信息同步”时，按职责逐层审计专题大纲与相邻正文、父级大纲、总索引与模块导读、实现讲解关联入口、源码基线、Atlas 地图/路线/内容索引、仓库首页，以及真实存在的出版清单和 Obsidian 调用方。不能只搜索专题名，也不能把正文同步成互相镜像；应同步入口、版本/配置边界、实现所有权和受影响规则，并让面向阅读的入口尽量直达完整标题锚点。

锚点片段必须等于目标标题渲染后的完整文字，例如标题源码 `## 5.3\_rcu\_replace\_pointer接口实现` 对应 `source_explanations/P05_xxx.md#5.3_rcu_replace_pointer接口实现`。源码讲解标题避免 `()` 等会干扰 Markdown 链接解析的符号；标题变化时同步更新所有入链，并用结构审计验证目标标题真实存在。

需要建立或审查这种结构时，读取 [references/source-evidence.md](references/source-evidence.md) 的模块概念导读与唯一实现讲解规范。

## 建立因果学习链

设计新材料或在大纲中组织已有章节时使用本节。仅排版模式只改变阅读组织和展示形式，不重新论证或替换已审技术内容。

除非具体领域证明其他顺序更清楚，否则采用以下顺序：

1. **问题压力：** 展示真实负载、参与者、旧方案、旧方案提供的保证，以及暴露缺口的精确交错或规模。
2. **抽象推演：** 不使用 Linux 字段名，从约束推出角色、状态、时间边界和证明义务。
3. **最小闭环：** 抽象契约成立后尽早给出最小正确接口、正常路径、失败路径、清理和拆除，使后续实现讨论具有具体落点。
4. **模型分化与加固：** 只有参与者集合或证明方式确实不同时才拆分执行模型；使用适用反例检验未来参与者、异步窗口、迁移、交叠、乱序和对象逃逸。
5. **Linux 实现：** 把抽象状态映射到地址、所有者、写入者、读取者、触发条件、通信路径和完成条件；分层机制先建立统一状态与通信全景。
6. **实现纵深与变体：** 只为足以独立学习的子状态机和真实实现家族拆篇，并回指同一操作周期。
7. **应用与选择：** 给出组合方式、诊断方法、误用、成本转移和替代条件，说明何时原方案仍更合适。
8. **证据与导航：** 按职责保存稳定知识、带版本源码、实验和平台证据，更新大纲、上一篇/下一篇链接、稳定 ID 和仓库检查。

保持认知悬念链：先复述已经成立的结论，再提出它无法解释的一个具体问题；用反例暴露缺少的状态维度，只增加解决本轮反例所需的角色、状态、通信路径或约束；随后用源码或实验兑现新增模型，并把尚未解决的问题交给下一章。不得在问题尚未出现时一次性展示成熟机制的全部字段和术语。

章节开头优先交代“上一章已经证明什么 → 仍然无法解释什么 → 本章只解决什么”，结尾交代“现在可以证明什么 → 仍然不能解释什么 → 下一章继续追踪什么”。这是思维桥接，不要求机械使用相同小节标题。

不要强迫所有阶段进入一个文件。如果一篇文档承担多个可独立学习的机制，或者源码细节打断因果解释，应拆分文档。只有确实承担连续性职责时，才保留短桥接文档。

## 让承担证明的章节从具体场景写起

创作或重写内容时使用本节。在仅排版模式中，保留已审场景的技术语义，只显化其顺序和关系。

讲理论前先建立：

- 有名称的负载及其规模；
- 具体任务、CPU、中断、线程、回调或设备；
- 共享状态的存储位置；
- 足以固定问题现场的真实或结构完整代码路径；
- 预期交错和可观察故障；
- 需要保护的正确性属性。

随后解释解决该场景的理论。完整应用代码必须覆盖分配、发布、错误清理、拆除流程和关键竞态语句；问题章中的最小现场代码不必提前承担最终 API 模板的全部职责。

并发或多角色机制专题整体至少包含：

- 一张角色/状态关系图，箭头标明状态或所有权流；
- 一张端到端时序图，覆盖正常路径和改变状态归属的关键分支；
- 对完整状态机制复用同一组 S0、S1……周期，并用阶段表说明；
- 明确区分安全性和活性；
- 解释被移除成本的去向和选择边界。

图表按证明需要放入相应章节，不要求每篇各自凑齐一套。

Mermaid 换行使用 `<br/>`，不得使用 `\n`。

## 显式建模分布式状态

先说明机制是单一状态机，还是由多个正交状态轴组成。区分当前状态、已经锁存的历史事件、绑定操作周期的代际证据以及仍未清偿的等待债务。每个阶段都记录：

| 必备事实 | 必须回答的问题 |
| --- | --- |
| 触发条件 | 什么事件使机制进入本阶段？ |
| 转换前后 | 哪个精确状态发生了什么变化？ |
| 存储位置 | 状态位于哪个结构、任务、per-CPU 区域、节点、对象或全局地址？ |
| 写入者 | 哪个执行上下文完成写入？ |
| 读取者 | 后续哪条路径消费该状态？ |
| 通信方式 | 本地写、共享内存、锁、轮询、回调、唤醒、IPI 还是分层上报？ |
| 退出条件 | 满足什么条件才能进入下一阶段？ |

始终闭合以下三个回路：

1. 状态所有权变化时，本地状态如何变成共享状态；
2. 局部证据如何汇聚为全局结论；
3. 等待方或延迟动作如何得知结论已经完成。

明确说明机制采用直接登记/通知，还是通过“不变量 + 已观察事件”间接证明参与者已经越过边界。未来参与者为什么不属于当前集合，必须由入口、代际或协议边界证明。

快路径移除全局登记或通知时，要说明被转移的工作分别怎样出现在正常的每操作路径、特殊状态转移路径以及延迟或强制路径中。

## 将结论映射到源码，但不以源码替代解释

使用 `rg` 追踪定义、调用者、配置分支和状态写入。通用机制优先检查上游公共目录。只有结论依赖指令、屏障、异常入口、缓存维护、页表或其他体系结构契约时，才检查架构代码。

每项重要源码结论都记录：

- 内核版本和相关 `.config` 选项；
- 上游相对源码路径；
- 结构体和字段；
- 函数及调用者/被调用者关系；
- 函数执行前后的状态；
- 执行上下文以及锁、抢占和 IRQ 约束；
- 该结论属于稳定契约、实现细节还是平台特有事实。

不得修改外部内核源码树。源码树不可用时，明确标记源码核对未完成，不得凭记忆重建细节。旧版本差异必须定位到精确字段或调用链边界，不得使用含糊的兼容性结论。

## 单独处理对象生命周期

区分发布可达性、临时受保护访问、长期所有权、宽限期完成、回调执行和最终内存销毁。在组合 RCU、kref/refcount、锁、工作队列或模块拆除前，先画出分配与所有权关系图。

每次分配只能有一个最终销毁协议。不得暗示彼此独立的机制会自动通知或适配。明确由哪个模块回调把控制权从一种机制交给下一种机制。

## 干净重构

章节顺序或路径发生变化时：

1. 先记录所选编辑模式和内容基线；
2. 移动前盘点每个 H2/H3 章节、代码块、图表、表格、实验、检查清单和链接；
3. 将每个属于保留范围的内容单元映射到一个目的位置，不得因为另一段内容看起来相似就删除；
4. 仅排版模式保留文件身份、技术语义和全部信息单元；允许记录在案的机械排版变化，不要求字节或正文行绝对不变；
5. 保留内容的结构调整模式完整移动单元，除非桥接内容必须变化，否则保留原措辞；
6. 内容修改或重写模式只修改明确授权的内容；
7. 更新专题大纲和上一篇/下一篇导航链；
8. 更新 Markdown、Obsidian、Atlas、出版清单、源码映射和其他真实调用方；全量信息同步时使用上面的分层审计矩阵，并记录不存在的调用方为无须修改；
9. 全仓搜索旧文件名和旧 ID；
10. 确认没有覆盖无关脏文件或已审内容。

编辑使用 `apply_patch`。除非用户明确要求，不得暂存、提交，也不得修改外部源码树。

## 交付前验证

先运行内置结构审计：

```text
python <skill-dir>/scripts/audit_topic.py <topic-directory> --repo-root <repository-root>
```

对具有干净 Git 基线的仅排版任务，还要运行内置内容守恒审计：

```text
python <skill-dir>/scripts/audit_content_conservation.py <topic-directory> --repo-root <repository-root> --baseline <baseline-ref>
```

如果任务开始时已有未提交的审定材料，应另行保存修改前快照或内容账本，因为仅使用 `HEAD` 不能代表该基线。记录修改前后的行数、标题数、代码围栏数、表格数和 Mermaid 图数，并证明每个属于保留范围的内容单元都有目的位置。内容守恒脚本执行严格的行级对比：失败表示存在需要人工核对的差异，不自动等同于技术内容丢失。排版必需的机械变化可以逐项说明并接受；超出授权的语义变化、无法解释的信息减少或遗漏才视为错误。随后在运行环境可用时，执行仓库自身的格式化、元数据/链接检查、针对性构建或实验编译，以及 `git diff --check`。条件允许时使用仓库渲染器解析 Mermaid。只有源码证据属于本次范围时才检查源码副本哈希。

所需环境不可用时，完成全部安全的静态检查，并准确报告未执行验证及其原因。不得把未编译的实验或未渲染的图表描述为已执行。
