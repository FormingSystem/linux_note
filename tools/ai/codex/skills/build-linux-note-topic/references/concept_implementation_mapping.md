# 概念到实现的映射与输入输出

本参考用于规范与产品、契约与源码、逻辑对象与实际载体之间的转换。重点是让读者重建对应关系，而不是多记一套名称。简单的同层事实不必套用完整表图；存在共享、分散实现或包含/连接歧义时，必须在正文就地展开。

## 先固定概念，再引入实现

概念阶段回答“必须有哪些职责、状态、输入输出和保证”，实现阶段回答“谁用什么载体与路径兑现这些职责”。按以下顺序推进：

1. 从当前问题建立概念，选定规范或契约及其版本，使用该层正式术语；说明对象按核、任务、队列、连接还是其他单位计数。
2. 引入选定产品、软件实现或集成实例，交代它所属层次及版本。实现名称首次出现就说明它是哪类对象，不能只给别名。
3. 在使用实现名称解释功能以前，把已建立的职责与状态逐项放到实际载体上，说明数量、归属和连接。
4. 复用概念阶段的同一场景，沿配置和运行过程证明映射怎样工作，最后再讨论共享资源、布局、扩展和电源等代价与收益。

讲解开始与层次切换时，先用短行明确告知读者当前层次及依据，再进入解释。例如：

- **讲解层次：概念层。** 本节依据某规范的指定版本，说明它要求的角色与保证。
- **讲解层次：实现层。** 本节以某产品修订版或软件提交为对象，说明实际模块、状态和访问路径。
- **讲解层次：概念到实现的映射。** 本节把前述规范角色对应到当前实现的载体。

实际正文把“某规范”“某产品”替换成已经核实的名称和版本；芯片集成等具体实例还要点明实例身份。标注放在标题后的讲解之前，不能藏在术语表、元数据或文末来源中；同层连续段落不重复贴标签，标题已明确给出层次与对象时可不另加一行。一个小节跨层推进时，在实际切换处重新标明，不能用一个笼统“实现”标签覆盖规范定义与产品选择。

规范中的功能组件不自动等于独立物理模块；软件对象不自动等于独立线程或进程；寄存器地址窗口也不自动等于其背后状态的物理位置。实现手册沿用规范名，或者厂商把两个产品名称作为同义名使用时，交代其命名范围，不能把这种同义关系扩大到规范层。

## 跨模块边界与当前问题

映射只能发生在已经说明关系的对象之间。两个模块都使用“编号”“状态”“域”或“映射”，不是把它们并列介绍的充分理由；当前正在解释物理来源和硬件端点时，不自动扩展到固件描述或操作系统资源管理。

引入另一个模块以前，先判断它是否承担当前步骤的必要职责：

1. **当前推导不依赖它：** 不插入旁支提醒。把相关知识留在负责模块；已有有效解释需要重组时，移动到其负责位置或复用已有权威说明，不为去掉枝节丢弃独有知识。
2. **当前确有交接或必须划清边界：** 点明模块及管理对象，说明它接收什么、产生什么、由谁维护，以及当前为何需要区分；只展开足以完成本节推理的关系，再精确链接现有负责章节。
3. **负责章节尚未落地：** 若不是当前前提，暂不引入；若是当前前提，先在当前授权范围补足必要解释，不能用空泛的“后续再讲”代替。未知实现明确承认，不虚构依据或跳转位置。

例如，比较两个处理单元的同号私有来源，可以用所属处理单元、来源编号和状态窗口闭合；将共享来源改送另一个处理单元，可以只追踪来源身份与目标字段。此时突然追加“操作系统显示的编号可能不同”，会把另一套管理规则塞进硬件判断。只有进入操作系统如何接管硬件通知的问题时，才引入它的中断管理模块，并说明硬件编号怎样参与该模块的查找；固件描述转换是另一个边界，也不能与运行时软件编号混称。

这项规则约束表达和依赖，不强制所有专题只讲硬件或只讲软件。配置寄存器的软件、异常入口、设备处理和完成通知若正处于当前事务中，仍要作为执行者说明。真正要避免的是无用途的跨模块比较，以及只丢出结论、没有所属模块和依据的悬空提示。章末可以提出由当前结论自然产生的下一问；若已经断言另一个模块的规则，就必须先完成上述最小交代。

## 变化与不变必须绑定动作和时点

“编号不变”“状态独立”“只改变目标”等结论，必须让读者知道正在比较哪个对象的哪个属性、经过什么操作、观察哪两个时刻。不能要求读者先猜出作者想比较的维度，再自行排除并发事件。

先用一句直接回答确定当前比较的范围。用户只问“更换接收者后，原来源的编号是否改变”，就比较接收者和来源编号；不能为满足写作模板，额外加入使能、清除、其他对象写入或无关状态机。**图表应澄清当前结论，不能扩大当前问题。** 以下要素用于核对当前结论是否成立，并不要求每一项都展开成独立段落或新增操作。

在当前比较范围内，用一个固定实例交代所需内容：

| 比较要素 | 必须说明的内容 |
| --- | --- |
| 对象与属性 | 具体对象怎样被选中；正在比较身份、使能、目标、内容还是运行状态，不能用笼统的“它”代替 |
| 初始条件 | 操作前该属性的值或关系；哪些输入、并发写入者和正在进行的事务已固定或排除 |
| 触发动作 | 谁通过哪个入口修改哪个字段，或者哪个事件推动了状态转换 |
| 观察时点 | 发出操作、被接收、写入可见、缓存失效、同步完成等时点不能混用；只要求展开当前推理依赖的时点 |
| 修改结果 | 被修改的属性如何从旧值变为新值；未被本次操作选中的属性为什么不受它直接修改 |
| 独立变化 | 其他写入者、输入事件、确认、完成等是否仍可能改变相关状态；若排除了这些事件，应明确该条件 |

涉及多个对象或多个可独立变化的字段、仅靠文字容易混淆时，**必须在第一次作出关键比较的位置提供前后对照表、并列时序图或流程图**，让读者能直接看到当前所问的动作和变化范围。对照表只放回答本问所需的比较项；时序图或流程图只展开本问依赖的传播、等待与生效次序。正文沿图表解释因果，不能在长段概念之后补一张只有名词的装饰图，也不能为了填满图表扩大操作范围。单一对象的一步简单变化不为凑形式强制制图。

“对象 B 的字段不受本次写 A 的操作修改”不等于“B 的所有状态一直不变”。如果只讨论使能，就明确使能；若输入仍可能改变挂起状态，就分开说明。改变目标字段也不等于改变来源身份，更不等于已经在执行的处理过程立即迁移。需要比较身份时，指出身份由哪些坐标或索引确定；换索引访问另一个对象与修改原对象的属性分别说明。

异步传播尤其不能只列“写前旧值、写后新值”：应说明何时允许旧值或新值、哪个已核实的完成条件之后才能依赖新值。资料只保证最终更新时，不编造立即生效或特定握手机制；缓存可能提前刷新时，不把同步完成之前写成“必定仍是旧值”。一项操作的完成标志不能移用为另一类寄存器写入或命令的完成保证。

图表中的“保持不变”都应经反问检验：**相对于哪一次动作不变？固定了什么条件？是否存在会推翻本结论的独立事件？** 只补足本结论必需的边界，不因此罗列所有可能改变其他状态的动作。若答案需要另一模块，应依照上一节先建立必要的交接与准确入口；无关的编号或状态体系不加入当前比较。

## 把对应关系落到职责与状态

首次跨层处用正文和必要的对应表回答下列问题。精确数量、落点和共享粒度只要求到当前推理所需且资料能够确认的范围；未公开时，明确未知以及可依赖的接口保证就是有效结论，不能为填表编造细节，也不能把缺少未公开信息判作讲解失败。表是组织依据的工具，不是每节都要机械重复的模板。

| 映射项 | 必须建立的关系 |
| --- | --- |
| 概念身份 | 规范/契约名称、版本、职责、逻辑对象计数单位及数量 |
| 实现身份 | 产品/源码名称、版本，属于物理模块、内部功能分区、软件对象、执行者还是地址视图 |
| 对应数量 | 一个载体承载几个逻辑对象，一个逻辑对象的职责是否分布在几个载体上；逻辑隔离依靠什么区分 |
| 状态落点 | 哪些状态由哪个模块或数据结构实际保存，谁负责更新与使用；共享状态和逐对象状态分别在哪里 |
| 访问与通信 | 配置入口、实际访问目标、转发路径、运行输入输出及各自接口；身份或索引怎样选中对象 |
| 形成时机 | 哪些结构在设计/综合/集成时确定，哪些在启动/枚举时建立，哪些允许运行时改变 |
| 证据边界 | 哪份规范支持职责，哪份实现资料支持落点，哪份集成资料支持本机数量；尚未公开什么 |

不能用“实现了一部分”“整合在一起”结束映射：必须列出当前块承担的职责和状态，列出其余职责的载体。若资料只确认功能分配而未公开内部 RTL 或存储电路，直接说明功能分配已经确定、内部微结构尚未知；不能因此把已证实的实现退回成一条含糊的“有关联”。

区分以下关系，不用一根无标注的箭头包办：

- **实现：** 具体逻辑或代码兑现某个抽象职责，不表示两者是串联的两个实体。
- **包含：** 实际模块或对象内部具有某部件、字段或功能分区；注明是已确认的物理组成还是仅按功能划分。
- **连接：** 两个实际端点通过端口、消息、共享内存或调用传递内容，注明方向与内容。
- **地址视图：** 某地址或接口暴露一组可访问状态，入口、解码点、存储点可能不同，须追踪其实际路径。

“每个 CPU 一个逻辑角色”与“一个物理块服务多个 CPU”可以同时成立，但不是解释终点：还要指出各 CPU 的状态如何区分、处理逻辑是否共享、接口如何识别对象。只有资料证明原有实体确实被合并，才写“把多个独立组件合并”；否则直接描述当前内部组成，不编造先独立再整合的过程。

## 对每个实际参与者建立输入输出模型

从当前运行过程提取状态与端口，而不是仅按手册目录逐个介绍组件。每个参与者在本场景中要说明：

| 问题 | 正文应给出的内容 |
| --- | --- |
| 输入来自谁 | 上游实际端点、进入的请求/数据/信号，以及接口或共享状态 |
| 当前依据是什么 | 本组件自己的准入、选择、输出规则及其状态位置；与其他组件的规则分别说明 |
| 配置改了谁 | 写入者、访问入口、目标标识、必要的转发、最终被修改的字段/寄存器状态及读取它的逻辑 |
| 输出交给谁 | 下游实际端点、输出内容、选择条件及其引起的状态变化 |
| 如何反馈 | 响应、确认、完成或错误由谁产生、经何路径返回、最终更新谁的状态 |

访问经过组件 A，不表示修改的是 A 的功能状态；A 的策略影响 B 收到哪些请求，也不表示 A 直接配置了 B。分别追踪 **配置访问路径、正常请求/数据路径、响应/完成路径**；涉及低功耗时再加入其控制路径，不因共享相同模块就混成同一条流。

读寄存器可能同时触发状态转换。说明读取值的产生位置、返回方向和读取副作用，不能把“观察”“确认”“完成”混写成一次笼统访问。设置的状态与收到通知后的反应也须区分；只有证据表明存在副本和同步机制，才引入影子状态及同步线路。

面对“到底配置大块还是里面的每对象功能”，应直接说明：软件从哪个接口选中哪个对象，修改哪个模块内部的哪份状态，由哪段逻辑使用。不能把“影响了某对象”当作“写入了该对象状态”的依据，也不能凭逻辑名称在模块外另画一个独立实体。

## 共享接口、分组与物理收益必须有实现路径

多个对象共用一条通信通道时，解释它们在哪一级汇聚、如何选择或复用、如何标识来源/目标、接收端怎样分派，以及返回信息如何找到原对象。资料未披露仲裁算法时，只说明已确认的选择功能及未知算法，不臆造命名电路或策略。

不能把多条箭头直接汇成一根线就宣称解决了并联到串联的问题。消息化、时分复用和电气上的串行链路不是同一概念；传输协议可能具有多位数据总线。只有资料给出接口宽度、连接拓扑或对比依据，才能定量声称减少多少信号线；局部线路仍然存在时说明减少的是哪一段连线。

“分组”“簇”“域”等名称必须注明按什么划分。计算拓扑、通信端口共享范围、缓存域、时钟域和电源域不能只凭名称相同就等同。说明谁在何时确定成员关系、软件配置能改变哪些策略、是否真的能改变连接或成员；允许选择目标不等于能够重新组织物理分组。由核心数、软件枚举数量或地址窗口数推算物理块数量，必须有当前集成资料支持。

布线与电源收益应由前面的状态位置和通信路径推出：哪段线缩短或被共享、哪些逻辑可独立关闭、哪些状态必须保留、唤醒如何交接。没有证据时限定为设计推演，不把合理动机写成该产品已实现的事实。

## 图必须让读者分清边界与动作

存在包含/连接歧义时，先给关系图，再追踪一次操作。必要时拆成“概念到实现的对应图”和“实际事务路径图”；不同图沿用对象名，不让读者重新猜配对。图放在第一次需要读者判断关系的位置，外链和章末附图不能替代当前讲解。

- 盒子注明物理模块、内部功能分区或逻辑归属；外框嵌套表达什么须在图注说明，不能借功能分组暗示芯片版图。
- 实际通信箭头连接确有交接关系的实际端点，标明方向、动作与内容；跨软硬件或接口边界时写清调用、指令或事务。概念到载体的映射线注明“由此实现”等含义，不能与通信线混用，也不能把抽象角色和实现它的载体串成两个额外执行步骤。
- 软件执行者、硬件接口和本地事件源分别定位，不能用一个“CPU”节点替所有路径发起请求或接收响应。
- 请求与返回分别画对方向。读值返回、操作确认、完成消息属于什么事务就明确写什么，不让同一箭头同时承担相反方向。
- 同色若仅表示对象对应关系，图注写明；同色、相邻位置和虚线分组都不能替代包含关系或物理距离的证据。
- 图中每条重要连线都应能在正文找到一次具体交接；正文中的“两者”“内部”“该块”须有唯一对象可指，端点改变时重新点名。

## 用最小实例检查是否仍在混层

以下是教学假设，不是任何真实控制器的规范：契约规定每个处理单元有一个端点角色，共四个。产品用模块 M 保存四份端点私有状态，用模块 G 保存四份控制记录并提供访问入口。于是四个逻辑角色的职责分散于 M、G，不能画成 M 外接四个独立端点器件，也不能把 M 的每份私有状态当作一个完整角色。

对端点 2 的私有状态写入由 G 接收并转发，最终修改 M 中对应端点 2 的记录；写入控制记录则在 G 落地。两种操作的入口相同，状态目标不同。是否存在共享仲裁器、记录由触发器还是 SRAM 保存，此假设没有提供，图中不补造。这个例子只校正对应关系与访问路径，实际专题须换成已核实的对象和证据。

## 冷读验收与误解修复

隐藏工作蓝图与外链，按声明的前置知识读正文，检查能否回答：

1. 讲解前能否看见层次标注及对应对象？当前名称来自哪层、哪份规范或实现？两个名称是同层别名，还是功能与载体？
2. 当前场景已确认几个逻辑对象、几个实际模块或软件载体？逐对象状态分别在哪里，共享的是什么？未公开的数量、落点或共享粒度是否明确标出？
3. 写入对象 X 的一个设置，从哪里进入、怎样找到 X、最终修改什么？是否同时改变对象 Y，依据是什么？
4. 一个请求经过哪些实际端点，谁依据自己的规则处理它，输出和返回分别交给谁？
5. 改变软件目标选择会改变请求去向、状态内容，还是物理成员关系？哪些结构在运行以前已确定？
6. 哪些落点已由资料确定，哪些微结构仍未公开？图中是否多画了没有证据的器件、连线或状态副本？
7. 本节每个跨模块名词是否参与当前推导？必要的跨模块关系是否已点明模块、管理对象和实际交接，并给出准确入口；有没有只说“另一个编号不同”或“后续会解释”的悬空结论？
