# 连续阅读与反形式主义验收

专题设计必须同时通过 **内容正确性** 和 **连续阅读性** 两类验收。目录、链接、表格、图、源码符号和版本信息都只是表达或证据手段，不能代替读者沿正文形成模型。出现下列任一情况时，即使结构审计全部通过，章节仍判定为不合格：

- 标题承诺讲解概念、机制或源码实现，正文却主要介绍资料位置、文件分流和外部入口；
- 删除链接目标或禁止点击以后，关键概念、问题、方案或状态转换无法从当前正文推出；
- 读者必须先理解测试编排、配置例外或后续章节，才能知道本章正在解决什么；
- 标题、表格、图、代码或配置先使用专题私有名称，正文后置解释，或者定义本身继续依赖未解释术语；
- 同一流程被多张表、图和清单重复转写，却没有产生新的判断能力；
- H2 只是复述 H1，或者标题下面没有任何解释便直接进入下一个标题；
- 概念、执行者、状态地址、流程阶段、配置变体、优化和诊断设施在同一层并列；
- 章节已经把下一章应通过反例推出的模型增量提前完整公布；
- 审稿只能确认“要素都在”，却不能用简短语言复述一条从问题到结论的主线。

## 标题契约

写正文以前先把标题翻译成读者任务：

| 标题承诺 | 当前章节必须本地兑现 | 不能用什么替代 |
| --- | --- | --- |
| 基础概念或原理 | 定义、边界、与相邻概念的区别、最小动态过程 | 术语链接或名词表 |
| 问题与证明模型 | 旧模型价值、具体矛盾、最小修正和证明边界 | 直接宣布成熟方案 |
| 状态与通信机制 | 参与者、状态位置、写读关系和完整周期 | 字段清单或总图 |
| 源码实现、源码讲解或源码机制 | 模块职责、输入输出、关键状态、真实调用链以及本地源码证据 | 源码索引、跳转表或“详见其他文件” |
| 实验与验证 | 环境、步骤、预期结果、失败现象和证明边界 | 命令名或未执行示例 |
| 导航或索引 | 分流条件、阅读顺序和入口职责 | 第二份机制教程 |

若知识正文只解释跨版本稳定的实现模型，应在标题中使用“实现模型、状态与通信”等准确表述，并把精确函数体链接到研究层。若标题明确承诺逐函数源码实现，则正文职责和保存位置必须服从源码阅读规范，不能把导航文件伪装成实现正文。

**重写后的标题复核也是交付门禁。** 内容扩写、重组或纠错后重新执行以下检查，不能因为标题原来存在就默认仍然适合：

1. **核对当前契约：** 用一句话概括改后正文实际解决的问题，再与标题承诺比较。若正文已从接口位置扩展到设计动机、状态职责或跨组件过程，标题也应反映当前主问题；不能只改正文而留下范围过窄或重心过时的标题。
2. **检查父子范围与同级推进：** 父标题须覆盖子节共同回答的问题，子标题各自承担一个可辨认的增量；同级标题应能看出问题怎样继续推进，而不是一串互不相干的模块名。子节扩展越过父级范围时，在授权范围内调整父标题或组织关系，不用一个泛化父标题掩盖割裂。
3. **优先写出对象与问题：** 教材机制标题尽量点出当前具体对象，以及正在解释的设计问题、因果或角色关系；仅写“功能、参数、映射”等泛称，容易遮蔽为何此时要讲。此类名称只在本节确实承担相应查询、目录或定位任务时使用，不因出现一张参数表就把机制讲解改名为参数说明。
4. **只读标题，再回正文验收：** 暂时只看当前标题、父标题和相邻同级标题，读者应能辨认机制推进及本节位置；再检查正文是否兑现承诺。标题不承担全文摘要，不以字数长、术语多为完整，也不强制所有标题改成问句或套同一模板。
5. **同步标题依赖：** 改名后检索旧标题及其渲染后完整片段，更新 Typora 完整标题锚点、Markdown 与 Obsidian 实际入链，以及专题大纲、前后篇导航和其他真实调用入口；涉及 H1 时同步文档标题元数据。随后核对新锚点确实存在、旧片段没有未处理引用，不能只改可见链接文字。

## 断链阅读测试

交付前把所有超链接视为不可点击，只保留当前文件可见文字，检查读者能否回答：

1. 本章第一次出现的核心概念是什么，与哪些相近类型不同；
2. 哪个具体现场提出了什么问题；
3. 当前模块增加了什么角色、状态、通信或约束；
4. 一次正常流程怎样从输入走到输出；
5. 哪项源码、实验或规范只是为已经讲清的结论作证；
6. 本章现在能够证明什么，下一章仍要解决什么。

任何问题只能靠点击链接回答，都表示链接承担了正文职责。修复方式是把当前场景所需的最小解释写回本地，再保留精确链接供深入追踪；不是复制完整外部教程。

## 模块局部闭环

一个章节含有多个实现模块时，按问题依赖逐个闭合，不先给全量组件目录。每个模块至少形成以下阅读动作：

```text
基础概念与类型定位
    → 当前模块面对的具体问题
    → 解决方案及状态/通信变化
    → 让读者预测一个中间状态、反例或失败后果
    → 用实现、源码、实验或日志验证
    → 把新结论交给下一个模块
```

“引导读者思考”不能退化成无答案的设问。问题必须位于答案以前，能够让读者使用已经建立的模型作出预测；随后的源码或实验再确认、修正或击穿这个预测。

## 主线、分支与表示预算

先冻结一个默认配置、一条正常路径和一组贯穿对象。优化、诊断、版本差异、特殊配置与下一执行模型在主线闭合后分区处理。每新增一种表示，都记录它独自回答的问题：

- 角色关系图用于定位状态或所有权；
- 时序图用于暴露执行顺序和异步窗口；
- 状态表用于比较转换前后与读写者；
- 源码摘录用于验证具体实现落点；
- 密集证据索引用于审稿或深入阅读，不占据主叙事；关键概念旁的精确官方对照仍保留在正文。

若两种表示回答同一个问题且没有新增判断能力，保留更清楚的一种。证据账本、批量链接清单和全字段覆盖表应留在参考、研究或审稿层；这不免除 [官方资料溯源](official_source_reading.md#独立讲解与官方资料溯源) 要求的就近引用，不能把阅读指导一并移走。

## 冷读复述门禁

最终审稿按已声明的读者基础与前置章节冷读，不查看作者蓝图，也不依靠临时跳转补洞。检查关键概念能否用于解释现象及预测结果，再复述本章为何承接前文、解决什么问题、怎样得出结论、还留下什么需要继续学习。还要检查相邻段落为何依次出现、实验前是否有值得预测的问题、答案是否有推导而非仅列结果。复述若只是文件名和字段名，或必须先补大量未知前提，继续重写。自行冷读不得称为真实读者试读，自动脚本也不能验收阅读体验。
