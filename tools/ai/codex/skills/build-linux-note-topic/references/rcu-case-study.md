## 0. 内容保护经验

RCU 方法是一种阅读架构方法，不是天然的压缩目标。对“已审稿且本次只要求排版”的笔记应用 RCU 风格，意味着显化阶段、前置条件、已解决问题和后续问题，同时保留技术语义、证明模型、源码实现、变体、诊断、实验和选择材料；不意味着用一篇新写的短教程替换原材料。如果用户明确要求重写或压缩，则可以在授权范围内修改这些内容。

用户只要求排版时，保留各章技术语义和信息单元，可以调整编号、空白、列表、表格、导航、锚点等机械表达，并在外围增加阅读地图。拆分、合并、重写或去重则按照用户明确授权的编辑模式执行。

## 0.1\_源码证据不能退化成链接路由

RCU 知识正文进入源码层以后仍要 **本地完成机制讲解**。源码唯一展开不允许把知识章节写成源码文件清单、模块导航、精确标题链接和证据核对表的集合。

以一轮普通 Tree RCU 同步等待为例，相关功能模块合计至少要闭合以下问题：

1. `synchronize_rcu()` 的等待对象是什么，写者睡眠以后由谁持有完成责任；
2. GP 请求、物理 GP、GP kthread、`rcu_state` 分别属于概念、请求、执行者还是状态载体；
3. CPU 本地 QS 证据怎样锁存，为什么它还不是共享完成结论；
4. `rcu_data`、`rcu_node` 与根节点怎样把局部事实汇聚为全局完成；
5. GP 完成以后，callback 或专用等待路径怎样把结果交还原写者。

每个问题都按“基础概念 → 背景缺口 → 解决方案 → 读者预测 → 源码证据”推进。它们可以分别归入同步等待、GP、QS、树形汇聚和 callback 模块，不要求由一篇纵向源码章全部承担。EQS、SRS、strict GP、force-QS、stall、抢占式任务债务、版本差异和 Lockdep 只能在默认主线闭合后进入对应模块分支。若隐藏全部链接以后读者无法回答上面五问，说明正文已经退化成路由页，必须重写或改名。

知识正文可以用短源码摘录、忠实伪代码和状态图解释当前场景；逐函数完整实现、中文 Doxygen 和可修改性说明仍保存在 `source_explanations/`。两层职责的区别是证据粒度，不是“一个负责讲、另一个只负责跳转”。

## 0.2\_RCU 术语必须先解码

RCU 文献同时使用论文缩写、Linux 实现家族名、Kconfig 符号、源码标识符和本专题为了推理引入的教学用语。它们不能被默认成一套人人都懂的“RCU 常识”。每篇章节先完成本章术语入口，再进入分类表、GP 树、状态债务或源码调用链。

至少区分下面几种名称性质：

| 首次出现写法 | 本章必须先告诉读者什么 |
| --- | --- |
| RCU | Read-Copy Update（读-复制-更新）的英文缩写，以及三个词在本场景分别对应什么动作；不能只给全称后立即进入源码。 |
| SMP | Symmetric Multiprocessing（对称多处理）的英文缩写；说明它描述多处理器/多中央处理器（Central Processing Unit，CPU）执行环境，不是一种 RCU 类型。 |
| GP | Grace Period（宽限期）的英文缩写；说明它是要被证明完成的一段逻辑等待边界，不是线程、树或固定时长。 |
| QS | Quiescent State（静止状态）的英文缩写；说明它是哪一类参与者越过旧访问边界的局部证据，以及在当前配置下是否足够。 |
| Tree RCU、Tiny RCU | Linux 普通 RCU 的实现家族专名，Tree/Tiny 不是需要继续展开的缩写；说明命名对应的实现规模和结构差异。 |
| `CONFIG_PREEMPT_RCU` | Kconfig 配置符号；说明它改变 Tree RCU 的读侧执行模型和证明债务落点，不把它写成第二棵 GP 树或另一套公共 API。 |
| “CPU 债务”“任务债务” | 本专题为解释“谁还欠当前 GP 一份完成证据”使用的教学模型词，不是 Linux 公共 API、正式 Kconfig 类型或必然存在的同名源码字段。随后必须映射到真实状态位置。 |

这个表只示范名称解码，不能成为以后章节的永久免解释凭据。P04 之类可以独立打开的分类章节仍要在首次出现处给出中英文名称或名称性质、一句本地解释和精确回链。分类表中的每一行还要说明它属于保护域、实现家族、执行模型、运行策略还是诊断设施；不得让读者只凭英文家族名、配置片段或策略简称的外观猜测分类依据。

RCU 私有术语的定义中若又出现新的英文角色名、状态缩写、代际名、保护域名、强制路径简称或回调卸载简称，先把这些词递归对齐，或者改用已经解释过的普通中文。链接到其他章节只能提供纵深和源码证据，不能让当前句子的基本语义依赖跳转。

## 1. RCU必须先按正交轴分类

RCU 同时包含公共 API、不同保护域、底层实现家族、读侧执行模型、GP 策略、callback 执行策略和诊断设施。它们不是同一层“类型”：

| 分类轴 | RCU 中的例子 | 读者需要先回答的问题 |
| --- | --- | --- |
| 公共语义与 API | `rcu_read_lock()`、`rcu_dereference()`、`call_rcu()`、`synchronize_rcu()` | 接口承诺什么，哪些内部选择被隐藏 |
| 保护域或 reader 定义 | 普通 RCU、SRCU、Tasks RCU | 等待的是哪类参与者，读者能否阻塞或迁移 |
| 实现家族 | Tree RCU、Tiny RCU | 用什么核心结构兑现普通 RCU 语义 |
| Tree RCU 读侧执行模型 | `CONFIG_PREEMPT_RCU=y/n` | 旧 reader 债务只跟 CPU，还是会转移到任务登记 |
| GP 运行策略 | normal、expedited | 怎样用系统扰动换等待时延 |
| callback 执行策略 | 本地执行、NOCB 卸载 | 谁推进和执行成熟 callback |
| 诊断设施 | stall、Lockdep、Sparse | 观察或检查什么，不能替代哪项功能保证 |

分类坐标必须早于任何“非抢占式完整源码链”或“抢占式完整源码链”。推荐的专题阶段是：

| 阶段 | 主要读者任务 |
| --- | --- |
| 通用概念与接口 | 建立发布、读侧临界区、GP、QS、callback 和对象回收的最小闭环 |
| 类型与配置坐标 | 区分保护域、实现家族和 Tree RCU 抢占模型，知道公共 API 隐藏了哪些选择 |
| 模块实现与变体差量 | 按模块讲公共职责，再比较非抢占/抢占等差量 |
| 应用与实验 | 组合生命周期、诊断、选型，并用实验验证前面的具体证明义务 |

对象生命周期组合（例如 RCU + kref）属于应用阶段。它可以在通用 API 以后提供独立入口，但不能插入“公共接口 → 分类坐标 → Tree RCU 公共骨架”的默认主线。

### 1.1\_Tree\_RCU按模块比较抢占差量

Tree RCU 的公共 GP 请求、节点拓扑、callback 分段和同步等待不能在两个配置章节中各讲一遍。模块矩阵至少包含：

| 功能模块 | 公共职责 | 非抢占式差量 | 抢占式差量 |
| --- | --- | --- | --- |
| 读侧进入与退出 | 建立普通 RCU 临界区契约 | 禁止抢占，不登记共享 reader 身份 | 任务保存嵌套状态，允许被抢占 |
| QS/EQS 证据 | 排除 GP 前的旧执行 | CPU QS 足以清偿普通 reader 债务 | 上下文切换时可能把债务转入任务登记 |
| GP 请求与生命周期 | 合并请求、开始代际、等待、cleanup | 基本走公共 GP 控制链 | 基本走公共 GP 控制链 |
| `rcu_node` 汇聚 | 把局部证据变成根完成 | 主要等待 CPU/子树位 | CPU 位清零后仍可能等待 blocked task |
| callback 与同步等待 | 绑定目标 GP、取得执行资格、唤醒或释放 | 基本走公共完成交付链 | 基本走公共完成交付链 |
| 慢路径与运行策略 | EQS、FQS、stall、expedited、hotplug、NOCB | 只解释适用差量 | 只解释适用差量 |

旧式“非抢占证明 + 非抢占完整源码 → 抢占证明 + 抢占完整源码 → 后面再按公共模块展开”会让公共实现出现三次，并把分类推迟到读者已经进入字段以后，属于本案例明确拒绝的反模式。非抢占与抢占确实有不同证明，但差异集中在 reader 状态归属、QS 有效性和节点完成条件；证明差量应在对应模块中被同一场景并列比较。

应用到其他主题时同样先判断公共模块与变体差量。简单机制可以合并问题、抽象和实现；只有变体改变大部分完整周期时才纵向拆篇，不得为复刻历史 RCU 文件数量创建空章节。

## 2. 决定性的场景拆分

两个都“执行读者代码”的任务可能属于不同集合：

- 已经进入队列、但尚未执行受保护查找的任务没有旧指针；
- 已经取得旧指针、随后被抢占的任务仍然携带旧读者债务。

这种区分迫使专题分别建立 CPU 证明模型和任务证明模型。它也说明场景必须精确交代指针何时被读取，不能只说存在一个读者线程。

## 3. 状态所有权经验

RCU 实现不能被讲成一个计数器：

- 任务本地嵌套状态表示正在执行的可抢占读者；
- 上下文切换可以把生命周期债务转移到共享节点链表；
- per-CPU 状态记录当前宽限期观察和本地静止态证据；
- 节点掩码汇聚 CPU 或子节点债务；
- 全局状态协调宽限期代次；
- 回调或 completion 把结果交给回收方。

核心教学义务是解释每一次转移，而不是只罗列这些结构。

## 4. RCU 与 kref 的经验

RCU 与 kref 不会自动互相通知，而是由对象所属模块组合二者。

至少区分以下模型：

1. 一个由 RCU 发布的对象在读侧窗口内取得长期 kref；
2. 一份发布引用存活至宽限期结束，并由回调释放；
3. 一个 RCU 版本根持有多个独立分配的 kref 数据块引用；
4. 短读者借用根对象对数据块的所有权，逃逸读者则取得自己的数据块引用。

每次分配都必须只有一个最终释放协议。`kref_put()` 在计数归零时调用调用者提供的 release；空回调是模块自身选择，不是 kref 默认行为，也不是 RCU 交接机制。

## 5. 成本经验

大量短读者不会导致每次读取都生成一份旧副本或执行一次 kref 操作。退休内存压力更适合近似为：

```text
退休版本生成速率
    × 宽限期/回调延迟
    × 每个退休版本独占的字节数
```

长读侧区间、高更新率、大型独占根对象、回调饥饿和高逃逸比例是不同的成本，进行有效比较时必须分别处理。

## 6. 源码证据经验

当一组 RCU 源码材料同时要服务模块理解、具体实现追踪和多篇知识正文时，`research/source_reading/rcu/` 按职责拆成两层：

- `navigation/` 包含一个总阅读索引，以及接口、读侧/QS、GP、节点汇聚、callback、运行策略和实现家族等功能模块导读；非抢占/抢占差异在相关模块中并列说明，只有真正改变完整证明域的 SRCU、Tasks/Tiny 等家族才保留独立导读；
- `source_explanations/` 面向具体宏、函数、字段或紧密关联的实现簇，提供上游相对位置、仓库补充的中文 Doxygen 注释、带中文行内注释的源码和实现原理；同一版本的同一实现只展开一次。

知识正文首次进入源码证据时链接总阅读索引和相关模块导读，遇到具体接口或检查点时再精确链接唯一源码实现标题。模块导读和其他调用链文档遇到已有公共实现讲解时也只引用，不再复制宏体或函数体。

对于 Linux 6.12，RCU 源码章节追踪：

- 同步等待请求与唤醒；
- 宽限期代次启动与清理；
- 节点掩码初始化；
- per-CPU 对新代次的识别；
- 本地静止态证据锁存；
- 向节点树异步上报；
- 被抢占任务的登记和最终解除阻塞；
- 用户态/空闲态的上下文跟踪证据；
- 回调具备执行资格以及实际执行。

进入具体实现层以后还要建立符号覆盖账本，不能因为前面的机制模型已经成立，就把实现中的虚拟锁、静态 key、配置初始化器、包装函数或回调上下文标记压缩成一句“接入 Lockdep”。例如 `rcu_lock_map`、`rcu_bh_lock_map`、`rcu_sched_lock_map` 与 `rcu_callback_map` 的 **通用 Lockdep 数据结构和查询算法** 归 Lockdep 专题唯一展开；RCU 专题必须独立追踪这些实例的 `extern` 声明、`update.c` 定义、等待类型、acquire/release 调用点、current 影子持有记录、RCU 查询/断言消费者和 `CONFIG_DEBUG_LOCK_ALLOC=n` 退化分支。还要说明它们是检查身份而非功能锁，以及修改调用顺序或遗漏配对会怎样改变诊断结果。

“前缀属于通用框架”不等于“实例也归框架专题”。交叉实现按所有权拆分：框架专题解释 `lockdep_map → lock class → held_locks[] → 查询`，RCU 专题解释自己的四个 map 怎样使用这条通路。该标准同样适用于 GP、QS、callback、NOCB、热插拔和其他源码实现簇。

Linux 5.10 的差异记录在具体字段和调用链边界，而不是笼统概括为“基本相同”。其他内核机制也采用同一标准。

## 7. 实验经验

RCU 实验有意构造两个阶段：

- 先释放旧版本，再允许受门控的未来读者执行第一次查找；
- 让读者取得旧指针后在同一 CPU 上被抢占，并证明宽限期会等待它最终解锁。

completion、CPU 绑定、定时释放和有序日志让因果边界变得可观察。实验明确说明它近似的是哪种调度条件，而不是声称能逐字复现不可控的“999 个排队任务”。

## 8. 认知悬念经验

RCU 专题持续引导读者的原因不是标题格式，而是未决问题在章节之间传递：

- P01 证明锁和原子换指针仍有缺口，P02 才推导发布边界和 GP；
- P05 先闭合 Tree RCU 公共 S0～S9 周期，P06 再用被抢占 reader 推出 CPU 债务与任务债务的差量；
- P08 先建立 GP 代际和协调者生命周期，P09、P10 再依次追踪本地 QS 证据与节点树汇聚；
- P11 只解决 callback 何时具备执行资格，P12 再解决何时以及由谁实际执行。

应用到其他专题时保持“一问一增量”：先让当前模型完整成立，再用最小反例暴露一个缺口，只引入解决该缺口所需的状态或路径，最后用源码或实验兑现。不要在问题出现以前提前罗列成熟实现的全部组件。
