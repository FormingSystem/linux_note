## 0. 内容保护经验

RCU 方法是一种阅读架构方法，不是天然的压缩目标。对“已审稿且本次只要求排版”的笔记应用 RCU 风格，意味着显化阶段、前置条件、已解决问题和后续问题，同时保留技术语义、证明模型、源码实现、变体、诊断、实验和选择材料；不意味着用一篇新写的短教程替换原材料。如果用户明确要求重写或压缩，则可以在授权范围内修改这些内容。

用户只要求排版时，保留各章技术语义和信息单元，可以调整编号、空白、列表、表格、导航、锚点等机械表达，并在外围增加阅读地图。拆分、合并、重写或去重则按照用户明确授权的编辑模式执行。

## 1. 从本地布局抽象章节角色

当前 RCU 大纲的价值在于章节之间的因果依赖，而不是文件数量：

| RCU 章节 | 本地职责 | 可复用的章节角色 |
| --- | --- | --- |
| P01 | 用锁和原子换指针建立旧方案价值与缺口 | 问题压力 |
| P02 | 从发布边界和旧读者集合推出 GP | 抽象机制推演 |
| P03 | 在实现纵深以前建立完整使用协议 | 最小 API 与使用闭环 |
| P04 | 区分 RCU、kref 和对象模块的职责 | 组合机制与生命周期 |
| P05/P06 | 先证明非抢占模型，再映射源码 | 执行模型证明与实现配对 |
| P07/P08 | 用抢占迁移击穿旧模型，再增加任务债务 | 反例修模与第二执行模型 |
| P09 | 用硬件和运行条件继续攻击朴素模型 | 现实条件加固 |
| P10 | 把任务、CPU、节点、全局和回调放进同一周期 | 统一状态与通信全景 |
| P11～P21 | 沿统一周期放大关键子状态机 | 实现纵深 |
| P22～P24 | 比较不同读者定义、域和部署配置 | 实现家族与配置边界 |

应用到其他主题时按证明边界裁剪：简单机制可以合并问题与抽象、证明与源码；没有跨机制所有权、分层状态或实现家族时，省略对应角色。不得为复刻 RCU 创建空章节。

通用经验是：API 用法要足够早地出现，为后续源码讨论提供具体落点；但它必须位于最小抽象契约已经建立之后。只有不同执行模型改变了参与者集合或证明方式时，才采用“问题/证明章 → 源码实现章”的配对。

## 2. 决定性的场景拆分

两个都“执行读者代码”的任务可能属于不同集合：

- 已经进入队列、但尚未执行受保护查找的任务没有旧指针；
- 已经取得旧指针、随后被抢占的任务仍然携带旧读者债务。

这种区分迫使专题分别建立 CPU 证明模型和任务证明模型。它也说明场景必须精确交代指针何时被读取，不能只说存在一个读者线程。

## 3. 状态所有权经验

RCU 实现不能被讲成一个计数器：

- 任务本地嵌套状态表示正在执行的可抢占读者；
- 上下文切换可以把生命周期债务转移到共享节点链表；
- per-CPU 状态记录当前宽限期观察和本地静止态证据；
- 节点掩码汇聚 CPU 或子节点债务；
- 全局状态协调宽限期代次；
- 回调或 completion 把结果交给回收方。

核心教学义务是解释每一次转移，而不是只罗列这些结构。

## 4. RCU 与 kref 的经验

RCU 与 kref 不会自动互相通知，而是由对象所属模块组合二者。

至少区分以下模型：

1. 一个由 RCU 发布的对象在读侧窗口内取得长期 kref；
2. 一份发布引用存活至宽限期结束，并由回调释放；
3. 一个 RCU 版本根持有多个独立分配的 kref 数据块引用；
4. 短读者借用根对象对数据块的所有权，逃逸读者则取得自己的数据块引用。

每次分配都必须只有一个最终释放协议。`kref_put()` 在计数归零时调用调用者提供的 release；空回调是模块自身选择，不是 kref 默认行为，也不是 RCU 交接机制。

## 5. 成本经验

大量短读者不会导致每次读取都生成一份旧副本或执行一次 kref 操作。退休内存压力更适合近似为：

```text
退休版本生成速率
    × 宽限期/回调延迟
    × 每个退休版本独占的字节数
```

长读侧区间、高更新率、大型独占根对象、回调饥饿和高逃逸比例是不同的成本，进行有效比较时必须分别处理。

## 6. 源码证据经验

当一组 RCU 源码材料同时要服务模块理解、具体实现追踪和多篇知识正文时，`research/source_reading/rcu/` 按职责拆成两层：

- `navigation/` 包含一个总阅读索引，以及非抢占式 Tree RCU、抢占式 Tree RCU、Tasks/Tiny RCU 等子功能或模块的源码概念导读；模块导读借源码讲清职责、状态、调用链和阅读顺序，不逐段展开上游实现；
- `source_explanations/` 面向具体宏、函数、字段或紧密关联的实现簇，提供上游相对位置、仓库补充的中文 Doxygen 注释、带中文行内注释的源码和实现原理；同一版本的同一实现只展开一次。

知识正文首次进入源码证据时链接总阅读索引和相关模块导读，遇到具体接口或检查点时再精确链接唯一源码实现标题。模块导读和其他调用链文档遇到已有公共实现讲解时也只引用，不再复制宏体或函数体。

对于 Linux 6.12，RCU 源码章节追踪：

- 同步等待请求与唤醒；
- 宽限期代次启动与清理；
- 节点掩码初始化；
- per-CPU 对新代次的识别；
- 本地静止态证据锁存；
- 向节点树异步上报；
- 被抢占任务的登记和最终解除阻塞；
- 用户态/空闲态的上下文跟踪证据；
- 回调具备执行资格以及实际执行。

Linux 5.10 的差异记录在具体字段和调用链边界，而不是笼统概括为“基本相同”。其他内核机制也采用同一标准。

## 7. 实验经验

RCU 实验有意构造两个阶段：

- 先释放旧版本，再允许受门控的未来读者执行第一次查找；
- 让读者取得旧指针后在同一 CPU 上被抢占，并证明宽限期会等待它最终解锁。

completion、CPU 绑定、定时释放和有序日志让因果边界变得可观察。实验明确说明它近似的是哪种调度条件，而不是声称能逐字复现不可控的“999 个排队任务”。

## 8. 认知悬念经验

RCU 专题持续引导读者的原因不是标题格式，而是未决问题在章节之间传递：

- P01 证明锁和原子换指针仍有缺口，P02 才推导发布边界和 GP；
- P05 证明按 CPU 等待成立以后，P07 用抢占迁移击穿该模型；
- P09 用反例提出成熟实现必须满足的需求，P10 才统一展示状态和通信；
- P17 只解决 callback 何时具备资格，P18 再解决何时以及由谁实际执行。

应用到其他专题时保持“一问一增量”：先让当前模型完整成立，再用最小反例暴露一个缺口，只引入解决该缺口所需的状态或路径，最后用源码或实验兑现。不要在问题出现以前提前罗列成熟实现的全部组件。
