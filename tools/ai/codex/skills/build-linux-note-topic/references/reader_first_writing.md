# 正文入口、术语与连续阅读门禁

设计、重组、创建、扩写或重写专题前必须完整阅读本文件，并在逐章交付前按本文件复核。仅排版任务仍服从主入口的授权边界，不借发现教学缺口改写技术内容。

## 让模块、平台与代际也从零建立

工作型蓝图可以使用“通用模型 + 多个平台落地 + 实现代际对照”之类的作者分类，但这些标签只帮助作者分解材料，**不得直接成为读者入口或隐含先修知识**。零基础不仅意味着解释缩写，还意味着读者最初不知道为什么存在这些模块、何谓平台、哪些名称位于同一层、版本或代际按什么变化轴划分。

每个模块、分类轴、平台、架构、产品、实现家族、版本或代际第一次承担阅读分流或比较职责以前，先完成以下闭环：

1. **它是什么：** 用已经对齐的普通语言说明对象类型和朴素含义，不用同组陌生名称互相定义；
2. **它为何出现：** 从一个具体问题、约束或旧模型缺口推出它，而不是先宣布成熟分类；
3. **它与谁相连：** 说明上游输入、下游输出、所属层次、拥有者和一次最小事务中的位置；
4. **它和什么不同：** 先给出比较轴，再区分相邻概念，不能把厂商、架构、处理器核、芯片、开发板、规范版本和驱动等不同层次直接并列；
5. **读者现在能做什么：** 先闭合该对象的一次最小过程或身份定位，再让它进入分类表、变体矩阵、平台纵向实现或代际比较。

硬件与平台专题尤其要先建立坐标关系，例如“规范或指令集架构 → 处理器核或控制器实现 → SoC 集成 → 开发板连接 → 固件与操作系统驱动”。具体专题按事实裁剪这条链，但必须回答每个名称由谁定义、属于哪一层、与相邻层怎样组合。第一个平台先完成自身身份和完整事务，后续平台或新代际再由新规模、新能力或新约束自然引出；只有两侧对象都已经独立建立以后，才总结共同点和差异。

因此，作者拿到组合式目标时，必须把它转换成读者因果链：**现实事件或任务 → 朴素模型 → 当前缺口 → 新模块及名称 → 身份与关系坐标 → 最小闭环 → 具体实现 → 新约束推动的变体或代际 → 已建立对象之间的对照**。不得把作者已经知道的专题终局结构冒充读者已经具备的知识结构。

## 先确定分类轴和模块变体矩阵

当一个专题同时具有 **公共概念/API** 与 **多个实现家族、配置分支或执行模型** 时，正文生成前必须先完成专题级分类，不能把不同轴上的名称混成一串“类型”，也不能直接选择一个变体纵向讲完整系统。

1. 先从具体问题推出公共职责和可能变化的维度，再为公共契约、保护域或语义 flavor、实现家族、执行模型、运行策略/优化、诊断设施等正交轴命名；同一个名称只能在它所属的轴上参与比较。
2. 分类坐标必须晚于构成坐标的概念进入，又早于第一个变体内部实现。读者进入“抢占/非抢占”“轮询/中断”“同步/异步”等分支前，应已经知道每个词是什么、它们为什么形成这一比较轴、哪些语义和模块共同存在以及该分支只改变什么。
3. 先建立公共概念、常用接口和一轮公共端到端骨架，再建立 **模块 × 变体矩阵**：行是能够独立学习的功能模块，列是公共职责、公共实现、各变体差量、源码/规范证据和对应实验。
4. 默认按模块推进：每个模块先讲概念、输入输出和公共职责，再比较变体怎样改变参与者、状态、通信、完成条件与成本。公共 GP、队列、拓扑、生命周期或错误处理不得在多个变体章节中各复制一遍。
5. 只有一个变体确实改变了大部分端到端参与者集合、证明方式、控制流和完成条件时，才允许为它建立完整纵向章节；若差异只落在一个或少数模块，就在对应模块内做并列比较。
6. 组合应用、对象生命周期、诊断与选型不能插入“公共接口 → 分类坐标 → 公共骨架”的必要前置链；它们在基础机制成立后进入各自阶段。
7. 实验既可以集中编排，也必须回链它所验证的具体概念或变体差异。不得在正文只写抽象结论、最后堆一个无法对应前文证明义务的实验目录。

全书蓝图必须能够回答：哪些内容跨变体保持不变，哪些只属于某个变体，为什么选择“按模块比较”或“按变体纵切”。如果两个变体章节都重复讲同一组公共执行者、状态载体和完整周期，说明专题主轴很可能选反，必须在写正文前重新设计。

## 为说明型章节固定建立读者入口

创建或补写概念、语法、接口、配置、源码导读等说明型章节时，不要在标题后直接罗列定义、字段、API 或分类表。先按以下顺序建立背景；这六步是内容契约，不要求机械写成六个同名标题：

1. **回收前置结论：** 说明读者已经从上一章、上层机制或常见实践中获得了什么有效认识，避免把既有知识写成错误。
2. **固定实际遭遇：** 选一段结构完整的代码、配置、日志、调用路径或操作现场，说明读者通常在哪里遇到本章主题以及当时正在完成什么任务。
3. **暴露剩余缺口：** 列出仅凭当前模型仍无法回答的具体问题，并解释按名称、表面语法或压缩结论猜测为什么会得出错误判断。
4. **定位本章层次：** 说明问题属于定义、语法、抽象机制、实现、运行时、诊断或工程流程中的哪一层，以及它与前后层怎样连接。
5. **限定讲解边界：** 明确本章只解决什么、不重复哪个权威专题、哪些问题有意留给下一章，防止背景演变成成熟术语总览。
6. **声明可检验结果：** 用读者完成后能执行的动作收束背景，例如能够手工展开、画出时间线、判断接口前置条件、定位状态地址或选择验证证据；随后正文继续复用同一场景和对象。

背景不是章节摘要，也不是“很重要、很复杂”式动机。完成入口后，读者应能回答“我为什么现在需要这一章、我要带着哪个现场往下读、读完后能多做哪一步”。若现有开头已经完整覆盖这三问，不重复添加第二份背景。

## 执行反形式主义与连续阅读硬门禁

创建、扩写或重写正文时，**要素齐全不等于章节合格**。不能因为文档已经包含场景、术语表、S0～Sn、Mermaid、源码链接、版本边界和核对表，就判定它完成了讲解。交付以前逐章执行以下硬门禁；任一项失败都必须继续修改，不能用“链接有效”“证据另有权威位置”或“专题其他章节已经讲过”抵消：

1. **标题契约：** 标题承诺“概念”“问题”“机制”“源码实现”“实验”或“导航”中的哪一种读者任务，正文就必须在本地兑现。标题包含“源码实现、源码讲解、源码机制”等承诺时，每个主要实现模块都要在当前章节解释实现原理、输入输出、关键状态和源码证据；如果正文只负责建立稳定模型或组织链接，应改用准确标题，不得让读者点入后才发现需要跳转。
2. **断链阅读：** 假设读者打印本文、隐藏 URL 且不点击任何链接，仍应能沿正文重建基础概念、背景问题、解决方案、关键状态转换和本章结论。链接只能验证、深化或进入唯一源码函数体，不能承担当个概念、模块职责或关键因果的首次解释。
3. **模块局部闭环：** 每个主要模块首次出现时，都要在本地完成“基础概念与类型定位 → 当前模块面对的问题 → 解决方案与状态/通信 → 留给读者的预测或反例 → 实现验证或源码证据”。这五项是内容闭环，不要求机械使用五个同名标题；不得先跨模块倾倒全部字段，再在后文反向解释。
4. **类型分层：** 在同一段、表格或全景图混用术语以前，先区分抽象概念、执行角色、状态载体、流程阶段、配置变体、优化分支和诊断机制。GP、GP 请求、GP kthread、`rcu_state`、SRS 和 stall 这类不同类型对象不能作为一组并列“概念”直接抛给读者。
5. **术语依赖可用：** 对当前推理所需的新缩写、专名、配置、源码符号或内部阶段名，就地建立名称、含义、职责及必要边界；不能用一串未知词解释另一个未知词。连续教材已明确建立的前置知识允许简短回顾，标题或待解释现象不承担理解前提；分类、比较与机制推理则必须建立在读者已经获得的认识上。
6. **主线优先：** 先选定一个默认配置和正常路径闭合主线；优化、版本差异、诊断、异常慢路径和其他执行模型只能在主线成立后作为分支出现。不得为了覆盖完整性打断本章正在解决的问题，也不得提前讲完下一章赖以产生认知悬念的反例。
7. **表示增量：** 第二张机制表、机制图或第二套阶段编号必须回答前一种表示无法回答的新问题。只把同一流程在时间线、位图表、关系图、阶段表、函数清单和证据表之间反复转写，属于形式堆叠，必须合并或删除。用于读者定位的同图复用是例外：保留统一路线和编号，只突出当前位置，不冒充新增机制解释。
8. **首屏与冷读验收：** 在源码文件清单、版本台账和密集链接以前，读者必须先知道“为什么现在读、正在追哪个现场、读完能完成什么”。审稿时由未参与写作的读者视角用五到八句话复述主线；如果必须点击链接、搜索后文或先理解测试编排器才能复述，章节不合格。
9. **标题层级不是装饰：** H2 不能只是去掉“第 N 章”后复述 H1，也不能在没有任何承上启下正文时直接进入下一个标题。空标题、标题回声和只为满足层级数量而建立的伞形小节必须改成真实阅读任务，或者删除并重新编号。
10. **跨标题连续性：** 连读上一节末段、标题和下一节首段，检查对象、条件、指代与问题是否接续。再临时遮住标题，检查正文是否丢失推理前提或突然换了现场；标题的分类与导航信息无须逐字重复，但结论的解释、变化条件和关键因果必须在正文中成立。只有“接下来介绍”或重复标题不能算修复，必须补足实际缺口；此项为语义冷读，不能由关键词或段落长度检测代替。

详细判据见 [连续阅读与反形式主义验收](reader_continuity_review.md) 和 [references/review-checklist.md](review-checklist.md)。源码章节还必须执行 [references/source-evidence.md](source-evidence.md) 的“链接只能作证，不能代替讲解”。

## 零基础术语门禁：先对齐语言，再展开概念

默认读者 **具备一般计算机常识、但尚未掌握当前专题私有词汇**；用户已说明的编程、工程或其他基础应保留，不重复补课。不得因为术语出现在内核源码、官方文档、前一章、开发者日常交流或专题标题中，就假定读者已经理解。解释完整性和思考连续性优先于篇幅；术语太多时按知识依赖拆分学习阶段，用具体问题逐步引出，不得用压缩解释换取短文，也不得用大术语表代替正文递进。

写作前建立工作型 **术语依赖账本**，至少记录：原始写法、正式英文全称或名称性质、准确中文名、术语类型、朴素定义、当前场景职责、前置术语、易混项、版本/配置边界、首次出现位置和权威精确入口。按依赖顺序安排正文；一个定义只能使用已经对齐的词，若解释中又出现陌生术语，先递归解释它，不能用一串新黑话解释旧黑话。

检查范围包括标题、导航、正文、表格、图、代码、配置和日志，但要区分“提出学习对象”与“把它当作已知前提”。标题提出问题、展示待解释的短代码或错误现象后紧接解释，是允许的教学顺序；要求读者先理解未讲概念才能继续推理，才是需要修复的断点。连续教材在概念首次建立时完成必要解释，后续章节以简短回顾和准确前置入口维持连续性，不机械重复英文全称及整套定义。独立入门文章则自行补齐其承诺范围内的前提。

术语第一次承担推理职责时，按适用范围完成一张“进入卡”：

1. **名字与突出：** 首次定义整体加粗为 **中文名（English Full Name，ABBR）**；没有通行缩写的概念使用 **中文名（English Full Name）**。命令、产品型号、项目、实现家族、历史昵称和源码标识符若不是缩写，说明名称性质，不得杜撰全称。后续普通提及不必反复展开或全部加粗；标题、代码和 Mermaid 保持原有语法，在紧邻正文完成名称对照与突出。
2. **类型：** 说明它是抽象概念、公共契约、执行角色、状态载体、流程阶段、实现家族、执行模型、策略优化、诊断设施、配置项、源码宏/函数/字段、语言语法、文件格式、构建产物还是观察工具。不同类型不得未经说明放在同一层比较。
3. **朴素含义：** 先用不依赖本专题黑话的一两句话回答“它到底是什么”，再引入精确定义。类比只能辅助，不能代替定义和边界。
4. **当前职责：** 说明它为什么在本场景出现，读取或接收什么，写入、输出或改变什么，由谁拥有，在哪个事件或阶段生效。
5. **边界与易混项：** 说明它不能保证什么、最容易与谁混淆、二者按哪条分类轴区分；版本、架构或 Kconfig 会改变含义时立即标注。
6. **本地解释与深入入口：** 当前章节先写足以继续阅读的最小解释，再给正文内精确标题锚点、权威专题精确标题或官方资料。链接用于深入和取证，不得替代本地首次解释；本地一句话也不得冒充完整权威讲解。

同一小节需要连续引入多个陌生词时，先检查是否把多个学习阶段挤在了一起。优先从具体任务暴露一个知识缺口，解释必要名称，用可观察的过程建立概念，再进入下一个概念。“进入卡”是作者应完成的解释责任，不是要求读者先背一组定义，也不是正文必须反复展示的固定字段模板。只有比较对象已经建立，才进入分类表、关系图或机制推演。表格和图中的私有名称须在附近完成必要解释；深读引用链接到 **完整标题锚点**，不能用链接代替当前推理依赖的解释。

专题私有命名还必须解释命名主体和作用域：是谁定义的名称、它指向概念还是某个版本的对象/状态/实现、状态保存在哪里且归谁所有、与通用概念是什么关系。Tree、Tiny、Tasks、flavor、debt、epoch 之类看似普通的英文词，一旦在专题内取得特殊含义，就按专有名词处理，不能依赖读者猜词义。

只有在术语依赖已经清零以后，才能开始类型比较、因果推演、源码链或配置矩阵。交付时随机抽取标题、表格、图和代码中的名称做冷读测试：读者应能不搜索外部资料说出中英文名称或名称性质、所属类型、当前职责、边界和精确深入入口。自动审计只能找候选词和明显的首次出现风险，不能代替这项人工判断。
