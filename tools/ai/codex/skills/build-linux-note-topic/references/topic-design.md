## 1. 确定读者结果

先写出读者起点：已经掌握什么、缺少什么、最可能带着什么错误模型进入专题。再写出完成专题后必须能够重建或判断的结果。优先选择需要重建时间线、状态机、通信路径或所有权关系的问题：

- 事件发生前后，每项状态分别归哪个参与者所有；
- 什么条件封闭了旧使用者集合；
- 哪项证据证明操作已经完成；
- 一个局部事实如何变成共享或全局事实；
- 谁唤醒等待者，或者谁执行延迟动作；
- 哪项成本从快路径消失了，它被转移到了哪里；
- 什么约束下原方案更合适，什么约束下新机制才成立。

除非已经分解成可观察、可推理的任务，否则拒绝使用“了解主要 API”或“理解原理”作为专题目标。

## 1.1. 清零术语依赖再展开概念

默认读者具备一般计算机基础，但 **不认识当前专题的缩写、源码黑话、实现家族名、配置私称和历史昵称**。专题设计不能把“读过前一章”“从事该子系统开发”或“见过源码”当作隐含先修条件。概念推理开始以前，先把读者理解句子所需的语言准备齐。

第一遍设计时建立工作型术语依赖账本：

| 账本项 | 必须回答的问题 |
| --- | --- |
| 原始写法 | 正文、源码、配置或工具实际怎样拼写？ |
| 中英文名称 | 缩写的 English Full Name 和准确中文名分别是什么？ |
| 名称性质 | 它是缩写、专名、历史昵称、命令还是源码标识符？不存在全称时是否明确说明，而没有杜撰词源？ |
| 术语类型 | 它属于概念、契约、角色、状态、阶段、实现家族、执行模型、优化、诊断、配置、源码符号、格式、产物还是工具？ |
| 朴素定义 | 不使用本专题其他黑话时，怎样用一两句话说清它到底是什么？ |
| 当前职责 | 它在贯穿场景中接收、读取、持有、修改或输出什么，由谁拥有，何时生效？ |
| 前置术语 | 理解本词以前必须先理解哪些词？这些词是否已经排在前面？ |
| 易混项与边界 | 它最容易和谁混淆，分类轴、不能保证的事项、版本/架构/Kconfig 边界是什么？ |
| 首次出现 | 它第一次出现在标题、正文、表格、图、代码、配置还是日志？进入卡是否位于此前或紧邻位置？ |
| 深入入口 | 当前正文的完整标题、权威专题的精确标题锚点或官方资料在哪里？ |

把“首次出现”按读者实际看到的顺序计算，范围包括标题、导航、表格单元格、Mermaid 节点、图片说明、代码与注释、配置、命令、日志和错误消息。不得只扫描普通段落，也不得在表格或源码块先使用、几页以后再补定义。每篇能够独立打开的章节都重新处理本章第一次出现；可以用一句提醒回收前文，但缩写仍给出英文全称和中文名。

术语按依赖关系排序，先解释没有前置词或只依赖通用词的入口，再逐层引入派生概念。一个定义若包含尚未对齐的词，先递归补齐这些前置词；“用更多术语解释当前术语”视为术语债没有清零。只有账本中当前推理所需的依赖已经闭合，正文才进入分类、比较、机制、源码或配置矩阵。

每个承担推理职责的词至少完成以下进入卡：

1. 中英文名称，或“这是不能展开的专名/源码标识符”的名称性质；
2. 所属类型以及与同表其他名称是否在同一分类轴；
3. 不依赖专题黑话的朴素定义；
4. 当前场景的输入、输出、状态所有权、触发时机或使用位置；
5. 不能保证什么、易混项以及版本/配置边界；
6. 当前章节足以继续阅读的本地解释，以及需要纵深时可点击的精确入口。

链接和本地解释承担不同职责：本地解释保证读者不断线，精确链接负责完整教程、版本化实现或证据。两者都不能省略另一方。若连续出现多个陌生词，在第一次使用以前设置“本章术语入口”或按依赖分组的小节；先对齐，再展示分类表、全景图和源码链。术语表若位于使用之后、只列中英文对照而不讲类型与职责，或者表格链接只到文件首页，均不构成合格入口。

专题私有命名必须额外解释：谁定义这个名字、它在该专题中指向概念还是实现对象/状态、状态落在哪里且归谁所有、与通用词义是什么关系。普通英文单词一旦被子系统赋予特殊含义，也按专有名词处理。

冷读时随机指向一个标题、表格、图或代码标签。若读者不能在当前章节找到并说出中英文名称或名称性质、类型、当前职责、边界和精确深入入口，或者解释过程中还要连续追问“这个词又是什么”，本章不合格。篇幅压力不是跳过解释的理由；应拆分章节、移动纵深材料或增加前置入口。

## 2. 服从本次编辑权限

先按 `SKILL.md` 的“先确定编辑授权”选择仅排版、保留内容的结构调整或内容修改/重写模式。本参考只决定怎样设计专题，不扩大正文修改权限。

记录任务开始时的工作树和已审材料。仅排版时，只显化现有章节的职责与依赖；结构调整时完整移动已盘点内容；内容修改时才允许补充推演、修正模型或重写正文。

## 3. 执行两遍生成

创建、扩写或重写专题时，先设计后写作。

第一遍建立专题设计账本：

| 设计项 | 内容 |
| --- | --- |
| 读者起点 | 已有知识、任务背景和最可能的错误模型 |
| 读者结果 | 最终能重建的过程、证明或选择 |
| 术语依赖 | 本专题私有词的中英文名称、类型、依赖顺序、首次出现和精确入口 |
| 全景定位 | 主题在系统中的层次、上下游模块与输入输出 |
| 贯穿场景 | 真实负载、规模、参与者和共享对象 |
| 旧方案 | 已有保证、实际价值和适用范围 |
| 故障链 | 从触发条件到错误或停顿的有序步骤 |
| 错误模型 | 为什么看似成立、由哪个反例产生矛盾、需要什么最小修正 |
| 证明义务 | 安全性、活性、顺序、生命周期或隔离 |
| 执行模型 | 会改变参与者定义、状态位置或证明方式的配置与上下文 |
| 状态轴 | 单一状态机或多组正交状态 |
| 观察视角 | 概念、状态、时序、调用者、源码、硬件或工程视角中的必要集合 |
| 工程约束 | 资源、构建、部署、恢复、观测和平台限制 |
| 证据计划 | 稳定知识、版本源码、实验和平台证据的目的位置 |

随后选择章节角色，画出 **完整** 依赖关系，并为每章建立契约。第二遍才按依赖图写正文。不要先生成大量章节，再反向寻找它们为什么存在。

仅排版任务不重新建立技术模型；第一遍改为内容账本，把现有信息单元映射到阅读阶段和目的位置。

## 3.1. 确定分类轴和模块变体矩阵

当专题既有公共语义或公共 API，又有多个实现家族、配置分支或执行模型时，不能只画章节因果链，还要先画 **分类轴与模块变体矩阵**。否则很容易把某个配置当成完整主题纵向讲一遍，再在另一个配置下重复公共模块。

先把名称放回各自的正交轴：

| 分类轴 | 回答的问题 | 常见误排 |
| --- | --- | --- |
| 公共契约/API | 调用者跨实现能够依赖什么 | 把内部优化写成 API 语义 |
| 保护域或语义 flavor | 哪些参与者和对象属于同一等待域 | 与底层实现家族并列成一种“类型” |
| 实现家族 | 哪套核心算法和数据结构兑现契约 | 用某个本地目录名代替家族定义 |
| 执行模型 | 抢占、迁移、阻塞、中断等条件怎样改变参与者或证明 | 为只改变一个模块的配置复制完整系统 |
| 运行策略或优化 | 普通/加速、卸载、批处理等怎样改变成本或通知路径 | 提前打断默认主线 |
| 诊断设施 | 怎样观察或检查功能路径 | 把检查器状态写成功能状态 |

分类结果必须在第一个变体内部实现以前进入正式阅读路线。随后以功能模块为行建立矩阵：

| 模块 | 公共概念与输入输出 | 公共实现 | 变体 A 差量 | 变体 B 差量 | 证据 | 实验 |
| --- | --- | --- | --- | --- | --- | --- |
| 一个可独立学习的职责 | 为什么存在、接收什么、输出什么 | 跨变体共享的角色与状态 | 只记录改变项 | 只记录改变项 | 源码/规范 | 对应证明义务 |

默认阅读顺序按行推进：先讲模块概念和公共职责，再并列比较变体。只有某个变体改变了大部分端到端参与者集合、证明方式、控制流与完成条件，纵向单独成篇才有必要。若两个变体章节重复出现相同的公共执行者、数据结构和完整时序，应回到矩阵重新判定主轴，而不是靠“详见前文”维持两份空心章节。

组合应用、对象生命周期、诊断和选型不能插入公共接口与分类坐标之间。实验可以在结尾集中编排，但每个实验必须回链它验证的模块结论或变体差异，读者能够说明“改哪个条件、观察哪个状态、支持哪条证明”。

## 4. 准备贯穿场景

比较不同设计时尽可能复用同一个场景：

| 项目 | 必备内容 |
| --- | --- |
| 负载 | 读写频率、CPU 数量、时延、内存、睡眠和拆除约束 |
| 参与者 | 有名称的任务、CPU、中断、回调、设备和数据结构 |
| 被保护对象 | 正式入口、共享状态、对象或硬件事务 |
| 现有设计 | 它提供什么保证，以及当前为什么正确 |
| 故障链 | 从触发条件到错误观察、竞争、UAF、停顿或泄漏的有序步骤 |
| 所需保证 | 安全性、顺序、生命周期、进展性或隔离属性 |
| 证据 | 所需的源码版本、配置、跟踪、实验或基准测试 |

先给出具体场景和必要代码，再从约束推导抽象角色。这里的代码用于固定问题现场；完整 API 模板可以在抽象契约成立以后出现。

## 5. 按职责选择章节角色

本地 RCU 专题提供的是以下可复用职责，而不是固定篇数或固定编号：

| 章节角色 | 解决的问题 | 使用条件 |
| --- | --- | --- |
| 问题压力 | 旧方案解决了什么，缺口如何逐步形成 | 所有专题 |
| 抽象机制 | 不依赖目标系统字段，怎样从约束推出角色、边界和证明义务 | 机制不能只靠 API 定义时 |
| 最小使用闭环 | 抽象动作怎样对应接口、正常路径、失败路径和拆除 | 存在公共 API 或调用协议时 |
| 组合与生命周期 | 多种独立机制怎样由对象所属模块完成交接 | 涉及引用、回调、工作队列或复合分配时 |
| 执行模型证明 | 某一配置或上下文下，安全性为什么成立 | 不同模型具有不同参与者集合或证明方式时 |
| 源码实现映射 | 证明模型怎样落实为字段、写路径、读路径和完成条件 | 需要版本化实现证据时 |
| 现实条件加固 | 哪些抢占、迁移、中断、离线、乱序或迟延条件击穿朴素模型 | 真实运行条件会改变模型时 |
| 统一状态与通信全景 | 多组状态和多条通信路径怎样完成一个操作周期 | 分布式或分层机制 |
| 子状态机纵深 | 统一全景中的关键模块怎样独立推进 | 单篇总图不足以解释实现时 |
| 实现家族与配置 | 不同变体改变了哪些保证、参与者和成本 | 存在可选择实现时 |
| 应用、诊断与选择 | 怎样正确组合、观察故障并选择替代方案 | 所有完整专题的收尾 |

抽象契约建立以后，最小正确用法应早于大段实现纵深，使后续源码讨论具有具体落点。

## 6. 决定合并与拆分

章节角色可以合并或省略：

- 只有一个简单执行模型时，证明与源码映射可以同篇；
- 没有跨机制所有权时，不创建组合与生命周期章节；
- 状态不分层、通信路径简单时，不强制建立统一总图；
- 没有实现家族时，不为对齐 RCU 创建变体章节；
- 一个子状态机不足以独立学习时，保留在统一实现章节；
- 一篇同时承担两套独立证明、两个完整生命周期或多种配置模型并影响连续阅读时，才拆分。
- 多个变体共享大部分端到端模块时，以模块为主轴合并公共实现并比较差量；不得仅因 Kconfig 名称不同就复制整条实现链。

文件数量由证明边界和阅读连续性决定，不由 RCU 篇数、历史七段式或八步法决定。

## 7. 为每章建立契约

写正文前为每章记录：

| 契约项 | 必须明确的内容 |
| --- | --- |
| 前置结论 | 本章允许假设读者已经知道什么 |
| 术语前置 | 本章首次使用哪些专有名词，怎样在使用前完成进入卡，定义依赖是否已经闭合 |
| 本章问题 | 本章只解决哪一个主要问题 |
| 为什么现在讲 | 上一章自然产生了什么问题，使本章此时成为必要步骤 |
| 贯穿场景 | 继续复用哪个对象、参与者和时间边界 |
| 错误模型或反例 | 本章要击穿什么误解，或用什么条件检验当前模型 |
| 新增模型 | 新增了哪些角色、状态、约束或通信路径 |
| 输出结论 | 本章结束后能够证明什么 |
| 证据 | 由代码、源码、配置、图、trace 或实验中的什么支撑 |
| 后续缺口 | 哪个问题有意留给下一章 |

章节契约不是必须提交的额外文件；优先把精简结果写入 `大纲.md` 的阅读地图。

章节之间通过未决问题连接，而不是只通过文件编号连接。每章开头回收上一章输出并暴露一个新缺口；正文一次只引入解决该缺口所需的模型增量；结尾明确本章新结论和下一章尚待兑现的证据。不得为了形式统一强迫 API 章、源码章和诊断章使用相同小节模板。

## 连续阅读与反形式主义验收

专题设计必须同时通过 **内容正确性** 和 **连续阅读性** 两类验收。目录、链接、表格、图、源码符号和版本信息都只是表达或证据手段，不能代替读者沿正文形成模型。出现下列任一情况时，即使结构审计全部通过，章节仍判定为不合格：

- 标题承诺讲解概念、机制或源码实现，正文却主要介绍资料位置、文件分流和外部入口；
- 删除链接目标或禁止点击以后，关键概念、问题、方案或状态转换无法从当前正文推出；
- 读者必须先理解测试编排、配置例外或后续章节，才能知道本章正在解决什么；
- 标题、表格、图、代码或配置先使用专题私有名称，正文后置解释，或者定义本身继续依赖未解释术语；
- 同一流程被多张表、图和清单重复转写，却没有产生新的判断能力；
- H2 只是复述 H1，或者标题下面没有任何解释便直接进入下一个标题；
- 概念、执行者、状态地址、流程阶段、配置变体、优化和诊断设施在同一层并列；
- 章节已经把下一章应通过反例推出的模型增量提前完整公布；
- 审稿只能确认“要素都在”，却不能用简短语言复述一条从问题到结论的主线。

### 标题契约

写正文以前先把标题翻译成读者任务：

| 标题承诺 | 当前章节必须本地兑现 | 不能用什么替代 |
| --- | --- | --- |
| 基础概念或原理 | 定义、边界、与相邻概念的区别、最小动态过程 | 术语链接或名词表 |
| 问题与证明模型 | 旧模型价值、具体矛盾、最小修正和证明边界 | 直接宣布成熟方案 |
| 状态与通信机制 | 参与者、状态位置、写读关系和完整周期 | 字段清单或总图 |
| 源码实现、源码讲解或源码机制 | 模块职责、输入输出、关键状态、真实调用链以及本地源码证据 | 源码索引、跳转表或“详见其他文件” |
| 实验与验证 | 环境、步骤、预期结果、失败现象和证明边界 | 命令名或未执行示例 |
| 导航或索引 | 分流条件、阅读顺序和入口职责 | 第二份机制教程 |

若知识正文只解释跨版本稳定的实现模型，应在标题中使用“实现模型、状态与通信”等准确表述，并把精确函数体链接到研究层。若标题明确承诺逐函数源码实现，则正文职责和保存位置必须服从源码阅读规范，不能把导航文件伪装成实现正文。

### 断链阅读测试

交付前把所有超链接视为不可点击，只保留当前文件可见文字，检查读者能否回答：

1. 本章第一次出现的核心概念是什么，与哪些相近类型不同；
2. 哪个具体现场提出了什么问题；
3. 当前模块增加了什么角色、状态、通信或约束；
4. 一次正常流程怎样从输入走到输出；
5. 哪项源码、实验或规范只是为已经讲清的结论作证；
6. 本章现在能够证明什么，下一章仍要解决什么。

任何问题只能靠点击链接回答，都表示链接承担了正文职责。修复方式是把当前场景所需的最小解释写回本地，再保留精确链接供深入追踪；不是复制完整外部教程。

### 模块局部闭环

一个章节含有多个实现模块时，按问题依赖逐个闭合，不先给全量组件目录。每个模块至少形成以下阅读动作：

```text
基础概念与类型定位
    → 当前模块面对的具体问题
    → 解决方案及状态/通信变化
    → 让读者预测一个中间状态、反例或失败后果
    → 用实现、源码、实验或日志验证
    → 把新结论交给下一个模块
```

“引导读者思考”不能退化成无答案的设问。问题必须位于答案以前，能够让读者使用已经建立的模型作出预测；随后的源码或实验再确认、修正或击穿这个预测。

### 主线、分支与表示预算

先冻结一个默认配置、一条正常路径和一组贯穿对象。优化、诊断、版本差异、特殊配置与下一执行模型在主线闭合后分区处理。每新增一种表示，都记录它独自回答的问题：

- 角色关系图用于定位状态或所有权；
- 时序图用于暴露执行顺序和异步窗口；
- 状态表用于比较转换前后与读写者；
- 源码摘录用于验证具体实现落点；
- 证据索引用于审稿或深入阅读，不进入主叙事。

若两种表示回答同一个问题且没有新增判断能力，保留更清楚的一种。证据账本、链接清单和全字段覆盖表应留在研究或审稿层，不得以“信息完整”为理由插入出版型连续正文。

### 冷读复述门禁

最终审稿从未参与写作的读者视角进行，不查看工作型蓝图，也不点击链接。先随机抽取标题、表格、图、代码和日志中的专有名称，确认读者能够说出中英文名称或名称性质、类型、当前职责和边界，且定义没有继续夹带未知词；再用五到八句话复述“前置结论 → 本章问题 → 模块增量 → 完成条件 → 后续缺口”。无法完成任一步、需要先解释大量例外，或者复述结果只是文件名和字段名列表时，必须继续重写。不得用自动脚本通过替代这一人工语义判断。

## 8. 区分抽象机制与具体实现

抽象章节使用调用者、参与者、局部证据、协调者、等待者和延迟执行者等角色，并推导这些角色为什么存在。

源码章节随后将角色映射到任务、per-CPU 状态、节点、全局结构、锁、回调以及调度器或中断路径。不得用某个 Linux 字段的存在反过来充当抽象机制存在的理由。

主要执行模型的证明方式确实不同时，先分别建立证明，再分别映射源码；只有字段不同而证明相同时，放入同一实现章比较，不机械成对拆篇。

## 9. 加固朴素模型

从 [mechanism-reasoning.md](mechanism-reasoning.md) 选择适用反例，检查未来参与者、抢占迁移、异步传播、多轮交叠、中断离线、对象逃逸、内存乱序和拆除竞态。

每发现一个缺口，都必须增加一种状态、一条通信路径、一项约束，或者一个明确的不支持场景。反例没有改变模型时，说明它由哪条既有不变量覆盖。

## 10. 保持权威专题独立

当一种机制依赖缓存一致性、内存顺序、原子操作、调度、kref 或其他可复用机制时：

- 将完整的通用教程保存在它自己的权威位置；
- 在当前场景保留该依赖及其失败后果；
- 在实际使用前置知识的位置添加链接；
- 避免创建无法独立成为研究专题的微型“扩展概念”；
- 确保被链接的权威专题拥有自己的场景、推导、证据，以及适用时的实验。

## 11. 让大纲成为学习地图

大纲先画章节依赖图，再为每章说明：

- 前置结论；
- 本章解决的问题；
- 新增的角色、状态或证明；
- 交给下一章的未决问题。

工作型蓝图必须规划完整章节链；仓库正式大纲只链接真实存在的文件，不复制各章解释，也不把尚未落地的设想章节列成已经完成的内容。分批生成时，每落地一章就更新正式大纲、前后导航和未决问题。读者沿默认顺序阅读时，应能看见模型怎样被问题和反例逐步完善。

## 12. 保留从错误模型到正确模型的突破路径

容易误解的关键机制不要直接宣布答案，按以下闭环推进：

```text
错误模型为什么看似成立
    → 固定参与者、状态位置和时间顺序
    → 用具体反例推出矛盾
    → 只增加解决本轮矛盾所需的状态、角色、通信或约束
    → 用正确模型重新解释原场景
    → 说明仍未覆盖的条件
```

只列“常见误区”而不展示它怎样导出矛盾，不构成理解突破。反例必须改变模型，或者明确由哪条既有不变量覆盖。

## 13. 使用多视角动态过程并区分抽象层

按主题选择概念、数据结构、状态机、时间/时序、CPU/线程/中断、调用者、源码、硬件和工程部署视角，不机械凑齐。所有视角复用同一组关键对象、阶段和事件，明确说明层间映射：

```text
定义 ≠ 实现
API 契约 ≠ 内部算法
逻辑状态 ≠ 具体字段或寄存器
软件同步 ≠ 硬件缓存一致性或内存顺序
协议保证 ≠ 控制器或平台能力
稳定模型 ≠ 某个版本的源码组织
```

关键结论至少展示一个完整周期：转换前状态、触发动作、中间传播、完成条件、转换后状态和失败分支。图用于角色、状态、时序、Before/After、层次、数据流和生命周期；箭头标出动作或状态流，正文解释关键转折。Mermaid 换行使用 `<br/>`，不使用 `\n`。

先用机制解释为什么成立，再用规范、源码、实验、日志、trace、波形或基准证明当前实现怎样兑现。证据不足时标记推论和边界，不得用“大概如此”补齐。

## 14. 按题型调整讲解顺序

| 题型 | 优先认知顺序 |
| --- | --- |
| 数据结构、算法与 API | 使用问题 → 最小正确用法 → 常见操作与失败清理 → 内部结构和动态算法 → 实现证据 → 复杂度、边界与选择 |
| 硬件、芯片与协议 | 系统位置 → 参与设备 → 一次完整事务 → 信号和时序 → 寄存器与控制器状态 → 驱动映射 → 板级约束 |
| 内核机制与并发 | 问题压力 → 抽象证明 → 真实条件加固 → 状态与通信闭环 → 源码证据 → 应用选择 |
| 工程系统 | 目标与环境 → 资源预算 → 构建和镜像或部署布局 → 启动与运行流程 → 故障恢复 → 可观测验证 |

资料原始顺序只作为查询入口，不直接充当学习顺序。数据结构/API 题型在最小契约成立后先解决“怎样正确使用”；工程题型必须纳入资源、构建、部署、恢复和观测约束。

## 15. 分批生成但保持深度

长专题可以分批写作，但先冻结完整工作型蓝图和每章契约。以完整章节或完整小节为批次边界，每批回收前置结论并记录已经兑现的结论、未决问题和下一批证据。后续批次继续满足相同的因果、动态过程和证据门禁，不因上下文增长而变成摘要。

篇幅压力不能成为删除“为什么”、故障链、关键状态转换、失败清理或边界条件的理由。证据推翻蓝图时，显式修订大纲和受影响章节。

## 16. 以可迁移心智模型验收

完成标准不是篇幅、知识点、源码或图表数量，而是读者能否：

- 画出主题在系统中的位置、关键对象和完整动态过程；
- 从旧方案的保证逐步推出缺口，并用反例检验错误模型；
- 区分抽象保证、API 契约、当前实现和平台边界；
- 在未直接讲过的新负载、配置或失败条件下继续推导；
- 根据约束选择原方案、当前机制或替代方案；
- 说明需要什么源码、实验或观测证据才能确认推论。

最终验收定义是否清楚、因果链是否闭合、模型是否自洽、动态过程是否完整、层次映射是否明确、边界是否可操作，以及模型是否支持继续推理。
