## 1. 来源与优先级

本参考提炼自当前仓库的以下材料：

- 当前确认的“技术书籍 / 专题生成”需求基线；
- `tools/ai/topic_summary_requirements/P01_主题章节的要求.md` ～ `P05_主题章节的要求.md`；
- `tools/ai/application/mermaid_require.md`；
- 当前仓库 `AGENTS.md` 的写作、信息架构、源码和专题组织要求。

技术书籍的通用认知设计以 [topic-design.md](topic-design.md) 为准；本文件负责把它落到 linux-note 的题型、目录和格式约束。历史要求面向不同书稿、题型和时间点，不能机械叠加成一套固定章节模板。发生冲突时，依次服从：本次用户明确要求、当前 `AGENTS.md`、当前信息架构与格式规范、本参考的提炼规则；历史文件中的题型模板只作为按需选择的结构。

## 2. 一句话主线

围绕一个明确主题完成以下闭环：

> 建立系统全景与读者坐标 → 明确要解决的问题或完成的任务 → 解释旧方案或错误模型为何看似成立以及缺口怎样暴露 → 展开参与者、状态、数据结构和动态过程 → 映射到源码、硬件、配置或接口 → 给出完整用法与示例 → 提供可观察验证 → 说明工程约束、边界、替代方案和后续关系。

这条主线是共同底线，不要求所有章节使用相同标题。

正文还必须通过 **断链连续阅读**：假设出版物隐藏 URL、读者不点击链接，当前章节仍能完成标题承诺的概念、问题、方案、动态过程和结论。链接只负责补充版本化证据、完整函数体或跨专题纵深，不能代替首次解释。标题、图表、阶段表、源码链接和核对表齐全只表示材料存在，不表示章节已经形成认知路径。

## 3. 按题型选择章节骨架

| 题型 | 优先骨架 | 必须强化的内容 |
| --- | --- | --- |
| 内核机制、并发与竞争 | 问题压力 → 抽象机制 → 真实条件加固 → Linux 实现 → 用法 → 代价与选择 | 状态所有权、通信路径、S0…Sn、角色图、端到端时序、源码证据 |
| 数据结构、算法与 API | 使用问题 → 最小正确用法 → 常见操作 → 内部结构与动态算法 → 实现 → 复杂度与选择 | 错误模型、Before/After、边界条件、失败清理；算法题按需补题型识别、朴素方案、隐藏测试和变形 |
| 芯片、控制器与通信协议 | 系统位置 → 一次完整事务 → 信号/时序 → 寄存器与状态机 → 驱动映射 → 板级约束 → 调试 | 参与设备、信号方向、采样边沿、寄存器状态、波形、平台能力与电气边界 |
| 驱动接口、DTS、U-Boot、Buildroot 或配置语法 | 主题引入 → 数据结构 → 开发者视角 → 用户/平台视角 → 图示 → 示例 → 调试验证 → 小结 | 语法四连问、配置到内核对象的映射、用户可观察结果、错误配置后果 |
| 面向应用的模块或原语用法 | 概念 → 能做/不能做 → 核心模式 → 混搭与边界 → 常见坑 → 最小模板 → 核对表 | 上下文限制、组合顺序、反模式、可粘贴模板 |
| 工程系统、升级与部署 | 目标与约束 → 资源/布局 → 状态机与正常流程 → 故障与恢复 → 构建部署 → 观测验收 | Flash/RAM/带宽预算、链接与镜像布局、掉电/回滚、幂等、安全边界和目标环境可实现性 |
| 出版型完整章节 | 背景与目标 → 原理与实现 → 使用方式 → 接口/工具 → 区别与限制 → 完整示例 → 小结 | 章节完整、标题连续、图表代码有解释、与前后章节衔接 |

先判断题型，再裁剪骨架。不得同时强制套用“七段式”“八步法”“每章三张表”和“纯因果链”等全部历史模板。

当同一题型还包含公共 API、多个实现家族或配置变体时，必须在骨架内继续执行：

```text
公共概念与接口
    → 正交分类轴
    → 公共端到端骨架
    → 按功能模块讲公共实现并比较变体差量
    → 与结论配对的源码或实验验证
```

分类轴早于变体内部实现；功能模块默认是实现纵深的主轴。只有变体改变了大部分参与者、证明方式和完成路径时才纵向独立成篇。不得把同一公共实现分别包装成“变体 A 完整源码链”和“变体 B 完整源码链”，再在后文第三次按模块展开。

## 4. 所有专题的共同内容底线

无论采用哪种骨架，都要覆盖适用的以下问题：

1. **主题与结果：** 本篇聚焦什么，读者完成后能重建哪条流程、作出什么选择或完成什么操作。
2. **背景与动机：** 原方案、默认行为或现状解决了什么，具体缺口怎样形成。
3. **对象与状态：** 参与者是谁，状态或配置保存在哪里，谁写、谁读、何时转换。
4. **机制与落点：** 抽象原理怎样落实到数据结构、调用链、配置项、寄存器或用户接口。
5. **用法与闭环：** 给出足够完整的初始化、正常路径、失败路径、清理和拆除流程。
6. **观察与验证：** 提供命令、日志、trace、sysfs、`dmesg`、实验或其他可操作证据，并说明预期结果。
7. **边界与选择：** 说明能做什么、不能做什么、常见误用、替代方案和适用条件。
8. **总结与衔接：** 提炼关键不变量、核对项，以及与前后专题的关系。
9. **迁移能力：** 给出一个没有逐字讲过的变体、负载或失败条件，让读者能够使用已建立模型继续推导。
10. **术语入口：** 把读者视为尚未掌握专题私有词汇的小白，在标题、表格、图、代码、配置和日志首次使用以前，给出中英文名称或名称性质、术语类型、朴素含义、当前职责、边界和精确深入入口。

某项与当前主题无关时可以省略，但不能用空泛结论代替承担方案选择依据的关键推导。

## 4.1. 零基础术语门禁

linux-note 的知识正文默认允许章节被单独打开阅读。每篇章节第一次使用英文缩写时，给出正式英文全称和准确中文名；命令、项目、实现家族、历史昵称和源码标识符不是缩写时，明确名称性质，不为满足格式杜撰全称。前一章已经解释过，只能减少重复纵深，不能省略本章的一句本地提醒和精确回链。

首次出现按读者可见顺序计算，包括标题、导航、正文、表格、Mermaid、图片说明、代码与注释、配置、命令、日志和错误消息。专有名词密集时，在第一次使用以前设置按依赖排序的术语入口；不得先给分类表、源码链或配置矩阵，再让读者去后文找定义。

每个影响理解或结论边界的术语至少回答：

1. 中英文名称是什么，或者为何它只是不能展开的专名/标识符；
2. 它属于概念、角色、状态、阶段、实现家族、执行模型、策略、诊断、配置还是源码符号；
3. 不依赖本专题黑话时，它到底是什么；
4. 在当前场景中谁拥有或使用它，它接收什么、改变什么、何时生效；
5. 它不能保证什么，最容易和谁混淆，版本、架构或 Kconfig 边界是什么；
6. 当前章节的最小本地解释和权威纵深的完整标题锚点分别在哪里。

定义中出现的新专有名词必须先递归解释。链接只负责深入和证据，不能替代本地解释；本地一句话也不能冒充完整教程。普通英文词被子系统赋予私有含义时，按专有名词处理，并说明命名主体、作用域、实际对象或状态落点。篇幅不足时拆分或增加前置入口，不得跳过术语对齐后直接展开概念。

## 5. 语法、接口和配置的四连问

遇到 DTS 属性、内核接口、配置项、命令或语法时，至少回答：

1. 它的作用和语义是什么；
2. 它在什么场景、阶段或执行上下文使用；
3. 不写、写错或使用默认值会发生什么；
4. 它被哪条驱动、解析、调用或寄存器路径消费。

涉及 DTS 或配置映射时，按需画出并解释：

```text
配置/语法 → 解析入口 → 内核对象或描述符 → 驱动使用路径 → 硬件或用户可观察结果
```

只展开与该语法直接相关的字段，不为展示源码而无边界罗列结构体。

## 6. 多视角是条件要求

- **开发者视角：** API 如何调用，回调、上下文、错误处理和资源释放怎样写。
- **用户视角：** 用户空间能看到什么，如何操作和验证。
- **平台视角：** DTS、ACPI、SoC、BSP 或构建配置怎样影响行为。
- **内核视角：** 数据结构、调用链、配置分支和状态转换怎样兑现契约。

驱动、接口和配置主题通常需要多视角；纯抽象机制章节可以只保留与证明相关的视角。不得为了凑齐视角重复无关内容。

## 7. 示例代码要求

- 示例要能编译，或至少结构完整并明确未编译的环境边界。
- 覆盖分配/初始化、发布或注册、正常操作、失败清理、撤销和最终释放。
- 仓库自有示例使用中文注释；原样引用上游源码时明确标注引用边界。
- 示例前用文字或图说明执行逻辑，示例后解释关键步骤、不变量和可观察结果。
- 只有主题涉及资源托管 API 时，才比较非 `devm_` 与 `devm_` 版本，并说明释放逻辑和适用边界；不得把 devres 强制扩展到所有专题。
- 最小模板服务于复用，但不能省略恰好决定正确性的语句。

## 8. 图表与表格要求

- 图用于解释文字难以直观看出的状态变化、通信、调用链、所有权或层级关系，不按固定数量堆图。
- 并发机制遵守当前 `AGENTS.md`：至少包含角色/状态关系图和端到端时序图，并标注动作或状态流。
- Mermaid `sequenceDiagram` 默认使用 `autonumber`，图后解释使用步骤号定位关键转折；不提供可定位顺序的宽时序图不得交付。
- 对比的两条路径若对事件是否发生、参与者集合或证明条件有不同结论，使用两张复用同一组对象名的独立时序图，并用颜色标出差量；不用单图 `alt` 把互斥的事件压在同一时间轴。
- Mermaid 使用原生语法，节点标签使用英文双引号，图中命名与正文和代码一致；遵守 `tools/ai/application/mermaid_require.md` 的当前规则。
- 当前 Mermaid 规范明确禁止为兼容旧模板而使用 HTML 实体转义或透明 `level` 子图强制排版。
- 表格优先用于并列比较、接口速览、状态矩阵和交付核对；不再把“每章固定三张表”作为所有题型的硬门禁。
- 自动审计按专题整体检查必要的代码与关系图、时序图，不把“每篇章节各有一份”作为告警条件。

## 9. 源码阅读复用结构

- 同一源码专题同时包含模块阅读与具体实现讲解时，在 `research/source_reading/<topic>/` 下使用 `navigation/` 和 `source_explanations/` 分离职责，不在专题根目录混放两类 Markdown。
- `navigation/` 包含一个总阅读索引和按子功能/模块组织的源码概念导读。总索引链接全部模块导读；模块导读借源码讲清模块职责、参与者、状态、调用链和阅读顺序，可以包含应用代码、伪代码、表格和 Mermaid，但不逐段展开上游宏体或函数体。
- `source_explanations/` 按具体宏、函数、字段或紧密关联的实现簇组织文档；同一版本的同一实现只有一个权威讲解标题，每篇实现讲解都回链总索引和所属模块导读，并提供上游相对位置、仓库补充的中文 Doxygen 注释、中文行内源码、实现原理、调用上下文与状态副作用。
- 知识正文首次使用版本源码证据时链接总阅读索引和相关模块导读，遇到具体接口或检查点时再链接“相对文件路径 + Typora 完整标题片段”，不复制已有源码实现讲解。
- 数据结构或字段簇首次承担机制推理时，当前章节先本地说明类型、所有者、当前职责和读写者，再使用完整标题锚点跳到权威结构/状态机/版本实现讲解；既不只抛结构名，也不复制全字段。
- 目录移动后同步专题大纲、源码基线、Markdown/Obsidian 和其他入链，全仓清除旧路径，不保留兼容副本。

## 10. 调试、验证与交付

- 每个重要结论都要说明如何观察，不只给命令名称。
- 调试部分至少写明操作步骤、预期输出、失败现象和定位方向。
- 实验必须说明环境、版本、配置、执行方式、预期结果和清理方法。
- 章节过长时以完整小节为边界分批，不能在代码、表格、图或推导中间截断。
- 分批生成前先冻结工作型全书蓝图和章节契约；后续批次不得因上下文增长而退化成摘要，证据推翻设计时应同步修订大纲和受影响章节。
- 输出直接遵守仓库当前标题、元数据、相对链接和中文代码注释规范，不复制历史模板中的旧编号样式。
- 交付前检查内容范围、源码边界、示例完整性、图表语法、链接、元数据和 `git diff --check`。

## 11. 不应提升为通用硬规则的历史要求

以下内容只在对应项目或用户明确要求时使用：

- 固定的七段式、八步法或每章三张表；
- “模块为纲”或“问题驱动”二选一的绝对要求；当前内核机制专题优先采用仓库规定的因果学习链；
- 固定 i.MX6ULL、GIC 版本、内核版本或某个 DTS 节点作为所有主题默认示例；
- 所有章节都必须同时具备用户、开发者、平台和内核四个视角；
- 所有资源主题都必须展示 `devm_` 版本；
- 每章必须为图表凑数量；
- 任何旧 Mermaid HTML 转义规则。

这些历史条款仍可作为具体书稿模板，但不能覆盖当前仓库规范或本次用户意图。

## 12. 精简验收清单

- [ ] 已选择与题型匹配的章节骨架，没有叠加互相冲突的历史模板。
- [ ] 存在多个家族或配置变体时，已在第一个变体实现以前建立公共契约、正交分类轴和公共骨架。
- [ ] 已建立模块 × 变体矩阵；公共实现只讲一次，各变体只展开参与者、状态、通信、完成条件和成本的真实差量。
- [ ] 组合应用、生命周期、诊断与选型没有打断公共接口到分类坐标的必要前置链；实验能够回指具体模块结论或变体差异。
- [ ] 主题、读者结果、背景动机和适用边界明确。
- [ ] 默认读者不掌握专题私有词汇；每章已经在标题、表格、图、代码、配置和日志首次使用以前完成中英文名称或名称性质、类型、朴素定义、当前职责、边界和精确入口对齐，定义没有继续夹带未知词。
- [ ] 已在正文前完成工作型全书蓝图、章节依赖和每章契约；正式大纲只链接真实文件。
- [ ] 开篇先建立系统位置与交互全景，没有直接陷入 API、寄存器或源码。
- [ ] 关键误解通过“错误模型 → 具体矛盾 → 最小修正 → 正确模型”完成推导。
- [ ] 选择了当前主题所需的观察视角，并让各视角复用同一组对象、阶段和事件。
- [ ] 关键机制给出动态过程，而不是只罗列定义、性质、字段或接口。
- [ ] 关键参与者、状态位置、数据结构和执行链能够相互对应。
- [ ] 语法、接口或配置回答了作用、场景、错误后果和实现落点。
- [ ] 示例覆盖正常、失败、清理和拆除路径，代码注释符合仓库规范。
- [ ] 图表和表格解释真实关系，没有为数量或单一渲染器堆砌结构。
- [ ] 提供了可执行的验证方法、预期结果和故障定位方向。
