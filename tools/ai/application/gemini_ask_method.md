# 第1章\_技术讨论的上下文与协作约定

复杂技术讨论容易出现两种断裂：回答只列结论，读者无法重建过程；分批继续时又丢失已经确定的范围、版本和未解决问题。本页把原有的“讲透、背景先行、图文结合、连续推进”偏好整理为可执行的请求方式。文件名沿用旧记录，规则不限定某一家模型产品。

本页是协作参考，不是某个服务已经保存偏好的证明。新会话是否得到这些内容，应以实际提供的上下文为准；在本仓库工作时，还应读取 [项目约定](../../../AGENTS.md) 和 [专题编写 skill](https://github.com/FormingSystem/ai_agent_skill/blob/main/skills/build-linux-note-topic/SKILL.md)，不依赖一句“我已经永久记住”。

## 1.1\_先说明读者要获得什么能力

比起只要求“详细讲解”，更有效的请求是说明读者起点和想解决的问题。例如：“我会 C，但不懂设备与驱动怎样绑定；请从设备发现的问题开始，讲到我能追踪一次 probe 失败及资源回收。”这样可以判断哪些背景是必要前置，哪些源码细节应稍后展开。

深度由推理是否闭合衡量：旧方案原来解决了什么，在什么条件下失败，新机制改变哪个步骤，状态归谁所有，代价与边界是什么。不能为了省篇幅删去决定结论的步骤；也不必把无关源码和术语填满每个段落。

| 协作偏好 | 具体做法 | 怎样判断是否落实 |
| --- | --- | --- |
| 背景先行 | 从场景、原方案和具体缺口引出新机制 | 隐去表格与术语后，读者仍能说明为何需要它 |
| 解释充分 | 展开角色、状态位置、动作顺序与结果 | 能预测改动一个条件后的行为 |
| 图文与证据配合 | 在因果过程难以直观看清处加图，在版本相关结论旁给源码或规范 | 图中箭头有动作；引用能追到具体依据，而正文无需跳出去才能理解 |
| Markdown 连续阅读 | 按问题安排标题，代码与命令就地解释，维护导航和锚点 | 标题能概括正文解决的问题，下一段接得住上一段 |
| 持续推进 | 在授权范围内分批完成并记录进度、限制和下一步 | 不把提纲、样章或一个批次冒充完整任务 |

原约定“每一部分都必须含源码与图”在这里按学习用途落实。概念推演先建立角色与保证，涉及实现时再进入固定版本代码；一个简单事实不必附装饰图，参考页也不应为了形式变成长篇教程。

## 1.2\_一段可以直接修改使用的请求

下面模板描述写作任务，不伪装成模型服务的系统级权限。把方括号中的项目换成实际内容，再提供需要处理的文件：

> 我希望把［专题及文件范围］整理为［连续教材／独立文章／查询参考］。读者已经会［前置知识］，读完应能［解释、预测或操作的具体能力］。
>
> 请按“问题背景—旧方案的价值与缺口—新机制推导—真实约束下的完善—目标实现—应用和代价”安排学习顺序。必要过程充分展开，不用一句优点代替推导；图表先有解释背景，再补状态、连接和字段细节。
>
> 操作命令和示例在正文就地讲清环境、步骤、预期结果及失败恢复。版本相关内容给出可核对依据；没有实际执行的构建、硬件实验和界面检查明确标记。
>
> 当前授权是［只排版／保留内容的结构调整／重写纠错］。复杂内容可以分章分批，但持续推进到约定范围完成；保留有效知识和原始证据，维护链接与完成记录，不以分批为由反复要求确认已授权的下一步。

将它放入新会话、项目说明或使用工具实际支持的偏好设置中，都需要确认工具是否确实读取；本页不承诺任何产品具有永久记忆，也不替用户修改账户设置。

## 1.3\_长任务如何交接而不重新开始

每次阶段交接保留四类事实：原始目标与范围、已经接受的决定、已修改与已验证的内容、仍未解决的问题及下一动作。文件任务还要给出真实仓库根目录、分支、已有工作树改动和证据版本，避免在同名旧副本中继续。

“已经检查”应说明检查了什么。例如“模型通过三种状态分支”不能改成“板上驱动已经验证”。人工评审状态与自动检查结果分开维护，不能因一轮 AI 修订就把章节标成开发者已读完。具体仓库状态规则由项目约定和唯一人工评审地图负责，本页不再建立第二份台账。
