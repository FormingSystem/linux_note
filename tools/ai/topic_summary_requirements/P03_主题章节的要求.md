# 第3章\_主题章节的要求

> **历史要求来源，附当前适用说明。** 本系列记录不同阶段的书稿要求，保留原条款是为了追溯写作方法的形成，不表示这些条款同时生效。2026-10-18 对照全仓教材规则复核；原稿可从提交 `e9b51de4` 的同路径取得。当前写作入口是 [build-linux-note-topic](https://github.com/FormingSystem/ai_agent_skill/blob/main/skills/build-linux-note-topic/SKILL.md)，冲突处理以 [仓库协作规则](../../../AGENTS.md) 和本次明确需求为准。下文标为历史条款的固定标题、数量与工具假设，不可直接覆盖当前规则。

这份并发写作要求希望读者知道原语能做什么、怎样组合、何时必须退出。这些目标仍成立，但“模块为纲，不以问题驱动”和每章固定三张表，会让成熟机制像凭空出现的工具清单。当前先从具体交错过程提出问题，建立状态与通信，再解释相应接口；模块用于定位职责，不能替代机制的产生过程。

并发讲解需要明确谁保存状态、谁改变条件、谁读取、等待者如何得到继续执行的机会。角色关系图与端到端时序应复用同一操作周期；边界表在模型成立后比较保证和代价。验证也不是随便补一句屏障或取消函数，而要检查会改变结论的关键路径。

| 历史诉求或模板 | 当前处理 |
| --- | --- |
| 概念、能力、组合和反模式 | 保留检查维度；按读者问题组织，不强制七段标题 |
| 三张表及固定数量的误用 | 只保留有实际比较信息的表与反例；先推导再归纳 |
| 环境细节一律后置 | 抽象模型不混平台；但接口或证据依赖版本、配置时必须及时说明 |
| 可粘贴的最小片段 | 仅在先修、状态和生命周期已经成立时给差量；初次实验提供完整程序 |
| `[INV]` 等注释标签 | 可用于作者检索，不能替代中文解释，也不是编译器或检查器协议 |
| 可选 YAML 配置 | 历史提示词格式，没有工具读取证明时不可称为生效的仓库配置 |

特别注意下面两段历史代码只记录当时的写作示意。第一段没有交代映射属性、设备协议与要保证的顺序，不能靠 `wmb()` 证明设备工作完成；第二段的 `cond_in_guard()` 是未定义占位符，既没有给出锁协议，也没有完成醒后取得资源的原子操作。因此二者均不属于可复制的驱动模板。MMIO 的访问顺序、写送达和业务完成是不同条件，见 [三种顺序问题](../../../knowledge/linux/io_model/mmio/P01_MMIO_访问顺序与屏障.md#1.1_先区分三种顺序问题)；等待必须围绕可重复检查的条件与完整协议建立，见 [等待队列正文](../../../knowledge/linux/synchronization_and_asynchrony/synchronization/waiting_notification/P01_等待队列.md)。

下面保留历史条款与提示词，**不作为当前执行指令**。


## 3.1\_文档写作输出规范类(面向\_并发与竞争\_主题)

### 3.1.1\_总目标

- 以**开发者视角为主**：告诉读者“这个模块是什么、解决什么、什么时候用、怎么用、能跟谁混搭、哪些坑”。
- **模块为纲，不以问题驱动**（避免跳来跳去）。
- **先概念后机制再装配**：前期不引入具体环境/SoC；中后期再接入项目与实战。
- 配套**表格体系**：每章固定的概念区分表 / 用法速览表 / 核对表；混搭篇另有混搭矩阵与禁配表。
- 语言风格：**中文教科书式，但不生硬**；术语先做“缓冲式介绍”，再逐步使用专业术语。

------

### 3.1.2\_全书结构(宏观节奏)

1. **序章/术语缓冲**（白话→专业术语映射，最小规则）
2. **篇一：可见性与顺序**（CPU↔CPU、CPU↔设备）
3. **篇二：互斥与临界区**（自旋、互斥、读写信号量）
4. **篇三：读多写少**（seqcount/seqlock、RCU）
5. **篇四：事件与等待**（waitqueue、completion）
6. **篇五：执行路径**（中断/软中断/线程化/工作队列、timer/hrtimer）
7. **篇六：设备交互**（文件操作并发、DMA 与一致性）
8. **篇七：生命周期与收尾**（devres/kref/get-put、有序停机剧本）
9. **篇八：混搭与装配**（混搭矩阵 + 与环境无关的可编译装配样例）
10. **附录**（术语索引、屏障速查、原语一览、停机清单）

> 环境/SoC/性能调优等**放到后段**或另册，不在初期章节出现。

------

### 3.1.3\_章节内固定结构(每章统一骨架)

1. 〔概念〕：先用白话解释，再给**术语最小定义**。
2. 〔能做/不能做〕：明确能力与边界。
3. 〔核心用法模式〕：2–3 个“可直接套用”的**模式**（伪代码或最小片段）。
4. 〔混搭与边界〕：能与哪些模块组合、顺序与锁序规则、边界条件。
5. 〔常见坑〕：列举 4–6 条“看到就该改”的反模式并给对照修复。
6. 〔最小模板〕：**可粘贴**的小段（与环境无关）。
7. 〔交付核对表〕：上线前逐项勾选。

> **测试/验证视角**：只在必要点“点到为止”（例如是否需要 `_sync` 取消、是否需要 `wmb()`），不喧宾夺主。

------

### 3.1.4\_表格体系(强制插入点)

- **每章三张表**（固定位置与名称）
  1. 〔概念区分表〕（开头，1 页内）：相似/差异/边界/典型误解。
  2. 〔用法速览表〕（核心用法前）：能做/不能做、上下文限制、是否可睡、是否自带顺序、推荐组合。
  3. 〔核对表〕（章末，可打印）：关键动作与常见遗漏。
- **每篇一张总览表**：该篇所有模块横向对比（能力/限制/放置点/与相邻模块关系）。
- **混搭篇两张表**：
  - 〔混搭矩阵〕（宜配/慎配/禁配，附原因）
  - 〔禁配对照表〕（错误组合→后果→替代方案）

------

### 3.1.5\_术语与注释约定

- 术语首次出现**先白话后术语**，之后统一使用专业术语。
- 代码/片段注释标记（便于审计与复用）：
  - `[INV]` 不变量（核心约束）
  - `[MIX]` 混搭提示（与其它模块协同的注意点）
  - `[PIT]` 避坑（反模式或危险调用）
  - `[CHECK]` 核对项（交付要勾的点）

------

### 3.1.6\_取舍与节制

- **不做**：API 大抄本、问题驱动的碎片化叙述、过早引入环境细节。
- **要做**：少量、可直接上手的**模式/模板**；把 **边界与混搭** 讲清。

------

### 3.1.7\_章节示例(模板占位名\_非环境绑定)

- 例：I/O 顺序章的最小模板

  ```text
  /* [INV] 设备必须先见到配置，再见到启动 */
  writel_relaxed(cfg0, base + REG_CFG0);
  writel_relaxed(cfg1, base + REG_CFG1);
  wmb(); /* [CHECK] 确认点：CPU→设备顺序保证 */
  writel(CTRL_EN, base + REG_CTRL);
  ```

- 例：等待队列章的最小模板

  ```text
  /* 条件函数在保护内评估 */
  if (wait_event_interruptible(q, cond_in_guard()))
      return -ERESTARTSYS;
  /* 醒后在保护内重检，再搬运到保护外 */
  ```

------

### 3.1.8\_最终交付形态(每章产出\_checklist)

- PDF/Markdown 章节文档
- 三张固定表格（概念区分、用法速览、核对）
- 最小模板代码块（可拷贝）
- 关键混搭提示与禁配项（若适用）

------

### 3.1.9\_可粘贴的「写作提示词」(以后开写时直接贴给我)

**粘贴区开始**
 你要按“模块中心、开发者视角”的**输出规范类**写文档：

- 先概念后机制再装配，不引入具体环境/SoC，直到后段。
- 每章严格包含：〔概念〕→〔能做/不能做〕→〔核心用法模式〕→〔混搭与边界〕→〔常见坑〕→〔最小模板〕→〔交付核对表〕。
- 每章**必须**插入三张表：〔概念区分表〕、〔用法速览表〕、〔核对表〕；篇首提供总览表；混搭篇有混搭矩阵与禁配表。
- 术语第一次出现先白话解释，再使用专业术语；代码注释用 `[INV]/[MIX]/[PIT]/[CHECK]` 标记。
- 避免问题驱动的碎片化叙述；以模块为纲，说明该模块**怎么用、注意什么、能与谁混搭**。
   **粘贴区结束**

------
