# 第1章\_主题章节的要求

> **历史要求来源，附当前适用说明。** 本系列记录不同阶段的书稿要求，保留原条款是为了追溯写作方法的形成，不表示这些条款同时生效。2026-10-18 对照全仓教材规则复核；原稿可从提交 `e9b51de4` 的同路径取得。当前写作入口是 [build-linux-note-topic](https://github.com/FormingSystem/ai_agent_skill/blob/main/skills/build-linux-note-topic/SKILL.md)，冲突处理以 [仓库协作规则](../../../AGENTS.md) 和本次明确需求为准。下文标为历史条款的固定标题、数量与工具假设，不可直接覆盖当前规则。

这份要求试图解决“只给概念或代码片段，读者却不知道怎样运行和观察”的问题。主题引入、开发者操作、用户观察、错误定位和前后章衔接仍有价值；但把它们拆成固定栏目，容易让同一次操作的代码、含义和结果彼此隔离。当前做法是沿问题推进，在操作发生处解释它，并让读者能预测和检查结果。

| 历史诉求 | 当前怎样使用 | 不应推导出的硬要求 |
| --- | --- | --- |
| 章节完整 | 本章承诺的问题在正文闭合，必要前提明确 | 每篇都必须从零重讲整门课程 |
| 数据结构、开发者、用户多视角 | 同一组对象和步骤分别解释内部状态与外部观察 | 先堆结构体，再用表格代替模块动机 |
| 最小可运行例子 | 指明源码版本、配置、材料、构建与实际验证层次 | 未编译就称“现代内核都能运行” |
| 图表和小结 | 图解释关系或时间顺序；结尾回收本章结论 | 每章必须两种材料、固定一句话总结 |
| 分批完成 | 每批闭合实际单元，工作记录保留未完成范围 | 在长期正文留下空的“未完待续”占位而当作完成 |

下面保留历史生成标准。其七类内容是审查维度，不是每章必须照搬的标题顺序；读者能连续理解比形式齐全更重要。




------

## 1.1\_写书章节生成标准(适用于\_Linux\_驱动/内核书籍类内容)

### 1.1.1\_输出方式

- 每次输出必须是一个 **完整章节**，章节号、标题、子标题要 **严格对齐**（例如“第 1 章 → 1.1 → 1.1.1 …”）。
- 如果算力不足，允许 **分批次输出**：
  - 每批次必须保证完整的小节，不要截断。
  - 明确标注“（未完待续）”，下一次从对应小节继续。
- 这样保证 **章节完整性** 和 **阅读连贯性**。

------

### 1.1.2\_内容结构

- 每章必须包含以下核心模块：

1. **主题引入**
   - 本章要解决的核心问题是什么？
   - 为什么对驱动开发者和用户重要？
2. **数据结构视角**
   - 详细解释相关 **内核数据结构**（字段、作用）。
   - 如果需要，分成 **原理视角** 和 **源码调用链视角**。
3. **开发者视角**
   - 说明开发者如何在驱动里调用 API（例如 class_create、device_create）。
   - 提供完整的 **最小化驱动示例**，能在现代内核中编译运行。
   - 示例必须覆盖本章的核心主题（如 sysfs 属性、class、uevent）。
4. **用户视角**
   - 展示用户空间如何操作（命令行示例：`ls`、`cat`、`echo`）。
   - 展示如何通过 `dmesg` 验证驱动是否响应。
   - 解释 `/sys` 和 `/dev` 的关系（如果涉及）。
5. **可视化图示**
   - 至少一种图示：
     - **目录树**（展示 sysfs 结构）
     - **流程图 flowchart**（展示调用链）
     - **时序图 sequenceDiagram**（展示事件交互）
   - 图必须与文字挂钩，帮助理解。
6. **调试与验证**
   - 提供可操作的验证方法。
   - 提示常见错误与排查思路。
7. **小结**
   - 概要本章内容，形成对比表格或要点。
   - 必须有“一句话总结”，强化记忆。

------

### 1.1.3\_主题化写作

- 每章只聚焦 **一个主题**，不要混杂多个主题。
- 主题要在开头 **明确提出**，中间通过 **数据结构、开发者实践、用户操作** 来逐层展开，最后总结。

------

### 1.1.4\_多视角要求

- **用户视角**：他们能看到什么？在 `/sys`、`/dev` 怎么验证？
- **开发者视角**：要写哪些代码？API 怎么用？回调怎么写？
- **内核视角（可选）**：源码链路或配置项的背景介绍。

------

### 1.1.5\_额外要求

- **分批次输出**：如果内容过长，允许拆分为多批，保证每次输出完整小节。
- **解锁算力限制**：不允许偷工减料或只给片段，必须保证书籍风格。
- **表格/代码/图示**：每章至少包含其中两类，避免纯文字枯燥。
- **mermaid输出要求**：mermaid输出的渲染软件为typora，采用通用语法，不要使用方言，保证语法正确。

------

### 1.1.6\_示例指令(以后可直接用)

> 按照“写书章节生成标准”，给我输出 **第 X 章：XXXX**。
>
> - 保证章节完整，标题层级严格对齐。
> - 必须包含：主题引入 + 数据结构解析 + 开发者视角 + 用户视角 + 图示 + 示例代码 + 调试验证 + 小结。
> - 如果内容过长，请分批次输出，保证每次是完整小节。
> - 需要从 **用户/开发者/内核多视角** 展开，不要只写单一角度。
