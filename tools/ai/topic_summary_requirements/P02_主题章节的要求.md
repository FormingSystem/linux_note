# 第2章\_主题章节的要求

> **历史要求来源，附当前适用说明。** 本系列记录不同阶段的书稿要求，保留原条款是为了追溯写作方法的形成，不表示这些条款同时生效。2026-10-18 对照全仓教材规则复核；原稿可从提交 `e9b51de4` 的同路径取得。当前写作入口是 [build-linux-note-topic](../codex/skills/build-linux-note-topic/SKILL.md)，冲突处理以 [仓库协作规则](../../../AGENTS.md) 和本次明确需求为准。下文标为历史条款的固定标题、数量与工具假设，不可直接覆盖当前规则。

这份补充抓住了一个有效问题：只展示 DTS 写法，读者无法知道谁读取它、何时生效、缺席时怎么办。因此“作用、场景、省略后果、消费路径”仍应在本地解释。困难在于，配置文本、内核对象与硬件状态并非天然一一对应；强行凑表会把真实的解析、复用和转发关系画错。

例如一个 pinctrl 状态可以包含多项设置，设置指向具体控制器；状态名和软件对象不能替代控制器中的实际引脚配置。先解释消费者请求怎样到达提供者，再按所选版本列出需要的对象与字段。实际例子见 [状态对象与硬件状态](../../../knowledge/driver_model/device_tree/P03_引脚状态切换与GPIO占用交接.md#3.1_状态对象与硬件状态分别保存在哪里)。

| 历史表述 | 当前校正 |
| --- | --- |
| 每个属性与结构体一一对应 | 核对真实关系，允许一对多、多对一、值被转换或不保留；不能为画图虚构对象 |
| 结构体都要有语法对应点 | 有些对象承担生命周期、占用或运行状态，并非某个 DTS 属性的副本 |
| 一条箭头串完全部类型 | 先区分包含、引用、解析和调用；类型列表不等于执行时序 |
| 不写就失败或取默认值 | 依具体 binding、驱动分支和配置说明，缺席、空值、非法值不能混写 |
| 先语法再所有结构体 | 先建立当前配置要解决的问题，必要对象在消费路径中逐步引入 |
| 每节小结、正式且不口语 | 用清楚自然的解释；只在确有回收作用时小结，不机械重复 |

下面保留 2025-10-09 的历史补充；其中“一一对应”和示意箭头不作为当前实现事实。

### 2.1.2\_语法讲解部分新增要求

1. **必须同时说明语法的作用与意义**
   - 每个语法关键字或属性都要解释它在系统中的真实用途，而非仅格式。
   - 必须指出它在系统中的实际作用，如“控制了哪类引脚”“决定哪个阶段的行为”“影响了哪部分驱动逻辑”。
   - 禁止只展示写法不解释用途。
2. **必须给出使用场景**
   - 每条语法都需配合具体示例说明使用场景，如“在 UART 初始化中如何用”“在休眠状态如何切换”等。
   - 若语法与低功耗、引脚复用、外设状态切换等相关，必须说明它在**驱动层的触发时机**（如 probe 阶段、suspend 阶段）。
3. **必须指出“不写会怎样”**
   - 每条属性要解释如果省略该字段，系统行为会如何（例如：使用默认配置、导致外设无法初始化、复用关系失效等）。
   - 若该语法为可选项，也应说明其默认行为。
4. **必须说明驱动中的使用逻辑**
   - 必须结合驱动层 API 或数据结构说明语法如何被使用，例如：
     - `pinctrl_select_state()` 切换状态；
     - `of_xlate()` 解析参数；
     - `pinctrl_lookup_state()` 查找状态。
   - 让读者能看到“语法在 DTS 中出现 → 被驱动解析 → 最终作用于寄存器”的全过程。

### 2.1.3\_数据结构讲解部分新增要求

1. **语法与结构体一一对应**

   - 对每个 DTS 属性，列出其在内核中的落点结构体（如 `struct pinctrl_state`、`struct pinctrl_map`、`struct pinctrl_dev` 等）。
   - 给出相应的结构体定义及字段注释，说明它与 DTS 属性的绑定关系。

2. **讲清从 DTS → 内核对象 的映射路径**

   - 使用“结构映射图”或“表格”展示从 DTS 节点到内核数据结构的层级关系：

     ```text
     device_node → platform_device → pinctrl → pinctrl_state → pinctrl_map → pinctrl_dev → 寄存器配置
     ```

   - 必要时用 Mermaid 流程图或 sequenceDiagram 表示解析顺序。

3. **数据结构仅为辅助，不喧宾夺主**

   - 只解释与 DTS 解析直接相关的成员，禁止过度展开驱动实现细节。
   - 所有结构体出现都要有语法对应点，做到一一匹配。

------

### 2.1.4\_整体结构保持不变

仍遵循《📖 写书章节生成标准》的七段式结构：

> **主题引入 → 数据结构视角 → 开发者视角（语法与语义） → 用户视角 → 可视化图示 → 示例代码 → 调试与验证 → 小结**

但“语法讲解”部分必须包含以下四个层级：

> **语法说明 → 实际作用 → 使用场景 → 驱动对应逻辑**

------

### 2.1.5\_编写风格与输出要求

- **风格：** 以“出版书籍”口吻书写，逻辑流畅、语气正式，不使用教学口语。
- **表达要求：**
  - 对关键语句使用 Markdown 表格或代码块展示；
  - 所有引用路径或函数使用反引号（` `）；
  - 所有 Mermaid 图必须符合 Typora 通用语法，并转义特殊字符；
  - 每节末尾要有“小结”概述关键点。
- **输出格式：**
  - 一级标题：章
  - 二级标题：节
  - 三级标题：子节
  - 代码与表格要带注释，图要有说明文字。

------

✅ 从本标准开始，今后的章节（如设备树 pinctrl 系列）将：

- 在讲解语法时 **同步说明语义、使用场景、驱动对应逻辑**；
- 在讲解结构体时 **保证每个 DTS 关键字都能在代码结构中找到落点**；
- 以“可出版教材”标准构建章节。
