# 第1章\_ADR-0009\_采用文件与文件夹工作区

## 1.1\_状态

`accepted`

本决策由 2026-08-02 的产品方向确认，取代 ADR-0003～0005 对目标产品的训练计划、AI 内容生成和专题电子书模型。旧 ADR 仅保留为 `0.1.0` 历史。

## 1.2\_背景

目标客户端的基础对象是用户已有的 Markdown 文件与目录。专题电子书、`book.json`、章节包、内容导入和应用正文副本会在真实文件系统之外制造第二套结构，也迫使链接、重命名、保存和外部编辑围绕私有模型做同步。

成熟编辑器已经证明，单文件快速编辑与单文件夹工作区可以覆盖核心场景：文件保持在原位置，目录就是组织结构，标签与窗口状态只作为应用状态恢复。

## 1.3\_决策

- 顶层入口只有新建文件、打开文件和打开文件夹。
- 打开文件夹建立单根工作区；第一阶段不做多根工作区。
- “打开”不复制正文、不生成电子书、不创建内容包、不写隐藏配置。
- 文件树按需枚举，文档按需读取，索引在后台增量建立。
- Markdown 文件是产品内容本体；应用只保存设置、窗口状态、恢复备份、本地历史和可删除索引。
- 当前训练库、电子书、知识声明、AI 发布和浏览器导入实现不进入目标架构；桌面纵向闭环完成后删除，不建兼容层。

## 1.4\_替代方案

- 延续专题电子书：可以保留训练结构，但与用户真实文件形成双重信息架构。
- 把目录导入应用数据库：便于集中查询，但破坏外部编辑、Git 与相对链接的一致性。
- 第一版支持多根工作区：能力强，但会提前引入根消歧义、跨根链接、设置作用域和信任传播复杂度。

## 1.5\_后果

- 产品导航、持久化、IPC 与安全统一围绕单文件和单文件夹能力设计。
- 普通 Markdown 不要求稳定 Front Matter ID 才能编辑。
- 目录结构由用户和文件系统拥有，应用不再维护并行训练分类或电子书目录。
- 若未来重新引入训练、AI 或多根工作区，必须作为建立在文件工作台之上的独立产品能力重新评审。
