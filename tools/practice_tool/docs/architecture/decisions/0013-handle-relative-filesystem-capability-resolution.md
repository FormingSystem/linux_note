# 第1章\_ADR-0013\_用平台安全原语实现句柄相对文件能力解析

## 1.1\_状态

`accepted`

本决策于 2026-08-03 在 D1B 最终安全复审中提出，经两轮独立只读评审修订后接受。实现必须以根句柄一次解析完整相对名称；不得用中间父句柄授权后续操作。

## 1.2\_背景

D1A/D1B 用 libuv `realpath/stat/lstat`、文件身份和根设备号建立了路径能力，并拒绝符号链接、junction、reparse point 与不同 `st_dev` 的挂载。但是 Linux 同一文件系统的 bind mount 保持相同 `st_dev`，挂载后的真实路径在词法上仍位于工作区根内。仅比较规范路径、inode 与设备号无法证明一次后续路径解析没有跨过该挂载点。

libuv 提供跨平台文件 I/O 和元数据，却不提供 Linux `openat2` 的 `RESOLVE_NO_XDEV`/`RESOLVE_BENEATH` 或等价的 Windows 句柄相对重解析约束。继续把“所有安全路径语义都必须只经 libuv”作为绝对规则，会迫使业务层在无法表达安全保证时仍签发能力。这是安全设计缺口，不应通过文档例外或“Linux 以后再测”兼容现状。

## 1.3\_决策

- Native Service 新增窄接口 `filesystem_capability_port`。工作区业务层只提交父目录能力、单个子名称、预期对象类型和操作意图，不提交可重新拼接的任意绝对路径。`child_name` 必须是一个非空路径组件：所有平台拒绝 `.`、`..`、NUL 和目录分隔符，Windows 还拒绝 `:`，避免 ADS 或驱动器语义进入对象名。
- `filesystem_capability_port` 独占工作区根句柄及其关闭职责。业务层只保存不可变组件链、平台身份字符串和显示元数据；Renderer 提交的不透明 ID 只能查到这些内部记录，不能提交或修改组件。根句柄不可复制，只随工作区移动并在工作区撤销时关闭。
- 每个目录能力保存从工作区根到该目录的不可变组件链和逐级身份，不把已打开父句柄本身当作仍归属于根的证明。每次特权操作都由端口把内部组件链组合成一个根相对名称，并在 **一次** 以 `root_handle` 为锚点的系统调用中解析完整相对路径；不能把逐组件取得的中间句柄串成授权链。逐级打开只可作为附加身份检查，最终完整路径打开及目标身份匹配才承担授权。父目录被 rename 到根外后，旧相对名称无法从根解析到原身份，能力随即失败关闭。
- 显式选择建立的是“所选根对象”能力，不是对当时路径字符串的租约。根目录本身在打开后被 rename 时，根句柄仍锚定同一个对象，当前工作区继续有效；根内某个后代目录被移出根时，其旧组件链不能再从根解析到原身份，因此该后代及其文档能力失败关闭。最近打开和下一次重开仍按新 locator 重新建权，不复用旧句柄。
- Linux 实现以工作区 `root_fd` 为唯一 `dirfd`，一次调用 `openat2(root_fd, complete_relative_name, ...)`，使用 `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV`；同设备 bind mount、其他挂载、magic link、符号链接、父目录移出根与 `..` 越界均在取得业务能力前失败关闭。`EAGAIN` 只允许固定小次数重试；`ELOOP`、`EXDEV`、`ENOSYS` 和 `EINVAL/E2BIG` 分别映射为链接/越界、挂载跨越、平台原语不可用和实现/内核不兼容，其他错误按权限、失效或内部错误失败关闭。
- Windows 实现一次调用 `NtCreateFile(RootDirectory=root_handle, ObjectName=complete_relative_name)`，`OBJECT_ATTRIBUTES` 设置 `OBJ_DONT_REPARSE`，并核对卷序列号、文件 ID 与 reparse 元数据。最终路径只作为附加诊断证据，不承担授权；`STATUS_REPARSE_POINT_ENCOUNTERED`、中间组件交换、无法查询身份或网络文件系统不提供所需保证时都不签发能力。
- 其他平台、旧内核或缺少所需安全原语时，文件夹工作区返回稳定的“不支持安全目录能力”错误；不回退到 `realpath` 路径复检，不保留双实现。
- 显式选择的工作区根可以本身位于挂载点或链接解析后的目标上，因为授权从该根句柄开始；授权后任何后代解析不得再跨挂载或链接边界。
- 目录、条目和文档能力持有平台端口返回的身份与根相对组件链。目录刷新、分页和正文打开总是以根句柄一次解析完整相对名称；显示相对路径只用于 UI，不重新成为授权依据。
- 目录枚举必须从端口已经安全打开的目录句柄读取，禁止在授权后再把路径交给 `std::filesystem::directory_iterator`。Windows 使用句柄目录信息类取得名称、属性、reparse tag 和文件 ID；Linux 使用安全目录文件描述符枚举，并对可访问子项从根 `openat2` 复核。枚举前后再次从根解析非根目录并核对身份；目录被移出或替换时丢弃整批结果。50000 项与 32 MiB 元数据上限必须在端口分配过程中执行，不能等无界枚举完成后再检查。
- `FileService` 接收端口已经授权并移交的同一文件句柄，在该句柄上执行有界读取、前后 `fstat`、UTF-8 校验与摘要；不得凭路径重新打开。读取完成后，业务层再次让端口从根解析完整组件链并核对期望身份，路径被替换时不把正文交给 Renderer。libuv 仍负责复合帧管道和可安全表达的跨平台句柄 I/O；平台专用代码只存在于文件能力端口，不扩散到协议、工作区状态机或 Renderer。
- Windows 本地目录能力要求 `FileIdInfo`、`FileAttributeTagInfo` 和句柄目录枚举均可用；身份由卷序列号与 128 位文件 ID 组成。所选根的驱动器类型必须先证明不是远程卷，`FileRemoteProtocolInfo` 一旦明确报告远程协议仍立即拒绝；本地 NTFS 对该信息类返回 `ERROR_INVALID_PARAMETER` 时，以已确认的本地驱动器类型继续，不把“远程信息类不适用”误判成所有本地文件系统都不受支持。关键身份查询失败或目录枚举不提供所需字段时，根建权失败为“不支持安全目录能力”，不降级到路径或旧 64 位 file index。Linux 身份由安全打开句柄的设备号与 inode 组成，但挂载边界仍由 `RESOLVE_NO_XDEV` 判定，不能用身份相同代替该解析约束。

## 1.4\_失败语义

| 失败 | 结果 | 恢复 |
| --- | --- | --- |
| 后代解析跨挂载、链接或根边界 | 不签发条目/文档能力；现有其他能力不变 | 刷新目录或选择其他根 |
| 目录身份在枚举期间变化 | 本次目录结果整体丢弃 | 重新打开工作区 |
| 显式根目录在会话中改名 | 根对象能力继续有效，显示名称可保持本次会话旧值 | 关闭后按新位置重新打开 |
| 平台缺少安全原语 | 文件夹工作区失败关闭 | 升级受支持系统；单文件显式选择仍可独立评审 |
| UNC/网络文件系统无法证明逐组件身份 | 文件夹工作区失败关闭，不降级为路径检查 | 选择受支持的本地文件系统 |
| 已开文档路径被替换 | 文档级读取失败，不覆盖内存草稿 | 刷新或重新打开 |

## 1.5\_替代方案

- **继续使用 `realpath + st_dev + inode`**：跨平台、实现简单，但无法识别同设备 bind mount，拒绝。
- **解析 `/proc/self/mountinfo`**：能观察 Linux 挂载表，但检查与打开之间仍有竞态，而且把 Linux 路径文本规则泄漏到业务层，拒绝。
- **只在文档中声明 bind mount 不受支持**：目标可能仍被签发能力，不属于失败关闭，拒绝。
- **禁止所有子目录**：安全但破坏已接受的文件夹工作区目标，拒绝。

## 1.6\_进入实现的评审门禁

- 平台端口必须让业务层无法绕过句柄相对解析重新打开任意路径。
- 平台端口测试必须证明根句柄只有一个所有者，关闭工作区后所有后代解析失败；目录枚举和正文读取均不重新打开绝对路径。
- 组件校验测试必须覆盖空值、`.`、`..`、NUL、两类目录分隔符和 Windows `:`/ADS。
- Linux 测试必须包含同设备 bind mount、不同设备挂载、symlink、父目录移出根、解析期间 rename、挂载/卸载竞态、替换、旧能力重放、`EAGAIN` 有界重试和不支持 `openat2`；没有可创建 mount namespace 的环境时不得把该平台条目标为 `COMPLETE`。
- Windows 测试必须覆盖 junction、symlink、普通 reparse point、UNC、卷边界、显式根 rename 后继续访问、父目录移出根、解析期间中间组件 reparse 交换、`STATUS_REPARSE_POINT_ENCOUNTERED` 与句柄身份替换。UNC 或网络文件系统无法证明身份时必须验证为失败关闭，而不是把测试标成跳过后仍宣称支持。
- 在完整端口落地前，状态文档把跨平台文件夹能力与 D1B 总体验收保持为 `IN_PROGRESS`；Windows 现有自动化只能作为局部证据。

## 1.7\_评审结论

首轮评审要求补齐根归属、严格单组件名称、Linux 错误映射、Windows `NtCreateFile + OBJ_DONT_REPARSE`、UNC 失败语义和并发挂载/rename 测试。第二轮进一步拒绝把逐组件父句柄串成授权链，最终收敛为“每次特权操作从根句柄一次解析完整相对名称”。这些约束已进入决策正文，允许开始开发平台端口；在双平台自动化完成前不得恢复 `COMPLETE` 状态。

第三轮实现前评审发现两个此前只被暗含、但会让代码重新落回路径竞态的缺口：授权后的目录若仍由标准库路径枚举，或者正文句柄若仍由 `FileService` 按绝对路径重开，根句柄解析都不能构成端到端授权。因此本轮把句柄枚举、句柄所有权转移、读取后从根复核和分配前资源上限写成强制接口契约；同时明确根对象 rename 与后代移出根是两种不同状态。评审后没有把兼容旧路径流留作 fallback，允许按该接口替换现有文件夹实现。

## 1.8\_影响的既有决策

本 ADR 接受后，将收窄 ADR-0010 中“项目代码不维护 Win32/Linux 私有 API 分支”的表述：业务层仍保持跨平台，只有无法由标准库/libuv表达的安全文件能力解析进入受测试的平台端口。该变化不引入兼容层，也不改变 Renderer 路径隔离。协议 v3 和“保存尚未开放”是本 ADR 接受时的实现边界，后续已由 ADR-0014 以协议 v4 安全保存取代，不保留兼容层。
