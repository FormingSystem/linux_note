# 第5章\_系统属性与接口选择参考

前四章已经建立对象、属性事务、节点发布和回调寿命。本页用于把这些判断迁移到真实系统，不另建一套网络、PM 或 cgroup 完整教程。表中的路径是接口形状，实例名、文件存在性、单位、配置和权限必须在目标系统确认；缺失文件首先是一条环境事实。

## 5.1\_按功能找到真正的子系统接口

下面按设备提供的功能查询。DRM（Direct Rendering Manager）是内核图形显示管理子系统；hwmon 组织硬件监测接口，IIO（Industrial I/O）组织工业输入输出设备及通道，ADC 是把模拟量转换成数字采样值的转换器。它们分别属于软件子系统和硬件功能，不是同一层的替代产品。

| 功能入口 | 可以观察什么 | 必须保留的边界 |
| --- | --- | --- |
| `/sys/class/net/<网卡>/` | address、mtu、carrier，以及驱动支持时的 speed | 网络数据使用 socket 等网络接口，不要求 /dev/网卡名；文件可能受链路状态影响而读失败 |
| `/sys/class/input/` | 输入设备 name、phys、properties 与 capabilities 子目录 | properties 不等于全部事件能力；用户事件通常经 input 提供的节点读取 |
| `/sys/bus/usb/devices/` | idVendor、idProduct、配置与授权等适用属性 | USB 设备对象和接口对象不同；授权写入会改变可用性，本页只读观察 |
| `/sys/class/drm/<连接器>/` | status、modes、二进制 edid | 连接器不是任意 card 目录；显示配置不等于直接写这些文件，正式接口由 DRM 提供 |
| `/sys/class/block/<设备>/` | size、queue 中设备支持的队列属性 | size 按 512 字节扇区计数，不能随意乘逻辑块大小；逻辑/物理块大小是另两个属性 |
| `/sys/class/hwmon/`、`/sys/bus/iio/devices/` | 硬件监测值或工业 I/O 通道、缓冲相关配置 | 依据设备能力与子系统 ABI 选择，不能把任意 ADC 与温度接口视为完全可互换 |
| tty、backlight、leds 等 class | 终端设备、亮度、指示灯等功能视图 | 先用对应子系统注册，保留单位、范围和生命周期；伪终端还涉及 devpts，不是统一照搬 device_create |

例如先用 shell 枚举 `/sys/class/backlight/*`，读实例的 max_brightness 再理解 brightness 范围。不要写死 255。读 CPU 频率属性时也需区分驱动报告、请求目标与瞬时实际频率，不能由一个文件断言所有 CPU 此刻运行在同一频率。

总线、类、设备、驱动是四种观察角度。`subsystem` 链接帮助定位对象归属，`driver` 链接表示当前绑定关系；缺少 driver 不代表没有对象或属性。一个物理器件的多个功能对象可以共享父设备，由多功能设备框架 MFD（Multi-Function Device）组织子设备，或由 Component 框架协调组件组合；仅仅创建几个类目录不等于已经建立资源与绑定关系。

## 5.2\_设备树输入不等于运行时控制值

设备树描述平台硬件，设备对象可能有 of_node，也可能来自其他固件、枚举或软件创建。不能对每个 device 无条件解引用 of_node。驱动应按属性契约用 `of_property_read_u32` 等接口读取并检查返回值，而不是把任意字节地址强转为本机整数指针。

sysfs 导出的设备树属性通常保留原始二进制编码。一个大端 32 位 cell 不能用 cat 的文本结果判断十进制数值，也不能假定它是小端。下面是独立可运行的编码实验：

```python
import struct

raw = bytes.fromhex("00 00 10 00")
value, = struct.unpack(">I", raw)
assert value == 4096
print(value)
```

这只说明单个 u32 cell 的字节序，不证明某个属性一定只有一个 cell；地址和范围还受 #address-cells、#size-cells 等约定影响。字符串、字符串列表和任意二进制属性又有不同解释方式。

若启动时从设备树读出 buffer_size，随后又公开可写属性，必须定义运行期写入改变什么。只把整数改大，而不重新分配实际缓冲或限制访问，会把配置值与容量分离。即使运行期修改成功，也不意味着原始设备树 blob 被同步改写。真实驱动应在锁、分配失败和正在使用的缓冲之间设计一份可回滚事务。

## 5.3\_电源管理属性的两个层次

系统睡眠控制整个系统的进入与恢复；运行时 PM 在系统仍运行时管理个别设备。名字都带 power，不代表同一个状态机。

| 读取入口或接口 | 解释 | 不应推出的结论 |
| --- | --- | --- |
| `/sys/power/state` | 当前支持的系统睡眠入口，可能包含 freeze、mem、disk 等 | 每台系统都支持所有状态 |
| `/sys/power/mem_sleep` | mem 对应的选择，可能列 s2idle、shallow、deep，方括号标示当前选项 | 写 mem 必然进入最深硬件挂起 |
| `.../power/control` | on 通常禁止该设备运行时自动挂起，auto 允许其策略运作 | on 阻止系统级 suspend，或保证网络永不断线 |
| `.../power/runtime_status` | 运行时 PM 软件状态 | 单次读取等于整个依赖图的原子状态 |
| pm_runtime_resume_and_get | 恢复并在成功后持有使用计数 | 只调用一次即可永久代替释放计数 |
| pm_runtime_get_sync | 增加使用计数并尝试恢复，失败也不自动撤销这次增加 | 返回错误后可以不处理计数 |

freeze 对应 suspend-to-idle；disk 指向休眠镜像流程，需要相应配置、平台与恢复存储条件。设备的 PM 回调和依赖关系还涉及父子拓扑、device link、驱动与总线。`pm_runtime_enable` 不是“创建全部 power 文件”的统一动作。涉及真实设备时应按目标驱动的获取/归还协议配对，而不是照抄一个只在成功路径 put 的模板。

本页只建议读取上述状态。改变系统睡眠、CPU 调频、电压或真实设备电源会改变正在进行的工作，不作为属性入门的默认写实验。版本证据来自固定树的 sleep-states.rst、runtime_pm.rst 和 cpufreq.rst，见[分类源码导读](../../../../research/source_reading/driver_entries/navigation/P03_分类对象与属性事务导读.md#3.4_配置与旁支证据)。

## 5.4\_相邻文件系统怎样选择

这些接口的比较轴是“谁创建对象、对象保存什么”。表中的 BPF 是内核提供的可验证程序与相关对象机制，bpffs 保存这些对象的持久引用；它不是拿一份设备属性文本换个存放目录。

| 接口 | 对象与创建方向 | 合适任务 |
| --- | --- | --- |
| sysfs | 内核注册对象，再导出属性；基于 kernfs | 按子系统 ABI 公开少量状态与控制，普通属性以文本和单值为主，也允许同类数组及专门二进制属性 |
| procfs | 内核提供进程和系统信息等接口 | 进程观察与已有 proc ABI；新驱动不能只因会写 seq_file 就随意新增 proc 配置树 |
| debugfs | 开发者提供诊断文件 | 调试视图与实验接口；不承诺稳定 ABI，也不自动保证安全权限 |
| configfs | 用户 mkdir/rmdir 驱动配置对象建立与删除 | 用户空间组织内核配置实例；它是独立文件系统，不是 kernfs 的另一名称 |
| tracefs | 跟踪框架的控制与数据接口 | 事件和函数跟踪；读取和启用具有不同权限及运行成本 |
| cgroupfs | 资源控制组层次，基于 kernfs | 进程资源归属与控制器配置，不是驱动自造任意属性的空间 |
| bpffs | 持久引用 BPF 对象的文件系统 | 固定对象路径与对象寿命管理；不基于 kernfs，也不是 sysfs 的“下一代替代品” |

挂载在 `/sys` 下面不等于属于 sysfs。同一个目录树可以容纳多个挂载，`findmnt -T 目标路径` 比按路径前缀猜文件系统更可靠。configfs 的用户驱动生命周期也不等于普通应用可以 mkdir 任何 sysfs 设备。

cgroup v1 可有多个层次，并允许适用控制器组合；v2 以统一层次组织，控制器是否可用还取决于配置和父级启用。cgroup namespace 改变可见的归属根和路径，并不是完整的权限隔离屏障。网络 class 的命名空间关联又是另一种对象可见性机制，不能把 class.ns_type 与 cgroup namespace 当同一个开关。入门只读查看 `/proc/self/cgroup` 与挂载信息，不移动一个任意 PID 来“验证限制”。

## 5.5\_稳定性\_权限与诊断成本

新增正式 sysfs ABI 要记录文件、单位、合法值、错误、读取时效和生命周期，并按上游 Documentation/ABI 的分类维护。已有稳定使用者不能因为实现重构而无说明地改变语义。调试文件不应被应用当成稳定承诺；但 debugfs 也不是必须在所有发布系统中删除，更不是“只要放在这里就自动只有 root 能读”。

权限检查不能代替数据校验。root 身份也不能凭空为只有 show 的属性生成 store，不能绕过一切只读挂载或安全策略。标准属性宏会验证模式，不能用随意添加对其他用户写权限的办法规避约束。应按最小必要访问范围设计专用组、服务代理或已有子系统接口，并保留严格的数值和事务校验。

排错从可观察结果开始：用户空间可用 strace 定位 open/read/write 哪一步返回错误，内核可用动态调试、已有 tracepoint 或受支持的函数跟踪定位回调。记录测试前的跟踪设置，只启用目标事件，限制采集时间并恢复设置。函数跟踪应先查 available_filter_functions，不能假定每个 static 函数都可跟踪；trace_printk 是开发诊断手段，不是生产日志协议。lockdep 依赖构建配置与检查器状态，不存在通用的“写一个 /proc/sys/kernel/lockdep 即开启全部检查”的步骤。

测量时应明确在比较字符串格式化、锁竞争、硬件延迟还是进程启动。普通压力工具若没有访问目标属性，就不能证明该回调经历过并发压力。对 note_control 最有针对性的下一步，是多个独立打开者反复写合法/非法值，同时按契约读取，记录每次调用的返回值；再以确知已进入回调的注入点测试撤销等待。没有执行这些路径，未告警只能算有限观察。

## 5.6\_查询后的自检

遇到一个新属性时，先问五件事：谁创建对象；谁拥有业务状态；一次读写承诺什么；错误后什么保持不变；对象撤销时谁仍可能使用数据。用这些问题可以识别“改数值但没改缓冲”“目录在就认为硬件在线”“同名 power 就照搬写值”等不同错误。

把本例扩成真实传感器时，应优先对照现有子系统的单位和采样契约；把本例用于大量数据时，应先决定队列、通知和无丢失保证，而不是先优化 sysfs 的一行输出。前四章提供的是作出这些判断的基础，不是替代各子系统规范。
