# 第1章\_错误指针接口与排错速查

本页供查询使用。首次学习从[专题大纲](大纲.md)开始；理解某个具体返回值时，最终依据始终是被调用接口的契约，不能用这张表替代它。

## 1.1\_返回形式与检查职责

| 接口或返回形式 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| `ERR_PTR(error)` | 把约定范围内的负错误码放入指针表示 | 不检查范围，不补负号，不分配错误对象 |
| `IS_ERR(ptr)` | 是否为错误编码 | 不验证 NULL、生命期、地址可访问性或引用权 |
| `PTR_ERR(ptr)` | 从已确认的错误指针恢复负码 | 不检查输入，不产生函数来源或调用栈 |
| `IS_ERR_OR_NULL(ptr)` | 是否为错误编码或 NULL | 不决定 NULL 在该接口上应算失败还是允许缺席 |
| `PTR_ERR_OR_ZERO(ptr)` | 错误指针转负码，其余转 0 | NULL 也得到 0；不保证初始化已全部完成，不释放对象 |
| `ERR_CAST(ptr)` | 显式传递已确认的错误值到另一种指针返回类型 | 不把成功对象转换为另一种对象，不自动检查 |
| 整数状态 | 按接口约定判断 0、负值或其他状态 | 不可一律按指针解释 |

实现及范围见[编码正文](P02_错误值的编码与判定.md)和[唯一实现讲解](../../../../research/source_reading/error_pointer/source_explanations/P01_err.h_错误值编码与检查.md#1.2_编码与还原)。`ERR_PTR_PCPU`、`PTR_ERR_PCPU`、`IS_ERR_PCPU` 是面向每 CPU 地址空间注解的辅助接口，不改变错误值契约；它们不提供跨 CPU 通信或同步。

## 1.2\_常见错误码不能替代现场

下表数值按本专题 ARM/Linux 基线采用的通用定义整理。名称是正错误码，许多内核状态返回使用负号；错误指针再把该负值编码。具体函数可能赋予原因更精确的场景含义。

| 名称 | 正值 | 通常含义 |
| --- | --- | --- |
| EPERM | 1 | 操作不允许 |
| ENOENT | 2 | 请求的条目不存在 |
| EIO | 5 | 输入输出错误 |
| ENXIO | 6 | 无对应设备或地址 |
| EAGAIN | 11 | 当前条件暂不可满足，是否重试由接口决定 |
| ENOMEM | 12 | 内存分配不足 |
| EACCES | 13 | 权限拒绝 |
| EFAULT | 14 | 当前访问地址不符合要求；不等于所有情况都不可恢复 |
| EBUSY | 16 | 资源忙 |
| EEXIST | 17 | 条目已存在 |
| ENODEV | 19 | 无合适设备或相应对象 |
| EINVAL | 22 | 参数或组合无效 |
| ENFILE | 23 | 系统文件表资源不足 |
| ENOSPC | 28 | 空间或资源容量不足 |
| EOPNOTSUPP | 95 | 操作不支持 |
| ETIMEDOUT | 110 | 等待超时 |
| EPROBE_DEFER | 517 | 内核内部的延迟探测请求；不是用户空间错误码映射规则 |

例如 -19 的 64 位编码是 `0xffffffffffffffed`，-22 是 `0xffffffffffffffea`。若手算结果与接口解码不符，应先查算术和位宽，而不是据裸地址猜平台。完整边界由[整数模型](P02_错误值的编码与判定.md#2.2_亲自检查阈值两侧)重现。

用户空间常见库函数把系统调用失败转换为 -1，并设置调用线程可见的 errno；具体规则仍以该库接口为准。内核内部错误指针需要先由调用链转换成相应接口的整数结果，不能直接当作用户 ABI（Application Binary Interface，应用二进制接口）。不存在“所有 EPROBE_DEFER 自动转成 EAGAIN”的通用约定。

## 1.3\_按症状缩小问题

| 症状 | 先查的契约或证据 |
| --- | --- |
| 非空指针却在成员访问处失败 | 获取接口是否返回错误指针；对象是否已释放；仅检查非空不够 |
| 内存不足却报告初始化成功 | 是否对 NULL 使用了 `PTR_ERR_OR_ZERO`，或将 NULL 的 `PTR_ERR` 返回 0 |
| 可选对象缺席后初始化只做了一半 | 是否把 NULL 与错误分支合并后提前返回 |
| 始终没有重新探测 | 是否把依赖的延迟原因改成其他错误；实际是否进入可重试路径 |
| 失败日志出现但先前资源泄漏 | 是否有明确清理责任，资源是否真正登记；错误表示本身不负责释放 |
| 没有错误日志 | 核对实际调用、返回值、调试配置与日志等级；静默不证明成功 |
| 注册成功但设备没有 driver 链接 | 区分驱动/设备注册与具体 probe 的结果 |

## 1.4\_类型化结果与跨语言边界

错误指针的两种含义共用 C 指针类型，调用者可能遗漏分支。更显式的设计可以把“成功值或错误”做成带标签的结果类型；第一章的状态与输出参数已展示 C 中一种无需特殊地址编码的选择。Rust 的 `Result<T, E>` 用成功和错误两个变体表达结果，C++ 的 `std::expected<T, E>` 也表达值或错误。这是表示方式的比较，不是 Linux 已规划用某一种语言全面替换错误指针的声明。

固定源码 `rust/kernel/error.rs` 中，内核 `Error` 包装一个非零 32 位整数并约束负错误范围，`Result` 是结果类型别名。`from_err_ptr` 检查 C 返回的错误编码后转成错误变体；非错误值进入成功变体，NULL 也可能被原样放进去。因此类型桥接仍不能凭空证明返回对象非空、已持有引用或可安全解引用。错误常量位于 `code` 模块，不能凭印象写成任意关联常量。

此处不提供未经核实的“Unified Error API”社区提案或 C++ 内核封装计划。把整个设备的 devres 清理塞进任意 C++ 对象析构函数，会越过其他资源的所有权边界；结果类型也不会使这一做法自动正确。跨语言包装应先证明 C 侧契约、生命期和释放协议，再决定怎样封装。

对应固定文件与检索位置见[源码模块导读](../../../../research/source_reading/error_pointer/navigation/P02_返回值与清理路径导读.md#2.4_其他表示与观测入口)。这段只比较接口表示，没有声称已构建或运行 Rust/C++ 内核程序。
