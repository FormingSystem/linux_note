# 第1章\_取得对象以后\_先判断返回了什么

写过[第一个内核模块](../../../../engineering/build/kernel_modules/大纲.md)以后，我们已经知道：初始化函数返回 0 才表示成功，返回负数则表示失败。但是，建立一个设备时还要取得内存、设备对象或某种硬件资源。这样的函数往往返回指针，它怎样同时告诉调用者“对象在哪里”和“为什么没有取得对象”？

先别急着把每个返回值都塞进同一种判断。看懂错误指针的第一步，是认清 **返回契约**：函数承诺哪些返回值、每一种值有什么含义，以及取得对象后由谁释放。本章从一个查找通道的小程序开始，最后再读 Linux 的三种实际写法。你需要会读 C 的结构体、指针、条件语句和函数调用，不需要先理解设备模型。

## 1.1\_空指针解决了什么\_又漏掉了什么

假设系统提供四个通道，编号为 0～3。程序请求 2 号通道，成功时拿到描述它的对象地址；请求 9 号时没有对应对象。最朴素的接口可以返回对象指针，失败返回空指针 `NULL`。调用者写 `if (!channel)` 就能避免把“没有对象”当成对象使用。

现在增加一个条件：2 号通道确实存在，但被另一个使用者占用了。如果两种失败都返回 NULL，调用者仍能知道“这次没拿到”，却无法判断应该修改编号还是等待占用者退出。问题不是 NULL 不安全，而是 **一个失败值承载不了两种失败原因**。

一种直接的改进是让函数返回整数状态，把取得的对象写进输出参数。下面的完整程序只演示接口设计，不模拟 Linux 的地址布局。`selected` 是调用者自己的指针变量，`&selected` 把这个变量的位置交给查找函数；函数用 `*out` 写回结果。

程序用自定义枚举常量 `LOOKUP_OK`、`LOOKUP_BAD_NUMBER`、`LOOKUP_BUSY` 分别命名成功、编号错误和被占用三种结果；它们不是 Linux 错误码。将程序保存为 `lookup_result.c`，也可取用[同名材料](../../../../labs/kernel/error_pointer/materials/lookup_result.c)：

```c
#include <stdio.h>

struct channel {
    unsigned int number;
    int busy;
};

/* 教学程序自定义状态值，不冒充系统 errno 编号。 */
enum lookup_status {
    LOOKUP_OK = 0,
    LOOKUP_BAD_NUMBER = -1,
    LOOKUP_BUSY = -2
};

static struct channel channels[] = {
    {0, 0}, {1, 0}, {2, 1}, {3, 0}
};

static int lookup_channel(unsigned int number, struct channel **out)
{
    /* 每次调用都先清除输出，失败时不留下上次的对象。 */
    *out = NULL;
    if (number >= sizeof(channels) / sizeof(channels[0]))
        return LOOKUP_BAD_NUMBER;
    if (channels[number].busy)
        return LOOKUP_BUSY;
    *out = &channels[number];
    return LOOKUP_OK;
}

int main(void)
{
    const unsigned int requests[] = {1, 9, 2};
    struct channel *selected = NULL;
    unsigned int index;

    for (index = 0; index < sizeof(requests) / sizeof(requests[0]); ++index) {
        int status = lookup_channel(requests[index], &selected);

        if (status != LOOKUP_OK) {
            printf("request=%u status=%d empty=%d\n",
                   requests[index], status, selected == NULL);
            continue;
        }
        printf("request=%u channel=%u\n", requests[index], selected->number);
    }
    return 0;
}
```

在有 C 编译器的工作目录中执行：

```bash
cc -std=c11 -Wall -Wextra -Werror lookup_result.c -o lookup_result
./lookup_result
```

预期输出如下。它来自程序中明确设置的三次请求，不需要设备或管理员权限：

```text
request=1 channel=1
request=9 status=-1 empty=1
request=2 status=-2 empty=1
```

第一次调用建立了有效输出，第二次失败又把它清空。这一步值得保留：如果调用者错误地忽略状态，至少不会继续拿着上次选中的 1 号对象。它仍不能替代状态判断，也不能把 NULL 解引用变成合法操作。

这里的对象是静态数组元素，调用者只借用它，不能 `free()`。**返回成功与取得释放权是两件事**。真正的分配接口可以约定把对象所有权交给调用者，查找接口也可能只交出一个受其他条件约束的借用地址。

## 1.2\_把状态放进指针返回值

输出参数方案已经正确解决问题，而且适用于普通 C 程序。Linux 还有另一种约定：某些返回指针的函数在失败时，把一个负错误码编码成特殊的指针值，称为 **错误指针（error pointer）**。它没有指向一个“错误对象”，没有为错误分配结构体，也不能读取成员。

这样，调用者得到一个指针类型的值，先判断它属于错误表示还是对象地址。信息随着普通函数返回传回本次调用者，不需要另找一份共享错误变量。代价是两种含义在 C 类型上没有分开：编译器看到的都是指针，程序员必须按契约检查后再访问。

```mermaid
flowchart LR
    a[调用者请求通道] -->|参数| b[提供者查找并申请]
    b -->|成功返回对象地址| c[调用者获得约定的访问权]
    b -->|失败返回编码值| d[调用者检查错误表示]
    d -->|解码后选择返回或恢复| e[上层得到整数状态]
    c -->|按生命期约定使用| f[访问对象并配对释放]
```

图中的“上层得到状态”是调用者执行了判断和返回的结果。没有异常抛出，没有自动跳过后续语句，也没有自动释放上一项资源。若忘记那个 `if`，控制流照样会走向成员访问。

从表示上说，输出参数方案把结果放在两个位置，错误指针方案复用一个返回值；它没有消除“成功或失败”的分支。只需要知道成功与否的分配接口继续使用 NULL 很合适；面向普通可移植 C 的多原因接口可以继续用状态与输出参数；已有 Linux 接口承诺错误指针时才采用相应检查，不应为了统一外观擅改契约。

## 1.3\_三种长得相近\_判断不同的调用

Linux 用正的错误码名称描述原因，在许多内核整数返回接口中取其负值。例如 `ENOMEM` 表示内存不足，`EINVAL` 表示参数不合法，`EBUSY` 表示对象或资源忙。错误码不是函数来源编号：不同函数都可能返回相同原因。

错误指针的三个基本接口属于 `<linux/err.h>`：`ERR_PTR` 把负错误码编码成指针；`IS_ERR` 检测值是否落入错误表示；`PTR_ERR` 从已确认的错误指针取回负错误码。它们都只处理 **值本身**，不读取所指地址。

下面是内核函数内的使用片段，不是可以独立装载的模块。`kzalloc` 分配并清零非零大小的内存，`GFP_KERNEL` 是允许普通可睡眠分配路径的标志；`class_create` 建立设备类对象；`alloc_chrdev_region` 为一段字符设备号登记所有权。

```c
/* 内存分配的失败值是 NULL。 */
buffer = kzalloc(128, GFP_KERNEL);
if (!buffer)
    return -ENOMEM;

/* 设备类创建失败使用错误指针。 */
device_class = class_create("note_example");
if (IS_ERR(device_class)) {
    ret = PTR_ERR(device_class);
    kfree(buffer);                 /* 释放前一步实际取得的资源。 */
    return ret;
}

/* 整数返回的登记接口直接检查状态。 */
ret = alloc_chrdev_region(&first_number, 0, 1, "note_example");
if (ret) {
    class_destroy(device_class);   /* 逆序撤销已经完成的步骤。 */
    kfree(buffer);
    return ret;
}
```

不要把第一处改为 `IS_ERR(buffer)`：NULL 不属于错误指针，内存不足时条件反而为假。也不要把第二处改为 `if (!device_class)`：错误指针通常非空，失败会漏过。这段只展示前缀失败路径；全成功后的服务发布、卸载和配对清理由[字符设备窗口模板](../../../driver_model/character_device/P10_字符设备驱动模板.md)完整实现。

本专题实现依据为 NXP 官方 Linux 6.12.20 固定提交；首次核对源码从[返回值与错误路径阅读索引](../../../../research/source_reading/error_pointer/navigation/P01_Linux_6.12_错误指针源码阅读索引.md#1.2_按问题进入源码)开始。判定接口的唯一函数体见[编码与识别](../../../../research/source_reading/error_pointer/source_explanations/P01_err.h_错误值编码与检查.md#1.2_编码与还原)；下一章先用整数实验把编码边界算清楚。

## 1.4\_回顾与练习

本章从“无法区分两种失败”推出了两种有效设计，而不是从几个接口名字倒推用途。读一个陌生调用时，先查返回契约，再分别安排失败处理、对象使用和释放责任。错误指针仅让失败原因搭乘指针返回通道。

1. 把程序中 2 号通道的 `busy` 改为 0，预测第三行输出。为什么无需修改调用者的判断？
2. 若删除 `*out = NULL`，第二次调用失败后 `selected` 可能还指向谁？这是否表示第二次查找成功？
3. 一个接口只返回对象或 NULL，能否用 `IS_ERR_OR_NULL` “更保险”地检查？说明它不能弥补什么。
4. 一个返回整数的包装函数遇到错误指针，应返回 `ptr`、`PTR_ERR(ptr)` 还是 `ERR_PTR(ptr)`？

**解答：** 第一题第三行成为 `request=2 channel=2`；状态契约没有变化。第二题残留 1 号对象地址，状态仍为编号非法，残留值没有获得新的语义保证。第三题虽然在这个契约下合并检查能拒绝 NULL，却不能验证悬空地址、生命期或任意坏指针；准确的 `!ptr` 更直接表达该接口的失败条件。第四题先确认 `IS_ERR(ptr)`，再返回 `PTR_ERR(ptr)`；包装函数承诺整数状态，不能把指针值塞进整数返回通道。
