# 第4章\_观察返回值与释放顺序

[上一章](P03_资源失败与驱动回滚.md)把申请结果和释放责任分开了。现在需要一个可以改变条件、又不依赖板上 GPIO 或时钟的现场：让同一个驱动分别遇到对象存在、可选对象缺席、提供者失败和后续失败，观察哪些动作继续执行、哪些已登记动作被回收。

本实验使用一个自行登记的平台设备。**平台设备（platform device）** 在这里是设备模型中的软件对象，不指向真实寄存器；同名平台驱动提供探测回调。模块先注册驱动，再注册一个同名设备，设备与驱动匹配后进入 probe。它不申请设备号、不建立 /dev 节点，也不代表任何 NXP 外设。运行前应已完成[模块构建与部署](../../../../engineering/build/kernel_modules/大纲.md)，并有与运行内核匹配的构建目录。

## 4.1\_先预测四条路径

我们用两个小对象标记释放次序。每次分配内存后，再登记一个只打印编号的释放动作。登记顺序为“内存 1、动作 1、内存 2、动作 2”，所以清理时动作 2 先运行，此时内存 2 仍在；动作 1 也在内存 1 释放之前运行。

`devm_add_action_or_reset` 登记“稍后用给定数据调用这个函数”。如果登记本身失败，它立即执行动作并返回失败，因此驱动不应再手动重复执行这个动作。动作只是打印，内存释放仍由先前的 devm 分配记录负责。这种顺序让观察回调始终能合法读取自己的编号。

模块参数 `scenario` 在装载时选择路径，权限 0444 使运行期间不能经参数文件改变它。自定义的 `note_get_optional` 是教学提供者：只返回静态整数对象、NULL 或错误指针，不触碰硬件。

| scenario | 预期 probe 过程 | 正常条件下能看到的释放标记 |
| --- | --- | --- |
| 0 | 取得值 7，继续建立第二项，最后成功 | 装载时不释放；卸载时 2、1 |
| 1 | 可选值缺席，但仍建立第二项并成功 | 同样在卸载时 2、1 |
| 2 | 第一项完成后，提供者返回忙错误 | 本次 probe 失败清理时只有 1 |
| 3 | 两项都完成后，驱动主动返回参数错误 | 本次 probe 失败清理时 2、1 |

表格假设系统分配及登记步骤本身成功。若实际内存不足，应先按那个失败点分析，不能硬套 scenario 的预期。软件“忙”和“参数错误”是为了制造确定的分支，不宣称真实硬件处于这些状态。

## 4.2\_完整模块与构建文件

把下面内容保存为 `error_pointer_demo.c`；[实验材料目录](../../../../labs/kernel/error_pointer/materials/README.md)保存相同文件。前半段控制返回值，probe 负责检查和登记，最后两段只处理模块与设备对象的建立、撤销。

`module_param` 声明参数，`MODULE_PARM_DESC` 为参数提供说明，`MODULE_DESCRIPTION` 为模块提供简介；初始化、退出和许可证宏沿用前置模块课程。文件开头的 SPDX 是 Software Package Data Exchange 许可证标识格式，此处 GPL-2.0 标识代码许可证，不参与错误处理。错误码、`ERR_PTR`、`IS_ERR`、`PTR_ERR` 与分配标志沿用前三章；日志中的 `%pe` 用来显示错误名称，数值仍同时用 `%ld` 输出。其余 `note_` 名称均为本实验自定义函数或对象。

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/init.h>
#include <linux/device.h>
#include <linux/platform_device.h>
#include <linux/err.h>
#include <linux/slab.h>

/* 0 为成功，1 为可选对象缺席，2 为提供者失败，3 为后续初始化失败。 */
static unsigned int scenario;
module_param(scenario, uint, 0444);
MODULE_PARM_DESC(scenario, "0=present 1=absent 2=provider_error 3=late_error");

struct note_state {
    int number;
};

static struct platform_device *note_device;
static const int optional_object = 7;

static const int *note_get_optional(void)
{
    if (scenario == 1)
        return NULL;
    if (scenario == 2)
        return ERR_PTR(-EBUSY);
    return &optional_object;
}

static void note_release(void *data)
{
    struct note_state *state = data;

    /* 此回调只作观察；其后的 devm 记录才释放 state 内存。 */
    pr_info("error_pointer_demo: release marker=%d\n", state->number);
}

static int note_probe(struct platform_device *pdev)
{
    struct note_state *first;
    struct note_state *second;
    const int *optional;
    int ret;

    first = devm_kzalloc(&pdev->dev, sizeof(*first), GFP_KERNEL);
    if (!first)
        return -ENOMEM;
    first->number = 1;
    ret = devm_add_action_or_reset(&pdev->dev, note_release, first);
    if (ret)
        return ret;

    optional = note_get_optional();
    if (IS_ERR(optional)) {
        dev_info(&pdev->dev, "provider error=%ld name=%pe\n",
                 PTR_ERR(optional), optional);
        return PTR_ERR(optional);
    }
    if (optional)
        dev_info(&pdev->dev, "optional value=%d\n", *optional);
    else
        dev_info(&pdev->dev, "optional absent; continue initialization\n");

    second = devm_kzalloc(&pdev->dev, sizeof(*second), GFP_KERNEL);
    if (!second)
        return -ENOMEM;
    second->number = 2;
    ret = devm_add_action_or_reset(&pdev->dev, note_release, second);
    if (ret)
        return ret;

    if (scenario == 3) {
        dev_info(&pdev->dev, "late error=%d\n", -EINVAL);
        return -EINVAL;
    }
    dev_info(&pdev->dev, "probe completed\n");
    return 0;
}

static struct platform_driver note_driver = {
    .probe = note_probe,
    .driver = {
        .name = "error_pointer_demo",
        .probe_type = PROBE_FORCE_SYNCHRONOUS, /* 便于按注册时序观察。 */
    },
};

static int __init note_init(void)
{
    int ret;

    if (scenario > 3)
        return -EINVAL;
    ret = platform_driver_register(&note_driver);
    if (ret)
        return ret;

    note_device = platform_device_register_simple("error_pointer_demo", -1,
                                                   NULL, 0);
    if (IS_ERR(note_device)) {
        ret = PTR_ERR(note_device);
        platform_driver_unregister(&note_driver);
        return ret;
    }
    /* 设备注册成功与它的 probe 是否成功是不同的结果。 */
    pr_info("error_pointer_demo: registration completed scenario=%u\n", scenario);
    return 0;
}

static void __exit note_exit(void)
{
    platform_device_unregister(note_device);
    platform_driver_unregister(&note_driver);
    pr_info("error_pointer_demo: exit completed\n");
}

module_init(note_init);
module_exit(note_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Error value and managed cleanup teaching example");
```

同目录的 `Makefile` 只有一个目标：

```makefile
obj-m += error_pointer_demo.o
```

这里的 `MODULE_LICENSE` 和初始化、退出宏沿用前置 Hello 模块。`PROBE_FORCE_SYNCHRONOUS` 是强制同步探测的策略枚举值，使本例首次匹配的观察与注册调用顺序对应。设备注册返回错误指针，因此初始化失败时先解码，再撤销已注册的驱动；设备注册成功以后，即使它的 probe 失败，也仍有一个已注册但未成功绑定的设备对象，由模块退出负责注销。

## 4.3\_运行时区分装载成功与探测成功

在匹配的 Linux 构建环境中，先构建，再到目标系统实验。下面第一行仅适用于目标本机已有匹配的内核构建目录；交叉构建时沿用前置章节已经核对的目标构建命令与架构，不把宿主内核目录当成 ARM 目标目录。

```bash
make -C "/lib/modules/$(uname -r)/build" M="$PWD" modules
sudo insmod ./error_pointer_demo.ko scenario=0
sudo dmesg | tail -n 40
sudo rmmod error_pointer_demo
sudo dmesg | tail -n 40
```

默认路径应先看到 `optional value=7` 和 `probe completed`，卸载时再看到 `release marker=2`、`release marker=1`。这些短文本由本模块明确打印；时间戳和设备前缀由运行环境决定。表中假设未开启 `CONFIG_DEBUG_TEST_DRIVER_REMOVE`，即驱动核心的自动拆除重探测测试；开启它可能在正常探测中额外执行一次拆除与重试。当前核对配置未开启此项，但目标运行配置仍应另查。只看最后若干行可能截掉前面的消息，繁忙系统中应扩大窗口或在另一个终端用 `sudo dmesg -w` 观察，完成后按 Ctrl+C 退出观察。

卸载完成后，分别用 scenario=1、2、3 重复装载、观察、卸载，始终一次只保留一个模块实例。对 1，关键不是没有错误，而是“缺席”之后仍出现 `probe completed`。对 2 和 3，关键是在 `registration completed` 附近已经看到失败与释放，而不是等到卸载才首次释放。

`insmod` 仍可能返回成功，因为本模块初始化要建立的是驱动和设备注册关系，probe 的具体失败并不必然使设备注册失败。这是两层返回契约，而非错误被编码机制“吞掉”。可只读查看绑定关系：

```bash
ls -l /sys/bus/platform/devices/error_pointer_demo/driver
```

成功绑定时应存在 driver 链接；失败时该链接缺失。此时设备目录可以仍存在。若本地设备命名或框架配置导致目录不同，先确认本模块的注册日志与实际目录，不以路径缺失直接认定模块未装载。

每轮最后执行 rmmod，确认退出日志；保留实验源文件，若要清理构建产物，再在相同构建环境执行 `make -C "/lib/modules/$(uname -r)/build" M="$PWD" clean`。不要在模块尚装载时反复替换产物后混淆哪一版代码正在运行。

## 4.4\_日志能证明到哪里

错误指针用 `%pe` 打印时，内核会尽可能显示错误名称，未知名称则显示数字；配合 `PTR_ERR` 的十进制值，读者无需从裸地址猜原因。在固定 6.12.20 实现中，普通 `%p` 对通常的对象地址进行哈希，但 NULL 与错误指针在实现中有例外，按值打印。不能把“所有 %p 都能展示真实地址”或“错误指针也一定被哈希”当作通用结论。

这个实验用自己明确的日志观察控制流，没有假设 devres 默认会打印“released 2 resources”。如果要使用动态调试，须先确认内核配置与控制文件可用，再找到目标函数中真实存在的调试调用；打开一个文件的调试开关不会凭空为所有函数添加日志。跟踪探针同样需要相应配置、可探测符号与明确事件，函数被调用的记录也不等于每个资源都已正确释放。

KASAN（Kernel Address Sanitizer，内核地址消毒器）属于内存错误检测工具，是否覆盖某个访问取决于配置、插桩和路径；DEBUG_PAGEALLOC 是针对页分配与访问的调试配置，debug objects 检查接入对象的生命周期。它们都不是错误指针的自动安全网。本实验不故意解引用错误指针，不用一次崩溃去“证明不可访问地址保证了安全”。

固定证据见[源码阅读索引](../../../../research/source_reading/error_pointer/navigation/P01_Linux_6.12_错误指针源码阅读索引.md#1.2_按问题进入源码)。本章给出可执行实验及从代码推出的预期；目标内核装载、实际日志和绑定关系仍需在对应目标执行后才能记为实测。静态语法检查或宿主模型不能代替这一步。

## 4.5\_练习与解答

1. 只把 scenario=1 分支改成“NULL 就 return 0”，哪条预期首先失效？
2. 为什么不能把动作 1 登记在内存 1 分配之前，并传一个尚未有效的地址？
3. scenario=2 的释放标记已经出现，随后 rmmod 时还应再次出现标记 1 吗？
4. 加入第三个标记对象，令它成功后再失败，预测释放次序并修改程序验证。

**解答：** 第一题不会建立第二项，也不会打印最后的完成日志，但回调返回 0 会被视为成功，这正是提前成功的危险。第二题动作需要一个在回调执行时仍有效的对象，先登记会破坏数据及顺序条件。第三题不应因同一笔记录再次释放，失败清理已消费它；若真的重复，应调查额外登记或重试，而不是归因于错误码重复。第四题按“内存、动作”的成对顺序登记，预期是 3、2、1；若分配在中间失败，则只释放已经完成的记录。
