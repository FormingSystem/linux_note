# 第2章\_初始化与基本操作

上一章已经把任务内容与连接分开。现在让 10、20、30 依次入队，把 20 摘下，再把它放回队尾。先用一个普通 C 程序观察指针变化；它没有内核依赖，也没有并发，因而我们可以把注意力留给拓扑。

## 2.1\_在两个邻居之间插入

把 N 插在 A 和 B 之间，需要使 A.next=N、N.prev=A、N.next=B、B.prev=N。四次赋值合起来才建立完整关系。从单线程执行结果看，只要中途没人观察，赋值过程中短暂的不对称不影响最终结果；一旦加入并发，另一个执行者可能恰好看见半成品，这正是下一章的问题。

删除 N 时，把 A.next 改成 B、B.prev 改成 A，就恢复两个邻居的直接连接。没有必要移动 N 的业务数据，也不需要遍历所有其他节点。若还不知道 N 在哪里，寻找 N 的遍历成本应另算，不能拿“修改常数条边”证明“按编号删除总是常数时间”。

## 2.2\_运行一次完整的拓扑实验

保存为 `chain_model.c`，或取[同一份材料](../../../../labs/kernel/linked_list/materials/chain_model.c)。这是教学模型，函数名故意与 Linux API 分开；它不提供毒化、并发、配置检查或内核类型约束。

```c
/* 教学模型：只演示单线程拓扑，不是 Linux list.h 的替代品。 */
#include <assert.h>
#include <stddef.h>
#include <stdio.h>

struct link {
    struct link *next;
    struct link *prev;
};
struct task {
    int number;
    struct link queue_link;
};

static void init_link(struct link *link)
{
    link->next = link;
    link->prev = link;
}

static void add_tail(struct link *node, struct link *head)
{
    struct link *tail = head->prev;

    node->prev = tail;
    node->next = head;
    tail->next = node;
    head->prev = node;
}

static void detach(struct link *node)
{
    node->prev->next = node->next;
    node->next->prev = node->prev;
    init_link(node);
}

static struct task *task_from_link(struct link *link)
{
    return (struct task *)((char *)link - offsetof(struct task, queue_link));
}

static void print_queue(struct link *head)
{
    struct link *cursor;

    for (cursor = head->next; cursor != head; cursor = cursor->next) {
        assert(cursor->next->prev == cursor);
        assert(cursor->prev->next == cursor);
        printf("%d ", task_from_link(cursor)->number);
    }
    putchar('\n');
}

int main(void)
{
    struct link ready;
    struct task tasks[3] = {{.number = 10}, {.number = 20}, {.number = 30}};
    size_t index;

    init_link(&ready);
    assert(ready.next == &ready && ready.prev == &ready);
    for (index = 0; index < 3; ++index) {
        init_link(&tasks[index].queue_link);
        add_tail(&tasks[index].queue_link, &ready);
    }
    print_queue(&ready);
    detach(&tasks[1].queue_link);
    print_queue(&ready);
    assert(tasks[1].number == 20); /* 摘链没有结束对象寿命。 */
    add_tail(&tasks[1].queue_link, &ready);
    print_queue(&ready);
    for (index = 0; index < 3; ++index)
        detach(&tasks[index].queue_link);
    assert(ready.next == &ready && ready.prev == &ready);
    return 0;
}
```

使用可用的 C11 编译器构建并执行：

```bash
cc -std=c11 -Wall -Wextra -Werror chain_model.c -o chain_model
./chain_model
```

三行预期顺序分别是 `10 20 30`、`10 30`、`10 30 20`。tasks 数组只提供三个稳定地址；链表的访问顺序由 link 决定，不再等于数组下标顺序。最后按数组下标依次摘除仍然合法，因为每次都已直接拿到那个节点，不依赖前一次遍历保存的连接。

`offsetof` 给出成员偏移，char 指针按字节减去偏移后找回宿主。只对真实 task.queue_link 调用转换函数，不对 ready 头节点调用。两个 assert 检查访问到的节点的双向局部关系，不能证明任意损坏指针都安全可读，也不检测另一个不可达环；后面会限定它的验证范围。

## 2.3\_将模型映射到Linux接口

| 需要做的事 | Linux 接口 | 结果 |
| --- | --- | --- |
| 定义并初始化一个头 | LIST_HEAD(name) | 产生带自环初值的 list_head 对象 |
| 初始化已有节点或头 | INIT_LIST_HEAD(ptr) | 将 next/prev 都写为自身；不能用来清空仍挂着的对象 |
| 放到头后 | list_add(node, head) | 连续插入呈后进先出顺序 |
| 放到尾前 | list_add_tail(node, head) | 连续插入保持到达顺序 |
| 摘链并毒化连接 | list_del(node) | 宿主仍在，节点不再是可判空的自环 |
| 摘链并重置 | list_del_init(node) | 宿主仍在，连接回到自环 |
| 访问宿主对象 | list_for_each_entry / list_entry | 类型与成员必须匹配 |
| 遍历时删除当前节点 | list_for_each_entry_safe | 先保存下一游标；只解决本轮删除当前节点 |
| 判断空表 | list_empty(head) | 测试 head.next 是否回到 head，不检查整个表 |

普通 list_add/list_add_tail 为内联函数，不要把所有接口都称为宏。插入函数会覆盖待插入节点的连接字段，初始自环有助于统一脱链状态，但不提供“重复插入自动拒绝”的保证。

原稿的人工追问保留：**“这里只有prev->next采用了WRITE_ONCE()有什么说法吗？”** 当前固定版本 INIT_LIST_HEAD 对 next 和 prev 都使用 WRITE_ONCE，而 __list_add 最后对 prev->next 使用该访问标记。回答必须对准具体函数和版本，不能由一个字段的写法推断整个链表已具备发布顺序或互斥保证。具体语句唯一解释在[list.h 初始化与接链](../../../../research/source_reading/linked_list/source_explanations/include/linux/list.h.md#1.1_初始化与四条接链赋值)。

这些片段的版本身份和阅读入口见[Linux 6.12 链表源码索引](../../../../research/source_reading/linked_list/navigation/P01_Linux_6.12_链表源码阅读索引.md#1.1_版本和阅读任务)，不要用别的内核版本补齐这里的语句顺序。

原有并发批注也保留：

<span style="color:red;">但是，`WRITE_ONCE` 并不解决**并发访问**中的**竞态条件**问题，即多个线程或CPU同时访问和修改链表结构时可能导致的数据不一致或破坏。在高并发环境下，多个线程可能同时访问链表的同一部分（例如同时修改 `prev->next` 指针），这种情况下，就需要使用**锁机制**来确保**独占访问**。</span>

这条质疑的方向成立；具体使用锁还是其他协议，要看访问者、上下文与寿命要求。不能再沿用旧稿中“WRITE_ONCE 绕过 CPU 缓存、保证四次赋值严格全局有序”的解释。

## 2.4\_删除后的指针为什么不是NULL

list_del 将被摘节点的 next/prev 写成 LIST_POISON1/2，留下容易识别的异常地址，帮助暴露误用。固定版本中它们是 `0x100`、`0x122` 加上配置相关的 POISON_POINTER_DELTA，并非总是两个低地址，也不是旧稿写的固定 `0x100/0x200`。

看到毒化相关故障，是“访问已不适合沿链使用的连接”的线索，不能立即断定宿主内存已释放。list_del 可以发生在一个仍存活的对象上；损坏来源也可能更早。NULL、错误指针和毒化值各有不同契约，不应用一张所有架构通用的地址空间示意图替代判断。

若需要重用节点，用已经证明合适的摘链/初始化流程。对 list_del 后的节点调用 list_empty 不会替你回答“是否不在任何队列”；对仍挂在链上的节点直接 INIT_LIST_HEAD，则会把它与邻居的关系割裂，遗留悬挂的拓扑。

## 2.5\_回顾与练习

1. 把模型 add_tail 的插入位置换成头后，三次插入后的顺序是什么？
2. 从遍历循环中摘除当前节点后，还能直接用当前节点的 next 找下一项吗？
3. 释放 tasks[1] 的内存是否是本程序正确操作？
4. list_empty 返回真，能证明不存在泄漏吗？

解答：第一题为 30、20、10。第二题取决于摘除操作怎样处理连接；本模型把它重置为自身，Linux list_del 会毒化，均不能据此继续，须提前保存下一项。第三题不可以，tasks 在栈上，不由 malloc/kmalloc 分配。第四题只能说明头所见为空，遗失而不可达的对象仍可能泄漏。
