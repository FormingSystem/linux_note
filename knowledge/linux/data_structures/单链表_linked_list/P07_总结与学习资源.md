# 第7章\_总结与学习资源

到这里，我们用同一组任务完成了建表、摘除、重入、私有构建、失败回滚和退出清理。继续看大型子系统前，先把这些动作连成一条可以复述的推理链。

## 7.1\_从对象寿命回看每个接口

对象先存在，连接才有地址；连接进入某个表，才有成员资格；成员资格撤销，不自动消除其他持有者。只有最后使用结束，才轮到实际分配者对应的释放方式。

因此，初始化头、分配宿主、插入成员、取得对象引用、摘除成员和释放宿主是不同动作。一个 API 的名字不替你补齐其他动作。list_for_each_entry 的类型化游标也只解决地址换算，不承担运行时类型检查；safe 迭代只保存下一游标，不替所有并发路径保活对象。

## 7.2\_常用操作的查询边界

| 查询任务 | 接口 | 先确认 |
| --- | --- | --- |
| 查看首项 | list_first_entry | 表非空；空表不能解引用伪宿主 |
| 空表时需要 NULL | list_first_entry_or_null | 仍需同步及寿命协议，NULL 不是锁 |
| 换一个队列或移到尾部 | list_move / list_move_tail | 节点当前在合法链内，源/目标关系受保护 |
| 把整段并入另一队列 | list_splice_tail_init | 两条表不同且受同一事务保护，源头随后恢复为空 |
| 暂时摘下以便重入 | list_del_init | 节点当前的成员资格清楚，不能重复并发操作 |
| 等待特定脱链完成 | list_del_init_careful / list_empty_careful | 采用匹配协议，不能同时任意重新 list_add |

最后一组带 careful 的接口提供特定顺序与双向检查，不是通用无锁队列。只要另一个 CPU 可能重新插入，或你需要遍历并任意增删，就不能从“careful”推断不需要其他同步。版本分支见[拓扑与发布导读](../../../../research/source_reading/linked_list/navigation/P02_拓扑修改与发布边界导读.md)。

## 7.3\_用一段错误设计自测

假设程序这样安排：分配 task，加入 ready；遍历时取出 task 裸指针并解锁；另一条路径 list_del 并 kfree；原遍历者随后读取 number。每一步单独看都调用了合法接口，组合为什么仍错误？

错误发生在“指针离开保护范围”时：原遍历者没有取得独占所有权或额外引用，删除方也不知道它仍在使用。修复可以是保持锁直到短访问结束，或在锁内取得引用后再解锁，再由最后引用回收。只把遍历宏换成 safe、只把 number 读取换成 READ_ONCE，均没有建立新的对象持有关系。

再看另一段：向 ready 依次头插 10、20、30，输出为 30、20、10，程序员因此认定链表坏了。这是预测错误，不是拓扑错误。调试之前先写出接口应产生的顺序，会少走很多弯路。

## 7.4\_继续阅读的理由

[源码总索引](../../../../research/source_reading/linked_list/navigation/P01_Linux_6.12_链表源码阅读索引.md)给出固定提交和按问题定位的顺序；需要具体函数时进入唯一实现标题，不再从多个旧版本片段拼出“当前实现”。
