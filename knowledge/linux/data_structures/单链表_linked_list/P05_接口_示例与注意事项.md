# 第5章\_接口\_示例与注意事项

前四章已经区分拓扑、共享访问与发布。现在把同一组 10、20、30 任务交给真实 Linux 链表接口：先构建一个私有批次，全部成功后接入 ready；移除编号 20，退出时释放剩余任务。示例只演示链表与模块生命周期，没有为它额外创建字符设备。

## 5.1\_给失败留一条可走完的路

我们需要两条表：局部 staging 保存正在构建的对象，静态 note_ready 保存成功批次。失败只清理 staging；全部成功后用 list_splice_tail_init 把整批接到 note_ready 尾部，并将 staging 恢复为空头。这是在独占环境中的拓扑转移，不是一个自动原子的并发事务。

一个只读模块参数 fail_after 控制模拟失败点：-1 不注入，0、1、2 分别表示成功分配这么多个节点后失败。真实 kmalloc 返回 NULL 也走同一条回滚路径。这样能够预测每次失败要释放几个对象，而不是等系统恰好内存不足。

## 5.2\_完整模块

保存为 `note_list.c`，材料目录的 Makefile 只有 `obj-m += note_list.o`。构建前提沿用[模块构建课程](../../../../engineering/build/kernel_modules/大纲.md)：构建树必须与目标运行内核匹配。

LIST_HEAD 和 INIT_LIST_HEAD 沿用第二章的自环初始化。分配标志 GFP_KERNEL 允许在本例的进程上下文等待内存；EINVAL 表示参数不合法，ENOMEM 表示内存不足。module_param 登记只读参数，MODULE_PARM_DESC 给它附上说明，均沿用模块课程的参数接口。

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/list.h>
#include <linux/slab.h>
#include <linux/errno.h>

struct note_task {
    int number;
    struct list_head link;
};

static LIST_HEAD(note_ready);
static int fail_after = -1;
module_param(fail_after, int, 0444);
MODULE_PARM_DESC(fail_after, "成功分配多少个节点后模拟失败，-1 表示不注入");

static void note_free_all(struct list_head *head)
{
    struct note_task *task;
    struct note_task *next;

    list_for_each_entry_safe(task, next, head, link) {
        /* 先从容器摘除，再释放本例独占的宿主对象。 */
        list_del(&task->link);
        kfree(task);
    }
}

static void note_print(const char *phase)
{
    struct note_task *task;

    list_for_each_entry(task, &note_ready, link)
        pr_info("note_list %s: %d\n", phase, task->number);
}

static int __init note_list_init(void)
{
    LIST_HEAD(staging);
    struct note_task *task;
    struct note_task *next;
    int index;

    if (fail_after < -1 || fail_after > 2)
        return -EINVAL;
    for (index = 0; index < 3; ++index) {
        /* 在私有暂存链上构建完整批次，任一失败全部回滚。 */
        if (index == fail_after)
            goto no_memory;
        task = kmalloc(sizeof(*task), GFP_KERNEL);
        if (!task)
            goto no_memory;
        task->number = (index + 1) * 10;
        INIT_LIST_HEAD(&task->link);
        list_add_tail(&task->link, &staging);
    }
    list_splice_tail_init(&staging, &note_ready);
    note_print("ready");

    list_for_each_entry_safe(task, next, &note_ready, link) {
        if (task->number == 20) {
            list_del(&task->link);
            kfree(task);
        }
    }
    note_print("after_remove");
    return 0;

no_memory:
    note_free_all(&staging);
    return -ENOMEM;
}

static void __exit note_list_exit(void)
{
    note_free_all(&note_ready);
    pr_info("note_list empty=%d\n", list_empty(&note_ready));
}

module_init(note_list_init);
module_exit(note_list_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("链表批次构建、失败回滚与完整清理");
```

`list_for_each_entry_safe` 先保存 next，再进入循环体，所以释放当前 task 后仍可沿提前保存的游标继续。在本例中没有其他访问者删除 next，因而这个游标仍有效；增加并发后，safe 这个名字不替代锁或引用。

局部 staging 位于初始化函数栈上，只能在函数返回前使用。拼接的 init 后缀把它恢复自环，成功后的节点都连接到长期存在的 note_ready；不能把仍引用栈头的链交给以后使用。普通 list_splice 不重置源头，继续把原源头当独立表遍历可能走错环；这里明确选择带 init 的版本。

`list_del` 之后才 kfree，是因为本例的宿主由 kmalloc 分配，且只有当前模块的独占路径使用。这个顺序不是“所有摘链对象都必须立刻释放”的规则。若任务还被另一个索引、引用计数或异步请求持有，删除成员关系后还要等待各自使用结束。

## 5.3\_正常路径与失败路径的预测

在目标 Linux 的材料目录执行，KDIR 指向已准备好的目标构建树：

```bash
make -C "$KDIR" M="$PWD" modules
sudo insmod ./note_list.ko
sudo dmesg | tail -n 12
sudo rmmod note_list
sudo dmesg | tail -n 12
```

预期 ready 阶段出现 10、20、30，after_remove 出现 10、30，退出时 empty=1。这些是需要在目标执行的预测，不是本文已经取得的装载日志。日志可能与其他内核输出交错，tail 的窗口也不保证只含本模块，应按 note_list 前缀辨认。

在模块已经卸载后，分别尝试：

```bash
sudo insmod ./note_list.ko fail_after=0
sudo insmod ./note_list.ko fail_after=1
sudo insmod ./note_list.ko fail_after=2
```

三次应返回加载失败，没有成功发布的 ready 批次；分别有 0、1、2 个已分配节点需要回收。初始化失败时不会再由 module_exit 替你清理，所以 no_memory 标签必须独立走完。输入 fail_after=3 会返回无效参数，不能把它当成第三次真实分配失败。

失败后的复测是重新用默认参数加载再卸载。这样检查失败是否留下会妨碍后续运行的状态。单凭一次日志里没有报错，不能证明没有泄漏或竞争；下一章会展开证据强弱。

## 5.5\_练习与解答

1. 第二次实际 kmalloc 失败时，staging 和 note_ready 分别是什么状态？
2. 为什么成功后再把 staging 头的地址保存到全局是错误的？
3. 想保留 20 以后重用，哪一行不能照搬？
4. 若改成 list_add 头插，两个打印阶段的顺序会怎样？

解答：第一题 staging 有一个对象，需要释放；note_ready 仍为空。第二题 staging 位于即将结束的栈帧，长期数据不能依赖它。第三题不能 kfree，应按脱链状态和未来所有权保留对象，必要时使用 list_del_init。第四题 ready 为 30、20、10，移除后为 30、10；这也是验证头插/尾插语义的最小变更。
