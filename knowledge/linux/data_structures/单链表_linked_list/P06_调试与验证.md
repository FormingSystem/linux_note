# 第6章\_调试与验证

上一章的日志显示了我们期望的顺序。但打印 10、20、30，是否足以证明链表正确？不是：它没有说明倒向连接正确，也没有证明遗失节点都被释放，更没有执行过两个并发修改者。

## 6.1\_让每种检查回答一个问题

| 检查 | 能支持的结论 | 不能单独证明的事 |
| --- | --- | --- |
| 按预期顺序遍历 | 此次执行的可达顺序 | 反向拓扑、其他不可达对象、并发寿命 |
| 检查 next.prev 与 prev.next | 此次检查访问到的局部双向关系 | 任意损坏指针安全可读、没有孤立环 |
| 分配/释放计数配对 | 已被记录对象的资源配对 | 未记录路径、真实异步使用者已退出 |
| list_empty | 头节点的 next 回到自身 | 越界检测、无泄漏、完整双向一致性 |
| 重复加载及失败后重试 | 执行过的路径没有留下可见阻碍 | 未来所有负载、所有错误分支都正确 |
| 动态检查器未告警 | 相关配置、hook 和已执行路径下的有限观察 | 未执行路径、未接入操作或全部硬件内存序 |

遍历输出前也要满足同步和寿命协议。不要为了排错把无锁遍历塞进正在并发修改的队列，再把新崩溃误归因于业务代码。容器转换宏依赖调用者提供正确类型与成员；它不是运行时类型识别器。

## 6.2\_跟着三个失败点核对清理

用第五章的模型列出应发生的动作：

| fail_after | 已分配并入暂存链 | 应释放 | 是否拼接到 ready |
| --- | --- | --- | --- |
| 0 | 无 | 0 个 | 否 |
| 1 | 10 | 1 个 | 否 |
| 2 | 10、20 | 2 个 | 否 |
| -1 且实际分配成功 | 10、20、30 | 先移除 20，退出释放 10、30 | 是 |

宿主故障替身可以精确检查这些数量，并额外让每一次实际 kmalloc 返回 NULL，确认不会读空指针。真实目标则应确认加载错误、后续正常加载和卸载，以及适用检查器的报告。两种证据互补，替身不能验证真实页分配、模块装载或内核并发。

如果只在 module_exit 清理，初始化失败的对象会遗留；如果未入链的当前分配也需要清理，应另有局部所有权记录。本例每次分配成功立即填写并接入 staging，之后没有该节点的其他可失败步骤，因此统一清理 staging 足够；换成更复杂的构建后要重做这份判断。

## 6.3\_链表检查器检查哪次动作

固定版本的 CONFIG_LIST_HARDENED 在增删前检查部分局部拓扑；CONFIG_DEBUG_LIST 对应更完整的报告路径。功能状态就是实际 next/prev，检查器读取这些指针和待插入节点关系，它没有维护一份“所有曾经入过队的对象”的全局历史，也不维护任意业务对象引用数。

插入前会检查邻居彼此相连、待插节点不是直接邻居等条件。它不是通用成员资格查询：把一个已经挂在别处的节点插进另一张看似自洽的空表，不一定被这些局部判断识别。删除前会检查空值、毒化或邻接关系，具体覆盖由配置分支决定。

报告函数拒绝后，内层接链/摘链动作可能返回；但外层 list_del 仍有毒化字段的语句。因此不要把一次检查失败理解成“整个 API 原子回滚、所有字段保持原样”。告警或 BUG 行为还受相关配置影响，不能在生产机器上故意执行重复删除来学习输出。具体分支见[链表源码导读](../../../../research/source_reading/linked_list/navigation/P02_拓扑修改与发布边界导读.md#2.2_检查发生在修改之前)。

## 6.4\_其他验证器与使用条件

内核地址检查器 KASAN（Kernel Address Sanitizer）可帮助发现接入路径上的越界和释放后访问，后者也称 UAF（Use After Free）；kmemleak 可辅助追踪某些潜在不可达分配。它们都不是“把表删空就自动启用”的功能。Lockdep 研究锁的使用关系，内核并发检查器 KCSAN（Kernel Concurrency Sanitizer）观察数据竞争，各有配置、运行状态和覆盖限制。只启用其中一个，不能声称已证明另外几类性质。

记录验证时应同时记录源码提交、构建配置、实际运行内核、执行动作、注入点、输出和未执行路径。宿主只编译成功，应写“宿主模型编译”；使用目标头文件的 -fsyntax-only 应写“目标架构语法检查”；只有实际通过 Kbuild 和装载的结果才写成相应验证，不用“编译通过”模糊它们。

## 6.5\_排错练习

1. 所有日志都正确，但退出后还有一个分配未释放，最先补哪种证据？
2. list_empty 返回真，但 head.prev 仍指向旧节点，这份表是否可继续用？
3. safe 遍历时另一个 CPU 删除 next，宏能保护它吗？
4. 有毒化地址故障，是否应立即把原因写为 UAF？

解答：第一题核对每次分配及归还、失败路径和不可达对象，不只是再打印一遍表。第二题违反空表双向约束，先查谁只改了一条边。第三题不能，需锁、引用或适用的不同协议。第四题先检查摘链与释放的事件顺序，毒化是线索，不是宿主已经释放的充分证据。
