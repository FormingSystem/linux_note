# 第47章\_从内核使用场景选择索引

现在已经能维护树形、缓存和摘要，也知道并发保护与检查的边界。进入真实子系统时，还要追问：树按什么字段排，取出的首对象是否满足业务条件？本章固定同一内核版本逐个核对，避免把通用树的能力误当成完整调度策略。

## 47.1\_Linux\_rbtree\_在内核中的典型使用场景

现在不再从“哪里用了红黑树”罗列名字，而是带着同一组问题读具体使用者：对象按什么排序，业务到底查询什么，最左缓存和子树摘要各帮助哪一步，还有哪些条件决定最终动作？先进入[固定内核场景导读](../../../../research/source_reading/rbtree/navigation/P10_内核调用场景与选择边界导读.md#10.2_按排序键和业务问题逐项阅读)，下面的版本化事实都限定在官方固定 Linux 6.12.20，不把历史用途当成当前所有子系统的共同规则。

## 47.2\_高精度定时器为什么适合缓存最小节点

假设队列里有几个未来到期的定时对象，每次加入或取消后，调用者又要知道最早的对象是谁。普通有序树已支持接入与摘除，但每次重新从根沿左链查首节点，会反复走同一类路径。timerqueue 将到期时间 expires 作为比较依据，并在 timerqueue_head 中使用缓存根，正好把这个频繁问题变为读取最左入口。

具体证据在[到期比较与插入](../../../../research/source_reading/rbtree/source_explanations/lib/timerqueue.c.md#1.1_到期时间决定比较顺序)及[取首函数](../../../../research/source_reading/rbtree/source_explanations/include/linux/timerqueue.h.md#1.1_从缓存取最早节点)。timerqueue_add 返回 true 的含义是“新节点成为最早”，false 不表示插入失败；[timerqueue_del](../../../../research/source_reading/rbtree/source_explanations/lib/timerqueue.c.md#1.3_删除返回余队列是否非空)则在删除后检查队列是否仍非空，含义与普通 rb_erase_cached 的返回完全不同。

固定 hrtimer 的 enqueue_hrtimer 使用这个队列，调用前要求持有相应 base lock。取得最早对象还不等于现在就执行回调：当前时间、软/硬到期语义、时钟基准与时钟事件设备的处理属于定时器层。cached 优化的是候选地址取得，不是整个定时器服务已经变成 O(1)，更不是可以绕过调用者同步。

用前面的缓存实验换成 expires 语义即可预测索引层：新增更早时间应改变首地址，取消非首对象不改变首地址，取消最后对象变为空。至于实际触发时刻，不能靠这个索引实验推断，需要定时器专题的独立运行证据。

## 47.3\_调度实体按虚拟运行时间排序的思路

这个标题保留了进入公平调度的一条历史直觉：累计得到较少服务的实体应有机会追上，经典 CFS（Completely Fair Scheduler，完全公平调度器）讲法用虚拟运行时间 vruntime 表达按权重折算的服务进度，常以最小 vruntime 解释有序候选。它有助于理解为什么需要持续调整的顺序，却不能直接拿来描述本章固定版本。

固定 fair.c 的 [entity_before](../../../../research/source_reading/rbtree/source_explanations/kernel/sched/fair.c.md#1.1_树按虚拟截止时间比较)按 **deadline** 比较。这里的 deadline 是虚拟截止时间，不是墙上时钟的硬实时承诺。EEVDF（Earliest Eligible Virtual Deadline First，最早合格虚拟截止时间优先）先判断实体是否有资格获得服务，再在合格候选中考虑较早的虚拟截止时间。因此“按什么排序”与“是否允许选择”是两个轴。

用三个等权实体的简化数值观察这一区别，虚拟运行时间的理想平均值为 `(25+15+5)/3=15`。先忽略当前运行实体和额外特性分支，只看候选索引：

| 实体 | vruntime | deadline | 在这个简化状态中是否合格 |
| --- | --- | --- | --- |
| A | 25 | 30 | 否，服务进度超过当前平均 |
| B | 15 | 40 | 是 |
| C | 5 | 50 | 是 |

按 deadline 的最左节点是 A，却不能直接选它；vruntime 最小的是 C，但 B 在合格者中有更早 deadline。这个例子要区分的是两个判断，不是用三个数值实现完整调度器。实际[资格计算](../../../../research/source_reading/rbtree/source_explanations/kernel/sched/fair.c.md#1.2_资格由虚拟运行时间另行判定)使用加权状态和避免除法精度损失的比较，还会处理当前实体的贡献。

为了不逐个扫过所有不合格对象，树中保存子树最小 vruntime：如果一棵子树连最小值都不合格，其中更大的值也不能提供所需候选；如果左子树存在合格可能，deadline 次序又告诉我们应先去左边。这正是本章刚建立的“排序 + 另一轴摘要”组合。[pick_eevdf](../../../../research/source_reading/rbtree/source_explanations/kernel/sched/fair.c.md#1.4_先取合格候选再与当前实体比较)先试最左资格，再在需要时按摘要下降，之后还比较当前实体；单实体与 RUN_TO_PARITY 等分支可能提前返回。

所以本固定版不能总结成“取最小 vruntime 的 rb_first_cached”。缓存和增强分别帮助候选取得与资格剪枝，完整服务分配仍属于调度策略。本节也没有证明所有调度状态、时间片维护或真实性能，只纠正容器键和选择条件的混同。

## 47.4\_I/O\_调度与按位置排序

块 I/O 请求有逻辑起始扇区和长度。若要找邻近请求、判断某个请求从哪里开始，或沿位置继续选择候选，等值哈希索引不能直接提供有序前驱后继；位置树则可以保存这种关系。[elv_rb_add 与 elv_rb_find](../../../../research/source_reading/rbtree/source_explanations/block/elevator.c.md#1.1_按逻辑扇区接入请求)明确按 blk_rq_pos 排序与比较。

但起始扇区有序不等于队列总是把扇区最小者先发出。固定 mq-deadline 同时维护按方向组织的 sort_list 和 FIFO（First In, First Out，先进先出）队列，分发时考虑批次、读写方向、请求等待期限与饥饿限制，再在位置候选和到期候选之间选择。它需要两种索引，是因为位置邻近性和等待时间不能由同一个键同时表达。

例如位置较近的新请求与已经等待较久的旧请求发生竞争，只按位置继续走可能使旧请求迟迟没有机会。FIFO 期限提供另一条选择依据，代价是额外队列状态和共同维护要求。物理设备是否因此减少寻道或延迟，还取决于设备、工作负载和调度参数；逻辑扇区相邻不能无条件等同于固态设备上的物理寻道收益。本节只核对索引和决策职责，不提供性能测量。

## 47.5\_epoll\_等对象集合为什么可能需要有序管理

epoll 管理的是用户登记的关注对象及其就绪通知。固定 eventpoll.rbr 是缓存红黑树，其中每个 epitem 按 **file 对象与 fd 的复合键** 定位；不是只按 fd，也不是按事件的就绪时间排序。[复合键与查找](../../../../research/source_reading/rbtree/source_explanations/fs/eventpoll.c.md#1.1_文件对象与描述符组成键)可见两步比较，ep_find 要求持有 ep->mtx。

为什么不能只看到树就推断输出顺序？因为注册管理和就绪交付是两个任务：新增、修改或删除关注项时需要定位注册对象，而等待者取就绪事件还依赖 rdllist、ovflist 等状态。它们有自己的更新路径与保护范围，不是沿注册树中序遍历就得到业务通知的全部语义。

源码中的 file 指针比较保留内核实现的上下文，不应照抄成标准 C 对无关对象指针排序的教材示例；我们的宿主复合键实验仍采用稳定业务 id。这里能够确认的是这个固定版本的注册键和容器职责，不能推出 epoll 永远只能使用这一数据结构或其完整锁协议已由本章验证。

## 47.6\_VMA\_历史上使用\_rbtree\_与后来转向\_Maple\_Tree\_的原因

VMA（Virtual Memory Area，虚拟内存区域）描述进程地址空间中的范围属性，通常以 `[start,end)` 表示，终点不包含在范围内。查一个地址属于哪个区域、从某地址开始遍历、寻找足够大的空洞和替换一个子范围，需求已经超过单个整数键的等值查询。

传统 VMA 管理结合链表、红黑树及查找缓存；本固定版本的 mm_struct 使用 mm_mt，VMA 查询与迭代接入 Maple Tree 和 vma_iterator。具体字段和查询证据已在[P14 范围实例](P14_Maple_Tree_与_VMA_管理.md#14.1_一个地址为什么需要三种查询)及其固定源码索引展开，本节保留选择关系，不再复制另一套 VMA 更新教程。

Maple Tree 面向非重叠范围的映射，采用多路节点组织更多边界和槽，提供范围遍历、空洞等相关能力。多路布局有机会减少逐个小节点的指针下行，但也引入节点容量、范围分裂合并、分配与更新规则；读侧保护和缓存效率需要具体路径才能证明，不能用“减少锁竞争”一句话自动宣称所有场景更快。

| 原来容易混淆的变化 | 应分别追踪的事情 |
| --- | --- |
| VMA 迁移到 Maple Tree | 非重叠地址范围、迭代与空洞管理的容器变化 |
| 页缓存或整数索引使用 XArray 等结构 | 由整数索引到对象的查询与标记需求，并非任意范围树替换 |
| 公平调度走向 EEVDF 语义 | 资格和虚拟截止时间的调度决策变化，本固定版本仍使用增强缓存红黑树 |
| 任意重叠区间查询 | 可由 interval tree 的起点次序与最大终点摘要支持，契约不同于非重叠映射 |

因此 mm_mt 取代某一套 VMA 容器，不表示全内核不再使用 rbtree，也不表示任务调度改用 Maple Tree。读取具体业务接口比追逐“新结构替代旧结构”的口号更能指导选择。

## 47.7\_interval\_tree\_与\_augmented\_rbtree\_的关系

通用区间树把每个区间的起点作为搜索次序，把子树最大终点作为摘要。查询闭区间 `[start,last]` 与节点区间是否相交，需要同时满足“节点起点不大于 last”和“节点终点不小于 start”。如果左子树最大终点小于 start，整棵左子树都不可能相交，可以跳过。

固定 include/linux/interval_tree_generic.h 的 INTERVAL_TREE_DEFINE 采用这组条件，并组合缓存根和增强回调；lib/interval_tree.c 为 interval_tree_node 实例化。这个接口容纳任意重叠区间并提供相交迭代，不能把前面教学示例的“重复起点拒绝、返回任意一个覆盖点的对象”当成它的全部语义。对应版本入口见[范围容器导读](../../../../research/source_reading/rbtree/navigation/P10_内核调用场景与选择边界导读.md#10.3_范围容器的两个不同契约)。

再比较端点：本节 interval tree 使用闭区间，VMA 说明使用半开区间。把 `[a,b)` 的 b 原样塞进包含终点的比较，会把边界上的不相交误判成相交。任何端点转换都必须先处理空范围、最大值和溢出，不能统一写成无条件加一或减一。

## 47.8\_从使用场景反推结构选择

先确定业务关系，再选择候选结构：

| 当前必须支持的关系 | 候选与应继续核对的代价 |
| --- | --- |
| 小规模顺序扫描 | 简单数组或链表；数组局部性、链表修改位置和对象寿命分别比较 |
| 主要等值查找 | 哈希结构；碰撞、容量、最坏路径与内存成本 |
| 整数索引到对象 | XArray 等整数索引结构；稀疏度、索引范围和标记需求 |
| 动态有序键、前驱后继 | rbtree；逐节点下行、比较与更新代价 |
| 频繁取得中序首对象 | cached rbtree；额外入口及更新一致性 |
| 用子树统计排除候选 | augmented rbtree；摘要计算、存储与每次变更维护 |
| 非重叠范围映射与空洞 | Maple Tree 类范围接口；分裂合并与读写协议 |
| 任意重叠区间的相交查询 | interval tree；起点次序、最大终点和输出数量 |

用三道题检查自己的判断：最早 deadline 的对象不合格时，缓存是否已经完成业务选择？最邻近的块请求等候时间很短时，位置树是否已经解决公平性？epoll 注册树中最左的对象是否一定最先就绪？三个答案都要求回到业务状态，而不是继续改良一个与问题无关的比较器。

本节实际核对固定 Git 对象中的应用文件和十八个具体函数，未运行调度器、设备 I/O、epoll 或定时器压力测试。调用关系为理解提供证据，无法替代这些子系统各自的正确性、并发和性能验证。
