# 第3章\_算法之魂\_哈希函数与位运算优化

前面的桶模型告诉我们：查找的最后一步仍然是比较完整键。现在只研究进入桶之前的计算。如果任务编号是 0、16、32、48，把低四位当作十六桶索引，它们都会进桶 0。多准备几个桶，却没有让这些输入分散，这就是本章要修正的认识。

Linux 的具体计算以 NXP 官方固定提交、Linux 6.12.20 为证据；历史目录中的 5.10 不代表这些语句来自 5.10。先从[源码总索引](../../../../../research/source_reading/hash_table/navigation/P01_Linux_6.12_哈希计算源码阅读索引.md#1.1_版本和任务边界)核对身份，再看下文模型。

## 3.1\_输入宽度与混合结果和桶号是三件事

设桶数为 2^b。桶号只需 b 位，但输入键可以是 32 位整数、64 位整数或指针。哈希计算可以先在固定宽度内混合输入，再取其中 b 位作为索引；因此 `hash_32(value, 8)` 不是返回一个任意 32 位大整数，而是返回 0～255 的桶号。

原有人工问题保留：

<span style="color:red;">为啥是32位？不是跟随机器位宽来的吗？如32位系统或者64位系统作以区分？</span>

关键是分开 **输入数据的宽度** 与 **机器上 unsigned long 的宽度**。64 位内核仍然会处理 u32 编号；32 位内核也可能处理 u64 文件位置或标识符。u32、u64 分别是内核的无符号 32 位、64 位类型。内核可以为这些组合选择不同实现，但不能仅靠“现在在某种机器上运行”推断一个表达式有几位。

固定版本的常用入口如下；本章实验使用 b=4，并把通用接口共同适用的输出范围限制为 1～32 位，不把非法移位当成特殊功能：

| 接口 | 输入与选择依据 | 需要警惕什么 |
| --- | --- | --- |
| hash_32 | 接收 u32，混合后取高 b 位 | 输入先转换到 32 位；高位信息可能已丢失 |
| hash_64 | 接收 u64；通用实现按 BITS_PER_LONG 分支 | 32 位与 64 位路径不保证得到同一桶号 |
| hash_long | 按内核 unsigned long 宽度选择 32/64 位入口 | 不是“任何整数的全部有效位宽” |
| hash_ptr | 指针转换为 unsigned long 后走 hash_long | 指针身份不等于指向内容的相等性 |
| hash32_ptr | 64 位时把高低 32 位异或，32 位时直接截取 | 是折叠值，没有完成乘法混合和指定桶数的截断 |
| hash_min | hashtable.h 按表达式 sizeof 选择 hash_32 或 hash_long | 插入与查找的表达式类型也必须一致 |

例如 32 位内核里把一个 u64 交给 hash_min，会选择 hash_long，而后者走 32 位入口；不能因此声称完整 64 位都参与散列。即使桶内仍比较完整键而保持正确，这也可能把大量只在高半部不同的键挤在一起。真正需要混合完整 u64 时，应明确选用合适的 64 位键哈希方案，不能把同一个已经缩小的桶号再交给 hash_add 当原始键，造成重复计算。

## 3.2\_乘法之后为什么取高位

固定 hash.h 的通用 32 位路径先乘常数 0x61C88647，结果保留低 32 位，再右移 32-b 位。无符号乘法按模 2^32 回绕；模型也必须明确保留这一宽度。用任意宽度整数或错误的有符号乘法替代，就可能算出不同结果，甚至触发有符号溢出。

乘法会把低位变化通过进位传播到更高位置，却不会把高位变化传回乘积的低位。因此，“任何一位变化都会均匀改变所有位”的严格雪崩描述不适合这个简单算法。对 16 的倍数，乘任意整数之后低四位仍是零；若继续取乘积低四位，原问题一点也没解决。取高位正是为了让低位模式以外的变化参与选桶。

```mermaid
flowchart LR
    key["u32 键"] -->|"乘 0x61C88647"| product["保留低 32 位的乘积"]
    product -->|"右移 32-b 位"| index["b 位桶索引"]
    index -->|"进入候选集合"| compare["比较完整键"]
    compare -->|"匹配才返回"| value["对应对象或值"]
```

常数与黄金分割比例有关。用 φ=(√5-1)/2 表示约 0.618 的比例，源码注释说明采用负向的 1-φ，并认为它稍易乘算、分布没有本质差别。32 位的 0x61C88647 也等于 2^32-0x9E3779B9。这里不需要再编造“补数更能消除低位偏见”或“特别适合所有乘法流水线”的理由。

这仍是确定的整数映射，不会为输入创造随机熵，也不是密码哈希。恶意选择的输入、特殊步长以及小样本都可能产生偏斜。乘法取高位提供了一种便宜的分布方法，不提供任意工作负载下的无冲突保证。

## 3.3\_用同一组键观察两种计算

下面是完整 C11 模型。bucket_32 对应固定通用 32 位算法；bucket_64 分别模拟 32 位机器上的高低位折叠和 64 位机器上的乘法。word_bits 是我们选择的模型参数，不是读取宿主系统的位宽。使用 stdint.h 的 uint32_t/uint64_t，避免 Windows 与 Linux 的 long 宽度差异影响实验。

UINT32_C/UINT64_C 构造适用宽度的常数，PRIu32 提供 uint32_t 的打印格式；它们来自标准头文件，不是本实验自创的接口。保存为 `hash_bits.c`，材料见[实验目录](../../../../../labs/kernel/hash_table/materials/README.md)。

```c
/* 固定宽度模型：观察桶分布，不把计数当作 CPU 性能测试。 */
#include <assert.h>
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>

static uint32_t multiply_32(uint32_t value)
{
    return value * UINT32_C(0x61C88647);
}

static uint32_t bucket_32(uint32_t value, unsigned int bits)
{
    assert(bits >= 1 && bits <= 32);
    return multiply_32(value) >> (32 - bits);
}

static uint32_t bucket_64(uint64_t value, unsigned int bits,
                          unsigned int word_bits)
{
    assert(bits >= 1 && bits <= 32);
    assert(word_bits == 32 || word_bits == 64);
    if (word_bits == 64)
        return (uint32_t)((value * UINT64_C(0x61C8864680B583EB)) >> (64 - bits));
    return bucket_32((uint32_t)value ^ multiply_32((uint32_t)(value >> 32)), bits);
}

static void print_counts(const char *name, const unsigned int counts[16])
{
    unsigned int index;
    printf("%s:", name);
    for (index = 0; index < 16; ++index)
        printf(" %u", counts[index]);
    putchar('\n');
}

int main(void)
{
    unsigned int low_counts[16] = { 0 };
    unsigned int high_counts[16] = { 0 };
    unsigned int index;
    uint64_t value = (UINT64_C(1) << 32) + 1;

    for (index = 0; index < 16; ++index) {
        uint32_t key = index * UINT32_C(16);
        ++low_counts[key & 15];
        ++high_counts[bucket_32(key, 4)];
    }
    print_counts("直接取低位", low_counts);
    print_counts("乘法取高位", high_counts);
    printf("截断为32位: %" PRIu32 "\n", bucket_32((uint32_t)value, 4));
    printf("完整64位/32位机器: %" PRIu32 "\n", bucket_64(value, 4, 32));
    printf("完整64位/64位机器: %" PRIu32 "\n", bucket_64(value, 4, 64));
    assert(bucket_32(123, 32) == multiply_32(123));
    return 0;
}
```

编译运行：

```bash
cc -std=c11 -Wall -Wextra -Werror -pedantic hash_bits.c -o hash_bits
./hash_bits
```

直接取低位的十六个桶中，第 0 桶有 16 项，其余为零。乘法取高位的计数为：

```text
2 2 0 2 0 2 0 2 2 0 2 0 1 0 1 0
```

它确实分散了候选，但并没有“一桶正好一个”。这比挑一组刚好漂亮的键更有用：我们看到算法解决了什么，也看到了它没有承诺什么。计数总和仍为 16，空桶和冲突可以同时存在。

最后三行依次为 6、8、14。它们来自同一个数 2^32+1 的三种处理：截断为 u32、保留 u64 但按 32 位机器折叠、按 64 位机器计算。不能把某平台的桶号持久化后，假定换个平台还可以直接复用；重新建索引时应按当前表的完整规则重新计算。

## 3.4\_从模型回到内核入口

hash_64_generic 的 32 位路径先取高半部，做一次 32 位混合，再与低半部异或，最后调用 hash_32。64 位路径使用 0x61C8864680B583EB，在 64 位范围乘算并取高位。源码没有要求两条路径等价，也没有允许把丢掉的高位在后面“恢复”。

hash_min 依据表达式类型大小选择入口，因此不要在一处用 u32 键、另一处用 unsigned long，再想当然地认为“数值一样就一定走同一计算”。定义一个稳定的键类型，让插入、查找、删除调用同一个封装，比在各处猜默认整数类型容易审查。

此外，HASH_SIZE/HASH_BITS 从真正的桶数组取得长度信息。把数组传进普通函数形参后，它会退化为指针；再用 sizeof 猜原数组大小就失去依据。固定 hashtable 宏适合声明时确定桶数的数组，并不是任意动态内存都可以直接套用的一套接口。定义和初始化也不同：DEFINE_HASHTABLE 带初值，DECLARE_HASHTABLE 声明无显式初值的数组；自动存储期的后者必须先按接口初始化。

具体语句只在[hash.h 实现说明](../../../../../research/source_reading/hash_table/source_explanations/include/linux/hash.h.md#1.1_32位乘法与取高位)展开，位宽和表达式类型的调用关系见[模块导读](../../../../../research/source_reading/hash_table/navigation/P02_键位宽与落桶导读.md#2.1_从调用表达式追到计算路径)。本章给出理解模型，不把上游实现复制成第二份教程。

## 3.5\_容量与对齐的真实代价

桶头大小跟指针宽度及实际表示有关，不是永远 8 字节。若使用一指针 hlist_head，1024 个桶在常见 32 位配置约占 4 KiB，常见 64 位配置约占 8 KiB；这还没算节点、分配器开销、锁和业务数据。增加桶可以缩短平均候选集合，但同时扩大要扫描或访问的数组。应记录实际键分布、桶长最大值、平均比较次数、负载变化和内存预算，再决定 bits，而不是背一张按元素数指定常数的表。

对象对齐使某些地址低位固定为零，但并非所有指针都按同一粒度对齐。hash_ptr 计算地址身份的索引；两个内容相同但地址不同的对象，若业务认为键相等，就不应只散列它们的指针。反过来，地址被释放后重新使用，也不代表它仍是原对象的同一世代。

对于 2 的幂，无符号余数可以表示为掩码；但“取低位余数”与“乘法结果取高位”不是同一个桶划分。常量取模也可能由编译器转换成乘法、移位或掩码，不能用固定的“除法 20～80 周期、位运算 1 周期”当所有机器的选择依据。此处的桶计数是算法观察，不是目标 CPU 性能测量。

## 3.6\_旧示例为什么必须核对版本

旧稿把 kernel/pid.c 的 pid_hashfn 当作当前范例，还推断不同命名空间一定散列到不同桶。本固定提交的 find_pid_ns 实际从命名空间的 idr 索引查找，upid 也不再包含旧示例的 pid_chain；不能只把文中的 5.10 改成 6.12 就继续沿用那段代码。

可保留的认识是：同一编号在不同命名空间可能指向不同对象，索引或比较必须包含身份范围。不同输入参与混合以后仍可能冲突；完整身份比较或索引的命名空间隔离才承担正确性。PID 子系统的完整生命周期不在本章展开，版本定位见[源码索引](../../../../../research/source_reading/hash_table/navigation/P01_Linux_6.12_哈希计算源码阅读索引.md#1.2_从问题选择入口)。

## 3.7\_回顾与练习

1. 为什么把 32 位乘算改成 64 位乘法，再直接取 64 位结果的高 b 位，会得到不同的计算规则？
2. 对 16 的倍数先乘一个奇数，再取低四位，能改善本例分布吗？
3. hash32_ptr 返回了一个 u32，是否已经得到十六桶索引？
4. 修改对象的 key 后，为什么仅重新计算 lookup 的哈希还不够？
5. 为什么随机种子也不能替代比较完整键、内存预算和输入限额？

解答：第一题可能失去规定的模 2^32 回绕；第二题不能，乘积仍是 16 的倍数。第三题没有按桶数截断，也没有完成通常的乘法混合。第四题对象仍挂在按旧键选出的桶中，必须按协议迁移索引。第五题散列只是缩小候选范围，不能保证无碰撞或无限资源，种子还必须与该张表的计算和重建策略一致。
