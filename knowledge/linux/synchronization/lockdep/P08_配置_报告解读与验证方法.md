# 第8章\_配置\_报告解读与验证方法

## 8.1\_先确认检查能力确实存在

动态检查只有在配置、运行状态和路径覆盖同时成立时才产生证据。Linux 6.12.20 的主要配置关系是：

| 配置 | 作用 | 省略结果 | 实现落点 |
| --- | --- | --- | --- |
| `CONFIG_PROVE_LOCKING` | 启用完整锁依赖正确性验证 | 不执行完整依赖闭包证明 | `lib/Kconfig.debug` 选择 `LOCKDEP`、`DEBUG_LOCK_ALLOC`、IRQ flags 等 |
| `CONFIG_DEBUG_LOCK_ALLOC` | 检查持锁对象释放、活锁重初始化、任务持锁退出等 | 相应生命期误用不被该层报告 | 同上，并选择 `LOCKDEP` |
| `CONFIG_LOCKDEP` | 编译核心状态与事件设施，通常由可见调试项选择 | map/held 状态与多数接口退化 | `include/linux/lockdep*.h`、`kernel/locking/lockdep.c` |
| `CONFIG_LOCK_STAT` | 在 Lockdep hook 上增加竞争与持有统计 | 不影响 Lockdep 的基本正确性职责 | `kernel/locking/lockdep_proc.c` 的 `/proc/lock_stat` |
| `CONFIG_PROVE_RCU` | 让 RCU 调用条件使用 Lockdep 状态诊断 | RCU 动态条件告警关闭，RCU 功能契约仍在 | `kernel/rcu/Kconfig.debug`、`include/linux/rcupdate.h` |

配置、查询和诊断的文件地图先见 [Lockdep 查询适配与诊断模块导读](../../../../research/source_reading/lockdep/navigation/P04_Linux_6.12_Lockdep查询适配与诊断模块导读.md#4.5_配置与生命状态)。具体 Kconfig 选择关系见 [`PROVE_LOCKING`、`DEBUG_LOCK_ALLOC` 与 `LOCKDEP`](../../../../research/source_reading/lockdep/source_explanations/P08_Linux_6.12_Lockdep查询注解与配置源码实现.md#8.5_PROVE_LOCKING_DEBUG_LOCK_ALLOC与LOCKDEP)。

目标机先检查：

```bash
zcat /proc/config.gz | grep -E 'CONFIG_(PROVE_LOCKING|DEBUG_LOCK_ALLOC|LOCKDEP|PROVE_RCU)='
grep -E 'debug_locks|lock-classes|dependency chains|max locking depth' /proc/lockdep_stats
```

若系统没有 `/proc/config.gz`，应从与正在运行内核完全匹配的构建配置核对；不能拿另一个内核的 `.config` 代替。

## 8.2\_最小顺序反转验证

下面的模块先完整执行 `first_lock → second_lock`，释放后再执行反向顺序。它不需要制造两个任务真实互等，第二条组件链就足以让 Lockdep 发现闭环。

```c
#include <linux/init.h>
#include <linux/module.h>
#include <linux/mutex.h>

static DEFINE_MUTEX(first_lock);
static DEFINE_MUTEX(second_lock);

static int __init lockdep_cycle_demo_init(void)
{
	/* 第一条已观察组件链：first_lock → second_lock。 */
	mutex_lock(&first_lock);
	mutex_lock(&second_lock);
	mutex_unlock(&second_lock);
	mutex_unlock(&first_lock);

	/* 第二条组件链闭合依赖环，但当前单任务不会真实卡死。 */
	mutex_lock(&second_lock);
	mutex_lock(&first_lock);
	mutex_unlock(&first_lock);
	mutex_unlock(&second_lock);

	return 0;
}

static void __exit lockdep_cycle_demo_exit(void)
{
}

module_init(lockdep_cycle_demo_init);
module_exit(lockdep_cycle_demo_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lockdep锁顺序反转验证模块");
```

仅在可重启的调试环境运行。预期步骤：

```bash
sudo insmod lockdep_cycle_demo.ko
sudo dmesg | tail -n 160
sudo rmmod lockdep_cycle_demo
```

预期输出包含 `possible circular locking dependency detected` 一类标题、当前新取得点、至少一条既有反向依赖链和当前持锁信息。很多严重 Lockdep 错误路径会调用 `debug_locks_off()` 停止继续证明；不应只凭“已打印一条告警”推断生命状态，而应直接核对 `/proc/lockdep_stats` 中的 `debug_locks`。为了保存干净证据，一次启动仍只验证一个故障，完成后重启恢复初始检查状态。

## 8.3\_报告按哪四块读取

不要从长堆栈第一行开始猜。按证据职责拆分：

1. **问题分类：** circular dependency、inconsistent lock state、bad unlock balance、unsafe locking scenario 或容量耗尽；
2. **当前新事件：** 哪个任务、哪个调用点正在取得或释放哪一锁类；
3. **历史反证路径：** 过去在哪些调用栈建立了反方向依赖或冲突使用状态；
4. **当前 held 状态：** current 此刻还持有哪些实例，它们怎样把新事件接到历史图。

对循环告警，最终要还原为：

```text
本次路径：持有A时准备取得B，产生候选A → B
历史路径：图中已经存在B → ... → A
图结论：新边将闭合强依赖环
代码修复：统一锁序、缩短嵌套、拆分所有权或重构调用方向
```

仅修改报告中最靠上的函数，未必修到协议根因；它可能只是最后补齐环的路径。

## 8.4\_使用状态告警怎样读

`inconsistent lock state` 或 IRQ inversion 报告需要同时找两个现场：

- 锁类第一次被标记为 hardirq/softirq safe 的取得栈；
- 同一锁类或依赖链在相应 IRQ 开启状态下使用的栈。

修复不一定是无条件改成 `spin_lock_irqsave()`。先确认共享数据是否真的由中断和进程共同访问，再决定：

- 所有进程路径统一屏蔽对应本地中断；
- 把中断工作移到线程化或延迟上下文；
- 用不同状态和锁拆开中断域与进程域；
- 消除从 IRQ-safe 锁到 IRQ-unsafe 锁的依赖链。

## 8.5\_proc接口回答什么

Linux 6.12.20 在相应配置下创建：

| 接口 | 用途 | 不能替代 |
| --- | --- | --- |
| `/proc/lockdep` | 枚举锁类和依赖信息 | 不代表每条业务路径都已覆盖 |
| `/proc/lockdep_chains` | 查看已记录锁链 | 只在完整证明配置下存在 |
| `/proc/lockdep_stats` | 查看类、边、链、栈、深度和 `debug_locks` 状态 | 不是锁竞争性能报告 |
| `/proc/lock_stat` | `CONFIG_LOCK_STAT` 下的竞争/等待/持有统计 | 统计热点不等于正确性证明 |

具体创建条件和统计字段见 [`lockdep_proc_init()` 与 `/proc/lockdep*`](../../../../research/source_reading/lockdep/source_explanations/P08_Linux_6.12_Lockdep查询注解与配置源码实现.md#8.6_lockdep_proc_init与proc接口)。

容量巡检示例：

```bash
grep -E 'lock-classes|direct dependencies|dependency chains|stack-trace entries|max locking depth|debug_locks' /proc/lockdep_stats
```

关注当前值是否持续逼近 `[max: ...]`，以及 `debug_locks` 是否仍为 `1`。只看到 proc 文件存在，不能证明检查器仍有效。

## 8.6\_怎样设计覆盖而不是只开配置

测试计划应从锁协议反推组件链：

| 协议维度 | 至少触发 |
| --- | --- |
| 正常锁序 | 每种条件分支、错误回退和 teardown 路径中的实际嵌套 |
| 上下文 | 进程、softirq、hardirq、workqueue、回调及 suspend/resume 等真实入口 |
| 读写类型 | 读、写、升级/降级或递归读的实际组合 |
| 对象层级 | 父/子、容器/成员和同类多实例的最大真实嵌套 |
| 生命周期 | 分配、初始化、发布、卸载、模块反复加载和异常释放 |

一次“启动成功且无告警”通常只覆盖初始化快路径，不能代表设备热插拔、错误恢复或电源管理锁链已经进入图中。

## 8.7\_本章结论

有效 Lockdep 证据要求正确配置、`debug_locks` 仍有效和目标组件链确实执行。报告应还原为新事件、历史反向路径、当前持锁账本和最终图规则；`/proc/lockdep_stats` 用于判断知识库容量与检查器生命状态。下一章将解释链缓存为何仍有显著成本、容量耗尽怎样使证明失效，以及无告警的边界。
