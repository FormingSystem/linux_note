# 第9章\_成本\_覆盖边界与工程选择

## 9.1\_链缓存消除了什么成本

完整验证需要把新锁与当前相关前驱比较，并在全局图上搜索环和 IRQ 使用冲突。若每次高频 acquire 都重复图搜索，成本会随锁类和依赖规模快速增长。链缓存把相同的“锁类与取得类型序列”只做一次昂贵验证：

```text
每次取得仍需：事件上报、当前账本维护、链键计算、缓存查询
首次新链额外需要：递归检查、图搜索、IRQ规则、保存堆栈、写依赖边
重复旧链可以省略：再次进行完整图验证和重复写边
```

因此缓存不是零成本。调试内核还会增大锁对象或 `task_struct`、保存全局类和堆栈、在 IRQ 状态变化时更新使用信息，并增加缓存行和分支开销。`CONFIG_PROVE_LOCKING` 适合开发、测试和故障复现，不应默认等同于生产低开销监控。

## 9.2\_固定容量也是证明前提

Linux 6.12.20 对持锁深度、锁类、依赖边、链、链元素和堆栈条目设置静态或可配置上限。当前源码的 `MAX_LOCKDEP_KEYS` 为 `1 << 13` 个槽位，任务持锁账本深度为 48；其他上限由 `CONFIG_LOCKDEP_*_BITS` 等配置决定。

进入这些版本数字以前，先用 [Lockdep 查询适配与诊断模块导读](../../../../research/source_reading/lockdep/navigation/P04_Linux_6.12_Lockdep查询适配与诊断模块导读.md#4.5_配置与生命状态)理解配置、容量和 `debug_locks` 的关系。Linux 6.12.20 中锁类槽位、任务持锁深度和容量失败行为分别见 [`lock_class_key` 与 `lockdep_map` 身份结构](../../../../research/source_reading/lockdep/source_explanations/P05_Linux_6.12_Lockdep身份与锁类源码实现.md#5.2_lock_class_key与lockdep_map身份结构)、[`task_struct` 持锁账本与 `held_lock`](../../../../research/source_reading/lockdep/source_explanations/P06_Linux_6.12_Lockdep取得释放与持锁账本源码实现.md#6.2_task_struct持锁账本与held_lock)和 [`register_lock_class()` 锁类注册](../../../../research/source_reading/lockdep/source_explanations/P05_Linux_6.12_Lockdep身份与锁类源码实现.md#5.4_register_lock_class锁类注册)。

官方设计文档中的部分旧示例把最大锁类写为 8191，而 6.12.20 源码数组常量是 8192 个槽位。诊断当前内核时应以匹配版本源码和 `/proc/lockdep_stats` 的 `[max: ...]` 为准，不照抄跨版本数字。

容量耗尽的后果不是“少记一条但其他证明仍完整”。为了避免半写全局图产生不可信连锁结论，Lockdep 通常报告内部上限并关闭后续检查。此后无告警不能再作为证据。

## 9.3\_锁类为什么会泄漏或爆炸

常见原因：

1. 动态对象没有通过稳定初始化调用点共享锁类，导致大量实例被拆成不同类；
2. 模块反复装卸产生新类，而旧类仍被依赖图引用，不能简单重用；
3. 动态 key 注册/注销和对象生命期不匹配；
4. 为压告警大量创建独立 key 或 subclass；
5. 测试工作负载本身覆盖了前所未有的大量合法类和链，当前配置上限确实不足。

先用 `/proc/lockdep_stats` 观察增长趋势，再比较 `/proc/lockdep` 中新增类名。不能一看到容量告警就只增大配置；若根因是错误初始化，扩大数组只会延后失效。

## 9.4\_无告警的四种不同含义

| 现场 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- |
| 检查有效，目标链已执行且无告警 | 这些已上报组件链在当前分类和规则下没有被发现冲突 | 未执行分支、未接入原语或业务生命期一定正确 |
| 配置关闭 | 没有动态 Lockdep 证据 | 锁协议正确 |
| `debug_locks=0` | 至少一条路径已经调用 `debug_locks_off()`，检查器停止继续证明 | 停检以后的路径无问题 |
| 测试只覆盖快路径 | 快路径未触发告警 | 错误恢复、IRQ、热插拔、卸载路径安全 |

“未报警”只有与配置、检查器生命状态和覆盖矩阵一起记录才有意义。

## 9.5\_误报与漏报优先核对输入模型

Lockdep 依据上报模型推理。觉得报告不符合业务时，依次检查：

1. 两个实例是否错误共享或错误分裂锁类；
2. `_nested()` 层级是否稳定且全路径一致；
3. trylock、读类型和 wait type 是否忠实；
4. acquire/release 是否覆盖失败、异常和非栈顶释放；
5. IRQ 开关与上下文跟踪是否由受支持入口报告；
6. 自定义同步原语是否根本没有接入。

只有证据表明模型与真实协议不一致时，才调整注解。若模型正确，报告通常是在揭示业务锁序问题，不能用 novalidate、notrack 或全局停检当作修复。

## 9.6\_Lockdep与其他工具怎样分工

| 问题 | 首选证据 | Lockdep 的位置 |
| --- | --- | --- |
| 潜在锁顺序环、IRQ锁反转、持锁断言 | Lockdep | 主工具 |
| 已经发生的共享内存数据竞争 | KCSAN、trace、代码审查 | 可能提示缺锁，但不直接检测所有数据竞争 |
| UAF、越界、双重释放 | KASAN/KFENCE、对象生命周期审计 | 只能检查部分锁对象释放和锁契约 |
| `__rcu` 等指针类型误用 | Sparse | Lockdep 补充动态上下文条件 |
| 睡眠上下文、原子上下文误用 | `might_sleep()`、IRQ/preempt 调试与 Lockdep wait-context | 协同而非完全等同 |
| 锁竞争和持有时长 | lockstat、perf lock、trace | 复用部分 hook，但正确性图不等于性能统计 |
| 内存顺序错误 | LKMM、litmus、架构实验、代码审查 | `lock_acquire()` 事件名称不提供硬件内存序 |

## 9.7\_工程选择核对表

开发或回归阶段启用 Lockdep 前确认：

- 使用与目标代码一致的调试内核和配置；
- 工作负载能够覆盖正常、错误、IRQ、回调、卸载和电源路径；
- 持续监控 `debug_locks` 和各容量计数；
- 首个告警单独保存完整 dmesg，不让后续噪声覆盖根因；
- 把每条告警还原成实例、锁类、当前账本、历史边和上下文状态；
- 修复后在干净启动上重新覆盖建立两方向组件链；
- 用 KCSAN、KASAN、Sparse、lockstat 或人工证明覆盖 Lockdep 不负责的问题。

生产环境若无法接受结构体膨胀和每次锁事件的开销，应在接近真实配置的专用测试内核中运行完整检查，再用较低开销工具做线上观测。不能因为生产内核关闭 Lockdep，就删除源码中的持锁断言和正确注解；它们仍是测试构建的可执行契约。

## 9.8\_专题结论

Lockdep 的力量来自把已观察的简单锁链组合成全局闭包，而它的边界也来自同一事实：未执行、未上报、错误分类或停检后的路径都不在证明范围内。链缓存降低重复图搜索成本，但不能消除事件维护、内存占用和容量上限。正确使用方式是把它作为锁协议验证器，与数据竞争、内存安全、类型、内存序和性能工具形成证据组合。
