# 第1章\_poll与epoll阅读路线

本专题从一个程序要等待多个输入开始，先建立“登记、状态、唤醒、重查”的共同模型，再引出长期兴趣集合与候选交付。读者需要能阅读C函数、数组与错误返回，知道fd代表已打开文件的句柄。等待的公共背景可查[等待与完成量](../../synchronization_and_asynchrony/synchronization/waiting_notification/大纲.md)；不必先掌握eventpoll字段才能进入第一章。

## 1.1\_从问题走向选择

```mermaid
flowchart LR
    A[串口和管道都要等待] -->|建立登记与重查| B[poll]
    B -->|集合长期不变且多数空闲| C[epoll持久兴趣与候选]
    C -->|读一半后谁继续推进| D[LT和ET及应用待办]
    D -->|计入管理与处理成本| E[按负载选择]
```

| 顺序与章节 | 带入什么 | 本篇解决什么 | 留给后文的问题 |
| --- | --- | --- | --- |
| [P01 poll登记与就绪复查](P01_poll登记与就绪复查.md#1.1_从等待一个输入到等待多个输入) | 多个输入与阻塞read的矛盾 | P0～P4连接登记、状态、睡眠和清理；C模型解释通知不预留数据 | 为什么每次还要处理不变的整张集合 |
| [P02 epoll持久登记与交付](P02_epoll持久登记与交付.md#2.1_把不变的兴趣集合留下来) | poll的登记与重查职责 | E0～E5连接兴趣、回调、候选与交付；管道实验区分LT/ET；补足生命周期和服务器扩展边界 | 节省扫描是否足以保证所有负载更快 |
| [P03 从负载选择poll与epoll](P03_poll与epoll的选择.md#3.1_用同一事件循环比较) | 两种等待模型和模式责任 | 分开N、R、K与增删成本，设计不丢数据的公平比较 | 具体应用还需依据业务状态机与实测作选择 |

## 1.2\_机制与证据的边界

[源码阅读索引](../../../../research/source_reading/io_polling/navigation/P01_poll与epoll源码阅读索引.md#1.2_按阶段阅读)按固定NXP Linux 6.12.20提交组织文件位置、阶段和函数合作。它负责找实现，正文负责推理机制和应用契约。当前未提供上游函数体的逐句实现教程，不把字段表冒充完整源码展开。

与[异步通知](../../synchronization_and_asynchrony/asynchrony/async_notification/大纲.md)相比，这里由应用显式等待并取回事件；两者都不能把“被通知”当成完成了数据传输。[VFS数据路径](../../../kernel_subsystems/vfs/P14_VFS_read_write分派.md)继续说明read/write怎样分派。DMA负责另一层的数据搬运与设备访问边界，不因使用epoll就自动变成异步I/O完成接口。
