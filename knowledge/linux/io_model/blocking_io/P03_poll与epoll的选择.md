# 第3章\_poll与epoll的选择

## 3.1\_用同一事件循环比较

前两章已经建立共同底座：文件.poll报告当前状态，等待队列传递状态可能变化的消息，应用仍要read或write。现在令N表示关注的描述符总数，R表示一轮被检查的就绪候选数，K表示最终交付给用户的项数。三个量并不相同：候选可能因别的消费者取走数据而失效，一轮也可能受maxevents限制只交付部分结果。

poll的每轮工作包含传入集合、扫描N项、必要时登记等待以及返回前清理。这里按每项检查成本相近讨论，某个驱动.poll本身昂贵时，还要单独分析。epoll把兴趣管理移到ctl路径，并在等待/交付路径主要处理候选；K项结果的检查与复制不可能凭空变成固定工作量。

## 3.2\_节省的工作移到了哪里

| 比较轴 | poll | epoll |
| --- | --- | --- |
| 兴趣集合 | 调用者每次传入数组 | 内核持久保存，ctl增删改 |
| 等待登记 | 本次等待创建，退出时撤销 | ADD关联目标队列，撤销时拆除 |
| 状态判断 | 扫描传入项，唤醒后重新判断 | 初始/修改时查询，通知形成候选，交付前再查询 |
| 结果交付 | 在原数组各项写入revents | 向结果数组写入交付项及用户标识 |
| 常驻成本 | 无长期epoll兴趣树 | 每个登记及目标队列钩子占用内存，增删需要维护关系 |
| 应用责任 | 检查事件，处理非阻塞结果与生命期 | 同样需要；ET或ONESHOT额外引入继续处理或重新启用责任 |

固定实现的兴趣索引用红黑树组织，查找随注册规模增长；候选链表避免每轮沿树扫描全部登记。这不等于ctl的全部成本只剩树查找，也不等于一次epoll_wait总是O(1)。回调数量、候选数、就绪失效、用户复制、锁竞争、嵌套检查和调度都会产生工作。

例如N很大、R和K很小、集合长期稳定时，poll反复检查的多数项都是空闲项；epoll能让它们的持久登记继续留着，本轮只跟进相关候选。这是合理优势。若几乎全部连接都活跃，R接近N，两者都要付出大量实际处理成本。若每轮都关闭旧连接、建立新连接，ctl和内存管理的费用也会成为主要部分。不能用固定的“超过一千就选epoll”代替负载分析。

## 3.3\_通知方式不替代调度策略

普通poll可以阻塞睡眠，不是被动忙轮询；epoll也会主动查询当前状态，不是纯粹“推送一切”。两者都依赖通知与重查配合。驱动是否使用中断、DMA完成、工作队列或其他生产路径改变状态，是下一层问题；ET不要求设备提供硬件边沿中断。

同样不能说poll一定唤醒所有进程，epoll一定只唤醒一个。目标等待队列如何登记、是否使用排他等待、多少epoll实例观察同一个对象、多少线程等待同一实例都会改变行为。EPOLLEXCLUSIVE针对特定多实例通知场景减少不必要唤醒，不是数据归属协议，也不承诺把每条消息精确分派给唯一应用消费者。

LT适合先建立正确、清楚的循环；它的重复就绪报告往往在提醒应用“你还没处理完”或“你关注了不需要的写事件”。ET可以减少某些重复交付，但需要读写推进、预算与应用待办队列共同设计。不能仅凭返回次数更少就认定吞吐更高：如果剩余数据再也无人处理，漂亮的低CPU占用其实是停工。

## 3.4\_怎样做公平的实验

先固定业务协议、读写量和错误处理，再只替换等待机制。至少区分三类负载：少量稳定fd；大量长期空闲、少量活动fd；大量增删且多数活动的fd。每类都记录实际N、活动比例、增删频率与每次处理预算，不能只记录连接上限。

测量除了吞吐量，还要包括事件到处理的延迟、CPU时间、系统调用次数、内存占用和连接退出时是否遗漏资源。输出必须完整送达，超时与失败必须计入；一个丢弃短写尾部的回显程序不具备比较资格。保持非阻塞策略与处理预算相当，并说明触发模式，否则比较的是两套应用调度方案，而不仅是poll与epoll。

本章没有给出虚构的百万连接测试或固定性能倍数。上一章的两字节实验隔离了LT/ET语义，不能回答真实网络吞吐；第一章的C模型解释观察失效，也不测内核性能。实验回答的问题越清楚，结果越容易迁移。

## 3.5\_选择与章末练习

少量fd、逻辑直接、跨POSIX环境的程序可以继续使用poll；很多长期存在而大部分空闲的Linux连接，适合评估epoll。普通文件等对象还要先确认目标是否支持epoll登记：poll的默认就绪回退不能证明epoll一定接受它。两者都不是用于等待普通文件磁盘I/O完成的通用异步完成接口。

先完成能处理EINTR、EAGAIN、EOF、短写、异常、退出与资源寿命的LT事件循环，再依据测量决定是否使用ET或ONESHOT。驱动一侧则首先保证.poll的状态判断、等待登记和生产者唤醒协议正确；不必为poll和epoll各写一套互不一致的缓冲逻辑。

1. N很大，但每轮K也很大，是否还能证明epoll总成本不随N变化？不能。至少K项交付和业务处理随实际工作增长；还需观察R与增删成本。
2. LT循环收到大量EPOLLOUT，但输出队列为空，应先换ET还是调整兴趣？先撤掉不必要的写兴趣；否则是在优化本不应安排的工作。
3. 两种实现吞吐相近，epoll版内存更高，是否说明实现错误？不一定。持久登记本来有内存成本，应结合空闲比例、延迟和规模判断。
4. 如何发现基准“看起来更快但实际丢数据”？给输入编号并校验完整输出总量与内容，把未完成请求和短写积压纳入结果，而不只统计循环次数。

读到这里，应能从负载、状态和处理责任做选择，而不是把poll与epoll记成旧与新、慢与快的标签。
