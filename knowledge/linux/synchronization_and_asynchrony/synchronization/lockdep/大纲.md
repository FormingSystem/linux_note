# 第1章\_Linux\_Lockdep专题大纲

## 1.1\_专题定位

本专题不把 Lockdep 写成一组字段、接口和告警名称，而是带着读者重新解决一个问题：**如果每一把锁都能正常加锁和解锁，系统为什么仍会死锁，我们又怎样在真实死锁尚未发生时证明这种风险？**

Lockdep 是 Linux 的动态锁协议验证器。它不替代 mutex、spinlock 或 rwsem，也不负责让一次加锁成功；它接收同步原语在约定时点上报的身份、取得、释放和 IRQ 状态事件，维护当前执行上下文的影子账本与跨时间的锁类历史，再检查递归、依赖环、IRQ 反转、等待上下文和持锁契约。

它也不是只有 Lockdep 核心维护者才能使用的内部设施。普通驱动或内核模块开发者只要在启用 Lockdep 的调试内核中运行使用标准锁的目标路径，就已经在使用它；维护公共调用契约时可以进一步加入断言和 pin；只有实现新同步原语或逻辑保护域时，才需要直接管理 `lockdep_map` 和 acquire/release 事件。环境资格、模块签名、可重启实验机和用户态边界分别在 P06 与 P08 落实。

读完以后，读者不只应记住“Lockdep 会找环”，还应能够自行推导：

1. 为什么一次单任务执行也能暴露需要多个任务才会真正发生的 ABBA 死锁；
2. 为什么功能锁的 owner、等待队列和锁地址不足以承担全局证明；
3. 一次 `mutex_lock()` 怎样映射到实例、锁类、当前账本、依赖图和链缓存；
4. 为什么中断上下文可以使用某些自旋锁，却不能等待 mutex 或 completion；
5. 一条告警究竟由本次新事件和哪段历史共同推出；
6. 无告警在什么配置、覆盖和检查器生命状态下才是有限证据。

前置阅读是[锁机制专题](../locks/大纲.md)：至少要能区分 mutex 的可睡眠等待、自旋锁的忙等待，以及进程、softirq、hardirq 上下文。遇到版本化字段和函数时，再从本专题跳到 Linux 6.12.20 源码材料，不要求读者一开始就阅读 `lockdep.c`。

## 1.2\_两个场景怎样接成一条问题链

专题只使用一个虚构设备 `demo_device`。进程 ABBA 与 IRQ 反转在功能上是两种现场，但它们不是并列插入的两个知识点：前者先迫使验证器保存可跨时间组合的锁序证据，后者再检验这份证据若不携带执行上下文会遗漏什么。

第一条是 **进程上下文的锁顺序问题**：

```text
配置路径：config_lock → state_lock
恢复路径：state_lock  → config_lock
```

两把锁都是 mutex。每条路径单独执行都能结束，两个任务以特定时序交错时才会互相等待。Lockdep 的目标是先分别收集这两条简单组件链，再在第二个方向出现时推出潜在 ABBA，不要求测试恰好重放真实卡死。

进程 ABBA 由此留下一个未决问题：如果 current 账本和全局锁类图已经能够组合 `A → B` 与 `B → A`，这套模型是否足以覆盖真实内核？为了检验它，第二阶段把同一设备推进到 **进程与硬中断共享队列的问题**：

```text
进程提交路径：本地硬中断开启时取得 queue_lock
硬中断路径：  取得同一个 queue_lock 更新完成队列
```

`queue_lock` 是自旋锁，不是 mutex。硬中断不能睡眠等待，但在普通非 PREEMPT_RT 内核中可以为短临界区取得自旋锁；若它打断了本 CPU 上持有同一自旋锁且没有屏蔽本地中断的进程路径，就会原地忙等，而被打断者永远无法运行到解锁。这个场景在不混淆 mutex 与自旋锁功能语义的前提下，为上一阶段的证据模型增加 IRQ 上下文和本地 IRQ 状态，最终再与 ABBA 一起进入同一个规则引擎。

## 1.4\_章节契约

1. [为什么需要 Lockdep](P01_为什么需要_Lockdep.md)
   - 承接：从两条局部正确 mutex 路径得到全局 ABBA 矛盾。
   - 建立：由难复现的真实卡死转向可组合组件证据，再由证据推出当前账本、历史账本和 IRQ 上下文。
   - 留下：若只执行简单路径，谁来保存当前前驱和跨时间历史？
2. [Lockdep 抽象模型与证明边界](P02_Lockdep_抽象模型与证明边界.md)
   - 回答：从“收集组件链”这一目标出发，最少需要哪些角色、状态和事件。
   - 建立：功能锁状态、当前影子状态、全局历史状态和验证器生命状态四层模型，以及 S0～S6 操作周期。
   - 留下：动态对象地址为什么不能直接永久充当全局图节点？
3. [锁实例、锁类、key 与 subclass](P03_锁实例_锁类_key与subclass.md)
   - 回答：成千上万个锁实例怎样共享协议结论；配置、`dep_map`、key 与 subclass 分别是什么。
   - 建立：实例用于当前查询，锁类用于跨实例推理，subclass 只表达经过证明的自然层级。
   - 留下：身份建立后，一次 acquire 到 release 究竟改写哪些状态？
4. [持锁账本、依赖图与状态闭环](P04_持锁账本_依赖图与状态闭环.md)
   - 回答：阻塞取得为什么在功能锁成功以前上报；失败怎样回滚；当前事实和历史结论怎样分离。
   - 建立：`held_locks[]`、链键、链缓存和锁类图的端到端状态流。
   - 留下：候选 `A → B` 到底要检查什么，为什么不是所有有向边都具有同样阻塞能力？
5. [递归、依赖环、IRQ 与读写规则](P05_递归_依赖环_IRQ与读写规则.md)
   - 回答：为什么添加 `A → B` 前必须从 B 搜索 A；硬中断、自旋锁和三类读写取得怎样扩展规则。
   - 建立：由真实等待可能性定义的强依赖路径，而不是“见环就报”的口号。
   - 留下：业务函数怎样消费当前账本，又怎样把自定义保护协议接入检查器？
6. [查询、断言、pin 与自定义原语接入](P06_查询_断言_pin与自定义原语接入.md)
   - 回答：普通驱动作者、契约维护者、测试人员和新原语实现者分别怎样使用 Lockdep；查询、断言、连续持锁检查和事件上报为何不能互相替代。
   - 建立：从标准原语自动接入，到断言/pin，再到受约束自定义事件的分层使用模型。
   - 留下：没有实体 mutex 的逻辑保护域如何复用 Lockdep？
7. [RCU 与子系统检查适配](P07_RCU与子系统检查适配.md)
   - 回答：RCU 为什么可以建立虚拟 lockdep map，业务锁条件 `c` 又怎样进入检查路径。
   - 建立：功能机制与检查机制并行、互不替代的子系统适配模型。
   - 留下：怎样确认配置、运行状态和测试路径真的让这些检查发生？
8. [配置、亲手实验与报告解读](P08_配置_亲手实验与报告解读.md)
   - 回答：自己的机器与权限能参与到哪一步；如何构建最小实验、读取 splat、核对 `/proc/lockdep*` 并设计路径覆盖。
   - 建立：从独立[锁顺序反转实验](../../../../../labs/kernel/lockdep/P01_锁顺序反转与报告解读/README.md#1.1_本实验把哪条推理交给读者完成)进入，再把新事件、历史反向链和 current 账本还原成代码协议。
   - 留下：一轮测试没有告警，能证明多少？
9. [成本、覆盖边界与工程选择](P09_成本_覆盖边界与工程选择.md)
   - 回答：链缓存、固定容量、`debug_locks` 停检、误报/漏报与工具分工。
   - 输出：能够判断何时启用 Lockdep、怎样记录有效证据，并把 KUnit/kselftest、trace、KCSAN、KASAN、Sparse、lockstat、`perf lock`、LKMM 与人工所有权证明接成按问题分工的验证流水线。

## 1.5\_四种阅读方式

- **第一次建立模型：** 按 P01～P05 连续阅读，不跳进源码；先能亲手推导候选边、反向路径和 IRQ 递归场景。
- **准备在代码中使用：** 阅读 P01、P03、P06、P08、P09，先确认自己处于标准原语使用、契约注解还是新原语接入层，再核对配置、锁类身份、断言和覆盖。
- **准备亲手参与：** 先读 P01 与 P08，再完成[锁顺序反转与报告解读实验](../../../../../labs/kernel/lockdep/P01_锁顺序反转与报告解读/README.md)，最后用 P09 为自己的驱动补路径覆盖和相邻工具。
- **准备阅读实现：** 先读 P01～P05，再从下节总阅读索引进入 `lockdep_map → held_lock → validate_chain() → check_prev_add()`，不要直接从某个报告函数逆猜整个机制。

- [中断机制专题](../../asynchrony/interrupts/大纲.md)解释硬中断、下半部和线程化执行；本专题只分析 IRQ 上下文怎样改变锁依赖。
