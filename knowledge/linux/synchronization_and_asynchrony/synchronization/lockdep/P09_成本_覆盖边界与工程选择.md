# 第9章\_成本\_覆盖边界与工程选择

## 9.1\_先把无告警写成条件命题

完成一次测试后，最容易说出过强结论：“Lockdep 没报，所以锁没有问题。”本专题建立的模型只允许下面这句话：

> 在记录的内核版本和配置下，检查器于目标路径执行期间保持有效；这些路径正确上报并形成了所列简单组件链；Lockdep 没有在当前分类、取得类型和规则范围内发现冲突。

这句话刻意没有证明：未执行分支、未接入原语、错误归类、数据竞争、UAF、内存序或业务活性问题。工程结论的强弱取决于输入证据，不取决于报告页面是否安静。

## 9.2\_链缓存消除了哪部分成本

首次出现一条锁链时，验证器可能需要比较当前前驱、搜索全局图、传播 IRQ 使用状态、保存证据栈并写依赖边。若每次高频取得都重复这些工作，调试内核很快不可用。

链缓存把成本分成两层：

```text
每次仍要承担：事件上报、current账本维护、链键计算、缓存查询
首次新链额外承担：递归/闭环/IRQ规则、证据栈保存、依赖边写入
重复旧链可以省略：再次完整搜索与重复写边
```

所以缓存不是“Lockdep 零开销”。调试配置还会扩大锁结构或任务状态，保存全局类、链和堆栈，增加分支、临界区及跨 CPU 缓存流量。`CONFIG_PROVE_LOCKING` 更适合开发、回归和专用复现内核，不应默认当作低开销生产监控。

## 9.3\_固定容量为何是证明前提

Linux 6.12.20 对不同状态池分别设限：锁类索引空间、每任务 held 深度、依赖边、链、链元素、堆栈条目和 BFS 队列都不是无限的。当前源码中：

- `MAX_LOCKDEP_KEYS` 为 `1 << 13` 个锁类槽位；
- `MAX_LOCK_DEPTH` 为每任务 48 条 held records；
- 其他池由 `CONFIG_LOCKDEP_*_BITS` 和内部常量继续约束。

这些数字属于版本实现，不是 Lockdep 永恒契约。目标机应以匹配源码和 `/proc/lockdep_stats` 的 `[max: ...]` 为准。先从 [Lockdep 总阅读索引](../../../../../research/source_reading/lockdep/navigation/P01_Linux_6.12_Lockdep源码导读.md#1.6_建议阅读顺序)取得版本坐标，并用[查询适配与诊断模块导读](../../../../../research/source_reading/lockdep/navigation/P04_Linux_6.12_Lockdep查询适配与诊断模块导读.md#4.1_模块问题)理解容量与停检状态的消费关系；具体证据见 [`lock_class_key` 与 `lockdep_map` 身份结构](../../../../../research/source_reading/lockdep/source_explanations/P01_Linux_6.12_Lockdep身份与锁类源码实现.md#1.2_lock_class_key与lockdep_map身份结构)、[`task_struct` 持锁账本与 `held_lock`](../../../../../research/source_reading/lockdep/source_explanations/P02_Linux_6.12_Lockdep取得释放与持锁账本源码实现.md#2.2_task_struct持锁账本与held_lock)和[容量常量与停检边界](../../../../../research/source_reading/lockdep/source_explanations/P04_Linux_6.12_Lockdep查询注解与配置源码实现.md#4.7_容量常量与停检边界)。

容量耗尽后不能理解成“只少记一条边，其他证明仍完整”。为避免半写全局状态继续产生看似可信的结论，相关错误路径会停检。此后的沉默不再具有证明意义。

## 9.4\_锁类或链为何异常增长

容量紧张可能来自真实覆盖扩大，也可能是模型错误：

1. 同一结构字段的动态实例没有共享稳定初始化 key，被拆成大量类；
2. 模块反复装卸产生新身份，而既有全局依赖仍需要安全处理；
3. 动态 key 登记、注销和对象生命周期不匹配；
4. 为压告警滥建独立 key 或 subclass；
5. 新测试确实覆盖了更多合法类、边和链，当前配置上限不足。

先比较 `/proc/lockdep_stats` 的增长趋势，再从 `/proc/lockdep` 定位新增类名，并回到初始化调用点和业务协议。若根因是错误分类，只扩大数组会延后而不会修复失效。

## 9.5\_四种无告警现场不能混写

| 现场 | 可以得出的结论 | 明确不能推出 |
| --- | --- | --- |
| 检查有效，目标链已执行，无告警 | 已上报组件链在当前模型下未发现冲突 | 未执行分支、未接入原语和生命周期一定正确 |
| 配置关闭或能力不完整 | 没有相应动态 Lockdep 证据 | 锁协议正确 |
| `debug_locks=0` | 之前已有错误、容量或内部路径使检查器停检 | 停检后的路径没有问题 |
| 只覆盖初始化/快路径 | 已覆盖快路径没有触发相应告警 | 错误恢复、IRQ、热插拔和卸载安全 |

有效测试报告必须把“无告警”与配置、检查器生命状态和组件链清单放在一起。

## 9.6\_觉得误报或漏报时先审计输入

Lockdep 按上报模型推理。报告与业务直觉冲突时，按因果顺序检查：

1. 实例是否被错误合并或错误拆分成锁类；
2. `_nested()` 层级是否由稳定拓扑决定并被所有路径遵守；
3. trylock、独占/读类型和 wait type 是否忠实；
4. acquire/release 是否覆盖成功、失败、超时、异常和非栈顶释放；
5. hardirq/softirq 状态是否来自真实受支持入口；
6. 自定义同步原语是否根本没有接入，或重复接入标准原语。

只有证据表明输入模型错误，才调整注解。模型正确时，报告通常在揭示业务锁序或上下文问题；novalidate、notrack 和 `lockdep_off()` 都不是普通修复方案。

## 9.7\_把Lockdep放进完整验证流水线

P08 的最小实验只完成了“让组件链进入历史并读懂报告”。真实工程还需要先证明目标路径确实被驱动，再分别检查数据竞争、内存破坏、类型、生命周期和性能。工具应按待证问题接力，而不是一次打开所有调试开关后等待一个万能结论：

```text
KUnit／kselftest／模块场景驱动真实路径
  → dynamic debug／ftrace／tracepoint确认组件链确实执行
  → Lockdep检查锁序、IRQ、wait context与持锁契约
  → KCSAN检查共享内存竞争
  → KASAN／KFENCE检查越界与UAF症状
  → Sparse／编译期检查核对类型和注解
  → lockstat／perf lock／trace分析竞争、等待与持有时间
  → LKMM、litmus与人工所有权证明补足内存序和生命周期
```

这条流水线没有规定所有项目必须使用全部工具。它只是把“怎样执行路径”“锁协议是否矛盾”“共享内存是否竞争”“对象是否被错误释放”“锁是否成为性能热点”拆成不同问题，让每个工具只承担自己有资格回答的部分。

| 要回答的问题 | 更直接的证据 | Lockdep 的位置 |
| --- | --- | --- |
| 潜在锁序环、IRQ 反转、持锁断言 | Lockdep | 主工具 |
| 共享内存数据竞争 | KCSAN、trace、代码审查 | 可能暴露缺锁，但不覆盖所有竞争 |
| UAF、越界、双重释放 | KASAN/KFENCE、生命周期审计 | 只覆盖部分锁对象生命期误用 |
| `__rcu` 等类型误用 | [Sparse 编译期注解](../../../../foundations/c_language/kernel_static_annotations/大纲.md#1.3_阅读依赖图) | 补充动态上下文条件 |
| 睡眠/原子上下文误用 | `might_sleep()`、IRQ/preempt 调试、wait-context | 与 Lockdep 协同 |
| 目标锁路径是否真的执行 | KUnit、kselftest、模块场景、dynamic debug、ftrace、tracepoint | 依赖这些覆盖输入，不能用“无告警”反推路径已执行 |
| 锁竞争和持有时长 | lockstat、`perf lock`、trace | hook 可复用，正确性图不等于性能统计 |
| 内存顺序正确性 | LKMM、litmus、架构实验和审查 | `lock_acquire()` 事件名不提供硬件内存序 |
| 对象跨临界区所有权 | kref/refcount、RCU GP 与业务证明 | held 状态不能替代引用所有权 |

第一次参与可以从[锁顺序反转与 Lockdep 报告解读实验](../../../../../labs/kernel/lockdep/P01_锁顺序反转与报告解读/README.md#1.1_本实验把哪条推理交给读者完成)开始：先只打开形成 Lockdep 证据所需的配置，保存首个报告并重启；修复锁序后，再在干净启动中加入路径覆盖和相邻检查。这样每轮实验只有一个主要变量，报告之间可以比较。

工具组合应围绕待证问题选择，不是把所有调试配置一次打开就自动得到完整证明。

## 9.8\_工程决策核对表

开发或回归阶段启用 Lockdep 前：

- 固定并记录源码版本、运行内核配置与 PREEMPT_RT/IRQ 形态；
- 从协议列出必须出现的组件链，而不是只写“跑压力测试”；
- 覆盖正常、失败、IRQ、回调、热插拔、电源和卸载路径；
- 监控 `debug_locks` 及各状态池用量；
- 第一个报告保存完整 dmesg，按实例、锁类、当前前缀和历史路径还原；
- 修复后在干净启动重新覆盖建立相关组件链；
- 用 KCSAN、KASAN、Sparse、lockstat、LKMM 和人工生命周期证明补齐边界。

生产环境若不能接受结构膨胀和每次锁事件开销，应使用接近目标配置的专用测试内核完成完整验证，再用低开销观测工具覆盖线上行为。源码中的正确断言和标准注解仍应保留，使调试构建能够继续核对契约。

## 9.9\_把新问题带回本专题模型

面对一个没有直接讲过的 Lockdep 报告，可以按下面的推理顺序处理：

```text
这是什么功能同步原语，真实等待方式是什么
  → 本次事件发生时current还持有什么
  → 具体实例怎样映射成锁类
  → 候选边和取得类型是什么
  → 历史中哪条路径或IRQ状态与之冲突
  → 检查器当时是否有效、组件链是否真的覆盖
  → 应修正业务协议、输入模型，还是补充其他工具证据
```

这套顺序比记忆某个 splat 模板更可迁移，因为它从状态所有权和等待因果出发。

## 9.10\_专题结论

Lockdep 的力量来自把已执行的简单锁链汇聚成全局历史，再在新等待边出现时搜索跨任务、跨时间的冲突组合；它的边界也来自同一事实：未执行、未上报、错误分类、容量耗尽和停检后的路径都不在有效证明中。

本专题最终形成的心智模型是：功能锁决定真实等待，current 账本描述本次等待前缀，锁类图保存可迁移历史，规则引擎按阻塞类型与 IRQ 上下文判断是否闭合，配置、覆盖和验证器生命状态共同限定证据。普通驱动作者通过标准锁、调试配置和路径覆盖就已经在使用 Lockdep；契约维护者再加入断言，只有新原语实现者才直接接入事件。读者应据此重建任何新报告，把 Lockdep 放入完整验证流水线，而不是把它简化成“自动找环的工具”。
