# 第1章\_RCU\_专题大纲

## 1.1\_专题定位

本专题只维护一条连续主线：先从读写锁和对象回收问题推出 RCU，再掌握公共 API；随后先建立分类坐标和 Tree RCU 公共骨架，按功能模块比较抢占 / 非抢占差异；最后进入 SRCU、Tasks、Tiny、对象生命周期、工程应用、检查与实验。

全专题禁止采用下面这种组织方式：

```text
非抢占式Tree RCU完整系统
    → 抢占式Tree RCU再讲一遍完整系统
    → 二十章以后才解释类型和公共模块
```

这种结构会重复 GP、`rcu_node`、callback 和同步等待，又让读者在分类坐标尚未建立时先背配置名称。重构后的规则是：

```text
公共概念与API
    → 分类坐标
    → Tree RCU公共完整周期
    → 每个功能模块内比较配置差异
    → 其他保护域与实现家族
    → 应用、检查和实验
```

`knowledge/` 正文负责跨版本稳定的因果模型、接口契约和工程选择；Linux 6.12 的字段、调用链和唯一函数实现分别保存在 `research/source_reading/rcu/navigation/` 与 `source_explanations/`。正文必须先就地解释清楚，再把源码链接作为证据入口，不能退化成链接路由器。

## 1.2\_先记住六条分类轴

| 轴 | 代表名称 | 它改变什么 |
| --- | --- | --- |
| 公共契约 | `rcu_dereference()`、`synchronize_rcu()`、`call_rcu()` | 调用者的发布、取得、等待和回收顺序 |
| 保护域 / flavor | 普通 RCU、SRCU、Tasks | 谁算旧 reader，什么证据能结束 GP |
| 底层实现 | Tree、Tiny、Tree SRCU | 状态按 CPU 规模和域怎样组织 |
| Tree 读侧模型 | `!PREEMPT_RCU`、`PREEMPT_RCU` | reader 被换出后债务留在 CPU 还是转到任务 |
| GP 策略 | normal、expedited | 用正常推进还是更高扰动换低延迟 |
| callback 策略 | 普通 per-CPU、NOCB | 成熟回调在哪些执行者上等待和运行 |

因此“抢占式 Tree RCU”“expedited GP”“NOCB”可以同时存在，它们不在同一轴。完整判断方法在 P04 建立；P04 之前只使用跨实现稳定的普通 RCU 概念和 API。

## 1.9\_实验与结论配对

实验不按 API 名字堆命令，而是对应前文的具体争议：

| 实验 / 观察 | 对应结论 | 控制变量 | 成功证据 | 不能推出什么 |
| --- | --- | --- | --- | --- |
| [晚到 reader 场景](../../../../../labs/kernel/rcu/P01_晚到读者与抢占读者/README.md#1.1_实验要回答的两个问题) | GP 不等待边界后的未来 reader | reader 已创建但在旧对象释放后才进入读侧 | 只读取新代际 | 不能证明抢占 reader 债务 |
| [被抢占 reader 场景](../../../../../labs/kernel/rcu/P01_晚到读者与抢占读者/README.md#1.5_预期证据) | CPU 已切换也不能越过未退出的旧任务 | reader 先取得旧对象，再被 FIFO 任务非自愿抢占 | unlock 先于 GP 返回和旧对象释放 | 不能把毫秒耗时当固定契约 |
| [RCU trace 观察](../../../../../labs/kernel/rcu/P01_晚到读者与抢占读者/README.md#1.6_可选trace证据) | 任务债务登记、清债与 GP 结束的事件顺序 | 目标内核启用对应 trace 事件 | `rcu_preempt_task` → unlock event → GP end | 缺少事件不能证明机制不存在 |
| [Sparse 与 Lockdep 验证路径](P23_RCU_类型语义_Sparse与Lockdep.md#23.7_三类检查不能互相替代) | 静态地址域与动态上下文是不同证据 | 分别启用 Sparse 和 PROVE_RCU/Lockdep | 各自对故意错误产生预期诊断 | 未告警不能证明对象生命周期正确 |

当前仓库中真实存在的 RCU 内核模块实验只覆盖前两项并提供可选 trace。callback、NOCB、hotplug 和 stall 的运行实验尚未形成独立、可复现材料，因此正文只提供源码与观察入口，不把“可以想象一个实验”伪装成已完成验证。

## 1.11\_专题完成标准

读者完成本专题后，应能：

1. 从读写锁和对象回收缺口推出 RCU，而不是先背 API；
2. 把公共契约、保护域、底层实现、抢占模型、GP 策略和 callback 策略分轴；
3. 沿同一 S0～S9 周期解释每任务、每 CPU、每节点和全局状态的读写所有权；
4. 在每个模块内部比较抢占 / 非抢占差异，不复制公共完整系统；
5. 区分普通 RCU、SRCU、Tasks 和 Tiny 的证明对象与适用边界；
6. 给出对象发布、删除、callback、模块退出和失败回滚的完整生命期；
7. 把源码、配置、trace 和实验结果限制在它们真正能证明的范围内。
