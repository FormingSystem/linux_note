# 第1章\_从模块生命周期进入构建与部署

已经知道模块有初始化和退出函数，仍然不足以把它运行起来。源文件要先与目标内核的配置、生成头文件、符号资料和工具链共同构建，得到目标能够接受的 `.ko`；随后才有装载、资源取得和退出。这里连接内核机制阅读与工程操作，完整教程位于[内核模块构建与部署](../../../../engineering/build/kernel_modules/大纲.md)。

## 1.1\_先明确自己要得到哪一种结果

一个只在装入与卸载时打印日志的模块，也已经是完整的模块生命周期实验。它没有设备号、字符设备映射或用户访问节点，因此不该期待 `/dev` 自动出现新文件。先让这份最小代码进入正确的内核，可以把构建问题和设备问题分开观察。

```mermaid
flowchart LR
    A[源文件与目标构建材料] -->|Kbuild 生成| B[模块文件]
    B -->|目标检查并调用初始化| C[内核中的模块代码]
    C -->|驱动另行登记与发布| D[设备访问入口]
```

最后一条箭头不是装载器自动补做的步骤。模块只是代码的组织与装入形式，驱动还要实现它所服务的设备或子系统契约。

## 1.3\_把字符设备实验接回正确位置

将 Hello 的源文件替换成字符设备实现时，Kbuild 的基本职责并没有改变：把指定文件组成目标模块。新增的问题属于设备访问契约，依次阅读[字符设备最小模型](../../../driver_model/character_device/P01_字符设备最小模型.md)、[设备号、映射与节点](../../../driver_model/character_device/P02_设备号_注册与设备节点.md)、[文件操作契约与数据路径](../../../driver_model/character_device/P05_文件操作契约与数据路径.md)。完整模板由[字符设备专题](../../../driver_model/character_device/大纲.md)集中维护。

旧式短例经常用 `register_chrdev(0, name, &fops)` 同时登记一段设备号范围并建立字符设备分派。它与只分配号码的 `alloc_chrdev_region` 不是同一个动作，也不会凭空完成设备模型注册和节点创建。动态返回的主设备号要按本次结果使用，不能把一次日志中的 240 当作所有机器的固定值。阅读已有代码时可以识别这条组合路径；设计具体实例则在字符设备专题中理解各层状态。

若实验让用户写入一段字节、再从设备读回，需要逐项说明：写入是替换还是按位置覆盖，超过容量怎样处理，读位置怎样推进，到结尾是否返回零，多个打开者怎样共享数据。`echo` 和 `cat` 只能覆盖其中很小的一部分情形，不能替代接口定义。

尤其不要把任意字节缓冲区直接用 `%s` 打印：一次写满容量、没有末尾零字节的输入会让字符串扫描越过有效边界。也不能忽略 `put_user` 的失败返回，或在没有同步时让读者同时观察缓冲区与长度的半更新状态。正确实验应把有效长度、用户复制结果与同步过程一起解释；构建成功不会发现所有这些运行时错误。

完成构建四章后，你应能把一次失败定位到源码组织、目标材料、部署或装载阶段。进入设备正文后再增加设备状态与 I/O 的失败场景，保持每一步只有清楚的新问题。
