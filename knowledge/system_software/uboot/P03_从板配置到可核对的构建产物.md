# 第3章\_从板配置到可核对的构建产物

[上一章](P02_从构建上下文找到实际进入镜像的函数.md) 已经能够解释某个函数为什么属于主 U-Boot 或 SPL。接下来把视野扩大到一次完整构建：板配置从哪里来，谁把配置变成编译参数，为什么成功以后会出现 ELF、bin、DTB 和打包镜像等多种文件？

本章以一个目标贯穿：**为 QEMU 的 AArch64 virt 平台准备并核对 U-Boot v2022.10 构建产物**。QEMU 是模拟机器的软件，virt 是它提供的一种虚拟板；这条路径无需把某块真实板的 DDR 参数、固件 blob 和烧写偏移混进第一次构建。后面再说明换成真实开发板时，哪些证据必须补上。固定源码为上游提交 `4debc57a3da6c3f4d3f89a637e99206f4cea0a96`，实现入口在 [源码总索引](../../../research/source_reading/uboot/navigation/README.md)。

构建流程按下图的 B0～B4 推进。**本次实际执行的是本章的宿主 Make 实验；完整 U-Boot 交叉构建与 QEMU 启动命令按固定版本原始规则核对，未在本机执行。** 两种验证的结果在各自位置说明。

```mermaid
flowchart LR
    b0["B0 固定源码和工具"] -->|选择板模板| b1["B1 Kconfig 求值<br/>生成 .config"]
    b1 -->|生成 Make 与 C 输入| b2["B2 选择对象和宏<br/>编译与链接 ELF"]
    b2 -->|转换和组合| b3["B3 bin / DTB<br/>平台打包产物"]
    b3 -->|核对身份和布局| b4["B4 模拟启动<br/>或进入板级交付检查"]
```

## 3.1\_B0\_先固定谁的源码与给谁生成的程序

**讲解层次：概念到实现的映射。** U-Boot 是引导软件项目；上游源码与芯片厂商的 BSP 分支都是具体实现来源。选来源的依据是目标板所需功能、厂商补丁、固件接口和维护要求，而不是“使用者只能用厂商版、开发者才能用上游版”。同一 SoC 的两块板可能有不同的内存颗粒、供电和外设连接，支持某个 CPU 指令集还不等于支持整块板。

先区分 **宿主工具** 与 **目标程序**。构建时的配置工具 `scripts/kconfig/conf`、镜像工具 `tools/mkimage` 要在开发机上运行；最终 U-Boot 要在目标处理器和启动环境中运行。即使开发机也是 ARM，宿主操作系统、ABI、工具格式与目标固件要求仍可能不同，不能只比较 CPU 名字。

GNU 工具链的前缀用于找到一组目标工具，例如 `aarch64-linux-gnu-gcc`、`aarch64-linux-gnu-ld` 和 `aarch64-linux-gnu-objcopy`。`CROSS_COMPILE=aarch64-linux-gnu-` 的末尾短横线是前缀的一部分；它不是处理器核型号。`HOSTCC` 则用于构建宿主工具。工具版本是否适用应看该 U-Boot 版本的构建要求及真实诊断，没有“编译器必须比源码年份早一年”的规则。

下面步骤在 **Linux Bash**、独立工作目录中进行。需要 Git、GNU make、宿主 GCC、AArch64 GNU 交叉工具链以及该配置所需的构建依赖；例如 Bison/Flex 生成配置解析器、OpenSSL 开发库支持部分宿主工具，Python 和相关模块可能被镜像工具使用。它们是 U-Boot 工具本身的依赖，不是把教学程序改成 Python。不同发行版的包名按其包管理器核对，固定版本的 [构建依赖说明](https://docs.u-boot.org/en/v2022.10/build/gcc.html#dependencies) 保留上游清单。

```bash
# 在准备存放新源码副本的工作目录执行；uboot-v2022.10 必须尚不存在。
git clone --no-checkout https://github.com/u-boot/u-boot.git uboot-v2022.10
git -C uboot-v2022.10 checkout --detach 4debc57a3da6c3f4d3f89a637e99206f4cea0a96
cd uboot-v2022.10
uboot_source_dir="$PWD"
git remote get-url origin
git rev-parse HEAD
git status --short
```

这里检出不可变提交，避免分支在以后前进导致同一笔记指向另一套规则。最后三条只读检查来源、提交和本地改动；空状态输出表示此刻没有工作树差量。仓库中的 `upstream/v2022.10/` 只是选取的阅读原件，**不是完整 U-Boot 源码树，不能在那里执行整项目构建**。

接着核对工具，并建立本章统一使用的输出目录：

```bash
# 仍在刚取得的完整 U-Boot 源码根目录。
gcc --version
aarch64-linux-gnu-gcc --version
aarch64-linux-gnu-gcc -dumpmachine
make --version
build_dir="$PWD/out-qemu-arm64"
export CROSS_COMPILE=aarch64-linux-gnu-
```

`-dumpmachine` 应报告目标为 AArch64 的工具链三元组；它不证明板级支持。`build_dir` 是本章自定名称，`O=` 才是 U-Boot 接收输出目录的构建接口。之后所有配置与构建命令使用同一个 `O=`，否则很容易修改源目录的 `.config`、却构建另一个目录里的旧配置。

## 3.2\_B1\_defconfig\_提供选择\_Kconfig\_负责求值

现在已有完整源码和工具，但还没有这次构建的配置。`configs/qemu_arm64_defconfig` 是板模板：它记录需要显式选择的值，许多默认值与依赖由 Kconfig 定义。因此 `make qemu_arm64_defconfig` 不是简单复制文件，而是让配置工具读取模板与 Kconfig 规则，产生完整的 `.config`。

```bash
# 完整源码根目录；配置输出统一写入 build_dir。
test -f configs/qemu_arm64_defconfig
make O="$build_dir" qemu_arm64_defconfig
grep -E '^(CONFIG_ARM|CONFIG_ARM64|CONFIG_SYS_CPU|CONFIG_SYS_BOARD)=' \
  "$build_dir/.config"
```

模板目标名必须与源码树真实文件匹配。上述检查会看到 ARM、ARM64 及派生路径选择；不能因为自己使用了 Cortex-A76 就杜撰一个同名 defconfig。上一章已经解释，v2022.10 的 AArch64 仍在 U-Boot 的 `arch/arm/` 中，不套用 Linux 的 `ARCH=arm64` 命名。

如果需要修改选项，继续在相同目录运行：

```bash
make O="$build_dir" menuconfig
make O="$build_dir" savedefconfig
```

`menuconfig` 提供终端界面，选项关系仍来自 Kconfig；它不是独立保存另一套功能定义。`savedefconfig` 在输出目录生成精简的 `defconfig`，适合审查相对默认值的选择。不要立即覆盖上游板模板：先比较、保留原配置与修改理由，确认这些变化是否确实应成为该板的默认值。跨版本迁移还要处理新选项和改变的依赖，不能认为旧模板在新树中一定得到同样结果。

配置求值为什么还需要一套构建规则？因为 `conf` 自己也是 C 程序。顶层 `%config` 规则进入 `scripts/Makefile.build`，再包含 `scripts/kconfig/Makefile`；后者要求先有宿主 `conf`，才能执行 `--defconfig=... Kconfig`。此版 `conf` 由 `conf.o` 和 `zconf.tab.o` 等实际依赖组成，宿主规则完成链接。`gcc -c conf.c -o conf` 只生成一个名字叫 conf 的目标文件，不能替代可执行配置工具。

完成一次正常构建所需的配置不止 `.config`。在本版中，Kconfig 与尚未完全迁移的板配置头并存；准备阶段还生成供 Make/C 读取的文件：

| 文件或输入 | 谁消费它 | 当前用途 |
| --- | --- | --- |
| `configs/*_defconfig`、各层 `Kconfig` | 配置工具 | 模板选择与依赖/默认值定义 |
| 输出目录 `.config` | 配置工具和构建准备逻辑 | 保存本次完整选择 |
| `include/config/auto.conf` | Make | Kconfig 求值后的 Make 赋值 |
| `include/generated/autoconf.h` | C 预处理路径 | Kconfig 生成的宏定义 |
| `include/configs/<板>.h` 与生成的 `include/config.h` | 预处理与配置生成 | 本版仍存在的板配置头选择 |
| `include/autoconf.mk`、阶段 `spl/include/autoconf.mk` 等 | 对应 Make 上下文 | 从实际预处理配置导出的 Make 值 |

表中的生成文件只有相应规则执行后才存在；配置目标刚完成时不应要求所有阶段产物已经齐全。也不能从名字以 `CONFIG_` 开头，就断言该旧版本的值必定由 Kconfig 直接生成。需要修配置时回到定义和模板，手改生成头会在下次准备时丢失。Kconfig 通用的默认值、依赖和保存关系见 [基础语法](../kconfig/基础语法.md)，本版具体路径见 [配置工具实现](../../../research/source_reading/uboot/source_explanations/P03_配置求值与构建产物实现.md#3.1_配置目标先构建宿主工具_再求值板模板)。

## 3.3\_B2\_Make\_沿依赖图决定要做什么

有了配置，为什么再次 `make` 不必把整个工程重新编译？Make 除了展开变量，还会建立目标与前置条件的依赖图，按目标缺失、依赖更新时间及规则决定执行哪些命令。U-Boot 在此基础上增加配置依赖和命令变化跟踪；不能把 Make 简化成“只做字符串替换”。

先用一个宿主实验看清最小关系。它可以在 Linux Bash 或 MSYS2 Bash、GNU make 和宿主 GCC 上运行，本次已用 MSYS2 GCC 15.3.0/make 4.4.1 验证。它独立于前面尚需完整 Linux 构建环境的 QEMU 操作。回到 **linux-note 仓库根目录**，复制 [build_graph 材料](../../../labs/system_software/uboot/build_graph/)：

```bash
# linux-note 仓库根目录；复制材料后在临时副本编译。
graph_dir=$(mktemp -d "${TMPDIR:-/tmp}/uboot-graph.XXXXXX")
cp -R labs/system_software/uboot/build_graph/. "$graph_dir/"
cd "$graph_dir"
```

目录里只有 `src/main.c`、`include/settings.h` 和 `Makefile`。完整 C 程序如下：

```c
#include <stdio.h>
#include "settings.h"

int main(void)
{
    /* 打印头文件的编译期取值，观察头文件依赖是否触发重建。 */
    printf("build_value=%d\n", BUILD_VALUE);
    return 0;
}
```

`include/settings.h` 是手写教学头文件，不假装它是 Kconfig 生成物：

```c
#ifndef DEMO_SETTINGS_H
#define DEMO_SETTINGS_H

#define BUILD_VALUE 7

#endif
```

Makefile 把“编译一个对象”和“链接一个程序”写成两条规则：

```make
.DEFAULT_GOAL := all
VPATH := src
CPPFLAGS := -Iinclude
CFLAGS := -std=c11 -Wall -Wextra -Werror -MMD -MP

.PHONY: all report
all: demo.exe

demo.exe: main.o
	$(CC) $^ -o $@

main.o: main.c
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

report:
	@printf 'report target ran\n'

# 缺少首次编译才生成的依赖文件不是错误。
-include main.d
```

这里 `VPATH` 让 Make 在当前目录找不到 `main.c` 时到 `src` 搜索，编译器寻找头文件则由 `-Iinclude` 控制；二者不互相替代。`$@` 是当前目标，`$<` 是第一个前置条件，`$^` 是去重后的全部前置条件。recipe 以 Tab 开头，`@` 只隐藏命令本身的回显，并不阻止执行。

`-MMD -MP` 让 GCC 生成 `main.d`，记录本次实际包含的用户头文件。Make 下一次读取它，才知道 `main.o` 也依赖 `include/settings.h`；Make 不会自行理解 C 的 `#include`。`-include` 允许第一次构建尚无 `.d` 文件。

```bash
# 教学副本目录。
make CC=gcc
./demo.exe
make CC=gcc
cat main.d
```

第一次会编译并链接，程序打印 `build_value=7`。第二次不再运行编译和链接命令；`main.d` 列出源文件和头文件。现在把 `settings.h` 的 7 改成 9，保存后再次 `make CC=gcc`，会重新编译对象、重新链接，运行得到 9。若编辑器或文件系统没有产生可识别的时间变化，可用 `make -B CC=gcc` 做强制对照；这与正常增量判定是不同实验。

再预测一次：手工创建名为 `report` 的普通文件，会不会让报告目标跳过？

```bash
touch report
make report
```

仍打印 `report target ran`，因为 `.PHONY: report` 声明它是操作目标。反之，若去掉声明，现存同名文件又无更新依赖，recipe 就可能不执行。`.PHONY: all` 会让 all 总被考虑，但不会自动强迫它所有已最新的文件依赖重新编译。目标是否伪目标与依赖是否需要重建要分别判断。

这个小 Makefile 没有实现“命令字符串变化就重建”。例如只改 CFLAGS，文件时间依赖没有变化时，旧对象可能继续复用；U-Boot 的 `if_changed`/`.cmd` 跟踪承担了额外工作。回到 U-Boot 排错时同时看依赖、配置和保存的命令，不能拿这个最小模型当完整 Kbuild。

## 3.4\_B2\_把依赖图映射到真实交叉构建

回到前面取得的 **完整 U-Boot 源码根目录**，恢复同一个输出目录和工具前缀，再执行构建：

```bash
# 完整 U-Boot 源码根目录；不是刚才的主机实验目录。
cd "$uboot_source_dir"
build_dir="$PWD/out-qemu-arm64"
export CROSS_COMPILE=aarch64-linux-gnu-
test -f "$build_dir/.config"
set -o pipefail
make O="$build_dir" V=1 -j2 2>&1 | tee "$build_dir/build.log"
```

`V=1` 展示实际命令，便于辨认 HOSTCC 与目标 CC；`-j2` 允许两个构建任务并行，不意味着每一行日志按调用栈顺序出现。`pipefail` 让前面 make 失败时整条管道也失败，避免只看到 tee 写日志成功。发现失败后从首个实际错误追依赖，后续“没有某文件”可能只是前一步失败的结果。

在固定版本顶层规则里，`head-y` 进入 `u-boot-init`，库目录经规则转换后进入 `u-boot-main`，这些对象与生成的 `u-boot.lds` 交给主链接任务。各目录的 `obj-y` 仍由局部规则和配置选择；没有一个“把所有 `.c` 找出来全部编译”的步骤。SPL 是否另行构建、如何排除主 `board_r.o`，沿上一章的上下文证据继续看。

顶层汇总也有版本边界：旧稿中的早期规则使用 `ALL-y`，**v2022.10 使用 `INPUTS-y`，`inputs` 依赖这些输入，`all` 还连接 binman 打包**。Binman 是 U-Boot 的镜像组织工具，按镜像描述组合各组成部分；只有配置启用相应路径时才执行对应打包。变量名不是跨版本不变的 API，阅读旧 SDK 时应从自己的默认目标往下追。

若某文件没有参与构建，优先检查它所在目录是否被递归选中、对象加入条件是否成立、当前是哪一阶段。若是 `undefined reference`，还要检查声明与定义、编译宏、归档抽取及链接输入。没有必要通过反复全量清理来碰运气；`clean` 主要删除生成物并保留配置，`mrproper` 会进一步删除配置等内容，用它之前必须已有需要保留的配置副本。

## 3.5\_B3\_ELF\_裸二进制与板级镜像分别交给谁

链接完成后，`u-boot` 是带节、符号和入口等信息的 ELF；CPU 或前级加载器不一定直接消费 ELF。`objcopy` 可以提取适合加载的二进制内容，后续规则还可能追加 DTB、生成镜像头、加入其他固件或封装签名。每次变换都解决一个下游消费者的问题，文件名相似不代表内容相同。

DTB 是设备树的二进制形式，它提供硬件描述，数据本身不是另一个执行阶段。在此版常规分支中，`u-boot-nodtb.bin` 由 ELF 转换而来；启用独立设备树且不省略追加时，`u-boot-dtb.bin` 合并裸程序与 DTB，`u-boot.bin` 再取对应结果。多 DTB/FIT、特定平台复位向量和其他打包分支会改变规则，不能无条件认为每个 `.bin` 都只是同一 ELF 的原样展开。

| 产物 | 适合用来回答什么 | 不能独立证明什么 |
| --- | --- | --- |
| `u-boot` ELF、`u-boot.map`、符号表 | 链入哪些对象、符号地址与布局 | 真实板 BootROM 是否接受它 |
| `u-boot-nodtb.bin` | 不含追加 DTB 的程序二进制内容 | 完整板级打包和前级要求是否满足 |
| `u-boot.dtb`、`dts/dt.dtb` | 该配置实际生成/选择的硬件描述 | 所描述硬件是否真的焊在目标板上 |
| `u-boot.bin` | 当前分支准备给后续使用的二进制 | 是否含 SPL、镜像头、签名或可直接写入任意偏移 |
| `spl/u-boot-spl*`、`tpl/u-boot-tpl*` | 启用时相应阶段的独立产物 | 没有生成时仍存在一个隐含阶段 |
| 平台封装、FIT 或 binman 镜像 | 下游装载/布局协议要求的组合 | 仅凭扩展名确认里面实际组件和认证关系 |

表用于核对职责，不要求每块板都生成每一项。QEMU virt 的固定版本文档使用 `u-boot.bin` 作为 `-bios` 输入；真实板可能需要 NXP `.imx`、Rockchip 的 loader/组合镜像或其他格式，应查看它的实际构建及 BootROM 协议。布局与 ELF 地址仍回到 [第一章](P01_从链接布局到启动阶段的交接.md)，不把磁盘文件偏移当成 CPU 地址。

构建成功后可只读核对：

```bash
# 完整源码根目录，build_dir 仍指向相同输出。
"${CROSS_COMPILE}readelf" -h "$build_dir/u-boot"
"${CROSS_COMPILE}nm" -n "$build_dir/u-boot" | grep ' _start$'
sha256sum "$build_dir/u-boot" "$build_dir/u-boot.bin" "$build_dir/.config"
```

ELF 头应显示 AArch64，符号表能给出 `_start` 值；SHA-256 用于以后辨认这一次具体文件。摘要没有自动覆盖工具链、源改动和外部固件，所以还应一同保存提交、配置、工具版本与构建日志。不能把“时间不同导致摘要不同”立即当成源码逻辑不同，也不能把“文件存在”当成刚才那次构建成功。

## 3.6\_B4\_启动观察与换板的证据边界

在已成功生成本章目标二进制、并安装 QEMU system AArch64 的 Linux 环境中，固定版本文档给出的启动方式为：

```bash
# 完整源码根目录；仅供已经完成该配置构建的环境执行。
qemu-system-aarch64 -machine virt -nographic -cpu cortex-a57 \
  -bios "$build_dir/u-boot.bin"
```

`-machine virt` 选择虚拟板，`-cpu cortex-a57` 明确选择 64 位 CPU 模型，`-nographic` 将串口交互放到终端。预期可观察 U-Boot 标识、初始化信息及命令提示符；退出使用先按 Ctrl-A、再按 X。未提供内核和启动介质时，不应把找不到可启动系统混同为 U-Boot 从未启动。该命令来源见 [本地 QEMU ARM 原件](../../../research/source_reading/uboot/upstream/v2022.10/doc/board/emulation/qemu-arm.rst)，本次未进行模拟器启动验收。

若换成真实板，保留 B0～B4 的推理顺序，但必须重新补齐板型号与修订、完整源码身份、defconfig、内存和外设配置、前级固件、镜像格式、装载地址与入口、介质布局等证据。新增一块板可能涉及 Kconfig、Makefile、板目录、设备树、配置头、DDR/电源初始化、镜像描述与维护者记录；不能只复制一个目录、改几个 `CONFIG_SYS_*` 字符串就认为移植完成。

最后做两次预测。第一，ARM64 板配置生成成功，但把 `CROSS_COMPILE` 改为宿主 x86 GCC 前缀，是否会自动改成 x86 配置？第二，`CONFIG_SPL` 没启用，能否只根据 `scripts/Makefile.spl` 存在，就继续解释“本次 SPL 的二进制如何生成”？

**答案：** 第一不会，配置选择与工具选择是不同输入，错误组合可能在检查或编译时失败；应修正工具并核对已有产物，而不是把配置成功当成工具正确的证明。第二不能，存在一条规则不等于本次依赖图选择了它。至此可以从来源、配置、命令和产物逐层解释构建；接下来还要看这些字节开始执行时，谁先建立栈、GD 和可用内存。
