# 第4章\_扩展接口的契约与选择

前三章已经使打开对象、请求位置和映射寿命各自完成了一轮可观察过程。接下来不再把整张操作表当作待填写清单，而是按实际需求选择接口。本篇是应用边界参考：解释旧稿涉及的控制、目录、事件、持久化、文件锁和传输优化，指出进入专门子系统前必须确认的条件；不把几行返回 0 的伪实现称作完整驱动。

## 4.1\_需要改变设备行为时

read/write 适合已定义的字节数据协议。若应用需要“选择模式”“取得结构化状态”等控制动作，可以定义 ioctl 命令，由 unlocked_ioctl 处理。命令号中的读写方向按用户视角描述：读意味着从内核取得结果，写意味着向内核提供参数。命令编码中的大小有助于辨认协议，不会自动替驱动验证参数、复制数据或加锁。

unlocked 名称源于不再由旧式大内核锁包围回调；它不表示这个函数天然无锁或可以不保护共享状态。应先复制并验证输入，再在设备自己的同步协议下改变状态；未知命令返回 -ENOTTY，不编造“成功但什么都没做”的行为。整数参数也并非都是指针，必须按每个命令的定义解释 arg。

ABI（Application Binary Interface，应用二进制接口）规定两边怎样解释字节。为长期 ioctl 结构优先使用固定宽度字段、显式保留位和明确对齐，避免把 long、裸指针和未初始化填充直接作为跨架构布局。一个声明为 __u64 的成员在 32 位程序中仍是 64 位整数；它不会自动缩成 32 位指针。若用它携带用户地址，要按约定转成用户指针，并继续执行访问检查。

compat_ioctl 处理兼容用户态调用，例如受支持配置下的 64 位内核运行 32 位程序。若所有相关命令都传指向同布局结构的指针，可考虑 compat_ptr_ioctl；含标量参数或布局不同的命令不能一概套它。尤其不能先复制到内核栈，再把内核栈地址传给会再次 copy_from_user 的普通入口。正确结构是“分别从两种用户表示解码 → 统一的内核数据对象 → 共同业务函数”。

当前 NXP ARM 目标没有因此变成 64 位兼容测试环境。本篇只核对固定版本接口规则，不宣称做过跨位宽运行。版本身份见[源码总索引](../../../research/source_reading/character_device/navigation/P01_Linux_6.12_字符设备源码阅读索引.md#1.1_版本和阅读边界)，具体参数约束见[版本证据中的 ioctl 文档](../../../research/source_reading/character_device/navigation/P03_文件操作与打开寿命导读.md#3.4_扩展接口的核对位置)。

## 4.2\_等待事件与提交异步工作

如果服务是会暂时空的流，read 应区分“目前没数据”“永久结束”和“复制失败”。poll 回调先通过 poll_wait 把需要的等待入口交给上层，再检查真实状态返回就绪位；poll_wait 本身不会在驱动这一行睡眠。等待表的回调由 poll/epoll 路径提供，生产者改变条件后唤醒，用户被唤醒后仍须重新判断，唤醒不转移数据所有权。

这条完整机制由[环形流教材](../character_device/P13_流式字符设备与等待通知模板.md)承担。有限内容中的 f_pos 到达结尾和消费队列的 used 变为零不能混用；把一个共享 readable 布尔值清掉，不能代替每个读者的位置或数据消费协议。

fasync 提供另一种通知入口：应用设置接收者并启用 O_ASYNC 后，驱动借 fasync_helper 维护登记链，事件产生后经 kill_fasync 发送 SIGIO 通知。链记录谁要接收信号，真实可读条件仍保存在设备自己的状态里；信号也不是每份数据的所有权凭据。先安排接收者与信号处理，再启用通知，以免初期通知无处处理；停用及最终文件清理要解除登记。相关声明在 linux/fs.h，不能引用不存在的 linux/fasync.h。

通知用户“有事可做”与异步完成一个已经提交的请求不同。io_uring 使用提交队列项 SQE 和完成队列项 CQE 交换请求和结果；uring_cmd 允许驱动处理该框架中的专用命令。驱动若立即返回结果，由框架处理完成；若接管请求并返回 -EIOCBQUEUED，则后续通过约定完成路径交回结果。不能既调用 io_uring_cmd_done 又普通返回同一完成结果，制造双重完成。

真正接管异步请求还需要保存请求与数据的有效引用，处理取消、设备退出、失败以及恰好一次完成。iopoll 与 uring_cmd_iopoll 是对应完成轮询入口，适用性取决于后端支持，代价是忙轮询占用 CPU；不是块设备或字符驱动一律必填的成员。Linux AIO 与 io_uring 是不同用户接口，旧 aio_read/aio_write 成员消失不等于 Linux AIO 整体被删除。

## 4.3\_需要列目录或显示状态时

目录读取传递的是目录项，不是任意文本行。VFS 的 iterate_shared 接收 dir_context，其中 pos 是恢复遍历的位置，actor 接收输出条目。普通 dir_emit 把一项交给 actor，是否成功决定是否可以推进游标；它不会替每种文件系统自动增加 ctx->pos。输出空间不足时应保留尚未输出条目的位置，下次才能接着给出它。

下面用完整 Python 模型观察“输出一项才前进”。它是目录恢复协议的整数模型，不是 procfs 实现：

```python
names = ["foo", "bar", "baz"]

def emit_page(position, capacity):
    output = []
    while position < len(names) and len(output) < capacity:
        output.append(names[position])
        position += 1  # 只有成功放入本次输出后才提交位置。
    return position, output

position = 0
for capacity in [1, 0, 1, 5]:
    position, output = emit_page(position, capacity)
    print(position, output)
```

预期是 1/['foo']、1/[]、2/['bar']、3/['baz']。第二次没有空间，所以位置不变。真实目录还要处理点条目、删除、重命名和并发修改；iterate_shared 名称中的 shared 表示共享锁约定，不是“自动 RCU 安全”。没有业务同步的动态数组不能仅凭换一个回调名字就安全。

procfs 由自己的目录代码组织 proc_mkdir 创建的目录。proc_create 在本基线接收 proc_ops，不能把 file_operations 指针传进去就构造一个自定义目录，也不能仅凭 dir_emit 一个名字保证那个名字能被路径查找并打开。目录的枚举和查找必须各自成立。

若只需要输出多行统计，seq_file 已处理分段输出和位置等公共问题，但它不冻结业务数据，也不保证 show 永远只调用一次。show 应能容忍重试，不能把“读出一行”当作执行不可重复副作用的命令。单一打开实例的观察可用第一章的 show_fdinfo；全局调试状态可考虑 debugfs，是否启用、挂载及可访问由配置和权限决定，不能假定生产系统永远不挂载它。

debugfs_create_u32 要求与 u32 匹配的存储，不能把 size_t 指针当成任何架构都相同的 32 位对象。想展示复杂或多字段状态时，用受控的 show 和适用的锁，比强制转换一个地址更清楚。长期稳定的用户接口也不应仅因为 debugfs 写起来方便就落在临时调试协议上。

## 4.4\_文件锁不是驱动内的互斥锁

两个应用要协调访问同一文件区间，可以使用记录锁；协调整个打开文件，可以使用 flock。它们面向应用之间的协议，通常是劝告性的：没有按约定参与的 I/O 不会因为你加了一个文件锁回调就自动受到驱动内部互斥保护。

传统 POSIX 记录锁与进程所有权相关；开放文件描述相关的记录锁另有语义。flock 与打开文件描述关联，因此 dup 共享，不能笼统说它属于一个 fd 数字。若业务要求严格单次打开，可以在 open 中用锁保护“已被占用”状态，在最终 release 解除；这是驱动执行的准入策略，与应用自愿调用 flock 是不同方案。

本版本在专用 lock/flock 回调缺省时仍有公共锁路径。不要为了“支持文件锁”给每个简单字符驱动强行包装一套 helper，更不能忽略传入 cmd 的查询、阻塞、取消或关闭语义。是否需要自定义回调，取决于是否有远端锁管理、特殊对象等公共实现无法承担的约束。

setlease 处理租约，即允许持有者在规则约束下缓存或使用文件，冲突访问会触发通知与降级/解除过程。它不是分布式文件系统一律需要手写的同一种协议；本版本的签名使用 struct file_lease，不能照抄旧 file_lock 指针签名。

## 4.5\_持久化与空间范围是另外的承诺

write 成功通常说明数据被当前接口接受，不一定已经到稳定介质。fsync 要把指定范围及必要状态推进到其持久化保证，datasync 允许省略不影响数据恢复的部分元数据，不能解读成“所有元数据都可以不写”。

一个没有持久化语义的演示字符设备，不应仅为让测试看起来成功就增加返回 0 的 fsync。flush 是关闭钩子，release 是最终清理，它们也不能代替一个尚未实现的 fsync。若数据重要，应用应在还能处理错误的阶段显式同步并检查结果，而不是默认 close 自动完成全部要求。

fallocate 处理空间承诺或范围变换。预分配需要真正安排后备空间或实现对应保证，只写 inode 大小并返回成功不算预分配。KEEP_SIZE 表示不改变可见大小；PUNCH_HOLE 配合 KEEP_SIZE 释放范围的存储并保留逻辑范围；ZERO_RANGE 让读取范围得到零，具体分配方式由实现决定。它们不都等于“只改一点元数据”，也不保证永远没有碎片或后续设备错误。

copy_file_range 请求内容复制，内核或文件系统可能用复制、克隆或卸载传输实现；remap_file_range 是内核回调，用于克隆/去重等范围共享，没有同名的通用用户系统调用可照抄。REMAP_FILE_CAN_SHORTEN 允许缩短本次完成范围，不是允许任意截断目标文件。克隆后的写时复制也仍需空间与错误处理，不能把创建克隆很快当作未来写入免费。

遇到不支持或跨文件系统等边界，是否回退由具体路径决定。返回 -EOPNOTSUPP 不保证所有接口都会自动变成普通 read/write；应用若需要后备路径，必须明确识别实际错误、处理短完成并保持目标文件状态。

fadvise 则只是访问提示：NORMAL 使用常规策略，SEQUENTIAL 表示顺序访问，RANDOM 表示随机访问，WILLNEED 表示希望预取，DONTNEED 表示范围暂不需要，NOREUSE 表示数据不拟重复使用。这些建议不能替代 fsync 的持久化保证，也不是每个设备必须实现的调度优化。

## 4.6\_减少复制之前先明确哪一次复制

普通“读到用户缓冲再写给另一个文件”有两个数据传递阶段。splice 通过管道连接文件端，可能减少用户缓冲中转；文件端通过 splice_read/splice_write 接入，管道保存页片段及相应持有协议。复用页与复制到新的页是不同实现，都不能仅凭接口名宣称完全没有复制。

用户写一条 cat 管道，并不证明两个程序调用了 splice；真正使用哪条系统调用路径，应由程序实现或跟踪证据确认。内核的 splice_to_pipe 也不接收“随便一个 char 指针加长度”的伪签名，页的引用、释放及消费边界必须成套管理。

减少系统调用不等于减少任务调度次数；用户态与内核态切换也不都发生任务上下文切换。判断收益应比较同一数据量下实际复制、调用、页持有和等待成本。小块或低频操作保留普通 read/write 往往更易维护；只有瓶颈已定位且后端路径支持，才值得接入专用搬运或忙轮询。

本固定版本已没有 file_operations.sendpage 成员。没有该字段，不代表所有文件到网络传输能力消失；应按实际 splice/迭代器和网络路径阅读，不能给操作表加一个过时字段。也不因为最新表多出一个字段，就要求所有调用方填它。

## 4.7\_怎样选择下一步

| 实际需求 | 先建立的保证 | 本专题已有起点 |
| --- | --- | --- |
| 每次打开保留状态 | 最后引用前不释放 | 第一章完整 session 模块 |
| 一次处理多段缓冲 | 缓冲游标和请求位置按实际进度提交 | 第二章 iter 模块 |
| 减少反复读取同一数据 | 后备页、权限及映射长期引用 | 第三章只读映射 |
| 等待会到来的字节 | 暂空、终止与就绪状态一致 | 既有环形流教材 |
| 结构化控制 | ABI、复制、参数检查与并发提交 | 本篇 4.1，再进入对应子系统 |
| 大数据路径优化 | 同一负载的成本证据和完整持有/完成协议 | 本篇 4.2、4.6，不先堆回调 |

预测练习：普通关闭日志正常，却未调用 fsync，能否证明断电后数据存在？一个目录列出了 foo，能否证明 open foo 一定成功？把 read 换成 read_iter 后复制次数必然下降吗？答案均是否定的：三者分别缺少持久化、路径查找和实际数据搬运的证据。
