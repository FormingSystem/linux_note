# 第8章\_设备模型与硬件子系统交接

## 8.1\_字符设备不是设备发现机制

真实 SoC 驱动通常先由设备树/ACPI 描述硬件，再由 platform 等总线创建设备并匹配驱动。`probe()` 取得资源、建立设备状态，再按入口及失败协议发布服务。字符设备解决用户分派，不负责发现寄存器、中断或 DMA 通道；cdev 登记与 class/device 节点发布也不是一个动作。

```mermaid
flowchart LR
    FW["DT/fwnode"] --> PDEV["platform_device"]
    PDEV --> PROBE["driver probe"]
    PROBE --> DEV["驱动设备对象"]
    DEV --> GPIO["GPIO descriptor"]
    DEV --> IRQ["IRQ + 完成状态"]
    DEV --> DMA["DMA channel/request"]
    DEV -->|"登记号码到操作表的分派"| CDEV["cdev + dev_t"]
    DEV -->|"建立分类对象并关联设备号"| NODE["class/device 与节点发布"]
```

## 8.2\_贯穿对象应是设备实例

同一 `struct demo_device` 通常保存 `struct device *`、`cdev`、资源句柄、锁、等待队列、请求队列和离线状态。`platform_set_drvdata()` 让 remove 找回它，`inode->i_cdev` 让 open 找回它，`file->private_data` 让 I/O 找回打开上下文。

这三条查找边汇入同一设备实例，但引用条件不同：probe/remove 的 driver data 不自动保证旧 file 仍安全；file/VMA/请求必须另有生命周期规则。

## 8.3\_GPIO\_IRQ\_DMA\_各自交付什么

| 子系统 | 交给字符设备组合层的对象/事件 | 字符设备保存的交叉状态 |
| --- | --- | --- |
| 设备树/fwnode | 属性、资源描述、依赖关系 | 不复制节点，保存解析后的资源句柄 |
| GPIO | `gpio_desc` 和方向/值操作 | 设备配置、错误和并发策略 |
| IRQ | Linux IRQ 号与处理入口 | 数据就绪、错误、计数及等待队列 |
| DMA | channel、映射、descriptor/cookie、完成回调 | 请求所有权、完成和取消状态 |

IRQ/DMA 完成方必须先按同步协议更新共享状态，再通知等待者。字符设备不能把一个瞬时中断信号直接等同于“用户尚未读取的事件”；若事件不可丢，必须用计数或队列保存。

## 8.4\_初始化发布顺序

`probe()` 应在任何可进入的回调或中断之前准备好它们依赖的状态。号码预留、cdev 分派、模型对象和节点有不同发布点；顺序要根据失败之后是否可能已有使用者来设计，而不是固定要求“cdev 总在节点之前”。例如[class 与属性控制实例](../../linux/device_model/class_sysfs/P02_让属性控制字符读取.md#2.3_发布顺序为何这样选择)先准备全部状态和模型对象，最后 cdev_add，允许短暂的可见而不可打开窗口；若反过来，后续失败必须处理已经打开的 file。真实硬件还要单独处理已启用的中断和 DMA，不能把软件实例的顺序直接当作硬件模板。

`devm_*` 简化资源释放，但不会替驱动排空已打开 file 或在途 DMA。回滚既要逆转已完成的取得步骤，也要阻止新的使用者并等待已开始的使用结束。

设备模型完整状态机见[设备模型专题](../../linux/device_model/大纲.md)；GPIO、IRQ、DMA 分别由其权威专题解释。本章保证它们在字符设备实例上的对象、状态和通知边连续。
