# 第11章\_构建运行与验证

上一章已经把有限窗口写成完整模块。现在要区分三件容易被一次成功输出掩盖的事：装入的是不是匹配目标内核的代码；打开的路径是不是分派到本次设备；读写是否符合位置与内容契约。只看到 `/dev` 多出一个名字，三件事都还没有证明。

本章使用 `note_window`，每次实验从新装载的空窗口开始，先以动态设备号和自动节点完成一次闭环，再各改变一个条件。目标是理解静态/动态编号、自动/手工节点是两个独立选择轴。模块参数、源文件和产物名称均直接对应第十章，不把几种无关模板统一改叫 `demo.ko`。

```mermaid
flowchart LR
    build["11.1 匹配构建与传送"] -->|目标核对产物| auto["11.2 动态号与自动节点"]
    auto -->|退出应用并卸载| manual["11.3 动态号与手工节点"]
    manual -->|保存号值并清理入口| fixed["11.4 请求指定号，比较两种节点"]
    fixed -->|保存观察并恢复| result["11.5 判断证据边界"]
```

每次切换组合都重新装载空窗口，下面各节沿这条路线推进；失败时停在首次失败步骤，后续比较不能沿用未成立的状态。

## 11.1\_把构建主机和运行目标分清

在构建主机上进入[实验材料目录](../../../labs/kernel/character_device/materials/README.md)。`kernel_build` 指向与目标内核匹配且已经完成必要构建的输出树；源码树和输出树分开时使用后者。`cross_prefix` 是目标工具链前缀。下面假设 ARM 交叉构建，两个变量应已按[模块构建第一章](../../../engineering/build/kernel_modules/P01_从C文件到匹配目标内核的模块.md)核实并设置，不能直接指向正在取证的只读内核树进行实验构建。

```bash
# 执行位置：构建主机上的实验材料目录，已核实两个变量。
test -n "${kernel_build:?先设置匹配目标的独立构建输出树}"
test -n "${cross_prefix:?先设置目标交叉编译器前缀}"
```

这两行只确认变量已设置且非空；路径对应哪个内核、工具链对应哪个目标，仍由前面的身份核对保证。

```bash
# 执行位置：同一构建主机材料目录。
make -C "$kernel_build" M="$PWD" ARCH=arm \
    CROSS_COMPILE="$cross_prefix" modules
```

这条请求生成 `note_window.ko` 和 `note_stream.ko`，由内核构建系统检查模块接口和导出符号。若只准备了窗口源文件，Makefile 应按第十章限定为 `obj-m := note_window.o`。

```bash
# 执行位置：同一构建主机材料目录，使用目标用户空间工具链。
"${cross_prefix}gcc" -std=c11 -D_DEFAULT_SOURCE -Wall -Wextra -Werror \
    window_probe.c -o window_probe
```

这里生成普通用户程序 `window_probe`，使用目标 C 库，不是把它编进内核。`-D_DEFAULT_SOURCE` 启用目标 C 库相应的默认接口声明，其余编译选项沿用普通 C 实验；目标 sysroot 和动态加载器也必须匹配。

把本次的 `note_window.ko` 和 `window_probe` 传到目标的独立实验目录，以下装卸与访问命令都在 **目标 Linux** 执行。继续核对目标 `uname -r`、产物 `modinfo ./note_window.ko` 和构建记录；只匹配版本字符串仍不能替代架构、配置、符号版本与工具链边界。程序不能执行时先检查架构和动态加载器，不拿它来推断驱动读写失败。

## 11.2\_先做动态设备号与自动节点

先确认没有另一次 `note_window` 实验正在运行，也没有同名实验节点遗留。以下片段在一个专用 Bash 会话中依次执行，启用 `set -e` 使单条命令失败时停止。装载两个窗口，容量设为 8，便于逐字节推演：

```bash
# 执行位置：目标 Linux 的本次产物目录，使用独立 Bash 会话。
set -e
sudo insmod ./note_window.ko major_number=0 instance_count=2 \
    auto_create_node=1 buffer_size=8
```

`major_number=0` 请求动态主号；另三个参数选择两个八字节窗口和自动类设备入口。成功装载后才继续观察。

```bash
# 执行位置：同一目标会话。
cat /sys/class/note_window/note_window0/dev
cat /sys/class/note_window/note_window1/dev
```

两个 sysfs 文件应显示相同的主号、次号分别为 0 和 1。记下本次值，再检查路径：

```bash
# 执行位置：同一目标会话。
ls -l /dev/note_window0 /dev/note_window1
test -c /dev/note_window0
test -c /dev/note_window1
```

`ls -l` 最左列应为 `c`，号值与刚才的记录一致；test 再确认目标是字符设备。节点缺失时，先按第二章区分设备对象已经创建、devtmpfs 是否挂载和用户空间设备管理是否处理完毕；不要用 `touch` 补节点，也不要在 `test -c` 失败后继续写入路径。

用下面的完整程序检查窗口。本次选择普通 C 程序，是为了保留同一个打开文件，在读写之间有意控制位置，并检查包含零字节的内容；shell 的两次重定向通常各自重新打开，无法观察同样的过程。[window_probe.c](../../../labs/kernel/character_device/materials/window_probe.c) 与这里内容相同。

打开标志 `O_RDWR` 请求读写访问；`fstat` 查询已经打开的对象，类型判断宏 `S_ISCHR` 确认它是字符设备。程序沿用上一章从起点计算位置的 `SEEK_SET`，用 `memcmp` 比较固定数量的字节，避免字符串函数遇到缺口零值就提前结束。`check` 是本例自己的检查函数；标准 C 的 `EXIT_FAILURE`、`EXIT_SUCCESS` 分别表示程序失败和成功退出，不是驱动返回码。

```c
/* SPDX-License-Identifier: GPL-2.0 */
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void check(int condition, const char *message)
{
	if (!condition) {
		fprintf(stderr, "检查失败：%s\n", message);
		/* 进程退出时，系统关闭仍打开的描述符。 */
		exit(EXIT_FAILURE);
	}
}

int main(int argument_count, char **arguments)
{
	const unsigned char expected[8] = {'A', 'x', 'y', 'D', 'E', 'F', 0, 'Z'};
	unsigned char buffer[8];
	struct stat information;
	int descriptor;

	if (argument_count != 2) {
		fprintf(stderr, "用法：%s 字符设备路径\n", arguments[0]);
		return EXIT_FAILURE;
	}
	descriptor = open(arguments[1], O_RDWR);
	if (descriptor < 0) {
		perror("open");
		return EXIT_FAILURE;
	}
	check(fstat(descriptor, &information) == 0, "读取节点属性");
	check(S_ISCHR(information.st_mode), "输入必须是字符设备");
	check(read(descriptor, buffer, 1) == 0, "本次装载的窗口应为空");
	check(write(descriptor, "ABCDEF", 6) == 6, "写入六字节");
	check(read(descriptor, buffer, 1) == 0, "同一打开位置已经到达末尾");
	check(lseek(descriptor, 1, SEEK_SET) == 1, "回到位置一");
	check(write(descriptor, "xy", 2) == 2, "覆盖两个字节");
	check(lseek(descriptor, 7, SEEK_SET) == 7, "越过旧长度但不越过容量");
	check(write(descriptor, "Z", 1) == 1, "扩展并填补缺口");
	check(write(descriptor, "", 0) == 0, "零字节请求不需要剩余空间");
	check(lseek(descriptor, 0, SEEK_SET) == 0, "回到开头");
	check(read(descriptor, buffer, sizeof(buffer)) == 8, "读回完整内容");
	check(memcmp(buffer, expected, sizeof(expected)) == 0, "逐字节核对缺口零值");
	check(close(descriptor) == 0, "关闭设备");
	puts("窗口的覆盖、位置、EOF 与缺口填零符合预期");
	return EXIT_SUCCESS;
}
```

```bash
# 执行位置：目标产物目录，两个窗口均为本次装载的初始空状态。
sudo ./window_probe /dev/note_window0
sudo ./window_probe /dev/note_window1
```

每次预期输出“窗口的覆盖、位置、EOF 与缺口填零符合预期”。先在第一个实例写满，再在第二个实例执行同一程序，仍应从空窗口开始，这就验证了两个次设备号对应不同内容。程序检查的是明确的单次请求结果；若断言失败，它终止并由进程退出关闭描述符，不会继续依赖已经不成立的状态。

同一实例不能原样重复运行，因为程序要求初始为空。重复测试应先卸载、再用同一参数装载；重新打开设备不会清空第十章定义的窗口。到这里已经验证字节内容和位置，但尚未验证并发、真实用户复制故障和目标资源耗尽。

## 11.3\_保留动态编号只改成手工入口

确认测试程序均已退出，然后卸载并关闭自动类设备创建：

```bash
# 执行位置：同一目标会话，两个 probe 已退出。
sudo rmmod note_window
```

先结束上一组自动节点实验，确认卸载成功，才开始路线的 11.3：

```bash
# 执行位置：目标产物目录。
sudo insmod ./note_window.ko major_number=0 instance_count=2 \
    auto_create_node=0 buffer_size=8
```

关闭自动创建只改变路径建立者，仍由内核动态分配号码。接着取得本次登记值：

```bash
# 执行位置：同一目标 Bash 会话，模块已成功装载。
major_number=$(awk '$2 == "note_window" {print $1}' /proc/devices)
case "$major_number" in
    ''|*[!0-9]*) printf '没有取得唯一的设备主号\n' >&2; exit 1 ;;
esac
printf '本次主号：%s\n' "$major_number"
```

awk 按第二列匹配登记名、输出第一列号码，case 拒绝空值或非数字结果。本次没有创建 class，所以不能再从上一节的 sysfs 路径取号。动态主号可能与上次相同，也可能不同，不能从上次日志复制；两个次号仍由驱动约定为 0、1。

手工节点使用不同的名字，直接观察路径名与模块名不必一致。在继续前，确认这两个路径都不存在，连悬空软链接也没有；若存在就停下来辨认来源，不覆盖它们。

```bash
# 执行位置：同一目标 Bash 会话，只检查下列两个实验路径。
for node in /dev/note_window_lab0 /dev/note_window_lab1; do
    if test -e "$node" || test -L "$node"; then
        printf '停止：路径已存在：%s\n' "$node" >&2
        exit 1
    fi
done
```

`-e` 检查存在的目标，`-L` 补充检查悬空软链接，任何一个命中都停止。确认没有冲突以后创建入口：

```bash
# 执行位置：同一目标会话，major_number 已取自本次登记。
sudo mknod -m 600 /dev/note_window_lab0 c "$major_number" 0
sudo mknod -m 600 /dev/note_window_lab1 c "$major_number" 1
```

`c` 选择字符节点，最后两项是主次号；权限 600 只允许本次 root 实验访问。mknod 不会加载模块或分配设备号。核对并运行：

```bash
# 执行位置：同一目标产物目录。
ls -l /dev/note_window_lab0 /dev/note_window_lab1
```

两条入口应是字符节点并带本次号值，节点名与模块名可以不同。

```bash
# 执行位置：同一目标产物目录，已核对节点类型和号值。
sudo ./window_probe /dev/note_window_lab0
sudo ./window_probe /dev/note_window_lab1
```

两份 probe 仍应分别通过初始空窗口与最终内容检查，说明路径名改变没有改变按设备号分派的规则。每个检查或命令失败都先停止，不能继续下一行。

完成后保存本次号值，卸载模块，再删除本节亲自创建的两个节点。手工节点不会因模块卸载自动消失；原节点留下来还可能在设备号被别人重新使用时指向别的服务。

```bash
# 执行位置：同一目标会话，测试程序已结束。
requested_major=$major_number
sudo rmmod note_window
```

保存刚才的主号供下一节申请，卸载后数据与内核登记退出，但手工路径还在。

```bash
# 执行位置：同一目标会话，只删除本节亲自创建的两条节点。
sudo rm -- /dev/note_window_lab0 /dev/note_window_lab1
```

这一步清理文件系统入口，不会再释放任何内核号段；后者已经由成功卸载完成。

## 11.4\_再固定主号观察另一个选择轴

现在请求刚才记下的主号。这是一次明确的范围申请，不是声明该号永久属于我们；卸载后若其他驱动先占用它，申请应失败。`/proc/devices` 的观察只能提供线索，最终以装载时的注册结果为准。

```bash
# 执行位置：同一目标产物目录，上一组已卸载并清理。
sudo insmod ./note_window.ko major_number="${requested_major:?先完成上一节}" \
    instance_count=2 auto_create_node=0 buffer_size=8
```

成功后核对 `/proc/devices`，重做上一节的两次 `mknod`、两次 probe、卸载与精确删除，设备号使用 `requested_major`。这完成“指定主号 + 手工节点”。如果装载失败，保留错误及日志，回到动态编号或选取明确可用于实验的号段，不能通过删除 `/dev` 节点释放内核中仍被占用的号段。

最后保持指定主号，只把节点方式改回自动：

```bash
# 执行位置：同一目标产物目录，指定号的手工实验也已结束。
sudo insmod ./note_window.ko major_number="${requested_major:?先记录请求号}" \
    instance_count=2 auto_create_node=1 buffer_size=8
```

现在保持指定主号，只恢复自动节点；数据实现仍相同。继续核对：

```bash
# 执行位置：同一目标会话。
cat /sys/class/note_window/note_window0/dev
ls -l /dev/note_window0 /dev/note_window1
test -c /dev/note_window0
test -c /dev/note_window1
```

号值应为 requested_major 配次号 0、1，节点类型仍为字符设备。

```bash
# 执行位置：目标产物目录，已完成节点核对。
sudo ./window_probe /dev/note_window0
sudo ./window_probe /dev/note_window1
```

仍应分别通过空窗口、覆盖、位置和缺口检查。两程序结束后退出本组：

```bash
# 执行位置：同一目标会话。
sudo rmmod note_window
```

对照 sysfs 与节点的号值应仍为申请的主号、次号 0 和 1。四种组合共享同一数据实现，没有哪种组合天然“更接近硬件”；它们只分别改变编号来源与入口的建立者。

## 11.5\_保留失败现场并明确验证边界

若 `insmod` 失败，先记录它的退出状态和内核日志，按“产物不匹配 → 参数检查失败 → 号段或类名冲突 → 内存或设备对象创建失败”缩小范围。模块未成功装载时，不能把一个遗留节点当成本次初始化成功的证据。若 probe 失败，保留打印的第一项失败名称；“首次窗口为空”失败与“最终字节不符”指向不同阶段。

若 `rmmod` 提示正在使用，寻找本次设备的打开者，先让应用正常关闭；不要用强制卸载检验内存回收。下一章按这些可观察现象继续排查。本章没有修改系统级 udev 规则，没有通配删除其他节点，也不需要向固定取证树写入模块构建产物。

这组实验若实际通过，能支持四个有限结论：本次模块能在这个目标装载；两种编号和两种节点方式都能连接同一文件操作；两个窗口内容独立；单进程位置、覆盖、EOF 和缺口填零符合契约。它不能证明真实硬件、所有用户复制异常、所有并发交错或热拔插安全。

## 11.6\_回顾与练习

1. 手工把节点名改成 `capture0`，不改主次设备号，probe 的结果会变吗？只修改文件名会换一份驱动内容吗？
2. 从动态自动改为动态手工时沿用上次主号，即使测试成功，为什么仍是错误的方法？
3. probe 第二次运行报“窗口应为空”，为什么不能立即判定退出清理失败？
4. 把两个手工节点都设为次号 0，第二个 probe 最早可能在哪里失败？

解答：第一题不会因改名改变数据分派。第二题的成功可能只是分配器碰巧复用旧号，下次分配并无此保证。第三题中重新打开保留设备内容，只有卸载重装才重新创建本例的窗口。第四题两个路径会指向同一个实例；第一份 probe 已写入数据，第二份在初始空窗口检查就能揭示映射错误。检查路径是否存在不够，还必须核对设备号和内容关系。
