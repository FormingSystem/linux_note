# 第1章\_体系结构内存顺序专题大纲

## 1.1\_专题要独立解决的问题

本专题不从 Linux 宏开始，而从多核处理器必须同时追求正确性与吞吐量的矛盾开始：若每条 Load/Store 都按程序顺序等待所有远端观察者确认，处理器容易理解却难以隐藏缓存、互连和内存延迟；若允许写缓冲、推测和并行事务，执行吞吐量提高，软件就必须明确哪些观察顺序真正不可打破。

```mermaid
flowchart LR
    A[程序顺序直觉] --> B[缓存未命中与所有权等待]
    B --> C[写缓冲／推测／并行访存]
    C --> D[不同 CPU 可能看到不同交错]
    D --> E[体系结构定义允许结果]
    E --> F[屏障／Acquire／Release／依赖顺序]
    F --> G[软件同步协议]
```

目标是让读者能够从一个并发程序独立完成：列出事件 → 指定观察者 → 推导可能结果 → 判断需要哪条顺序边 → 说明该顺序边的不可规避成本，而不是只记住“弱内存模型要加屏障”。

## 1.3\_递进阅读路线

1. [为什么需要体系结构内存模型](P01_为什么需要体系结构内存模型.md)：从消息传递失败建立事件、程序顺序、观察顺序和同步边的共同语言。
2. [访问粒度、对齐与撕裂](P02_访问粒度_对齐与撕裂.md)：先确认一次 Load/Store 到底是不是一个不可分割事件，再讨论事件之间的顺序。
3. [乱序执行、Store Buffer 与观察时机](P03_乱序执行_Store_Buffer与观察时机.md)：沿流水线、写缓冲、缓存所有权和远端观察走完 Store Buffering 反例。
4. [一致性序、传播与多副本原子性](P04_一致性序_传播与多副本原子性.md)：从同一地址扩展到多个地址、多个写者和多个观察者，推导 IRIW/WRC 类结果。
5. [屏障、Acquire/Release 与依赖顺序](P05_屏障_Acquire_Release与依赖顺序.md)：从需要禁止的结果反推单向顺序、全屏障、累积性和依赖关系。
6. [Litmus Test 并发交错推演](P06_Litmus_Test_并发交错推演.md)：统一推演 MP、SB、LB、IRIW、WRC 和 ISA2，不靠运行概率判断正确性。
7. [反汇编、压力测试与形式化验证边界](P07_反汇编_压力测试与形式化验证边界.md)：把静态检查、硬件实验和模型验证组合成可复现研究流程。

## 1.4\_配套实验和研究入口

- [访问宽度、对齐与 ARM 反汇编实验](../../../../labs/foundations/computer_architecture/memory_ordering/P01_访问宽度_对齐与ARM反汇编/README.md)：观察自然对齐 32 位、64 位和 packed 访问怎样映射为不同指令序列。
- [Linux LKMM Litmus 实验](../../../../labs/kernel/memory_ordering/P02_LKMM_Litmus_消息传递与屏障/README.md)：对同一 MP、SB、IRIW 模型逐步增加 ONCE、屏障和 release/acquire，比较允许结果。
- [Linux 6.12 LKMM 源码与模型导读](../../../../research/source_reading/memory_ordering/P01_Linux_6.12_LKMM_源码与模型导读.md)：追踪 `linux-kernel.def/.bell/.cat/.cfg` 各自承担的模型职责。

实验不代替契约：观测不到某个结果，可能只是样本不足或当前机器更强；形式模型也不模拟任意编译器优化、MMIO、DMA 和所有访问宽度。专题正文会在使用每种证据时标明它能证明到哪里。

## 1.5\_完成后的验收能力

完成本专题后，应能：

1. 区分程序顺序、执行顺序、传播顺序和某个观察者的取值顺序。
2. 区分访问撕裂、同址一致性、跨址排序和对象生命周期。
3. 用完整交错解释 MP、SB、IRIW 等反直觉结果怎样形成。
4. 说明 Store Buffer 和推测为什么有性能价值，以及屏障为何有不可规避成本。
5. 从禁止结果反推 acquire、release、全屏障或依赖顺序，而不是从 API 名字猜保证。
6. 选择反汇编、压力测试、Litmus 模型或体系结构手册作为合适证据，并承认各自边界。
