# 第3章\_把模块接入Kconfig与内核构建

[上一章](P02_让多个源文件形成清楚的模块边界.md)已经能组织多个源文件，但每次都直接要求构建模块。现在要把 Hello 实验作为内核的一项可选功能：产品不需要它时完全排除，需要时可选择内建或可加载。新增的不是一种 C 语法，而是配置与构建之间的联系。

本章只在你拥有的 **独立学习副本** 中演示内核树集成，不改动用于取证的标准外部工作树。需要前两章的完整双文件 Hello 程序，以及能正常构建目标内核的工具与配置。集成操作会改变副本中的源码和配置；仅阅读通用机制时不必真的构建整棵内核。

## 3.1\_先把源码位置与链接方式分开

“放进内核源码目录”和“编译进内核映像”不是同一句话。源码位置回答由谁管理这些文件；链接方式回答运行时代码从哪里来。内核树内的驱动可以构建成模块，树外的源码也不是因目录位置才获得模块身份。

本章的可选项使用 Kconfig。Kconfig 是内核配置系统的描述语言，用来声明选项、帮助和依赖；Kbuild 使用已经确定的配置，决定进入哪些目录、构建哪些目标。它们分别回答“允许怎样选”和“选定以后怎样构建”。

```mermaid
flowchart LR
    A[父 Kconfig] -->|source 引入选项| B[HELLO_NOTE 选项]
    B -->|配置工具保存选择| C[.config 与生成配置]
    C -->|CONFIG_HELLO_NOTE 值| D[父目录 Makefile]
    D -->|选择进入目录| E[子目录 Makefile]
    E -->|选择链接方式| F[内建对象或 hello_note.ko]
```

只接通菜单，编译器未必会访问你的目录；只接通构建目录，没有配置来源，条件又可能永远不成立。我们把这两条入口都写清楚。

## 3.2\_给现有实现增加配置入口

在学习副本中创建 `drivers/hello_note/`，放入上一章的 `hello_note_main.c`、`note_value.c`、`note_value.h`。这是一个新练习布局，使用下面的 `Makefile`，**不要把外部实验的 Kbuild 和包装 Makefile 一起复制进来**。如果遗留 Kbuild，它的读取优先级会干扰你对新 Makefile 的判断。

新增 `drivers/hello_note/Kconfig`：

```kconfig
config HELLO_NOTE
    tristate "Hello note teaching example"
    help
      启用最小日志实验，用于学习配置与构建的连接。
      选择 M 生成可加载模块；选择 Y 将代码内建到内核。
      本实验不注册设备，不控制板上外设。
```

`HELLO_NOTE` 是配置符号名，保存到配置后使用 `CONFIG_HELLO_NOTE`。`tristate` 表示这个选项有三种逻辑值：`n`、`m`、`y`。其中 `m` 的可用性受内核模块支持和其他依赖限制，不是任何配置下都一定能选到。`help` 是给配置者的解释，要说明功能而不是只重复符号名。

在父级 `drivers/Kconfig` 的适当位置加入：

```kconfig
source "drivers/hello_note/Kconfig"
```

这一行让配置系统读取选项。重新进入配置界面后，才能寻找 `HELLO_NOTE`。如果选项没有出现，先确认父入口确实被读取、拼写正确，再看依赖，不要通过直接改生成头文件把它“强行打开”。

## 3.3\_接通父目录和具体目标

在 `drivers/Makefile` 加入目录选择：

```make
obj-$(CONFIG_HELLO_NOTE) += hello_note/
```

在 `drivers/hello_note/Makefile` 描述模块组成：

```make
obj-$(CONFIG_HELLO_NOTE) += hello_note.o
hello_note-y := hello_note_main.o note_value.o
```

这里没有新的代码功能。make 展开配置变量后，把目标放入对应的 `obj-y` 或 `obj-m` 列表；未选择时不会通过这些有效目标列表构建它。父级决定是否访问这个功能目录以及所处构建类别，子级再把功能映射到实际对象。两层连接不是任选一层就够了。

| 配置选择 | 对这个功能的预期 | 如何观察 |
| --- | --- | --- |
| `CONFIG_HELLO_NOTE=y` | 对象参与内建，随相应内核启动执行初始化 | 检查构建记录，并在真正启动新内核后查看消息；不要求有可装载的 `.ko` |
| `CONFIG_HELLO_NOTE=m` | 形成 `drivers/hello_note/hello_note.ko` | 完成本次模块构建后检查文件，再按目标身份部署 |
| 未选择 | 不把该功能纳入本次目标 | 检查配置与构建记录；先前遗留文件不代表本次又构建了它 |

`hello_note-y` 中的 `-y` 是 **组合对象的组成列表**，并不把上面的 `m` 偷换成内建。这是两个变量在不同层次上的含义。判断是否生成模块，要回到目标被放入哪一个 `obj-*` 列表。

Linux 中确实可以直接写 `obj-m`；它不是外部模块专属语法。但需要由配置控制的功能，应像这里一样把选择接到配置符号上。否则用户取消选项，文件仍被硬编码加入目标，就违背了菜单给出的承诺。

## 3.4\_先理解依赖再增加开关

本例只记录日志，不依赖板上设备，因此不应该随手写 `depends on ARM` 或 `depends on OF` 来模仿其他驱动。只有代码真实需要某项能力，才增加相应依赖。依赖的作用是限制合法组合，不是给菜单贴分类标签。

例如，未来真的增加了必须依赖某子系统的实现，就要检查它的配置符号、接口可用条件及内建与模块组合。一个内建调用者不能依靠“以后可能装入的模块”来满足启动时的直接符号引用。配置系统的三态依赖帮助约束这类组合，但作者仍须正确表达条件，不能期待它理解任意 C 代码。

`bool` 是只有开与关的选项，常用于不独立形成可加载单元的特性。是否需要额外选项，取决于用户是否有真实选择需求。把每个 C 文件都变成菜单项，会迫使使用者处理本应由实现内部保证的组合。

## 3.5\_一次只改变一个选择并核对结果

先保存当前副本的配置来源与工具链信息，再进入它原有的配置和构建流程。若该副本使用独立输出目录 `O=...`，配置、构建和查看配置都必须指向同一个输出目录；不要在源码目录查看旧 `.config`，却在另一个目录构建新配置。

一个检查过程可以这样安排：

1. 在启用模块支持的目标配置中选择 `HELLO_NOTE=m`，构建该目标所需的模块，查看构建记录与 `.ko`。
2. 把该项改为 `y`，构建对应内核映像，核对目标进入内建过程。只有启动这个新映像，才能验证启动时的日志。
3. 关闭该项，检查本次不再构建它。若旧 `.ko` 仍留在目录，追踪其时间和来源，而不是判定配置无效。

实验日志至少记下配置选择、源码提交、输出目录身份、工具链与实际执行的命令。只记“make 成功”无法解释成功构建了哪个组合。对生产板更换启动内核还涉及启动介质与恢复方式，本章不把它包装成无条件可执行的一行命令。

若你的目标只是快速试验树外模块，没有交付内核配置项的需求，继续使用前两章的外部构建即可。进入树内构建增加了父入口、配置和整体构建维护责任；它的价值在于统一产品配置与交付，而不是天然让驱动更正确。

## 3.6\_练习与解答

1. 菜单能选到 Hello，但编译记录完全没有它，首先检查哪条连接？
2. `CONFIG_HELLO_NOTE=m` 与 `hello_note-y := ...` 是否矛盾？
3. 选择 `y` 后执行 `insmod hello_note.ko` 能否用来验证本次内建结果？
4. 关闭选项以后发现一个旧 `.ko`，还需要哪些证据才可判断配置失效？

第一题检查父 Makefile 是否进入目录，再检查子 Makefile 是否把配置映射到目标；菜单入口不能代替构建入口。第二题不矛盾，前者选择模块链接类别，后者列出组合对象成员。第三题不能，内建代码随新内核启动；装入旧文件甚至会让你观察另一个版本。第四题应确认配置来自本次输出目录，并查看实际命令与产物来源，不能只凭文件存在做结论。

现在源码位置、配置选择和链接类别已经分开。剩下的问题是：构建正确的 `.ko` 怎样进入目标系统，其他模块依赖它时又怎样找到它？下一章沿着[构建、安装与装载三个现场](P04_部署模块并沿错误定位构建问题.md)继续观察。
